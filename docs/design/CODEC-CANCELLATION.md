
## Peer receipt versus consumed Send source

The current host/replay donor separates these subjects explicitly. Replay validates a non-cancelled Send's recorded source bytes against its still-owned loan; cancelled Send retains the native NIL-payload convention and derives its consumed prefix from that loan before posting. Capability field 3 is a consumed-source transcript, not a delivery counter. Field 8 stores successful exact segments and failed/cancelled unknown-prefix constraints. The actual client RX observation is checked against those constraints; replay without a client observation does not establish receipt.

`sim/envelope-output.lisp` provides a resumable matcher: one step handles a list cell, peer byte or boolean-row cell. Ordinary exact output and a final single unknown prefix take a linear path. Ambiguous intermediate prefixes use dynamic-programming rows, with polynomial work proportional to remaining source bytes times remaining peer bytes; there is no recursive search backtracking. The convenience checker supplies a structurally derived work budget, not a stored-data ceiling. Source admission, guards, the budget/refinement proof, and the actual post-to-peer controls are pending. A passing pure matcher fixture alone does not qualify native emission or OpenSSL delivery semantics.

The clean donor starts at root `5bd5a38cf`, incorporates the qualified failed-Send classifier from `11ceb6ada`, and composes the actual TLS emitter, shared host closure extraction, physical-input replay consumer and logical/native capture fixtures. The canonical machines-b 76-book prefix is identical, but `books/host-codec` needs 78 additional dependencies and the actual TLS/replay fixture needs 151 additional dependencies. These are planned as shared convergence, not separate cold application builds.
