Keep the separation of logical selection, retention obligations, and physical borrowing. Reject the chapter’s amendment as written. “Fatal” below means fatal to the stated argument or rule, not to that separation.

1. **Fatal — Tradeoff 4 mistakes a query-definition version for a storage snapshot.**  
   `query-version` changes with selection semantics or group configuration; `view-version` tracks visibility/authorization changes. Neither is the storage frontier. Each poll pins a frontier temporarily; a durable cursor does not thereby retain that snapshot. The contract explicitly separates a retaining consumer mode as a charged durable hold. Replication slots are a useful analogy for that **optional hold**, not for every cursor. Delete the “month-old query-version” example. See [consumer-progress.md](~/dev/fn/specs/consumer-progress.md:31).

2. **Material — Kafka preserves positions, not fn’s historical selection-and-identity answers.**  
   Retention causes `OffsetOutOfRange` when the requested offset falls outside the retained range—not merely when some segment below it disappears. Compaction instead leaves holes: seeking a removed offset returns the next surviving record. Kafka need not retain the removed record’s key or identity. Thus an offset is neither a retention pin nor fn’s promised historical catalogue. “The log retains everything regardless” directly contradicts the mechanism being described. (`kafka2026-docs-design.md`, “Log Compaction.”)

3. **Minor — CT supports zero marginal retention, not free everlasting pins.**  
   A meaningful remembered checkpoint includes the log identity and authenticated root, not just tree size. A consistency proof authenticates prefix extension; it does not establish ongoing availability. If the service already retains the complete log and proof material, another client checkpoint adds no history-retention obligation. That conditional statement is useful; “free forever” is not. (`rfc6962-certificate-transparency.txt`, §§3.5, 4.4, 5.)

4. **Material — The PostgreSQL removal is real; the causal account is embellished.**  
   Removal in 17 is correct. The maintained mapping was **timestamp-to-XID**, with page LSN checks—not simply time-to-LSN. The removal commit cites correctness/performance problems and a prolonged absence of a repair plan; it does not establish the chapter’s specific explanation about unpredictability. A numerical cutoff still needs correct admission, publication, and reclamation synchronization. (`grittner2016-postgres-commit-add-snapshot-too-old.txt`; `munro2023-postgres-commit-remove-snapshot-too-old.patch.txt`; [mapping documentation](https://www.postgresql.org/docs/16/oldsnapshot.html).)

5. **Material — Oracle, CockroachDB, and Spanner do not establish one universal policy.**  
   Oracle’s `UNDO_RETENTION` is not an unconditional guarantee: space pressure can overwrite unexpired undo; `RETENTION GUARANTEE` instead permits writes to fail. CockroachDB combines TTL with **protected timestamps**, including scoped protections for backups and changefeeds—the chapter’s proposed alternative already exists there. Its current documented default is four hours; the asserted transition date needs evidence. Spanner defaults to one hour, configurable through seven days, and can fail an already-running read when its timestamp becomes too old. These are distinct choices about which promise loses under pressure. ([Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/18/admin/managing-undo.html), [CockroachDB protections](https://www.cockroachlabs.com/blog/protected-timestamps-for-less-garbage/), [TTL](https://docs.cockroachlabs.com/docs/stable/configure-replication-zones), [Spanner](https://docs.cloud.google.com/spanner/docs/transactions?hl=en).)

6. **Material — FoundationDB is described too categorically, and “strictly kinder” is false.**  
   The documented five seconds run from the first read; subsequent server reads usually fail, cached reads need not, and writing commits fail. Long snapshots through application-layer versioning are explicitly discussed. More importantly, fn’s proposed metadata window also expires selection. A client needing complete payloads may prefer an atomic transaction failure to a stable list of unavailable objects. These contracts are incomparable. (`foundationdb2026-docs-known-limitations.txt`; `zhou2021-foundationdb-unbundled-transactional-kv-store.txt` §6.4.)

7. **Material — The physical comparisons repeat correction 8’s unfair comparison.**  
   LMDB’s long-reader reclamation problem is real, but growth follows unreusable page churn and available free space, not an unconditional whole-write-stream identity; `mdb_reader_check` clears stale readers, not live slow ones. TigerBeetle documents table-version retention and explicitly unimplemented persistent snapshots; that is not a lower bound for every LSM. SQLite checkpoints can advance up to readers’ end marks; completion/reset can be blocked, while the WAL index mitigates lookup cost. Tahoe permits deletion after lease expiry **when GC is enabled**, which is not its default. Its renewable retention lease is not an operation borrow. Compare all candidate engines under the same logical-pin/object-lease contract. (`lmdb2026-docs-lmdb-h.txt`; `tigerbeetle2026-internals-lsm.md`; `sqlite2026-docs-wal.txt`; `tahoelafs2026-docs-architecture.rst`.)

8. **Material — Neither “zero cost” nor the byte optimum has been established.**  
   Zero *additional historical storage* is possible when the baseline already retains all required answers. Registration, indexing, traversal and accounting still cost something. Likewise, `C × A` bounds logical payload size only under explicit concurrency/profile assumptions. Physical storage includes rounding, stranded extents, relocation copies and recovery dependencies. An object lease alone proves none of those away. The chapter reinstates exactly the overclaim correction 7 removed.

9. **Fatal — The metadata lower bound is false as quantified.**  
   One key can change a million times after a single pin; preserving its value at that pin and its current value need not preserve a million changes. Even “any selection question at v” does not imply “every intervening historical version.” The lower bound concerns information needed to distinguish the **supported observations**, not raw churn. For immutable article metadata plus birth/withdrawal stamps, much historical selection may already be covered by permanent metadata. Scoping can reduce retention, but `Ω(changes within scope)` is not a general theorem either.

10. **Fatal — The re-seek “iff” omits the publication invariant and versions the wrong thing.**  
    An article born before `v` can acquire group membership after `v`; filtering only article birth admits a phantom. Every selection-relevant fact needs appropriate historical semantics. Require complete materialization through the published frontier, no retroactive changes to that history, stable logical keys, and preservation of the entire query result under compaction. Birth fields are one implementation, not a necessity. Also retain progress through **examined** invisible entries: “last emitted key” alone can repeatedly rescan the same filtered suffix after budget exhaustion. Finally, an LSM resume can touch several runs and directories; “one descent, `O(log n)` page reads” is unproved.

11. **Material — Tradeoff 1 is real and already discussed, but its compaction floor is wrong.**  
    Opus §C already proposes bounded-age rebasing for metadata. The missing work is its precise contract. “Oldest unprotected pin” ignores protected obligations: a protected pin at 80 still matters when the window starts at 100 and the oldest ordinary pin is 120. Conversely, an expired ordinary pin must not hold the floor indefinitely. Derive retention from supported observations and protected holds; make expiration effective before discarding their evidence. A BODY/XOVER already promised at one version must not silently switch versions mid-response. “Hours, not seconds” is a workload choice, not a theorem.

12. **Material — Tradeoff 2 is a useful optimization, not a demonstrated missing requirement.**  
    “Historical metadata needed by supported pins” does not prescribe global retention. Declare scopes where useful, but close them over dependencies: membership, shared withdrawal facts, view definitions, authorization, and relevant schemas. A cold group can still depend on changing shared metadata. Nor does naming `GROUP` prove that existing NNTP clients tolerate an invented cross-scope rebase response. Scope granularity and bookkeeping cost belong in the comparison.

13. **Material — Tradeoff 3 is sound, partly already covered, and oversells its bound.**  
    Adopt logical object leases with shorter physical borrows. Copying may proceed while old readers borrow the source; **retiring/reusing** that source waits for completion and recovery safety. Placement resolution and borrow acquisition must be atomic against retirement and checked against allocation generation. One block send bounds bytes, not elapsed time: a stalled external borrow can persist indefinitely. If a disk block has been copied into owned pool memory, the disk borrow can end before the network send. Relocation also needs spare space and a bounded-copy policy; it does not make stranded space instantly disappear.

14. **Material — Tradeoff 5 confuses event inclusion with proving a query answer.**  
    A signed event-log root proves inclusion of an event, not that an XOVER result is complete, currently authorized at `v`, or unaffected by a withdrawal before `v`. Those require authenticated state/range proofs or evidence connecting the fold to the log. Later signed roots can authenticate earlier prefixes with suitable evidence. Checkpoint snapping is an optional latency/staleness policy, not the general prerequisite for provable reads.

15. **Material — Tradeoff 6 is real, but the proposed mandatory page-pin rule is unjustified.**  
    A page retained across scheduler yields still consumes shared cache capacity and can obstruct maintenance. Allow a charged, bounded, disposable traversal cache if measurement supports it; correctness must survive eviction and re-seek. “Execution yield versus external wait” alone does not establish either a memory bound or a reclamation-progress bound.

16. **Minor — Tradeoff 7 identifies a real observation but overstates its meaning.**  
    One `unavailable` answer need not show reclamation happened *after* the pin, much less identify expiry versus withdrawal. A payload could already have been absent. State the permitted disclosure precisely, including authorization changes and distinguishable failure reasons; do not infer the hidden cause from the result.

17. **Fatal — Durable linearizability does not imply repeatable answers after restart.**  
    A later read cannot ordinarily linearize before its invocation merely because it requests version `v`. Specify a historical-read operation or snapshot object whose sequential semantics permits that result. Durable linearizability preserves completed operations’ effects across crashes; it does not promise that replaying a read returns the same answer, resurrect volatile leases, or prevent later legal reclamation. Fence-before-publication is necessary evidence, not this entire theorem. (`izraelevitz2016-durable-linearizability.txt`, Definition 3.)

18. **Fatal — Perennial’s versioned memory is not MVCC.**  
    Its version numbers identify **crash generations** and invalidate old capabilities. Its recovery leases mediate exclusive modification of durable resources; recovery reconstructs fresh capabilities after a crash. They are not historical `(key, version)` entries or read leases persisting across restart. Both “exactly” analogies must go. The applicable contribution is concurrent recovery refinement and disciplined transfer through crash invariants. (`chajed2019-perennial-crash-safety-concurrency.txt`, §§5.1–5.3.)

19. **Material — Fractional permissions explain borrowing, not the whole cleaner.**  
    Fractions can model immutable physical reads; full ownership authorizes mutation/reuse. A logical retention lease needs a separate obligation model. Copying an immutable source need not await full ownership. A zero borrow count is sufficient only with complete token accounting, generations, completion matching, prevention of new borrows, and durable placement/recovery invariants. Epoch reclamation also needs ownership and external-I/O rules; it is not “one inequality and no ownership story.” (`jung2018-iris-from-the-ground-up.txt`.)

20. **Fatal — The oracle theorem remains under-specified, and its proposed teeth are insufficient.**  
    Equal-input/equal-observation determinism is useful only after defining legal observations independently of the output being justified. Rebase/view-change outcomes also affect replies, so availability alone no longer captures the amendment. State a relational property over aligned request observations, with the same history identity and relevant connection state. Separately prove legal lease acquisition, release, failure classification, and exact payload delivery. “Committed release and no lease” must not disguise corruption or unknown persistence as ordinary unavailability. Teeth need reachable positive schedules **and hypothesis-removal witnesses**—especially release racing acquisition, relocation racing a borrow, and expiration during a cursor.

**My amended wording**

> **Pinned versions:** a supported pin identifies a published logical version, history/incarnation, selection semantics, and supported query scope. While valid, it preserves selection and identity through physical reorganization. The engine retains sufficient evidence for those answers; neither retaining every intervening change nor retaining old physical roots is required. Consumer query/view versions and durable scan positions are distinct from storage snapshot pins and create no implicit retention hold.
>
> Profiles may define explicit pin-expiration and rebase rules. Expiration, protected historical holds, and any promised historical-read window jointly determine which observations compaction must preserve. Expiration never silently changes an already-started response. A cursor preserves logical scan progress and re-seeks safely after suspension; cached physical traversal state is optional and bounded.
>
> Before promising payload success, acquire a logical object lease atomically against release. Physical reads and sends hold generation-checked borrows until the relevant adapter releases them. Relocation preserves the leased content identity and publishes durable replacement placement before retiring old storage; reuse additionally requires all old borrows and recovery dependencies to have ended. Replies refine the reference semantics for explicit availability, rebase and fault outcomes. A valid lease prevents reclamation-induced loss of a promised payload under the declared platform assumptions.

**Five additions**

- Define pin admission, renewal, expiration and scope extension as transitions, including races with compaction and profile changes.
- Specify authorization revocation during an old pin and during an already-leased response.
- Separate historical-read retention, replay-history retention, payload retention and crash-recovery dependencies in both accounting and diagnostics.
- Add executable adversarial witnesses: post-pin membership, invisible scan suffix, protected old pin, stale placement generation, crash during relocation, and expiration after response status.
- Repair M4’s controls: use a real historical pin rather than an old `query-version`; compare identical contracts across engines; measure temporary relocation space, actual LSM read amplification, and reclamation progress under stalled borrows.
