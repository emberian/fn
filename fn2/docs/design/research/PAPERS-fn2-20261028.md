# fn2 reading list: crash models, proof automation, node design, derived code (2026-10-28)

Annotated bibliography for fn2, the semantics-first rebuild of fn's ACL2-verified NNTP/store node
into a general high-performance database node (and someday a robigalia/seL4 component). Brief:
`~/dev/fn/build/coordinator/briefs/PAPERS-20261028.md`. Every entry names its file in
`~/paperbin/` (a `.pdf` with a `pdftotext` `.txt` beside it unless marked `.md`). Entries marked
*(already here)* were in paperbin before this pass. The baseline everything is measured against
is fn's crash model v2, `~/dev/fn/books/byte-store.lisp` (spec `specs/crash-model-v2.md` §1):
inodes + directories + an ordered pending list; per-inode `fsync` and per-directory `fsync(dirfd)`
fences; a crash lands an arbitrary subsequence of pending ops, issue-ordered among survivors, each
write torn at write-unit pieces that land / land as zeros / land as garbage; environment-chosen
outcomes (`:eio`, `:enospc` with partial progress); a failed fsync lands a torn selection and
discards the rest; rename = one `:set-entry` + a separate `:del-entry`; `read` takes no outcome
and returns the view; the post-failed-fsync view is left unspecified (programs never read it).

Found with Scry (HN over `fsync` / crash-consistency / storage-fault stories: SquirrelFS, the
TigerBeetle storage-fault-model thread, Rebello), the arXiv API (all 117 ACL2-tagged abstracts,
the Verus/LLM-proof cluster), and Kagi for the URLs the obvious hosts refused. Anna's Archive was
not needed in the end (its reachable mirrors sit behind a browser check; the API key works for
`fast_download` but there is no keyed search to get an md5).

## 1. Crash and storage-fault models tougher than ours

Each line ends with **misses:** what the paper's model admits that fn's v2 model does not. The
table at the end collects these.

### Empirical: what disks and file systems actually do
- **Pillai et al., "All File Systems Are Not Created Equal" (OSDI 14)** — ALICE: abstract
  persistence models per FS (ext3/4 modes, btrfs, xfs) and 60 vulnerabilities in 11 apps; the
  source of fn's rename split. **misses:** per-FS *stronger* guarantees fn could exploit (and must
  not rely on), and append atomicity/size-before-data distinctions; fn's model is already the
  weakest one for ordering, which is right. `pillai2014-all-file-systems-not-created-equal.pdf`
- **Rebello et al., "Can Applications Recover from fsync Failures?" (ATC 20)** — fsync failure
  behaviour on ext4/XFS/Btrfs and in Redis/LMDB/LevelDB/SQLite/PostgreSQL. **misses:** ext4
  `data=journal` does *not* report the fsync failure on that fsync (a later one sees it), so an
  `:ok` fsync can still lose data; Btrfs *reverts* the in-memory view to the old state while
  ext4/XFS keep the unwritten data in cache (fn leaves this view unspecified and forbids reading
  it — good, but recovery programs that re-open the file still see one or the other); metadata
  (size) can advance while the data block failed; a journal-write failure remounts read-only, so
  every later syscall fails. `rebello2020-can-applications-recover-fsync-failures.pdf`
- **Bairavasundaram et al., "An Analysis of Data Corruption in the Storage Stack" (FAST 08)** —
  1.53M drives: checksum mismatches, identity discrepancies (misdirected / lost writes), parity
  inconsistencies; corruption is spatially and temporally correlated. **misses:** corruption of
  *durable* data at rest; misdirected writes landing on another block; lost writes that were
  acknowledged. `bairavasundaram2008-analysis-data-corruption-storage-stack.pdf`
- **Bairavasundaram et al., "An Analysis of Latent Sector Errors in Disk Drives" (SIGMETRICS 07)**
  — LSE rates, locality, discovery by scrubbing. **misses:** `read` failing (EIO) on durable data;
  fn's `fn-bs-read` has no outcome. `bairavasundaram2007-latent-sector-errors-disk-drives.pdf`
- **Krioukov et al., "Parity Lost and Parity Regained" (FAST 08)** — model-checks RAID/checksum
  designs against torn writes, lost writes, misdirected reads and writes, latent errors.
  **misses:** misdirected *reads* (the right data exists but the wrong block comes back) and the
  fault-taxonomy as an explicit enumerated environment. `krioukov2008-parity-lost-parity-regained.pdf`
- **Zheng et al., "Understanding the Robustness of SSDs under Power Fault" (FAST 13)** — 15 SSDs
  under power cuts: bit corruption, shorn writes, *unserializable* writes, flying writes,
  metadata corruption, dead device. **misses:** a power cut corrupting data that was *not being
  written* (already durable); device-level reordering across a completed flush; the whole device
  becoming unreadable. `zheng2013-ssd-robustness-under-power-fault.pdf`
- **Zheng et al., "Torturing Databases for Fun and Profit" (OSDI 14)** — power-fault injection
  under 8 databases with block-trace replay; ACID violations in all. **misses:** the same
  device-level faults, plus "durability lies" where a flush/FUA is acknowledged before the data
  is stable. `zheng2014-torturing-databases-power-faults.pdf`
- **Schroeder, Lagisetty, Merchant, "Flash Reliability in Production" (FAST 16)** — six years of
  Google flash: uncorrectable errors are common, bad blocks appear and grow, and age matters beyond wear. **misses:**
  uncorrectable read errors on durable data; slow growth of bad regions. `schroeder2016-flash-reliability-in-production.pdf`
- **Maneas et al., "A Study of SSD Reliability in Large Scale Enterprise Storage Deployments"
  (FAST 20)** — the SSD silent-corruption and misdirected-IO rates TigerBeetle cites.
  **misses:** as above, with the numbers fn2 needs to justify a scrub cadence. `maneas2020-ssd-reliability-enterprise-storage.pdf`
- **Gunawi et al., "Fail-Slow at Scale" (FAST 18)** and **Huang et al., "Gray Failure" (HotOS
  17)** — hardware that keeps working but 10-1000x slower; partial, differential observability.
  **misses:** time entirely (fn's outcomes are instantaneous): fail-slow fsync, stalls, and the
  liveness/timeout story a node needs. `gunawi2018-fail-slow-at-scale.pdf`,
  `huang2017-gray-failure-achilles-heel-cloud.pdf`
- **Prabhakaran et al., "IRON File Systems" (SOSP 05)** — the fail-partial disk model (block
  read/write failure, corruption) and a detection/recovery taxonomy applied to ext3, ReiserFS,
  JFS, NTFS. **misses:** fail-partial reads and the requirement that the FS *above* fn may itself
  silently ignore write errors. `prabhakaran2005-iron-file-systems.pdf`
- **Ganesan et al., "Redundancy Does Not Imply Fault Tolerance" (FAST 17)** — CORDS: one corrupted
  or unreadable block in Redis, ZooKeeper, Cassandra, Kafka, RethinkDB, MongoDB, LogCabin,
  CockroachDB; most lose data or crash. **misses:** single-block corruption / EIO of durable state
  as the unit fault fn2's recovery must survive. `ganesan2017-redundancy-not-fault-tolerance-cords.pdf`
- **Alagappan et al., "Protocol-Aware Recovery for Consensus-Based Storage" (FAST 18)** — CTRL:
  distinguish a crash-torn log tail from mid-log corruption, repair from peers instead of
  truncating. **misses:** corruption inside the durable log and the crash/corruption
  disambiguation that makes truncate-on-bad-checksum unsafe; essential once fn2 replicates.
  `alagappan2018-protocol-aware-recovery-consensus-storage.pdf`
- **Mohan et al., "CrashMonkey and ACE" (OSDI 18)** — bounded black-box crash testing; finds
  ext4/btrfs/F2FS bugs where fsync'd data or a renamed/linked file is gone after a crash.
  **misses:** the FS violating its own documented fsync semantics (fn trusts `fsync :ok`).
  `mohan2018-crashmonkey-bounded-black-box-crash-testing.pdf`
- **Arpaci-Dusseau, OSTEP ch. 42 "Crash Consistency: FSCK and Journaling"** — background: data /
  ordered / writeback journaling, why writeback mode exposes stale blocks. **misses:** nothing
  new; it is the vocabulary for the rest. `arpacidusseau-ostep-crash-consistency-fsck-journaling.pdf`
- **TigerBeetle, safety / data-file / VOPR / testing docs (2026 main)** — an explicit storage
  fault model (corruption, misdirected IO, latent sector errors, torn writes, gray failure),
  O_DIRECT to its own page cache or a raw block device, checksummed hash-chained immutable data,
  PAR, and the VOPR deterministic simulator that injects all of it. **misses:** all of the
  durable-state faults above, and the O_DIRECT setting where fn's "issue order among survivors
  per file" (a page-cache property, stated in `fn-bs-crash-select`) no longer holds.
  `tigerbeetle2026-concepts-safety.md`, `tigerbeetle2026-internals-data-file.md`,
  `tigerbeetle2026-internals-vopr.md`, `tigerbeetle2026-internals-testing.md`

### Formal: models and logics that verify against them
- **Bornholt et al., "Specifying and Checking File System Crash-Consistency Models" (ASPLOS 16)**
  — Ferrite: litmus tests + axiomatic crash models of ext4/btrfs, run on real kernels and checked
  by SMT; synthesizes the fences a program needs. **misses:** per-FS models (fn has one) and the
  *litmus-test* discipline for validating a model against real kernels — fn's model is a
  hypothesis no test has confronted with a kernel. `bornholt2016-ferrite-specifying-checking-fs-crash-consistency.pdf`
- **Sigurbjarnarson et al., "Push-Button Verification of File Systems via Crash Refinement"
  (OSDI 16)** — Yggdrasil: an async block disk with flush, crash refinement checked by Z3 with no
  manual proofs, a stack of verified layers. **misses:** the *block-device* level (volatile write
  cache + flush, sector atomicity) that fn2 needs on robigalia, where there is no kernel FS; also
  a model of the push-button route itself (heading 2). `sigurbjarnarson2016-yggdrasil-push-button-crash-refinement.pdf`
- **Chen et al., "Using Crash Hoare Logic for Certifying the FSCQ File System" (SOSP 15)** — disk
  where each block holds a list of possible values; crash conditions in specs; recovery as a
  separate semantics, idempotent under crashes *during recovery*. **misses:** an explicit
  crash-during-recovery obligation (fn can express it by running recovery in the model; check the
  top theorem quantifies over it). `chen2015-fscq-crash-hoare-logic.pdf`
- **Chen et al., "Verifying a high-performance crash-safe file system using a tree
  specification" (SOSP 17)** — DFSCQ: deferred writes, `fdatasync` vs `fsync`, metadata/data
  split, log-bypass writes; the spec is a tree of possible durable states. **misses:**
  `fdatasync`/`O_DSYNC` (data without metadata) and data writes bypassing the journal.
  `chen2017-dfscq-verifying-high-performance-crash-safe-fs.pdf`
- **Ileri et al., "Proving confidentiality in a file system using DiskSec" (OSDI 18)** — SFSCQ:
  data-noninterference across crashes. **misses:** confidentiality — fn's "garbage" can be another
  tenant's stale block (ext4 writeback does this); fn proves integrity against it, not secrecy.
  `ileri2018-sfscq-proving-confidentiality-file-system.pdf`
- **Chajed et al., "Verifying concurrent, crash-safe systems with Perennial" (SOSP 19)** — Iris
  extension: crash invariants, recovery helping, versioned memory, concurrent recovery.
  **misses:** concurrency — fn's model is one sequential process; threads with ops in flight
  across a crash, and helping, are absent. `chajed2019-perennial-crash-safety-concurrency.pdf`
- **Chajed et al., "GoJournal" (OSDI 21)** — verified concurrent journaling over a 4 KB-atomic
  async disk with barriers; sub-block objects. **misses:** the disk-level barrier model and
  concurrent transactions. `chajed2021-gojournal-verified-concurrent-journaling.pdf`
- **Chajed et al., "Verifying the DaisyNFS concurrent and crash-safe file system with sequential
  reasoning" (OSDI 22)** — Dafny proves the sequential FS over GoJournal's transactions; Perennial
  lifts it. **misses:** nothing new in faults; it is the automation result (heading 2).
  `chajed2022-daisynfs-verifying-nfs-server.pdf`
- **Hance et al., "Storage Systems are Distributed Systems (So Verify Them That Way!)" (OSDI 20)**
  — VeriBetrKV: the disk as another host with async, out-of-order IO; proven under process crashes
  *and disk sector corruption* under a checksum assumption. **misses:** out-of-order async IO
  completion and sector corruption detected by checksum; the closest published model to what fn2
  on io_uring/O_DIRECT needs. `hance2020-veribetrkv-storage-systems-are-distributed.pdf`
- **Ridge et al., "SibylFS" (SOSP 15)** — loose executable POSIX spec (HOL4/Lem) as an oracle for
  21,070 tests across real FSes. **misses:** the non-crash nondeterminism fn collapses (which errno,
  path-resolution edge cases, short successful writes); also the oracle-testing route for checking
  fn's model against kernels. `ridge2015-sibylfs-posix-specification-oracle-testing.pdf`
- **Amani et al., "Cogent: Verifying High-Assurance File System Implementations" (ASPLOS 16)** —
  BilbyFs and ext2 in Cogent on seL4; UBI flash: erase blocks, write-once pages, async sync.
  **misses:** raw-flash semantics (erase-before-write, out-of-place updates) for a seL4 target
  without an FTL. `amani2016-cogent-verifying-high-assurance-fs.pdf`
- **CertiFlash (2026, arXiv 2609.10347)** — verification framework for FTLs: wear levelling, bad
  block management, crash recovery via journal+checkpoint. **misses:** the FTL beneath the block
  device, i.e. *why* the device-level faults above happen. `certiflash2026-formal-verification-framework-flash.pdf`
- **LeBlanc et al., "SquirrelFS" (OSDI 24)** — persistent-memory FS whose soft-updates ordering is
  checked by Rust typestate at compile time. **misses:** PM store/flush/fence ordering; the
  typestate idea is an automation route. `leblanc2024-squirrelfs-rust-crash-consistency.pdf`
- **Raad et al., "Persistency Semantics of the Intel-x86 Architecture" (POPL 20)** and **Khyzha &
  Lahav, "Taming x86-TSO Persistency" (POPL 21)** — Px86: `clflush`/`clflushopt`/`sfence`
  persist ordering, 8-byte persist atomicity. **misses:** memory-mapped persistence (PM, CXL,
  `mmap`+`msync`) where the crash cuts a store buffer, not a syscall list.
  `raad2020-persistency-semantics-intel-x86.pdf`, `khyzha2020-taming-x86-tso-persistency.pdf`
- **Kaashoek et al., "Extending concurrent separation logic to the hardware level to verify the
  xv6 OS kernel on RISC-V with AI agents" (2026, arXiv 2609.04043)** — MachCSL over Sail RISC-V,
  crashes that stop the kernel anywhere and power on again, agents automate large parts of the proof work that used to be written by hand.
  **misses:** crash at the instruction level of the *kernel* under the FS, i.e. the whole OS as
  the thing that crashes — the level a robigalia node has to own. `kaashoek2026-csl-hardware-level-xv6-riscv-ai-agents.pdf`

## 2. Proof automation and program logics that reduce manual proof

### Separation logic, crash logic, and refinement frameworks
- **Jung et al., "Iris from the ground up" (JFP 2018)** — the modular higher-order concurrent
  separation logic Perennial, Grove and MachCSL are built in; ghost state and invariants as the
  only primitives. Gives fn2 the vocabulary for crash invariants if a Coq/Rocq route is chosen.
  `jung2018-iris-from-the-ground-up.pdf`
- **Chajed et al., Perennial / GoJournal / DaisyNFS** (heading 1) — the measured automation point:
  DaisyNFS proves a concurrent crash-safe NFS server by writing the FS *sequentially in Dafny*
  over a verified transaction layer, so almost no crash or concurrency reasoning touches the
  application. This is the pattern fn2 wants: prove the storage-transaction layer once, write
  the node as sequential transactions. `chajed2022-daisynfs-verifying-nfs-server.pdf`
- **Sharma et al., "Grove" (SOSP 23, extended)** — Iris library for distributed systems with
  crashes and durable state (leases, reconfiguration, a replicated KV). The replication-era
  logic for fn2. `sharma2023-grove-separation-logic-distributed-systems.pdf`
- **Hawblitzel et al., "IronFleet" (SOSP 15)** and **"Ironclad Apps" (OSDI 14)** — Dafny +
  TLA-style refinement from protocol to implementation for Paxos and a sharded KV; its
  proof/implementation line counts and person-months are the baseline cost to beat. `hawblitzel2015-ironfleet-distributed-systems.pdf`,
  `hawblitzel2014-ironclad-apps.pdf`
- **Li et al., "Linear Types for Large-Scale Systems Verification" (OOPSLA 22)** — linear Dafny
  in VeriBetrKV: linearity replaces heap-framing proofs, cutting proof effort on mutable state.
  The analogue of what ACL2 stobjs already give fn. `li2022-linear-types-large-scale-systems-verification.pdf`
- **Klein et al., "Comprehensive Formal Verification of an OS Microkernel" (TOCS 2014)** and the
  original **seL4 SOSP 09** — refinement stack, the cost data (person-years per kLOC), and the
  invariants that a robigalia-hosted fn2 will sit on. `klein2014-sel4-comprehensive-formal-verification-tocs.pdf`,
  `sel4-formal-verification-os-kernel-sosp2009.pdf` *(already here)*
- **Appel, "Verified Software Toolchain" (ESOP 11)** — separation logic for CompCert C with a
  foundational soundness proof; the C-level route if fn2's hot path is C. `appel2011-verified-software-toolchain.pdf`
- **Ringer et al., "QED at Large" (2019 survey)** *(already here)* — proof-engineering survey: what
  makes proofs maintainable (proof repair, automation, decomposition). `qed-at-large-proof-engineering-survey-ringer-2019-2003.06458.pdf`

### Automation-heavy verifiers (the benchmarks for "little manual proof")
- **Lattuada et al., "Verus: A Practical Foundation for Systems Verification" (SOSP 24)** — SMT
  automation for Rust with linear ghost state; measures proof/code ratios and verification time
  against Dafny, Prusti, Creusot, F*, Iris on systems case studies (page tables, a KV store, a
  persistent-memory log). The current speed/effort frontier. `lattuada2024-verus-practical-foundation-systems-verification.pdf`,
  and the OOPSLA 23 paper `verus-linear-ghost-types-oopsla2023-2303.05491.pdf` *(already here)*
- **Leino, "Dafny: An Automatic Program Verifier for Functional Correctness" (LPAR 10)** — the
  base of IronFleet/VeriBetrKV/DaisyNFS. `leino2010-dafny-automatic-program-verifier.pdf`; see
  also `static-coverage-deductive-verification-dafny-boogie-2025.pdf` *(already here)* for
  checking what an automated proof actually used.
- **Protzenko et al., "Verified Low-Level Programming Embedded in F*" (ICFP 17)** — Low*: a
  C-shaped subset of F* extracted to readable C by KaRaMeL. `protzenko2017-lowstar-verified-low-level-programming-fstar.pdf`
- **Zinzindohoué et al., "HACL*" (CCS 17)** and **Protzenko et al., "EverCrypt" (S&P 20)** —
  verified high-performance C/assembly at production speed, with an agile multiplexing API.
  `zinzindohoue2017-hacl-star-verified-crypto-library.pdf`, `protzenko2020-evercrypt-verified-crypto-provider.pdf`
- **Bond et al., "Vale" (USENIX Security 17)** — verified assembly via a DSL whose proofs are
  discharged by Dafny/F*; how to verify hand-tuned hot loops. `bond2017-vale-verifying-high-performance-crypto-assembly.pdf`
- **Astrauskas et al., "Prusti: Leveraging Rust Types for Modular Specification and
  Verification" (OOPSLA 19)** — ownership types remove most framing annotations.
  `astrauskas2019-prusti-rust-types-modular-verification.pdf`
- **Le Blanc & Lam, "Surveying the Rust Verification Landscape" (2024)** — covers Creusot, Kani,
  Aeneas, Verus, Prusti; stands in for the Creusot paper, which HAL would not serve (see Gaps).
  `survey2024-rust-verification-landscape.pdf`
- **Kumar et al., "CakeML: A Verified Implementation of ML" (POPL 14)** — verified compiler
  bootstrapped in HOL4; the trusted path from a functional spec to a binary. `kumar2014-cakeml-verified-ml-implementation.pdf`

### ACL2: the automation fn already has, and what to use more of
- **Goel, Hunt, Kaufmann, "Abstract Stobjs and Their Application to ISA Modeling" (ACL2 13)** —
  logical model ≠ executable representation, with correspondence proved once; the x86 model's
  speed and proof resilience come from this. fn2's store state should be an abstract stobj.
  `goel2013-acl2-abstract-stobjs-isa-modeling.pdf`
- **Kaufmann, Sohail, Hunt, "Mutable Objects with Several Implementations" (ACL2 25)** —
  `attach-stobj` (ACL2 8.6): one abstract stobj, implementations attached later — e.g. a
  reference implementation for proofs and a fast one for the node. `kaufmann2025-acl2-mutable-objects-several-implementations.pdf`
- **Swords, "Incremental SAT Library Integration Using Abstract Stobjs" (ACL2 18)** — an external
  library behind an abstract stobj with a logical model; the pattern for fn2's I/O boundary.
  `swords2018-acl2-incremental-sat-abstract-stobjs.pdf`
- **Goel et al., "The x86isa Books" (ACL2 17)** — the largest stobj-based machine model;
  system-call modes, a model of what a verified binary does to the OS. `goel2017-acl2-x86isa-books.pdf`
- **Swords & Davis, "Bit-Blasting ACL2 Theorems" (ACL2 11)** (GL) and **Swords, "New Rewriter
  Features in FGL" (ACL2 20)** — symbolic execution to AIG/SAT with a rewriter in front; the
  push-button route for fixed-width encode/decode, checksums and layout lemmas.
  `swords2011-acl2-bit-blasting-gl.pdf`, `swords2020-acl2-fgl-new-rewriter-features.pdf`
- **Peng & Greenstreet, "Smtlink 2.0" (ACL2 18)** — sound Z3 integration as a verified clause
  processor; for arithmetic/array side-conditions GL cannot bit-blast. `peng2018-acl2-smtlink-2.pdf`
- **Moore, "Stateman: Using Metafunctions to Manage Large Terms Representing Machine States"
  (ACL2 15)** — metafunctions keep big state terms normalized; directly applicable to a store
  state threaded through long syscall sequences. `moore2015-acl2-stateman-metafunctions-machine-states.pdf`
- **Hardin et al., "Reasoning About LLVM Code Using Codewalker" (ACL2 15)** — Codewalker
  decompiles machine-model code into ACL2 functions automatically (Moore's tool); the route from
  an interpreted implementation to clean semantic functions. `hardin2015-acl2-codewalker-llvm.pdf`
- **Kaufmann & Moore, "Iteration in ACL2" (ACL2 20)** — `loop$` with guard-verified execution;
  replaces hand-written recursion + induction schemes for list sweeps. `kaufmann2020-acl2-iteration-loop.pdf`
- **Swords & Davis, "Fix Your Types" (ACL2 15)** — the fixing-function discipline behind FTY that
  makes theorems hypothesis-free and rewriting cheap. `swords2015-acl2-fix-your-types.pdf`

### LLMs and agents driving provers (2023-2026)
- **First et al., "Baldur" (FSE 23)** — whole-proof generation + repair from error messages
  (Isabelle); the baseline agent loop. `first2023-baldur-whole-proof-generation-repair-llm.pdf`
- **Thakur et al., "COPRA" (COLM 24)** — in-context agent for Lean/Coq with backtracking and
  retrieval. `thakur2023-copra-in-context-agent-theorem-proving.pdf`
- **Yang et al., "LeanDojo" (NeurIPS 23)** *(already here)* — retrieval-augmented proving with an
  open gym. `leandojo-retrieval-augmented-theorem-proving-neurips2023-2306.15626.pdf`
- **Thompson et al., "Rango" (ICSE 25)** — adaptive retrieval of proofs *and lemmas from the
  current project* for Coq software verification (CoqStoq); the retrieval design fn2's agents need.
  `thompson2024-rango-retrieval-augmented-proving-coq.pdf`
- **Yang et al., "AutoVerus" (OOPSLA 25)** and **Chen et al., "SAFE" (ICLR 25)** — LLM agents
  generating Verus proof annotations; SAFE self-evolves training data from the verifier.
  `yang2024-autoverus-automated-proof-generation-rust.pdf`, `chen2024-safe-rust-proof-generation-self-evolution.pdf`
- **Yang et al., "VeruSAGE: A Study of Agent-Based Verification for Rust Systems" (2025)** —
  agents proving functions of real verified Rust systems given their specs;
  they do well per function and fail at project-level abstraction (closed spec functions) and at
  decomposing a goal into specs and lemmas (an earlier RAG attempt on four systems got ~20%).
  `yang2025-verusage-agent-based-verification-rust-systems.pdf`
- **Sun et al., "VeriStruct" (2025)** — agentic verification of whole data-structure modules
  (specs + invariants + proofs) in Verus. `sun2025-veristruct-ai-verification-data-structure-modules-verus.pdf`
- **Bursuc et al., "A benchmark for vericoding" (2025)** — formally verified program synthesis
  from specs: 12,504 tasks, off-the-shelf success 82% Dafny, 44% Verus, 27% Lean —
  SMT-automated languages are far easier for agents than tactic ITPs today.
  `bursuc2025-vericoding-benchmark.pdf`
- **Ren et al., "DeepSeek-Prover-V2" (2025)** and **Lin et al., "Goedel-Prover-V2" (2025)** —
  open-weight Lean provers: subgoal decomposition and verifier-guided self-correction.
  `ren2025-deepseek-prover-v2-subgoal-decomposition.pdf`, `lin2025-goedel-prover-v2-scaffolded-self-correction.pdf`
- **Li et al., "A Survey on Deep Learning for Theorem Proving" (COLM 24)** — map of the field.
  `li2024-survey-deep-learning-theorem-proving.pdf`
- **Kaashoek et al., MachCSL / xv6 with AI agents (2026)** (heading 1) — the strongest data point
  that agents can carry systems-scale separation-logic proofs given a good decomposition and
  design documents. `kaashoek2026-csl-hardware-level-xv6-riscv-ai-agents.pdf`
- **Ringer et al., proof repair** *(already here)* — PUMPKIN PATCH/PI: repair proofs across type
  equivalences after a refactor, the non-LLM half of keeping proofs alive. `ringer2018-adapting-proof-automation-to-adapt-proofs.pdf`,
  `ringer2020-pumpkin-pi-proof-repair-equivalences.pdf`
- No ACL2-specific LLM-proof paper exists on arXiv (all 117 ACL2-tagged abstracts were read by
  title; the nearest are ACL2(ml) 2014 and the 2023 proof-debugging tools). fn2 would be first.

## 3. High-performance node design

- **TigerBeetle, "TigerStyle"** — assertion density, static allocation at startup, no

## 4. Metaprogramming for succinct systems: DSLs that emit code and proof obligations

- **Coglio, "A Proof-Generating C Code Generator for ACL2 Based on a Shallow Embedding of C in
  ACL2" (ACL2 22)** — ATC: ACL2 functions in a C-shaped subset become C plus an ACL2 proof that
  the C (under a formal C semantics) computes them. fn2's most direct derived-executable route
  off ACL2. `coglio2022-acl2-atc-proof-generating-c-code-generator.pdf`
- **Coglio, "A Complex Java Code Generator for ACL2 Based on a Shallow Embedding of ACL2 in
  Java" (ACL2 22)** — ATJ: the same for Java, with a shallow and a deep (AIJ interpreter) mode;
  the paper compares the code-generation design space. `coglio2022-acl2-atj-java-code-generator.pdf`
- **Coglio, McCarthy, Westfold, "Syntheto: A Surface Language for APT and ACL2" (ACL2 22)** — a
  readable spec language whose refinements run through Kestrel's APT transformations, each
  emitting a proof. `coglio2022-acl2-syntheto-apt-surface-language.pdf`
- **Coglio & Westfold, "Isomorphic Data Type Transformations" (ACL2 20)** — APT `isodata`:
  change a data representation (e.g. list model → packed bytes) and get the new functions and the
  equivalence theorems generated. The tool for moving fn2 from the logical store to the fast one.
  `coglio2020-acl2-apt-isomorphic-data-type-transformations.pdf`
- **Amani et al., "Cogent"** (heading 1) — a linear-typed functional DSL compiled to C with a

- **Padon et al., "Ivy: Safety Verification by Interactive Generalization" (PLDI 16)** — protocols

- **Erbsen et al., "Simple High-Level Code For Cryptographic Arithmetic – With Proofs, Without

## Crash model: what ours misses, by paper

"fn v2" is `books/byte-store.lisp` as of origin/dev. **Absent** = the model cannot produce the
behaviour; **partial** = it produces some of it; **covered** = included for contrast.

| # | Behaviour the environment can produce | fn v2 | Papers that show it happens / model it | What fn2's model would add |
|---|---|---|---|---|
| 1 | Durable data silently corrupted at rest (bit rot, firmware) | absent: crash and every syscall leave `inodes`/`dirs` untouched | Bairavasundaram 08, Maneas 20, Schroeder 16, Ganesan 17, TigerBeetle safety | a corruption step on any durable unit at any time; theorems say "detected", not "prevented" |
| 2 | `read` of durable data fails (latent sector error, uncorrectable flash error) | absent: `fn-bs-read` takes no outcome | Bairavasundaram 07, Schroeder 16, Prabhakaran 05 (IRON), Ganesan 17 | `read` takes an outcome (`:eio`, or data) like every other syscall |
| 3 | Misdirected write: the bytes land on a different block/file | absent | Bairavasundaram 08, Krioukov 08, Zheng 13 ("flying writes"), TigerBeetle | a pending write may land on another unit, damaging durable data there |
| 4 | Misdirected read: the right data exists, another block comes back | absent | Krioukov 08, TigerBeetle | read outcome may return another unit's content |
| 5 | Lost write: write/flush acknowledged, data never stable (device ignores flush, FS bug, deferred error) | absent: `fsync :ok` drains into durable | Zheng 13/14 (unserializable writes), Mohan 18 (CrashMonkey), Bairavasundaram 08, Rebello 20 (ext4 `data=journal` reports the failure on a later fsync) | a named "lying device" profile where fenced writes may still be dropped; obligations become detection + repair |
| 6 | Power cut corrupts data that was not being written | absent: crash touches pending ops only | Zheng 13 | crash may corrupt any durable unit (bounded count or unbounded) |
| 7 | Device or FS dies stickily (dead SSD; journal failure remounts read-only) | partial: each call may fail, but nothing stays failed | Zheng 13, Rebello 20 | a sticky failed mode the recovery must reach a safe stop from |
| 8 | View after a failed fsync: ext4/XFS keep the unwritten data in cache, Btrfs reverts to old | partial: deliberately unspecified; programs may not read it | Rebello 20 | keep the restriction, and state both views for re-open-and-recover paths |
| 9 | fsync error delivered to a different fd/process, or once only (errseq) | absent: one fence per inode, error on that call | Rebello 20 | per-descriptor error delivery |
| 10 | Tearing inside the declared unit (512 B sectors in a 4 KiB unit, shorn writes) | covered if "garbage" ranges over all octet strings and the theorems hold for every `unit` (they do) | Zheng 13, Pillai 14 | nothing; pin the dev profile to the sector size, not the FS block |
| 11 | Two in-flight writes to one unit complete in either order (O_DIRECT, io_uring, NVMe queues) | absent: survivors land in issue order, justified by the page cache | Axboe 19, Hance 20 (async out-of-order IO), TigerBeetle architecture | a direct-IO profile with no per-file order among in-flight ops |
| 12 | Concurrent threads with syscalls in flight at the crash | absent: one sequential process | Chajed 19 (Perennial), Chajed 21 (GoJournal) | interleaved pending lists, or a single-threaded-core rule made a theorem premise |
| 13 | Crash during recovery, repeatedly | partial: expressible by running recovery in the model; not a named obligation | Chen 15 (FSCQ idempotent recovery), Chajed 19 | a top-level theorem quantifying over crashes during recovery |
| 14 | `fdatasync`, `O_DSYNC`, `sync_file_range`, FUA, `fallocate`, `truncate`, `mmap`/`msync` | absent (truncate deliberately) | Chen 17 (DFSCQ), Bornholt 16 (Ferrite), Raad 20 | only the ones fn2's IO path uses, each with its own fence |
| 15 | Block device without a file system: volatile write cache, flush, FUA, sector atomicity | absent: the model is POSIX-level | Sigurbjarnarson 16 (Yggdrasil), Chen 15, Chajed 21, TigerBeetle (raw block device) | a block-device model under or instead of the byte store — needed for robigalia/seL4 |
| 16 | Raw flash: erase-before-write, write-once pages, FTL crash recovery, bad blocks | absent | Amani 16 (BilbyFs/UBI), CertiFlash 26, Schroeder 16 | only if fn2 drives flash without an FTL |
| 17 | Persistent memory / CXL: cache-line persist order, 8-byte atomicity | absent | Raad 20, Khyzha 21, LeBlanc 24 | only if fn2 targets PM |
| 18 | Crash exposes another file's stale data (confidentiality) | partial: "garbage" admits it, proofs cover integrity only | Ileri 18 (SFSCQ), OSTEP ch. 42 (writeback mode) | a noninterference statement for multi-tenant stores |
| 19 | Fail-slow / gray failure: operations succeed but take seconds | absent: no time | Gunawi 18, Huang 17, TigerBeetle | a latency outcome and liveness/timeout obligations |
| 20 | Replicated log: crash-torn tail vs mid-log corruption must be told apart; repair from peers | n/a (single node) | Alagappan 18 (PAR), Ganesan 17, TigerBeetle | when fn2 replicates: never truncate on a bad checksum before consulting peers |
| 21 | The model itself never checked against real kernels | absent | Bornholt 16 (litmus tests), Ridge 15 (SibylFS oracle), Mohan 18, Pillai 14 | run the model as an oracle over recorded block/syscall traces from ext4/XFS/Btrfs |
| 22 | Other errnos, short successful writes, `EINTR` | partial: `:eio`/`:enospc` with partial progress | Ridge 15 (SibylFS) | a looser outcome set per syscall |

The single most consequential gap is rows 1-6: fn v2 treats the durable tables as perfect, so
every checksum in fn is unverified against any fault it exists to catch. Row 11 is the one
fn2's high-performance IO path will hit first.

## The three automation routes most likely to cut manual proof for fn2

**Route 1 — Prove one storage-transaction layer against the tough model; write the node as
sequential transactions over it; derive the fast representation by verified transformation.**
DaisyNFS is the measured instance: the hard crash and concurrency reasoning lives in GoJournal
and Perennial once, and the NFS server above is sequential Dafny. In ACL2 the same shape is
already native: the store is an abstract stobj (logical alist model, proved correspondence),
`attach-stobj` swaps in the fast implementation, APT `isodata` regenerates functions and
equivalence theorems when the representation changes, and ATC emits C with a proof. Stateman
keeps long state terms tractable. Papers: Chajed 22 (DaisyNFS), Chajed 21 (GoJournal), Chajed 19
(Perennial), Goel 13 (abstract stobjs), Kaufmann 25 (attach-stobj), Swords 18 (library behind an
abstract stobj), Coglio 20 (isodata), Coglio 22 (ATC, Syntheto), Moore 15 (Stateman), Li 22
(linear types replace framing), Amani 16 (Cogent).

**Route 2 — Keep the obligations in decidable or bit-blastable fragments, so they are
push-button.** Yggdrasil checks crash refinement of a whole FS stack with Z3 and no manual
proofs by keeping each layer finite and bounded; Ivy keeps protocol invariants in EPR so
inductiveness checks terminate; Ferrite checks crash litmus tests by SMT. In ACL2, FGL/GL
bit-blast fixed-width codec, checksum and layout lemmas and Smtlink discharges arithmetic side
conditions; `loop$` and FTY fixing remove recursion and type-hypothesis boilerplate. Design rule:
make per-unit storage state finite and bounded so the crash obligation of each layer is
bit-blastable. Papers: Sigurbjarnarson 16, Padon 16, Bornholt 16, Swords 11, Swords 20, Peng 18,
Kaufmann 20, Swords 15, Hance 20.

**Route 3 — Humans (or the orchestrator) decompose; agents fill proofs, with project retrieval
and verifier feedback.** The evidence is consistent: agents prove individual functions well when
specs and lemma signatures are given (VeruSAGE, VeriStruct, AutoVerus), and fail at
decomposition and at respecting abstraction boundaries (VeruSAGE). SMT-backed verifiers are far
easier for them than tactic ITPs (vericoding: 82% Dafny, 44% Verus, 27% Lean). Retrieval of the
project's own lemmas is what lifts systems-scale success (Rango). MachCSL/xv6 is the existence
proof at kernel scale, driven by design documents. ACL2's waterfall plus `:hints` is closer to
the SMT style than to tactics — a proof is mostly lemma statements and hints — which is the shape
agents already do well; there is no ACL2 agent literature, so fn2 would be measuring it first.
Papers: Kaashoek 26, Yang 25 (VeruSAGE), Sun 25 (VeriStruct), Bursuc 25, Thompson 24 (Rango),
Yang 24 (AutoVerus), Chen 24 (SAFE), First 23 (Baldur), Ringer 18/20 (proof repair).
