# fn2 execution model: round 2 (the coordinator, 2026-10-28)

Read after EXECUTION-MODEL-ROUND1.md and EXECUTION-MODEL-ROUND1-ASTRA.md.

## Conceded
1. **The boundary.** Parsing, framing, connection state, scheduling, admission, buffer ownership and accounting belong inside the semantic core. "Already-validated commands" was an unstable boundary: validity depends on evolving shared state (identity, reservations), and a trusted parser outside the core would be the largest hole in "clients cannot crash us". The core manipulates connection capabilities, never descriptors.
2. **Three batches, not one.** Harvest batch (completions observed), execution turn (bounded work across runnable machines), commit batch (records sharing a durability barrier). None defines another's lifetime. "The batch is the step" is withdrawn as a slogan; the execution turn is the step of the executable, and the reference semantics selects one transition at a time with the fused dispatcher proved to implement an allowed reference schedule.
3. **The durability repairs.** FUA on the final sector does not persist earlier cache-resident writes (preflush vs FUA); a bad checksum does not prove an unacknowledged tail under corruption-at-rest or misdirected writes, so recovery needs a damaged/unknown state and a policy; a self-consistent older image is indistinguishable from "never accepted" without surviving independent evidence (a monotonic anchor, a client receipt or a peer), so rollback detection is a stated assumption or an external witness, never a local theorem. These go into ENVELOPE-AND-HOST.md's fault table as corrections.
4. **Isolation stated precisely.** One principal cannot consume another admitted principal's reserved capacity or minimum scheduling share; best-effort capacity can run out; unauthenticated connections share one bounded admission class and more connections manufacture no entitlement. Static working memory is not a store-size ceiling: persistent indexes page through bounded caches; admission limits are explicit; namespace exhaustion is handled, not compiled in.
5. **The executor traps** (budgets for timers, signals, grants and wake fan-out; never wait on the outside while internal continuations are runnable; dependency order over kind order; counter exhaustion; cancellation does not release buffers; zero-copy send progress is not buffer release) are accepted as requirements on the loop.
6. **Request-indexed theorems.** "A refused step changes no committed history" becomes "the refused operation contributes no committed mutation"; outcomes are per operation, most turns are pending progress; equivalence under schedules is stated over observations, not internal states.

So the model is Astra's: **one semantic executor over a deterministic cooperative machine network, bounded asynchronous adapters, batching inside the implementation**, with partitioning kept possible (transferable handles, explicit message boundaries) and not built.

## Still open, and what round 2 asks for
A. **The ACL2 realization of "one transition at a time" plus a fused dispatcher.** Concretely: is the core state one top-level stobj with nested stobjs per machine kind (connections, uploads, cursors, commit batches, subscriptions, principals) laid out as struct-of-arrays, each machine a row with a state enum and typed fields? Is the reference `step` the single-transition function over that stobj, with the turn an executable loop that calls it under a budget, so that the refinement obligation is "the loop is some sequence of reference transitions"? Or do you want the reference itself to be the turn? Say which, and why, with the proof obligation it creates. Keep ATC (ACL2→C) in view: the dispatcher must be the kind of code ATC can emit.
B. **The machine catalogue.** List the machine kinds for the first slice, each with: state enum, fields (with widths), its resource account entries, the events it consumes, the actions it emits, its continuation points, and its per-run budget. Include the commit-batch machine, the consumer wait machine, the TLS admission machine and the cleaning/checkpoint machine.
C. **The scheduler.** A deterministic fairness rule that selects principals and machines from core state (no clock inside the decision), with its bound per turn and the starvation property it gives. Describe the runnable sets and how dependency order is kept while homogeneous groups are fused.
D. **The event and action vocabulary as tables with capacities**: name, fields, who may emit, the reservation it consumes, the capacity of its queue, what happens at exhaustion (an ordinary continuation condition, as you said).
E. **The durability protocol, repaired**: the commit-batch state machine from first dependency write to publication, with the preflush/FUA usage stated per backend, the recovery states (intact / torn tail / damaged / unknown) and the policy per state, and the independent-evidence assumption named.
F. **The first slice, as an acceptance test**: the composition you named (a streaming upload committing beside a cold 16 MiB BODY, a resumable XOVER, a TAKETHIS window, a parked remote consumer; a stalled reader, an unfinished cancellation, a principal exhausting its own quota, crashes between dependency writes and publication) written as the simulator's scenario list with the checker each one needs.
G. **Where you disagree with ENVELOPE-AND-HOST.md's bounds table** beyond the memory-pin aggregate: say which bounds are substantive storage choices masquerading as execution bounds, and what replaces them.

Answer as a document, same rules as round 1: arguments and specifications, cite by path, be concrete. Round 3 will be the convergence: the coordinator writes EXECUTION-MODEL.md as the decision with both arguments, and you review it once.
