# fn2 inbox delivery: selection, fan-out, or per-edge hybrid (2026-10-28; Opus scholar; present state)

The question: how does a consumer's *inbox* (everything addressed to it across groups: room posts, DMs, mentions) reach it? Write-time fan-out (a row per recipient at commit), a selection query at read time over the log with per-stream cursors and subscription edges for wake, or a hybrid. Ember, verbatim: "what does fastmail do in their infrastructure does anyone know? what does bluesky vs twitter vs anyone else do? I don't wanna manually go through the evolution of twitter scaling up in our own software, hitting every single headsmack and roadbump along the way that they did. We should build our software for scale from the start, but we also should be thinking smart about how to have mechanisms now that enable the policies we'd need later."

Binding context read first: `EXECUTION-MODEL.md` rules 4-7 (scheduler with a protected subscription-notification service class; isolation; one byte pool; internal notifications such as `SubscriptionDirty` are state bits, never a queue) and ROUND2-ASTRA §B.2 (the subscription edge row `wait, stream-id, stream-prev/next, wait-prev/next, observed-frontier`; `Esub` = 4,096; scenario 7 "registration's final frontier check prevents lost wake; wake is only a hint"; scenario 8 "one wait watches room, DM, and mention streams"); `STORAGE-DESIGN.md` §1 and §4 decision 1 (one ordered semantic event history; `State = Fold(Summary_k, Events_{k+1..n})`; every fold names its interpretation, initialization and coverage; overview keyed (group, number) from first materialization; a retaining consumer is a charged, inactivity-bounded durable hold); `CLIENTS-AND-DATA-MODELS.md` §1-2; `RELEASE-PLAN.md` §6 D5 (recommend the selection query; "fan-out can be built above it later as a materialized selection").

## 1. The systems

A vocabulary used throughout. A **stream** is an ordered sequence of events with one writer order (a room, a DM lane, a newsgroup, a Twitter user's own tweets, a Kafka partition). A **consumer** follows a set of streams. **Fan-out on write** (push, materialize) writes a reference to each event into a per-consumer structure when the event commits. **Selection on read** (pull, query on demand) merges the followed streams when the consumer asks. A **wake** is the signal that tells a parked consumer to ask. Every system below separates three things that the question bundles together, and the separation is the main finding: (a) *where the event's bytes live* (always once, in every mature system), (b) *how a consumer finds which events are its own* (fan-out or selection, frequently different per kind of address), and (c) *how a consumer learns that it should look* (the wake, which is a hint everywhere it works).

### 1.1 Fastmail / Cyrus IMAP: write-time placement, because mail has no shared stream

**What it does.** Mail delivery is placement at write time: the MTA speaks LMTP to Cyrus's `lmtpd`, which files the message into each recipient's own mailbox (after the recipient's Sieve script, run with the recipient's authority). Email has no shared object across administrative domains, so the envelope's recipient list *is* the fan-out, and it is decided by the sender. Inside one server Cyrus does not copy the bytes per recipient: "If a delivery attempt mentions several recipients ... the server attempts to store as few copies of a message as possible. It will store one copy of the message per partition, and create hard links for all other recipients of the message" (single instance store); quota still charges "each copy of a message ... independently, even when the server can conserve disk space use by making hard links" [cyrus2026-docs-overview-and-concepts.txt]. Duplicate delivery suppression is keyed by (Message-ID, envelope recipient) [same]. The per-mailbox structure is a message file per UID plus `cyrus.index` (fixed-length per message), `cyrus.cache`, and `cyrus.seen` ("variable-length state information about each reader of the mailbox") [same]: so a **shared folder** (Cyrus calls the early form a "bulletin board", and its netnews mode stores newsgroups as mailboxes) is *one* copy read by many users, with per-reader seen state kept beside it, and optionally "shared \Seen flags between all users with access to a mailbox" for team queues [cyrus2026-docs-shared-seen-state.txt]. Shared folders are therefore selection: the group's content is a stream, each reader keeps its own position and flags.

**JMAP (RFC 8620, written by Fastmail) separates the wake from the data.** Every data type per account has a *state string*; `Foo/changes` returns what changed since a state; push "sends minimal data over the push channel: just enough for the client to know whether it needs to resync. The format allows multiple changes to be coalesced into a single push update and the frequency of pushes to be rate limited by the server. It doesn't matter if some push events are dropped before they reach the client; the next time it gets/sets any records of a changed type, it will discover the data has changed and still sync all changes" (§7); a `StateChange` carries only per-account, per-type state strings (§7.1) [rfc8620-jmap-core.txt]. When history is gone the server answers `cannotCalculateChanges` and "The client MUST invalidate its Foo cache"; servers "SHOULD be able to calculate changes from any state string that was given to a client within the last 30 days" (§5.2) [same]. Fastmail's own client implements the state string as a **modseq**, "a counter we keep per account, per data type", with created/updated modseq on every record and an index on updated modseq; it keeps destroyed records as tombstones "so we can calculate changes" up to a `highestPurgedModSeq` [fastmail2024-blog-offline-architecture-modseq-state.txt].

**What it cost them.** The cost of write-time placement in mail is bounded by the envelope (a sender names its recipients; mailing lists expand at a list server, outside the mailbox store), so Fastmail's published pain is not fan-out but identity and replication: in 2026 eight accounts lost folders because Cyrus replication followed mailbox *name* history and usernames had been reused ("We made a decision way back in the early days to use the primary email address directly as the username in Cyrus ... This has caused some pain over the years!"); the planned fix is "moving the replication protocol to be more based on the user's inbox uniqueid for everything rather than mboxname" [fastmail2026-blog-data-resilience.txt]. Lesson for fn2: per-consumer state keyed by a stable identity and epoch, never by a name; payload once, references per recipient; the wake is a coalescable hint over a monotone state counter; "changes since" needs tombstones up to a declared horizon and an explicit "cannot calculate" outcome.

### 1.2 Twitter: the canonical evolution, with every headsmack in order

1. **2006-2008, pull from one database.** The home timeline was a query over the tweets of everyone you follow. Krikorian (2013): "Naive materialization is a massive select statement over all of Twitter. It was tried and died" [twitter2013-highscalability-krikorian-timelines-at-scale.txt]. Twitter "started as a 'content management platform not a messaging platform'" [twitter2009-infoq-weaver-evolving-architecture-vector-cache.txt].
2. **2008-2009, write-through vector caches and a queue.** "The first architectural change was to create a write-through Vector Cache containing an array of tweet IDs ... This cache has a 99% hit rate"; then a row cache and a fragment cache; a page cache whose generational keys gave the cache "only a 5 hour effective life time"; and the queue: "on average, each user has 126 followers, it means there are 126 messages placed in the queue for each tweet", with peaks at the Obama inauguration "3 times the normal traffic", and the Ruby queue (Starling) crashing under GC until it was rewritten (Kestrel) [twitter2009-infoq-weaver-evolving-architecture-vector-cache.txt]. This is fan-out on write arriving as a cache.
3. **2010-2013, fan-out on write into Redis home timelines.** "Do a lot of processing when tweets arrive to figure out where tweets should go"; each home timeline is a Redis list of at most 800 entries (tweet ID, author ID, 4 bytes of flags), replicated 3 times; fan-out pipelines "4k destinations at a time"; 300K QPS of timeline reads against about 6,000 writes per second; 400 million tweets a day, 30 billion deliveries a day, "3.5 seconds @ p50 to deliver to 1m; ... @ p99 it could take up to 5 minutes" [twitter2013-highscalability-krikorian-timelines-at-scale.txt].
4. **Headsmack: inactive users.** Only users active within 30 days are kept in the cache; "If you fall out of the Redis cluster then you go through a process called reconstruction ... Hit disk for every single one of them and then shove them back into Redis" [same]. The materialized view became a cache with a slow rebuild path.
5. **Headsmack: the celebrity problem.** "@ladygaga has 31 million followers ... It's a lot of tweets to write in the datacenter when one of these people tweets. It's especially challenging when they start talking to each other"; "Replies are being seen all the time before the original tweets for celebrities. They introduce race conditions throughout the site" [same].
6. **The hybrid.** "Not fanning out the high value users anymore. For people like Taylor Swift don't bother with fanout anymore, instead merge in her timeline at read time. Balances read and write paths. Saves 10s of percents of computational resources" [same]. This is Feeding Frenzy's per-edge rule (§2), arrived at empirically.
7. **Search is the inverse.** Earlybird indexes each tweet once (O(1) write) and a query scatter-gathers every shard (O(n) read) [twitter2013-highscalability-krikorian-timelines-at-scale.txt; busch2012-earlybird-real-time-search-twitter-icde.pdf]: selection with an index, accepted where reads are rare.

What it cost them: six years and two rewrites to reach a hybrid whose decision variable (who is high-fanout) is a per-producer property, plus a permanent reconstruction path and a consistency anomaly (replies before originals) that came from asynchronous fan-out, not from pull.

### 1.3 Bluesky / AT Protocol: a log (firehose), fan-out timelines, materialized notifications, pull feeds

**What it does.** Each user's data is a signed repository on a PDS; the Relay crawls repositories and emits the **firehose**, which "does not interpret or index the records"; the **AppView** "consumes the firehose ... counts the number of likes on every post, ... collates the thread of replies ... maintains the set of followers for each user, and constructs the timeline containing the posts by the accounts that each user is following"; **feed generators** "typically take the firehose as their input" and "return a list of post IDs they have selected", which the AppView hydrates [kleppmann2024-bluesky-at-protocol-usable-decentralized-social-media-2402.03239.pdf]. So: the log is the authority (repos and the firehose); the following timeline is fan-out on write; custom feeds are selection computed by third parties and pulled per request; notifications are private per-user state [same, §2].

**Timelines** fan out: "looking up all of your followers, then inserting a new row into each of their Timeline tables", sharded by user in ScyllaDB, "regularly trimmed when written to" [bluesky2025-jazco-lossy-timelines.txt]. **Notifications** are materialized per recipient at indexing time, with a bounded recipient set: the AppView's post indexer emits one notification per distinct recipient (`notified` set, the author excluded) for mentions in the post's facets, the quoted post's author, and reply ancestors up to `REPLY_NOTIF_DEPTH = 5` [bluesky2026-src-appview-indexing-post-ts.txt]. Mentions are thus fan-out on write, but their fan-out is the *addressing* of the post, not the audience.

**What it cost them.** Hot shards from consumers, not producers: "some of them will do abnormal things like... well... following hundreds of thousands of other users", making a timeline "hyperactive with writes and trimming" and slowing "tens of thousands of other users sharing a shard"; tail latency stacking made "a user followed by 2,000,000 other users" take up to 5 minutes to fan out [bluesky2025-jazco-lossy-timelines.txt]. The fix is deliberate loss: `loss_factor = min(reasonable_limit/num_follows, 1)` drops writes to over-following timelines, which cut fan-out p99 by 96% ("Jobs that used to take 5-10 minutes for large accounts now take <10 seconds") [same]. That is acceptable for a timeline nobody can read in full; it is not acceptable for an inbox. The firehose itself had to be shrunk "by >99%" for consumers (Jetstream: filtered, JSON, by collection) [bluesky2024-jazco-jetstream-shrinking-firehose.txt]: whole-log consumption does not scale to many small consumers.

### 1.4 Mastodon: fan-out on write into Redis, notifications in Postgres, Sidekiq in between

**What it does.** `FanOutOnWriteService` pushes a status to "home and mentions feeds": `deliver_to_all_followers!`, `deliver_to_lists!`, `deliver_to_mentioned_followers!` enqueue `FeedInsertWorker` jobs, and `notify_mentioned_accounts!` enqueues `LocalNotificationWorker` jobs that create durable notification rows [mastodon2026-src-fan-out-on-write-service-rb.txt]. Home feeds are Redis sorted sets, `MAX_ITEMS = 800`, trimmed on insert; `push_to_home` returns early "unless account.user&.signed_in_recently?" [mastodon2026-src-feed-manager-rb.txt], and the window is `ACTIVE_DURATION = ENV.fetch('USER_ACTIVE_DAYS', 7).to_i.days` with the comment "status fan-out to followers will include only people active within this time frame"; a returning user triggers `regenerate_feed!` via a `RegenerationWorker` [mastodon2026-src-user-activity-rb.txt; mastodon2026-src-user-rb.txt]. Between servers, ActivityPub delivery uses `sharedInbox` so that "delivery to all followers" sends one copy per receiving server, which then fans out locally (§7.1.3) [w3c2018-activitypub.txt].

**What it cost them.** The feed is a cache: "Home feeds, list feeds, and Sidekiq queues ... are backed by Redis and that's important data you wouldn't want to lose (even though the loss can be survived ...)" [mastodon2026-docs-admin-scaling.txt]; returning users met empty timelines ("It took roughly 48 hours until the feed came back to normal", issue #5634) [mastodon2017-issue-5634-returning-users-empty-timelines.txt]. The write path is a job queue whose backlog is the outage: during the November 2022 exodus a server's Sidekiq queue reached "over 200,000 queued jobs" and "multi-hour delays in incoming federation", because "Each of these messages necessitates a Sidekiq task which integrates it into the database, users' timelines and notification lists" [mastodon2022-tindall-scaling-in-the-face-of-an-exodus.txt]; the documented remedy is queue priorities (`default` for local users above `ingress` for remote activities) and more workers [mastodon2026-docs-admin-scaling.txt]. Lesson: unbounded asynchronous fan-out converts write load into latency nobody can see until the queue is hours long.

### 1.5 Matrix: per-room logs, /sync as a selection, push rules as write-time fan-out of counters

**What it does.** Each room is its own event DAG; `/sync` is a selection over the user's joined rooms: the response carries `next_batch` (passed back as `since`) and per room a `prev_batch`; long-polling holds the request open "returning early if an event occurs"; and "if a large number of events arrive between calls to `/sync`, a 'limited' timeline is returned ... The client may therefore end up with 'gaps'" that it fills with `/rooms/{roomId}/messages` [matrix2026-docs-client-server-api.md, "Syncing"]. Notifications are not a selection: "When receiving a new event homeservers process push rules for each of the local users in the room (excluding the sender)", producing a new unread count and possibly a push-gateway request, and "The updated notification count from a new event MUST appear in the same `/sync` response as the event itself" [matrix2026-docs-push-module.md, "Server behaviour"]. Receipts then clear counts "prior to and including that event" [same].

**What it cost them.** (a) Selection that enumerates all subscriptions per request: "The current `/sync` endpoint scales badly as the number of rooms on an account increases ... On large accounts with thousands of rooms, the initial sync operation can take minutes"; the replacement's first goal is "Sync time should be independent of the number of rooms you are in" (MSC3575), now Simplified Sliding Sync (MSC4186) native in Synapse [matrix2022-msc3575-sliding-sync.md; matrix2024-blog-moving-to-native-sliding-sync.txt]. (b) Write-time per-recipient rows: Synapse's `event_push_actions` (one row per event per notified user) and its roll-up into summaries are a long-running performance problem; the maintainers record that "if a user sends a bunch of messages into a room with a huge number of members it resulted in a huge number of entries in event_push_actions, which was enough to cause serious slowness when summing over the table" [matrix2022-synapse-issue-13846-push-actions-unread-counting.txt]. Lesson: the per-room selection is right; the per-room-member write is where the big room bites; counts must be a fold with a bounded update, not a sum over fan-out rows.

### 1.6 Zulip: a UserMessage row per recipient, and soft deactivation as the per-edge hybrid

**What it does.** Zulip stores "one UserMessage row in the database for each user who is a recipient of the message (including the sender), with appropriate flags for whether the user was mentioned, an alert word appears, etc.": rows `(message_id, user_id, flags)` with 32 bits of flags, because its threading model "requires tracking which individual messages each user has received and read (in other chat products, the system either doesn't track what the user has read at all, or just needs to store a pointer for 'how far the user has read' in each room or channel)" [zulip2026-docs-subsystems-sending-messages.txt].

**What it cost them, and the fix.** "The server backend was introducing a latency of about 1 second per 2000 users subscribed to receive the message" [same]. The fix, **soft deactivation**: users idle "for a few weeks" stop receiving UserMessage rows; "If/when the user ever returns to Zulip, we can at that time reconstruct the UserMessage rows that they missed ... We can construct those rows later because we already have the data for when the user might have been subscribed or unsubscribed from channels"; the exception is "a few flags that result from content in the message (e.g., a message that mentions a user results in a 'mentioned' flag)", for which rows are still created at send time, because re-parsing is expensive and "those messages are rare"; the result: "one can send a message to a channel with 5K subscribers of which 500 are active, and it'll arrive in the couple hundred milliseconds" [same]. This is exactly a per-(consumer, stream) policy switch from materialize to select, with a backfill that is correct only because subscription history is retained, and with mentions kept materialized regardless.

### 1.7 Kafka consumer groups: pure pull with an offset per partition

"Our topic is divided into a set of totally ordered partitions, each of which is consumed by exactly one consumer within each subscribing consumer group ... the position of a consumer in each partition is just a single integer ... This makes the equivalent of message acknowledgements very cheap"; pull because "a push-based system has difficulty dealing with diverse consumers ... the consumer tends to be overwhelmed when its rate of consumption falls below the rate of production"; long poll because "the consumer may end up polling in a tight loop" otherwise; offsets are stored as messages in an internal topic so a transactional producer can commit output and offset atomically [kafka2026-docs-design.md]. **What it cost them**: offsets expired on a timer even for live groups: "committed offsets are removed even when there are still active, but rarely committing, consumers ... the consumer is forced to start from the start or end of the log ... leading to potential duplicate consumption or missing records" (KAFKA-4682, fixed by KIP-211) [kafka2026-docs-kip-211-offset-expiration-semantics.txt]. Kafka never fans out to consumers: the consumer group is the unit of subscription, and a consumer wanting several topics holds a vector of offsets.

### 1.8 Slack and Discord: channel-centric pull with per-user read state; mentions as counters

**Slack**: Channel Servers are "stateful and in-memory, holding some amount of history of channels", consistent-hashed by channel ID ("A 'channel' in this instance is an abstract term whose ID is assigned to an entity such as user, team, enterprise, file, huddle, or a regular Slack channel"); Gateway Servers "hold users' information and websocket channel subscriptions"; a message goes to the channel's server, which "sends out the message to every GS across the world" subscribed to it, which pushes to online clients; 500 ms worldwide delivery [slack2023-eng-real-time-messaging.txt]. The real-time path fans out to *connected* clients only; durable history is per channel and pulled. **Discord**: messages are partitioned "by the channel they're sent in, along with a bucket, which is a static time window"; the cost is read-side hot partitions ("a big announcement on a large server that notifies @everyone: users are going to open the app and read the message, sending tons of traffic to the database"), fixed with data services that coalesce concurrent reads [discord2023-blog-how-discord-stores-trillions-of-messages.txt]. Per-user state is the **Read States** service: "There is one Read State per User per Channel. Each Read State has several counters ... For example, one of the counters is how many @mentions you have in a channel"; it is "accessed every time you connect to Discord, every time a message is sent and every time a message is read", an LRU cache over Cassandra with "hundreds of thousands of cache updates per second" [discord2020-blog-go-to-rust-read-states.txt]. Lesson: room content is selected; per-(user, channel) cursors are small mutable folds; mentions are maintained at write time as a counter on that fold, bounded by the mention's addressing.

### 1.9 Facebook Multifeed and TAO, LinkedIn FollowFeed: read-time aggregation over per-producer indexes

**Multifeed**: a Tailer feeds user actions into **Leaf** servers that index "most recent News Feed actions ... in memory"; an **Aggregator** "accepts user queries and retrieves News Feed info from backend storage", ranking and filtering at read time; the 2015 redesign disaggregated them for a 40% efficiency gain, because "It was not uncommon for an aggregator to get a heavy request from a user with a lot of friends, leading to a sudden spike in CPU usage" [facebook2015-eng-serving-multifeed-redesign.txt]. **TAO** serves the graph as association lists `(id1, atype) → [anew ... aold]` with `assoc_range` and `assoc_time_range`; its trace shows that "only 1.9% of the calls to assoc time range returned any edges" and "45% of calls [to assoc count] return zero" [bronson2013-tao-facebook-distributed-data-store-social-graph-atc.pdf]: a read-time selection is dominated by empty probes, so the negative answer must be cheap. **LinkedIn FollowFeed** (2016) indexes each entity's records in a *timeline* keyed (entity id, content type) in RocksDB, including "member is mentioned in an article", and aggregates at read time; it chose fan-out on read because "data size with this model [fan-out on write] was 62 times greater than pull based architecture", and because re-ranking a materialized feed means "grandfathering every pre-materialized feed" [linkedin2016-eng-followfeed.txt]. Feeding Frenzy cites Digg's materialized "green badge" feature growing from "tens of GB to 3 TB" [silberstein2010-feeding-frenzy-selectively-materializing-event-feeds.pdf]. The theory of the shared intermediate is Gionis et al., "Piggybacking on Social Networks" (PVLDB 6(6), 2013, doi:10.14778/2536336.2536342): serving two friends' requests through a third friend's view ("hub") minimizes requests; the optimal hub set is NP-hard with an O(log n) approximation (abstract via OpenAlex W2043521128; the PDF could not be fetched).

### 1.10 NNTP and INN: groups as streams, the newsrc as a cursor, NEWNEWS as the disabled selection

NNTP is the oldest pure-selection inbox and fn's own lineage. A group is a stream with per-group article numbers; a crosspost is stored once and indexed into each named group (the Xref line), so fan-out goes to *streams named by the author*, never to readers; each reader's newsrc is client-side read state, a set of number ranges per group (a cursor plus holes); XOVER reads the per-group overview index [rfc3977-nntp.txt; rfc2980-nntp-common-extensions.txt]. NEWNEWS is the cross-group selection by time ("returns a list of message-ids of articles posted or received on the server, in the newsgroups whose names match the wildmat, since the specified date and time", RFC 3977 §7.4.2), and it is the cautionary tale: "NEWNEWS is one of the commands frequently disabled" (RFC 2980 §4.4) [rfc2980-nntp-common-extensions.txt]; INN documents that it "used to put a heavy load on the server in older versions of INN, but is now reasonably efficient, at least if only one newsgroup is specified by the client" (`allownewnews`) [inn2026-docs-inn-conf.txt]. The cost was never selection as such; it was selection by scanning a global time-ordered history instead of seeking per-group indexes.

### 1.11 The pattern across all ten

| System | Room/channel content | Addressed items (mentions, DMs, notifications) | Per-consumer read state | Wake |
|---|---|---|---|---|
| Fastmail/Cyrus | shared folders: one copy, selected; private mail: placed per recipient (envelope-bounded), bytes hard-linked | the envelope | `cyrus.seen` per reader; JMAP modseq state | JMAP StateChange, coalescable, droppable |
| Twitter | fan-out to 800-entry Redis lists; high-fanout producers merged at read | an activity timeline maintained on write | none (lists are the state) | push to sockets for streaming clients |
| Bluesky | fan-out timelines, lossy past a follow limit; custom feeds pulled | notification rows per recipient, bounded by facets/quote/reply depth 5 | notification unread state | client polling |
| Mastodon | fan-out to Redis (7-day active users), regenerate on return | durable Notification rows | Redis feed | streaming API |
| Matrix | per-room DAG, /sync selection over joined rooms | push rules evaluated per member at event time, counts in sync | receipts | long-poll |
| Zulip | UserMessage row per recipient; soft-deactivated users selected and backfilled | "interesting flags" still written eagerly | flags on UserMessage | event queues |
| Kafka | partitions pulled | none | offset per partition | long-poll |
| Slack/Discord | per-channel storage, pulled; real-time push to connected clients only | mention counters on per-(user, channel) Read State | per-(user, channel) cursor | websocket |
| Facebook/LinkedIn | read-time aggregation over per-producer indexes | indexed into the addressed entity's own timeline | — | — |
| NNTP/INN | per-group streams, crosspost indexed per named group | — (Followup-To, no addressing) | client newsrc ranges | none (polling) |

Three convergences: **(i)** shared streams are read by selection over per-stream indexes everywhere that survived growth (Matrix, Slack, Discord, LinkedIn, Facebook, NNTP, Cyrus shared folders, Twitter's high-fanout path, Zulip's inactive path); per-reader materialization survives where it is cheap (small audiences) or where it was retrofitted with a lossy escape hatch (Bluesky, Mastodon, Twitter's 800 entries). **(ii)** Addressed items are materialized at write time everywhere (Bluesky notifications, Mastodon notifications, Matrix push actions, Discord mention counters, Zulip mention flags, LinkedIn "mentioned in"), because their fan-out is bounded by the addressing, not the audience; the one place this hurt (Synapse, Discord @everyone) is where an address meant "the whole room". **(iii)** The wake is a coalescable hint carrying at most a version, never the data (JMAP §7, Kafka long-poll, Matrix long-poll, Slack's online-only fan-out).

## 2. The theory

### 2.1 Feeding Frenzy: the per-(producer, consumer) decision and its cost model

Silberstein, Terrace, Cooper and Ramakrishnan, "Feeding Frenzy: Selectively Materializing Users' Event Feeds", SIGMOD 2010 [silberstein2010-feeding-frenzy-selectively-materializing-event-feeds.pdf] formalize a *follows application* as a bipartite graph of consumers and producers, each producer a relation `PE_j` of timestamped events, and a feed as a "most recent window" query over the followed producers: under **global coherency** the `k_g` most recent events across all followed producers, under **per-producer coherency** the `k_p` most recent per producer. Each feed must be time-ordered, gapless (no missing event between two shown events of one producer) and duplicate-free. Two strategies per edge: **push** (write the event into a materialized per-consumer feed at a cost `H`) and **pull** (read a small batch from the producer's stream at query time at a cost `L_j`, amortized over the events retrieved). Notation: `φ_pj` producer event rate, `φ_ci` consumer query rate.

Claim 1 (per-producer coherency): over an event's lifetime (until `k_p` newer events from the same producer supersede it), push costs `H` and pull costs `L_j(φ_ci/φ_pj)`, because the consumer views the event `φ_ci·k_p/φ_pj` times, each pull amortized over `k_p` events. **Lemma 1**: push iff `φ_ci/φ_pj ≥ H/L_j`, else pull. **Theorem 1**: choosing push or pull separately for each producer/consumer pair by Lemma 1 is the global MinCost, because "no assignment made on any one edge imposes any restrictions on the assignments we can make to any other edges". Under global coherency the producer rate is replaced by the consumer's aggregate `Σ φ_pj` and the decision becomes per consumer (Lemma 2, Theorem 2). The latency-constrained variant (shift pull edges to push until an Nth-percentile latency target is met) is equivalent to knapsack (Lemma 3, NP-hard) and is handled by a greedy adaptive algorithm: sort pull edges by `φ_ci/ε_ij` (benefit over the extra cost `ε_ij = φ_pj(H − L_j φ_ci/φ_pj)`) and shift the top ones to push, shifting back when latency is below target. The theorem breaks for aggregating producers (an edge can push only if its upstream edges push), so they move consumers as blocks. Experimentally on PNUTS, a push threshold of 3 minimized load across query:event ratios; Push All cost 47% more than Push None at a high event rate, Push None 23% more than Push All at a high query rate, and the hybrid beat both everywhere; flash loads are absorbed by switching affected pairs from push to pull [same, §5].

The result's practical content is that **the decision variable is a ratio of two locally measurable rates per edge**, and that the system can adapt one edge at a time without re-optimizing globally. Twitter's "merge in her timeline at read time" and Zulip's soft deactivation are both instances.

### 2.2 Re-deriving it for an inbox: cursors cap the pull penalty

Feeding Frenzy's model is a *window*: an event unseen before it leaves the window is never paid for under pull, and a consumer who views often re-pulls the same events every view (that is why its pull cost grows with `φ_c` without bound). An inbox is different in exactly those two places: every event addressed to the consumer must be delivered (at least once until acknowledged, CLIENTS §1.1), and a consumer with a cursor never re-reads what it has acknowledged. Redo the model for an edge `e = (c, s)` (consumer `c`, stream `s`) with:

- `λ_s` the stream's event rate, `φ_c` the consumer's poll rate (a wake followed by a poll; an ack rides the next poll);
- `r` the cost to read one delivered entry once located (identical under both strategies, so it cancels);
- `L_s` the cost of one positioned seek into stream `s`'s index (an ordered-run probe; cold or warm, M2's subject);
- `ε` the cost of discovering that `s` has nothing new for `c` (an in-memory comparison of `s`'s committed frontier with `c`'s position, ROUND2's `observed-frontier`);
- `H` the cost of appending one reference to `c`'s materialized inbox fold (one ordered-run insert inside a commit batch, amortized);
- `L_f` the cost of one seek into `c`'s fold.

**Selection.** A poll seeks only the dirty streams. The number of polls per unit time that find `s` dirty is `d_e = φ_c(1 − e^{−λ_s/φ_c}) ≤ min(φ_c, λ_s)` for Poisson arrivals and polls at rate `φ_c`. Cost rate: `C_sel(e) = L_s·d_e + ε·φ_c + r·λ_s`.

**Materialization.** Each event costs `H` at write; each poll that finds the fold dirty costs one seek `L_f`, shared by all of `c`'s materialized edges. Cost rate: `C_mat(e) = H·λ_s + r·λ_s + (e's share of) L_f·d_f`.

**The two regimes.**

1. *Slow consumer, busy stream* (`λ_s ≫ φ_c`; Zulip's inactive users, Twitter's celebrity, a seat asleep while a task room churns): `d_e ≈ φ_c`, so `C_sel − r λ_s ≈ L_s φ_c` against `C_mat − r λ_s ≈ H λ_s`. **Select** whenever `λ_s/φ_c > L_s/H`; the advantage grows without bound as the consumer sleeps longer. This is Lemma 1's pull side unchanged.
2. *Fast consumer, quiet stream* (`λ_s ≤ φ_c`; an interactive seat in its home room): `d_e ≈ λ_s`, every event provokes its own poll, so selection pays at most one seek per event per edge, `L_s λ_s`, against materialization's `H λ_s` plus the fold seek. Per poll that finds `k` dirty selected streams carrying `n ≥ k` new events in total, selection pays `k·L_s` and materialization pays `L_f + n·H`. **Materialize** only when `(k − 1)·L > n·H`: when one poll's new events are spread thinly across many streams *and* seeks cost more than inserts (cold streams, warm fold).

The inbox's version of Lemma 1, then: materialize edge `e` iff `min(1, φ_c/λ_s) > H/L_eff(e)`, where `L_eff` is the seek cost net of the fold seek it replaces. The `min(1, ·)` is the whole difference from the window model: **because a cursor never re-reads, the pull penalty is capped at one seek per event, so materialization's best case is a constant factor `L/H` better than selection, while selection's best case is an unbounded factor `λ_s/φ_c` better than materialization.** That asymmetry is the theoretical reason for selection as the default, and it holds only if three mechanisms exist: per-stream indexes (else `L_s` is a scan of the whole log, the NEWNEWS cost), the in-memory frontier check (else `ε` becomes `L_s` and every poll pays a seek per subscribed stream, Matrix's "sync scales with the number of rooms" and TAO's 98% empty `assoc_time_range` probes), and a cursor per consumer (else Feeding Frenzy's unbounded re-pull returns). Theorem 1's independence survives: edges interact only through the shared fold seek `L_f` (a per-consumer coupling, like Lemma 2's global coherency) and through the per-consumer latency constraint (knapsack, handled greedily).

### 2.3 Read and write amplification for inbox delivery as a function of fan-out and poll rate

Per committed event with audience `f` (members or followers who will receive it), `g` named streams (the groups it is filed in, crossposts included) and `a` addressed principals (mentions, DM recipients):

| | Selection | Fan-out on write | Per-edge hybrid |
|---|---|---|---|
| Durable writes per event | `g` stream-index entries + `a` addressing entries | `f` inbox entries (+ `g` if streams are kept for history) | `g + a` + one entry per *materialized* edge |
| Bytes retained per event | payload once; `(g + a)` index entries | payload once (if references) or `f` copies; `f` references (LinkedIn measured 62×, Digg tens of GB → 3 TB) | between |
| Commit-path latency | independent of `f` | grows with `f` (Zulip: 1 s per 2,000 recipients; Twitter p99 5 min at 1M) unless asynchronous, in which case visibility lags and orders invert (Twitter's replies before originals) | independent of `f` if the materializer is asynchronous with a coverage frontier |
| Read work per poll | `k` seeks for `k` dirty followed streams + `ε` per clean one | 1 seek | 1 fold seek + seeks for selected dirty streams |
| Read work after a long absence | `|F_c|` seeks + the delivered entries | the delivered entries if the fold was kept; a reconstruction if it was evicted (Twitter, Mastodon, Zulip) | same as selection for selected edges |
| Resident wake state per parked consumer | one subscription edge per followed stream | one edge (its own fold) | one edge for the fold + one per selected stream |
| Wake work per event | walk `s`'s parked edges, coalesced (a pending wake is not re-queued) | rides the append to each fold | both |

The rows that decide fn2's case are the commit-path latency (selection's independence of `f` is what EXECUTION-MODEL rule 3's bounded runs want), the read work after absence (selection's cost is proportional to what is delivered, materialization's to what was written), and the resident wake state (the one place selection costs more, and the one that can force a hybrid).

### 2.4 Where selection wins, where fan-out wins, where a hybrid is forced

**Selection wins** when consumers are slow relative to the streams they follow (sleeping agents, humans reading daily, archive consumers), when audiences are large (`f` large), when the selection rule changes (LinkedIn's re-ranking; for fn: authority and view changes rechecked on every poll, CNS-011), and when correctness must survive the loss of every derived structure (the log is the only authority; a fold that is a cache is a reconstruction path waiting to be exercised).

**Fan-out wins** when audiences are small and consumers are fast and follow many thinly active streams (`(k−1)L > nH`), when the per-poll latency target cannot absorb `k` cold seeks, and when the delivered item carries per-recipient state that must exist before the recipient looks (Zulip's per-message flags; Matrix's counts that "MUST appear in the same /sync response as the event itself").

**A hybrid is forced** in five situations, each observed in §1: (1) skew in both `λ_s` and `φ_c` inside one consumer's subscription set (Feeding Frenzy's experiments; Twitter's hybrid); (2) addressed items inside busy streams, which a slow consumer must receive without selecting the busy stream: the addressing index is fan-out by *address* (bounded by `a`), consumed by selection (Bluesky notifications, Zulip mention flags kept eager under soft deactivation, LinkedIn's "mentioned in" timeline entries); (3) resident wake capacity, when `Σ |F_c|` over parked consumers exceeds the edge table: a consumer following hundreds of streams waits on one fold instead; (4) a per-consumer latency constraint (Feeding Frenzy's knapsack); (5) group addresses ("@room", "@everyone"), which must stay a property of the room entry resolved at read, because expanding them is fan-out to the whole audience (Synapse's `event_push_actions` failure, Discord's @everyone hot partitions). Gionis et al.'s piggybacking adds a sixth, later option: a shared intermediate view serving several consumers; in fn2 a group already is that hub, and a fleet-wide aggregate stream would be a second one.

## 3. fn2's workload and constraints, and what each lesson implies here

### 3.1 The workload

- **helm/arc on akapug's fleet** (CLIENTS §1.2-1.3): about 30 seats on 4 boxes; "about 3-7k rows/day at about 1 KB/row"; 427 rooms + 27 DM lanes, 49,960 rows, 281 MB live; each seat watches "home room, DMs and mentions from any room"; addressees are stamped on the row at post; per-room order from one writer is enough. Measured pain today: room-tap wake 0.34-2.16 s (a 2.0 s poll tick), "a fresh mention did not wake the seat beacon within 36 s (n=1)", the old waiter cost "7-10% of a core per waiter". The falsifiers akapug set: wake p95 > 2 s; heap > 2 GB at one day of chat; the waiter cap blocks a 30-seat fleet; an acked row redelivered after a crash. #14's critiques: 12 waiters too few, "A sleeping waiter should not hold a control-client slot", one group and one article per poll. helm keeps waking an idle seat, tracking who owes a reply, and per-seat signed turns for itself ("wake is helm's layer in either design"); its 10-16 transport port is `append(row) -> Evidence`, `read(room, after=row_id)`, `wait(seat, timeout)`, `ack(seat, row_id)`.
- **Mini / sleeping agents** (§1.1): one consumer, one group, at most 16 events per poll; exactly-once is the consumer's own (its inbox keyed `(history, incarnation, source, application-id, operation-id)`); the remote consumer (PKT-255/CNS-011) is the same `fncu` cursor and report bytes over an authenticated connection.
- **The archive consumer** (§1.3): about 40 rows a day into a private group.
- **Human readers** (§1.4): NNTP with a newsrc, already pure selection; the web reader.
- **Peers** (§1.5): crossposts, distributions, out-of-order import; every node derives its own indexes from authored fields.
- **ClockDAG-style small devices** (§1.3, #17): checkpoint and drop bodies; never silently erase a promise.

Arithmetic at akapug's scale, pessimistic (7,000 rows/day, every row to a room all 30 seats receive): fan-out on write is at most 210,000 inbox references a day (about 6.7 MB at 32 bytes each), selection is 7,000 stream-index entries plus the addressing entries. Both are negligible against the cost that *is* material and identical under both strategies: acknowledgements. 30 seats acknowledging every row individually is 210,000 isolated durable acks a day, which STORAGE-DESIGN §3 item 9 prices at one 4 KiB journal unit each, about 860 MB/day, unless acks overlap in commit batches (M5 measures exactly this). The inbox decision at this scale is therefore made on semantics, failure modes and the path to larger scales, not on today's I/O; the I/O that matters is the ack's, and it argues for a cursor (one ack covers a prefix) over Zulip-style per-entry flags.

### 3.2 The constraints the decisions already impose

1. **The log is the only authority; folds are materialized** (STORAGE §1, §4.1): a per-consumer inbox fold may exist only as a declared fold (interpretation, initialization, coverage) over the one history, rebuildable from it; it can never be the place an event first exists. Fan-out on write as the *authority* (helm's inbox "as a stream of its own" written per recipient) is excluded; fan-out as a *derived fold* is allowed.
2. **The commit path is bounded** (EXECUTION-MODEL rules 3, 8): one bounded transition installs the committed root; "replies and wake fan-out proceed incrementally afterward and do not gate visibility". Per-recipient work proportional to audience cannot sit inside a commit batch's install; at most bounded per-event index entries can.
3. **Subscription edges are resident, capped rows** (ROUND2 §B.1-B.2): `Esub` = 4,096; a wait run touches at most 32 edges; "repeated wakes do not advance a queued machine"; `SubscriptionDirty` is a state bit or reserved link, never a queue (rule 7); the subscription-notification service class has a protected share of the 80-entry calendar (rule 4).
4. **The wake is a hint and the final frontier check is the correctness** (scenario 7); one wait may watch room, DM and mention streams with exact edge accounting and authorization rechecked (scenario 8).
5. **Isolation** (rule 5): a principal's activity cannot consume another admitted principal's reserved capacity; costs are charged to the principal that causes them. Write-time fan-out charges the *poster* for the audience's work; selection charges each *reader* for its own reads; the addressing index charges the poster for a bounded number of addressed entries.
6. **Retention** (STORAGE §4.1-4.2): consumer query and view versions and scan positions create no implicit retention hold; a retaining consumer is a charged, inactivity-bounded durable hold; a consumer cut is "retained delivery under a charged, inactivity-bounded obligation, or state bootstrap with an explicit gap".
7. **Sealed streams** (STORAGE §4.5): the node "indexes only deliberately public fields". Addressing that the node can index must be a public envelope field, never parsed from sealed or free-text bodies.
8. **The remote contract fn1 selected** (CNS-011, `specs/consumer-progress.md`): durable immutable multi-group queries with query versions, current-authority recheck on every poll and wake, view-version rebase, operation identities, independent report limits. The fn1 *source* scanner "uses the dense all-event source, validates token and ordinal custody, and offers EVERY non-NIL event to current visibility before query selection", and the cursor's `position` is "the committed Store-record prefix scanned". That is the semantics fn2 keeps; the dense scan is the cost fn2 must not keep (§3.3, lesson 1).

## 4. Mechanisms now, policies later

The goal ember set: build for scale from the start, and have the mechanisms that make the later policies (selection, fan-out, per-edge hybrid, shared hubs) runtime decisions over one authority, so that no later policy needs a format change, a client change or a migration of truth. The design below has seven mechanisms; the first four are needed by selection alone and are what 5.1.1 serves; the last three exist in the format and the reference model in 5.1.1 so that switching policy later is a row change, not a project.

### 4.1 Streams and positions (layer C; no new schema)

- A **commit position** is the event's place in its commit domain's one order: `(domain, sequence)`, `domain = 0` in every 5.1.1 node (STORAGE §4.1: one atomic mutation belongs to one commit domain). It is the only ordering any consumer sees.
- A **stream** is anything with an ordered per-stream index whose entries carry their commit position: a group's overview, keyed (group, article-number) from first materialization (STORAGE §1), is already one, because numbers are assigned in commit order, so position is monotone in key order within a group and a positioned seek is a search over the same pages and restart points (no second key). A DM lane is a two-member private group. The addressing index (4.2) contributes one stream per principal. A materialized inbox fold (4.6) is one stream per consumer. A stream id is the 128-bit `stream-id` of ROUND2's edge row, typed by kind (group, address, fold) so later kinds (a fleet aggregate hub, §2.4) add a kind, not a format.
- Each stream has a **committed frontier**: the position of its newest entry, published by the commit machine's `install` for every stream the batch touched, resident while any parked edge watches it, paged otherwise (rule 9).
- **`Seek(stream, after = p)`** returns the first entry with position > p. The C brief's range cursor (stable resume key plus logical version) already is this; C3 adds the position-keyed entry point and its M2 measurement (cold sparse groups past cache capacity).

### 4.2 The addressing index as a derived ordered schema (layer C, written by D5's transaction machine)

- **Schema `addr`**, keyed `(principal-id, position)`, value `(event reference, arriving stream, reason bits)`; one entry per addressed principal per event, deduplicated (Bluesky's `notified` set).
- **Source**: deliberately public envelope fields only (STORAGE §4.5): an authored addressing header naming principals by key identity (helm's "the key is the identity", CLIENTS §2.1), filed with the article; never parsed from bodies, never from sealed content, never from display names (Fastmail's lesson). The exact header grammar is E3's specification quest; the schema does not depend on it.
- **Written in the event's own transaction**, like overview: it is the only per-recipient write in the commit path, so it is bounded: `a ≤ max-addressees` (a live `policy set` row within a structural capacity), exceeding it is a named refusal word, never truncation; charged to the posting principal (rule 5).
- **Group addresses are not expanded** ("@room", "@everyone", "@channel"): they set a flag on the room's own stream entry, which each member's selection reads as a reason (lesson 8; Synapse, Discord).
- **Fold declaration** (STORAGE §4.1): interpretation "for each committed article with an addressing field, one entry per named principal"; initialization empty at history start; coverage from history start, or, if introduced after events were reclaimed, from the oldest retained event with the earlier range declared unavailable. Rebuildable by replay; a node that peers derives its own `addr` from the authored fields (peers never ship index entries).
- **Authorization is not decided at write**: an entry for a principal who cannot read the stream is invisible to that principal's selection, because CNS-011 rechecks current authority on every poll and wake (fan-out at write would have to be rechecked at read anyway, so it saves nothing here).

### 4.3 The subscription registration and its versions (layer C fold, D wait machine, E wire)

- A **registration** is durable, keyed by `(consumer-id, registration-epoch)` (never a name; lesson 13): principal, query-id, query-version, and an edge set, each edge `(stream-id, start-position, reason filter, policy)`. Mentions-from-any-room is one edge on the principal's own `addr` stream; a seat does not subscribe to all rooms to hear its mentions.
- **Query-version transitions are log events** with explicit per-edge effects: *add stream from now* (start = the stream's current frontier, which is ≥ the cursor, so the scalar cursor stays valid; the default), *add stream with history* (a **backfill edge** with its own position held in the registration fold until it reaches the main cursor, its items marked as backfill on the wire, its progress acknowledged with the main ack), *remove stream* (end position), *change policy* (§4.5). fn1's "a changed register refuses with rebase-required" and the view-version rebase stay for authority and view changes (CNS-011); joining a room no longer forces a rebase from zero, which at helm's 427 rooms would be the Matrix initial-sync cost.
- Because every subscription change is in the log, the exact edge set at any position is recomputable: a fold can be built or rebuilt for any past range (lesson 6, Zulip's `add_missing_messages`).
- **The per-(consumer, stream) read-state fold** (lesson 16): cursor, per-stream unread and mention counters, latest-only, updated by ack transactions and commits, the Discord Read State and the newsrc in one declared fold.

### 4.4 The selection and the wake (layer D: the D8 wait semantics, the D brief's item 9, and the timer/grant/wake services)

**Selection** (one consumer poll, a bounded resumable run, ≤ 32 edges or scan entries and 4 KiB output per run, ROUND2 §B.3): for each edge, compare the stream's committed frontier with the cursor (`ε`; most probes are empty, TAO's 98%); for each dirty edge, `Seek(stream, after = P)`; k-way merge of the dirty streams by position; deduplicate per event, accumulating reasons; recheck current authority and view (CNS-011); stop at the report limits (`max-remote-report-items`, `-octets`) with a `more` indication; propose the next cursor = the position through which the merge is complete. Work is proportional to dirty streams plus delivered entries, never to the log or to the number of clean subscriptions (lessons 1, 11).

**Wake** (the subscription-notification service class, protected share of the calendar, rule 4):
1. `install` publishes the new frontiers of the touched streams and sets each touched stream's `SubscriptionDirty` bit (a state bit, rule 7).
2. The service walks a dirty stream's intrusive edge list (`stream-prev/next`), at most 32 edges per run, resumable; for each edge whose `observed-frontier` is below the new frontier and whose wait is not already pending, it sets pending and makes the wait runnable at its principal's tail. A stream that commits again mid-walk only raises the target frontier; repeated wakes do not advance a queued machine (rule 4). The walk is charged to the service class with the per-edge work attributed to the edge's principal.
3. The wait runs the selection. Before parking again it performs the **final frontier check** over its edges (≤ 32 per run, resumable): if any frontier exceeds its position it polls again rather than park. A lost or delayed wake therefore costs latency up to the wait's timeout, never an event (scenario 7; JMAP §7).
4. Edges are reserved at registration through D0's acquisition order (a per-principal `max-subscription-edges` policy row inside the structural `Esub`), released at cancel or close, and held by a parked wait without a worker or a connection-slot entitlement (#14: "A sleeping waiter should not hold a control-client slot").

The wake path is in-memory end to end; its latency is the scheduler's starvation bound plus one selection, far inside akapug's 2 s p95 falsifier, and the simulator measures it (E's acceptance already reports wake p50/p95 at 30 waiters).

### 4.5 The per-edge policy table (layer C fold; operator rows in 5.1.1, a controller later)

- **Fold `edge-policy`**: `(consumer-id, epoch, stream-id) → [(policy, since-position)]`, an interval list, policy ∈ {`select`, `materialize(fold-id)`}; default `select`; every change is a log event at a position, so the reader always knows, for any position, which source answers for that edge.
- In 5.1.1 the table is written only by an operator verb (`policy set` family, E6) and by the simulator; a cost-driven controller (Feeding Frenzy's greedy adaptive algorithm over the §4.7 counters) is a later policy over the same rows.
- A stream may carry a **stream-level ceiling**: above a parked-edge or follower count it is never materialized for anyone (Twitter's hybrid: high-fanout producers are always merged at read).

### 4.6 The optional materialized inbox fold and its coverage declaration (layer C schema, D maintenance machine)

- **Schema `inbox`**, keyed `(consumer-id, epoch, position)`, value `(stream-id, event reference, reasons)`: references, never payload (Cyrus single-instance store; Twitter's 800 IDs; LinkedIn's 62×).
- **Written by a materializer**, a budgeted maintenance-class machine (lesson 14: never an unbounded job queue), which consumes the stream indexes of materialized edges in position order and commits fold entries in later ordinary batches (rule 8: the commit path never waits for it). It publishes **`cov(c)`**, the position through which every materialized edge of `c` is complete in the fold.
- **Coverage declaration and the read rule**: for each edge and each position range, the policy interval says *materialize since p0*, and the fold's coverage says *complete through cov*; the selection reads the fold for materialized intervals up to `cov`, and the source stream everywhere else, including above `cov` on materialized edges. So a lagging or lost materializer delays nothing and changes no content: it only moves cost back to selection (lesson 5). Switching select → materialize at `p0` starts coverage at `p0` (no backfill unless asked); switching back at `p1` ends it; fold entries below `p1` remain valid until trimmed.
- **Trimming**: fold entries at or below the consumer's acknowledged position are reclaimable (Matrix's "deleted on receipt"); the fold is never a retention hold on payloads (STORAGE §4.2: a retaining consumer is a separate, charged, inactivity-bounded hold). A reclaimed payload behind a fold reference reports the same explicit `unavailable` gap selection would.
- **Wake for materialized edges**: they hold no `Esub` edges (that is their resident-state saving, §2.4 case 3); the consumer's wait watches its fold stream as one edge, so wake latency on those edges includes the materializer's lag, measured and reported.
- **The equivalence obligation** (the reason the fold exists in the reference model in 5.1.1): for every policy assignment and every materializer schedule, a consumer's observations (items, order, reasons, gaps, cursor proposals, ack outcomes) equal those of the select-only reference. The CONSUMER checker runs it as a differential check; as a top-level statement it has teeth (a materializer that skips an entry, or a reader that trusts the fold above `cov`, is caught by a two-edge, one-switch scenario in the tiny profile).

### 4.7 The cost accounting that would trigger a policy change (layers D and E; status, never wire)

Counters, kept as bounded per-row fields and exported through `fn consumer status` and health:

- per edge: events delivered; dirty polls (seeks) and the fraction that were cold (page misses); clean probes; reason mix;
- per stream: entries committed (`λ_s`); parked edges; walk length per dirty epoch; follower count;
- per consumer: polls (`φ_c`), wakes, delivered per poll, dirty streams per poll (`k`), poll latency p50/p95/p99, wake-to-reply latency, edges held, fold entries written, fold resident bytes, materializer lag (`frontier − cov`);
- per principal: the charges of all of the above (rule 5), so a hyper-subscribing consumer is visible as its own cost.

These are exactly the inputs of §2.2's rule (`λ_s`, `φ_c`, `k`, measured `L` cold and warm, measured `H`) and of §5.3's triggers.

### 4.8 What the consumer protocol's wire frames must carry, so clients never change when the policy does (layer E3)

- **The cursor stays opaque** `fncu` v1 bytes, its `position` the commit position through which the merged selection is complete, its query and view versions as today. Never a fold sequence, never a per-stream token vector (Matrix's composite tokens couple clients to server internals). E3's owed bridge between v1's 32-bit fields and fn2's wider positions encodes position as `(domain = 0, sequence)`, so a later multi-domain node issues a new cursor version without changing what a cursor means. Backfill-edge progress lives in the registration fold under the cursor proposal's identity, not in the client's bytes.
- **Each item** is the existing RECORD or target-only FNWD1 (with FNRB1 collections for several), plus: its commit position; the stream(s) it was selected through; its reason set (`room`, `dm`, `mention`, `group-address`, `backfill`), deduplicated per event; unknown reason codes are ignorable by contract. Items are in commit-position order.
- **Each reply** carries the next cursor proposal; a `more` indication when a report limit stopped it (pagination, never a Matrix-style `limited` gap); explicit `gap(from, to, cause)` items for retention (`unavailable`) and declared bootstrap, the only gaps that exist; the current query and view versions; `rebase-required` and the other refusals unchanged.
- **Wait** carries only a timeout; a wake's reply is an ordinary poll result (the wake carries no data, JMAP §7). **Ack** carries a cursor proposal, forward-only, with the three outcomes and `position` to settle an uncertain one (unchanged).
- **Never on the wire**: which edges are materialized, fold coverage, materializer lag. Those are operator observations (§4.7). A policy change is therefore invisible to every client byte; only its cost is visible, and only to the operator.
- **The same selection on the other faces** (later, by parity): helm's port maps directly (`append(row)` → POST with the addressing header; `read(room, after = row_id)` → one-stream selection, with `row_id` mapped through the exact Message-ID index; `wait(seat, timeout)` → the seat's registration; `ack(seat, row_id)` → ack); a newsreader could read a principal's `addr` stream as a per-login virtual group through ordinary GROUP/XOVER.

## 5. The recommendation for 5.1.1, the headsmacks it avoids, and the triggers

### 5.1 The recommendation

**D5 stands as recommended (the selection query), with four amendments that make it the scalable form rather than fn1's.** In 5.1.1:

1. **Serve selection over per-stream indexes with one commit-position cursor** (§4.1, §4.4): the consumer's durable registration names an edge set of streams (groups, DM lanes, its own addressing stream); a poll is a bounded merge of the dirty edges' streams sought at the cursor, rechecked for authority, deduplicated with reasons. fn1's dense all-event scanner is replaced; its observations (position as the committed prefix, query and view versions, rebase, withdrawal reports, the three outcomes) are kept.
2. **Add the addressing index** (§4.2), written in the event's transaction from a public envelope field, bounded by `max-addressees` with a named refusal, charged to the poster, with group addresses as flags on the room entry, never expanded. This is the only write-time fan-out fn2 performs, and it is the hybrid every surveyed system converged on for mentions and DMs.
3. **Wake through subscription edges with the final frontier check** (§4.4): in-memory, coalescing, a hint; parked waits hold edges, not workers or connection slots; per-principal edge quotas inside `Esub`.
4. **Put the policy mechanisms in the format and the reference model now** (§4.5, §4.6, §4.8): the `edge-policy` fold (all rows `select`), the `inbox` fold schema with its coverage declaration, the wire's position/reason/gap/`more` fields, and the CONSUMER checker's differential equivalence between select-only and any policy mix. The served materializer is not enabled in 5.1.1; it is built when a §5.3 trigger fires (at akapug's scale none does: 30 seats × about 10 edges is about 300 edges against 4,096, and every cost in §3.1 is negligible beside the acks).

Where this lands in RELEASE-PLAN's quests: C3 adds the position-keyed seek and the `addr` schema (with M2's cold-group measurement covering seeks); C4 adds the registration, read-state and `edge-policy` folds with their three declarations; D5's transaction machine writes `addr` entries and owns the `max-addressees` refusal word; D8 (the wait-semantics quest; the D brief's contract item 9) implements selection, wake and the final frontier check, with scenarios 7 and 8 plus five new tiny-profile scenarios (backfill edge reaching the cursor; group-address flag in a 30-member room yields one entry; addressing bound refusal; a policy flip at `p0` under a lagging and then a lost materializer, checked differentially; a hyper-subscribed principal at its edge quota cannot move another principal's wake latency); E3's specification quest fixes the addressing header grammar, the reason codes, the gap and `more` frames and the position bridge; E6 adds the `max-addressees`, `max-subscription-edges` and `edge-policy` rows.

### 5.2 The headsmacks it avoids, each with the system that hit it

1. **The global scan as the selection**: Twitter's "massive select statement over all of Twitter. It was tried and died"; NNTP's NEWNEWS, "one of the commands frequently disabled" (RFC 2980 §4.4), heavy in INN until restricted to one group. Avoided by per-stream seeks (§4.4).
2. **Commit latency proportional to audience**: Zulip's "1 second per 2000 users subscribed"; Twitter's p99 of 5 minutes to 1M followers; Bluesky's 5-10 minute fan-out jobs. Avoided: no per-recipient work in the commit path; only `g + a` bounded entries (§4.2).
3. **Asynchronous fan-out reordering what readers see**: Twitter's "Replies are being seen all the time before the original tweets". Avoided: one commit order; every derived structure is read in position order up to its declared coverage (§4.6).
4. **The celebrity problem and its late hybrid**: Twitter's "For people like Taylor Swift don't bother with fanout anymore". Avoided by starting where Twitter ended: high-fanout streams are read, never written per follower (§4.5's stream ceiling).
5. **Hot shards from hyper-subscribers**: Bluesky's users "following hundreds of thousands" slowing "tens of thousands of other users sharing a shard"; Multifeed's aggregator spikes from "a user with a lot of friends". Avoided by per-principal budgets and edge quotas (rule 5; §4.4).
6. **Materialized feeds as caches with a reconstruction path**: Twitter's 30-day active set and reconstruction; Mastodon's 7-day `ACTIVE_DURATION`, "It took roughly 48 hours until the feed came back to normal", Redis loss emptying home feeds. Avoided: correctness never depends on a fold; a fold's coverage is declared and selection answers the rest (§4.6).
7. **Backfill that needs history the system threw away**: Zulip's soft deactivation works only because "we already have the data for when the user might have been subscribed or unsubscribed". Avoided by making every subscription change a log event (§4.3).
8. **Expanded group addresses**: Synapse's `event_push_actions`, where "a user sends a bunch of messages into a room with a huge number of members" caused "serious slowness"; Discord's @everyone hot partitions. Avoided by flags, never per-member entries (§4.2).
9. **Lossiness smuggled into delivery**: Bluesky's `loss_factor`, Matrix's `limited` timelines with gaps, the 800-entry trims of Twitter and Mastodon. Avoided: pagination with `more`, gaps only for declared retention (§4.8).
10. **Live cursors expiring on a timer**: Kafka's KAFKA-4682 ("committed offsets are removed even when there are still active, but rarely committing, consumers"). Avoided: durable registrations; inactivity bounds are obligations with named outcomes (STORAGE §4.1-4.3).
11. **Sync work proportional to the number of subscriptions, and composite tokens**: Matrix's /sync ("can take minutes" on accounts with thousands of rooms; MSC3575's goal "independent of the number of rooms"). Avoided by `ε` probes and a scalar cursor (§4.4, §4.8); joining a room is "add from now", not a rebase from zero (§4.3).
12. **The wake treated as delivery**: helm's own "a fresh mention did not wake the seat beacon within 36 s"; fn1's CNS-007 "each commit wakes every waiter, so a commit costs up to 12 polls". Avoided: per-stream edges wake only the waits on touched streams, and the final frontier check makes a lost wake cost latency, never an event (JMAP §7's model) (§4.4).
13. **Names as identity**: Fastmail's 2026 folder wipes from reused usernames and replication by mailbox name. Avoided: everything keyed by (consumer-id, epoch) and stream-id; addressing by key, not display name (§4.2, §4.3).
14. **Unbounded asynchronous work queues**: Mastodon's "over 200,000 queued jobs" and "multi-hour delays in incoming federation"; Twitter's Ruby queue collapsing under GC. Avoided: any materializer is a budgeted maintenance machine with a reserved share and backpressure (§4.6).
15. **Storage blow-up and frozen selection rules from fan-out**: LinkedIn's "62 times greater" data and re-"grandfathering every pre-materialized feed"; Digg's tens of GB to 3 TB. Avoided: payload once, folds of references, policy and selection changes as fold migrations with new coverage (§4.6).
16. **Per-entry acknowledgements**: Zulip's per-message flag rows and Synapse's receipt-driven recounting. Avoided: one cursor ack covers a prefix; per-stream counters are a latest-only fold (§4.3), which is also what makes the 210,000-ack/day pessimistic figure batchable (M5).

### 5.3 The measurements that would move an edge from selection to materialized (and back)

Each trigger reads the §4.7 counters over a window (initially one hour or 10,000 events, whichever is longer), with hysteresis so an edge does not flap (Feeding Frenzy's best threshold was a ratio of 3, not 1):

| Trigger | Measurement | Fires when | Action |
|---|---|---|---|
| T1 resident wake state (forced) | edges a consumer's wait needs; parked edges in `Esub` | a consumer's need exceeds its `max-subscription-edges`, or parked edges exceed a set share of `Esub` | materialize that consumer's quietest edges into its fold, keeping one fold edge |
| T2 per-edge cost ratio | per edge: dirty polls × measured seek cost (cold-weighted, from M2), against events × measured fold insert cost | seeks × L > 3 × events × H for the window (§2.2's fast-consumer, thin-stream regime) | `materialize` from the current position |
| T3 latency | consumer wake-to-reply p95 and its decomposition (k dirty streams × cold-seek fraction) | p95 over the target (akapug's 2 s; an operator SLO) with seeks as the dominant term | Feeding Frenzy's greedy step: shift the edges with the best `φ_c / ε` first, until under target |
| T4 never materialize | stream follower or parked-edge count; per-edge `λ_s / φ_c` | count over the stream ceiling, or `λ_s / φ_c > L / H` (slow consumer, busy stream) | keep or return to `select` (Twitter's celebrities, Zulip's inactive users) |
| T5 materializer health | `frontier − cov`; fold resident bytes; materializer share used | lag over its bound or bytes over budget | return edges to `select` (losslessly: the read rule already falls back above `cov`) |
| T6 regression detector (not a policy) | log entries examined per poll against entries delivered plus dirty seeks | ratio above a small constant | a defect: some path is scanning the log (headsmack 1) |

The 5.1.1 runs that establish the inputs, reported beside the profile and never as gates (performance is published, never a gate): measured warm and cold `L` and `H` on the concrete profile (C3/C4's numbers, with M2); wake p50/p95 for 30 waits of about 10 edges each replaying a 7,000-row day with bursts (against akapug's 2 s p95 falsifier); bytes per ack isolated against batched (M5); the distribution of `k` and of delivered entries per poll over that replay; the differential equivalence under policy flips with a lagging and a lost materializer; and the isolation run (one principal at its edge quota, another's wake latency unchanged).

### 5.4 The recommendation in three sentences

Serve 5.1.1's remote consumer inbox as a durable, versioned selection over per-stream indexes (groups, DM lanes, and a per-principal addressing stream) with one commit-position cursor, woken by in-memory subscription edges whose final frontier check makes the wake a hint, so that delivery work scales with what is delivered and never with audience size or log size. Perform write-time fan-out only by address: a bounded, poster-charged addressing index written in the event's own transaction, with group addresses kept as flags on the room entry. Put the per-edge policy table, the materialized inbox fold with its coverage declaration, the policy-invariant wire fields and the select-versus-materialize equivalence check in the format and the reference model now, so that moving any edge to materialized later (on the §5.3 triggers) is a row change with no client change and no change of authority.
