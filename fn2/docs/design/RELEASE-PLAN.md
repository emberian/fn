# fn2 to its first release: subsume fn1's public surface, start assurance (2026-10-28; present state, rewritten whole)

Ember, verbatim (EMBER.md, 2026-10-28): "think about how we can bring it up to a 6.6.1 (or whatever the next release was supposed to be) worthy thing (ie ~entirely subsume the previous 'public' surface plus maybe a bit of a start towards some aspects of assurance)". This plan is the answer, grounded in the named files; nothing is from memory. It sits under `FN2-ORIENTATION.md`, `EXECUTION-MODEL.md`, `STORAGE-DESIGN.md` and `briefs/FN2-SEAT-COMMON.md`, and it adds two layer briefs beside the existing three: `briefs/FN2-LAYER-D-MACHINES-NNTP.md` and `briefs/FN2-LAYER-E-SURFACE.md`.

**The version the first fn2 release carries: `5.1.1`.** Reason, in one paragraph. The release line is settled by ember on 2026-10-14 (EMBER.md ~12:30 and ~15:20 EDT): `5.1.1 → 5.2.2 → 5.3.3 → 5.4.4 → 5.5.5 → 6.7.x (open-ended) → 6.6.0–6.6.5 (the landing sequence, chronologically after 6.7) → 6.6.6 → +.6`. It is encoded in `planning/release-sequence.json` on origin/dev and read by `tools/release_sequence.py`, whose `cut-check` (gate 01 of `tools/cut_release.sh`) accepts only the entry after the newest existing `v*` tag by position, or the first release when none exists; the only tags are the five prehistory tags `v1.0.0`–`v5.0.0`, which the gate ignores, so the version it will cut is `5.1.1` (the script also accepts the newest existing release's own tag for a re-run of the cut's commit; the tag set is re-checked at the cut, *[Astra]*). `VERSION` on dev already reads `5.1.1-pre` (commit 572a09312, "start ember's 5.1.1 line"). "6.6.1" is not next in any reading of the line: 6.6.x comes after the whole 6.7.x series, and ember's own sentence hedges it ("or whatever the next release was supposed to be"). The line itself is not ambiguous, so this plan does not ask; the one visible consequence (the public node's banner goes from the never-cut `fn 6.6.0 (a3553e6b4a23)` it runs today down to `fn 5.1.1`) is a documented consequence of the settled line, not a decision (*[Astra]*: it is not ember's to re-arbitrate); the FAQ article and `docs/nodes/fsn1.md` say so. The releases after it are `5.2.2` and on; ember's "assurance isn't a *major* focus until the 5.4 series" places the assurance start of §4 as a start, not a focus, which is what this plan gives it.

**What "subsumes the previous public surface" means here.** Every item a client, peer, reader, consumer or operator of fn1 could reach from outside the process (the wire, the CLI, the web page, the config file, the release tarball), enumerated in §1 with its fn1 evidence, carried by fn2 with the same observable contract or a recorded, documented change, each row proven by a named test. Internals (the owner mutex, the 1,916 host entries, the stobj representations) are not surface and are not carried. The 87 black-box natives (QUARRY §natives) are the classical witness that the carried surface is the same surface.

**Reading order for this file.** §1 the surface table; §2 the behavioural and property-based suite over it (ember's prerequisite for any assurance); §3 layers D and E (summaries; the briefs are the specification); §4 the assurance start; §5 the release definition, the root swap and the schedule in quests with the critical path; §6 ember's decisions. One Astra (Codex, gpt-6-astra, read-only) review of the whole was run on the first complete draft and is folded in where marked *[Astra]*; its full text is `build/coordinator/fn2/lanes/plan-review/R1.last.md` (34 findings: 20 RED, 11 AMBER, 3 NOTE; verdict "would not sign this version"; every RED is answered in place below, and its ten first actions are the ten *[Astra]* marks). Astra confirmed 5.1.1 and the direction (surface inventory, executable models before proof work, the D/E layering, one atomic root swap).

## 1. fn1's public surface, enumerated

Scope rule: a row is *surface* when something outside the node process observes it: wire bytes (NNTP, the consumer frames, HTTP, TCPCL/BP), the CLI's argv and exit codes, `fn.toml`, the tarball and images, the public node. fn1 evidence is on origin/dev (6521f18c4) unless a path is under `build/coordinator/`. Layer: A-E as in `FN2-SEAT-COMMON.md`; R = a release quest (§5.6). Status: **built** (on fn2/main or a pushed layer branch today), **brief** (named by a layer brief's contract, A-E), **plan** (named only here; the D/E briefs carry it from this plan), **drop** (not carried; the reason is in the row and the drop is a §6 decision). Test: the simulator scenario (ROUND2-ASTRA §F.2 numbers), the checker, the carried native (`tests/test_native_<name>.py` via the `Node` adapter of §2.6), a conformance fixture, or a release-quest check. A row is proven when its named test is green on the release sha (§5.2).

Counts: 31 keywords in `*fn-nntp-served-command-table*` (`books/nntp-help.lisp:52-59`) covering ~36 RFC commands with arguments and 3 fn extensions (XREDEEM, XFNCATCHUP, XFN-ZARTICLE); 11 consumer request codes in 15 exported wire families and 4 exchanges; 11 CLI chapters with ~60 verbs (215 host entries, one per verb arm) plus the registered top-level verbs; 15 web routes on 12 paths; 5 peering modes; BP/TCPCL; 29 config delta kinds, ~45 `fn.toml` keys in 12 tables and ~30 live limits; 5 store operator operations; 4 release artefacts; 87 black-box natives plus the socket halves of 33. *[Astra]*: a row is a compound; a green module is evidence for the assertions the row names, not proof of the row, so `planning/release-v5.1.1.md`'s F-rows (R1) split every compound row of this table into its observable assertions, each with its shipped status, release disposition and executable evidence, and the counts above are headline counts, not the claim.

## 2. The behavioural and property-based suite over the full surface

Ember's question (EMBER.md 2026-10-28): "do we have a behavioural and property-based test suite that exercises the full surface of our software? that level of testing is usually a useful prerequisite to further formal verification (we prefer to find bugs by testing rather than by failed proof effort)." The honest present answer: fn1 had a wide *example-based* suite (247 native modules, 42 load bars, the F-cells, a grammar fuzzer with nine reproducer sets) and one property-shaped corner (the harness's three-outcome contract with shrinking, GAUNTLET "Harness contract"); fn2 today has a real deterministic simulator with four of eleven checkers (OWN, WORK, TRACE, ACCOUNT) over layer A's echo/null/scribe machines, 26 fault classes, 10,000-seed runs, and no public surface yet. This section designs the suite the release needs, family by family, in the four forms the brief names, and says where and when each runs.

### 2.3 The reference model (form S), concretely

One Python module per protocol, deliberately small and written from the specs: `node_model.py` holds `groups: dict[name, list[msgid]]` (numbers = index+1, never reused: retirement leaves holes), `articles: dict[msgid, bytes]`, `withdrawn: set`, `accounts`, `access rules`, `limits`, `consumers: dict[id, Cursor]`, and the per-connection view `(pinned_version, current_group, current_article, authenticated_as, tls, compressed)`. Each rule is `(precondition, command bytes, expected reply predicate, model update)`. Hypothesis's `RuleBasedStateMachine` with `Bundle`s for msgids, groups and logins; `max_examples` 200 per commit, 5,000 nightly; `stateful_step_count` 50. The model is also what form H's checkers read. It is *not* derived from fn2's code; if the model and fn2 disagree the spec decides, and the spec is rewritten when it is wrong (R3). This is the "conformance suite for ordering/agreement" CLIENTS §4 lists as a gap for akapug's ports: the model file ships in the tarball beside `wire-grammar.json`.

### 2.4 The grammar fuzzer (form F), concretely

`defgrammar` (D2) emits for every wire: the parser over pool ranges, the renderer, and `fn2-<grammar>-generate seed budget` producing a valid transcript of bounded size, plus `fn2-<grammar>-mutate seed bytes` (byte flips, truncation, insertion of CR/LF/NUL/`.`, length-field corruption). Under the simulator a fuzz run is a scenario (`fuzz-nntp`, `fuzz-fnct`, `fuzz-http`, `fuzz-tcpcl`) whose pass condition is WIRE and WORK green and no run over budget; against the live node it is `tests/test_fuzz_*.py` with the nine fn1 reproducer sets as the corpus seed and a 10-minute budget per commit, one hour nightly. A crash, hang, over-budget run or non-typed reply is a RED with the seed and the minimal mutated transcript recorded as a new reproducer fixture.
