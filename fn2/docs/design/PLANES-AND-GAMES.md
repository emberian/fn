## 1. Architectures per game class, with sources

The question asked of every system below is the same five-part one: what is durable, what is live (delivered now or never, no history), what is fast (per-tick, lossy, superseded); what the tick rate and latency budget are; who is authoritative; what state is a fold over an input log and what is ephemeral; and what they got wrong, from their own post-mortems.

### 1.1 RTS: deterministic lockstep, and the observation that the match is an append-only input log

**Age of Empires / Age of Kings** (`bettner2001-1500-archers-aoe-network-programming.pdf`). Every client runs the whole simulation; only commands cross the wire. Commands issued in communications turn *n* execute in turn *n*+2; "Turns were typically 200 msec in length"; the turn length and frame rate are re-chosen each turn by a host from every client's reported ping and frame time ("Total of 2 bytes was used" for the report). Target: a Pentium 90 on a 28.8k modem, 8 players, 1,500 units. Latency budget: "250 milliseconds of command latency was not even noticed - between 250 and 500 msec was very playable, and beyond 500 it started to be noticeable", and "a consistent 500 msec command latency was playable, but one that varied was considered 'jerky'": consistency beat speed. Authority: nobody and everybody; "Any simulation that ran differently was tagged as 'out of sync' and the game stopped. ... Security was a huge win." The cost: "In every project, there is one stubborn bug that goes all the way to the wire - I think out-of-sync is going to be it" (a deer foraging differently becomes a checksum mismatch in food minutes later; "Giant (50Mb) message traces"). Age of Kings added recorded games almost by accident: "Because our simulation is deterministic, and recorded games are synchronous in the same way that multiplayer is synchronous, a game recording gave us a great way of passing around repro cases for bugs because it was guaranteed to play out the exact same way every time." Persistent stats were a structure "we ... upload at the end of a game" to the Zone matchmaker: the only durable server-side datum.

**The pattern stated by its practitioners** (Scry over HN, `lockstep` with `desync`/`replay`): "if its deterministic lockstep, then all you need to do is record inputs and replay the inputs ... If it's client/server and non-deterministic, then you need to record the entire state of the system at every step" (HN 47823580); "you don't save the path of every unit, you save one move command for the whole group" (HN 48634546); "most game replay infrastructure is built on networking ... Replay is usually as easy as just timestamping packets (or storing input if you're running a lockstep sim)" (HN 9696456). StarCraft: Brood War replays are command streams decoded by `icza-screp-starcraft-replay-parser-readme.md`.

**What lockstep got wrong, cited.** Floating point and toolchains: Spring/BAR "used native floats, compiler fastmath flags, and stdlib math functions throughout. So you'd desync instantly playing against anyone whose game was built with different compiler flags, or Windows x86 vs ARM" (HN 50049476); Hedgewars moved to fixed point, Spring to streflop, 0AD kept "desync matrices" (HN 29154151); a driver flipping the FPU precision bit mid-game (HN 3580951); uninitialized memory (HN 46424517). Slowest-player coupling: "lockstep deterministic (LSD) games are bound to the SLOWEST player's machine ... you either pause the simulation for all players until they catch up or you slow down time itself. Source: shipped RTS games" (HN 37459805); AoE2:DE team games where "1/3-1/2 ... had someone lagging from the start" (HN 31545317). Unrecoverable divergence: Supreme Commander "sometime hours deep into a big game, you would get a 'desync' error and it was unrecoverable" (HN 24236193). Map hacks: "the client has to have everything by definition" (HN 28005171). Practitioner remedies: "Develop strong out of sync (OOS) detection tools early ... a client needs to compute a hash of some relevant game data" (HN 16385014); ground-truth replays run in CI against new PRs (HN 48791940); `gamedeveloper2015-minimizing-pain-lockstep-multiplayer.txt`, `yal2021-preparing-game-deterministic-netcode.txt` and `gaffer2014-deterministic-lockstep.txt` (every unacknowledged input redundantly included in each UDP packet, and a playout-delay buffer as the tunable).

**Its successors, predict-and-rollback.** Photon Quantum (`photon-docs-quantum-intro.txt`): "In deterministic systems, game clients only exchange player input with the simulation running locally on all clients. Game clients are free to advance the simulation locally using input prediction, and an advanced rollback system takes care of restoring game state and re-simulating any mispredictions"; a "game-agnostic authoritative server component ... to synchronize clocks and manage input latency. Clients never need to wait for a slower client ... as they would in lockstep"; "up to 128 players". Fighting games (GGPO lineage) do the same at 60 Hz with frame-exact inputs (`infil2019-fighting-games-delay-rollback-netcode.txt`). Jefferson's Time Warp (`jefferson1985-virtual-time.pdf`) is the general form: optimistic execution, rollback on a straggler message, and Global Virtual Time as the frontier below which nothing can be rolled back and history may be fossil-collected. Mauve's local-lag-plus-timewarp (cited by name only; not fetched) and Cronin's trailing state synchronization (`cronin2002-trailing-state-synchronization-mirrored-game.pdf`: several copies of the state at increasing delays, the trailing one used to repair the leading one) are the same idea for mirrored servers.

**Anti-cheat in the lockstep family.** The lookahead cheat (waiting to see the opponent's move) is defeated by Baughman and Levine's lockstep protocol (`baughman2001-cheat-proof-playout-online-games.pdf`): each player commits a hash of its move for turn *n*, then reveals; asynchronous synchronization relaxes it to players whose spheres of influence intersect. A proposal to re-simulate every recorded game asynchronously on trusted servers and ban on discrepancy (HN 4107813) turns the replay log into anti-cheat evidence.

**The observation the brief named, made precise.** A lockstep match is a totally ordered, append-only log of turn records `(turn, [(player, commands)])`; the game state at turn *n* is `Fold(initial(map, seed, versions), turns[0..n])`; a replay is the log plus the initial parameters; a desync is two folds over the same log disagreeing, detected by comparing state digests at the same turn; a save game is a checkpoint `(turn, state)`; a rejoin is checkpoint plus suffix. That is STORAGE decision 1 (`State = Fold(Summary_k, Events_{k+1..n})`) with the summary as the save game and the digest comparison as a checkpoint claim. What lockstep never needed was a server: the "log" lives in each client's memory and is discarded, except as a file when recording is on.

| RTS | |
|---|---|
| Durable | the input log (if recorded), match parameters, the result and stats |
| Live | lobby, chat, matchmaking, presence |
| Fast | the turn exchange (200 ms turns in AoE; one frame at 60 Hz in rollback titles) |
| Authority | every peer equally, by agreement on the fold; a relay or clock server in Quantum |
| Fold vs ephemeral | the whole game state is a fold of the input log; nothing else exists |
| Got wrong | non-determinism (floats, toolchains, uninitialized memory), slowest-player coupling, unrecoverable desync, total information on every client |

### 1.2 FPS: server authority, snapshots, prediction, lag compensation

**Quake 3** (`fabiensanglard2012-quake3-network-model.txt`): UDP only; the server keeps a history of snapshots and sends each client a delta against the newest snapshot that client is known to hold (a zeroed "dummy" snapshot when it holds none, which makes the delta a full update), so a lost packet is never retransmitted, only superseded. **Source** (`valve-wiki-source-multiplayer-networking.txt`, `valve-wiki-lag-compensation.txt`, after `bernier2001-latency-compensating-methods-client-server.pdf`): "By default, the timestep is 15ms, so 66.666... ticks per second"; the client "creates user commands ... with the same tick rate that the server is running" and sends them about 30 times a second; "the server doesn't send a full world snapshot each time, but rather only changes (a delta snapshot) that happened since the last acknowledged update"; entity interpolation renders 100 ms in the past ("cl_interp 0.1; this way, even if one snapshot is lost, there are always two valid snapshots to interpolate between"); lag compensation "keeps a history of all recent player positions for one second" and rewinds hitboxes to the shooter's view. Gambetta's three-part explainer (`gambetta-fast-paced-multiplayer-*.txt`) and Gaffer's snapshot pair (`gaffer2014-snapshot-interpolation.txt`, `gaffer2015-snapshot-compression.txt`, `gaffer2015-state-synchronization.txt`) are the canonical derivations: client-side prediction with server reconciliation for the local player, interpolation for everyone else, and the jitter buffer as the price.

**Overwatch** (GDC 2017, Tim Ford; summarized in `edgegap-overwatch-2016-netcode-architecture-rollback.txt`): "fixed 16ms command frames (dropping to 7ms in tournament mode)"; ECS reduced the netcode surface "to just three systems out of hundreds"; "Time Dilation as a Packet Loss Shield: When the server detects input starvation, it signals the client to simulate slightly faster, flooding the input buffer"; everything predicted, rollback against an authoritative server. **Valorant** (`riot2020-valorant-netcode-peeking.txt`): "a smooth 128 server tickrate to all players", with buffering time broken down tick by tick; and **Fog of War** (`riot2020-valorant-fog-of-war-wallhacks.txt`): the server withholds positions a client could not see, so a wallhack has nothing to draw: interest management as anti-cheat. **Rocket League** (`cone2018-gdc-rocket-league-physics-networking.pdf`): fixed-step physics at 120 Hz, inputs buffered at the server, the client predicting the ball and cars and resimulating on correction.

**Durable in an FPS**: almost nothing. Match results, ranks, unlocks, and optionally a demo or replay (a snapshot log: non-deterministic engines must record state, not inputs; HN 47823580). Killcams are a ring buffer of recent snapshots, ephemeral by design.

| FPS | |
|---|---|
| Durable | results, ranks, inventory/unlocks, optional demo (snapshot log) |
| Live | lobby, party, voice signalling, presence |
| Fast | 64-128 Hz server tick (Source 66, Overwatch 62.5 or about 143 from its 16/7 ms frames, Valorant 128), 20-60 snapshots/s per client, 100 ms interpolation, ~1 s rewind history |
| Authority | the dedicated server; clients predict their own movement only |
| Fold vs ephemeral | per-match state is ephemeral; the server's tick state is a fold of inputs but nothing keeps the inputs |
| Got wrong | trusting clients (aimbots, speedhacks), sending what the client cannot see (wallhacks, fixed by fog of war), peeker's advantage from interpolation delay (Riot's article is about reducing it) |

### 1.3 MMO: zones, shards, instances, single shard, time dilation, interest management

**Guild Wars** (2005). "In Guild Wars, all locations are instanced ... Players can only meet non-party members in outpost instances" (`guildwars-wiki-instance.txt`). Instances are short-lived processes created per party; towns and outposts are the shared meeting points, split into districts. Pat Wyatt (`wyatt2012-codeofhonor-scaling-guild-wars-massive-concurrency.txt`): every game was recorded server-side, and recordings served load testing ("We were able to record hundreds of games and play them back on a server"), crash reproduction ("We'd play-back recordings of crashed games, fix the bug, run the build system, and often turn around new builds of the game in under five minutes"), hardware qualification (Opteron vs current servers on the same recordings) and esports replays. `wyatt2026-codeofhonor-twenty-years-of-guild-wars.txt`: "years of reliable service with no downtime, including no timeouts for maintenance or patches", and the business constraint behind the architecture: EverQuest's hosting "around a dollar per player, per month" would have sunk a game with no subscription. **Guild Wars 2's megaserver** (`arenanet2014-introducing-megaserver-system.txt`) replaced fixed home-world maps with map instances created on demand and populated by affinity (friends, guild, language): the instance is a policy over a projection of the population, not a place.

**World of Warcraft**: realms are shards (independent copies of the whole world), cross-realm zones and "sharding" copy single zones, and Classic's "layering" copies whole continents at launch. The player-visible failure: a summoned raid member "couldn't see us, nor us see him", an enemy group "disappeared" mid-fight (r/classicwow c03ol5); Blizzard committed to removing it ("There will never be layering after Phase 1, period", r/classicwow bokg8d). Copies of a world are invisible walls between players; they are a capacity policy that players experience as a semantic change.

**EVE Online**: one shard; each solar system is hosted by one SOL node process (with PROXY nodes holding sessions; `eve2023-devblog-tranquility-tech-iv.txt`), which makes a 3,000-player battle one process's problem. Time dilation (`eve2011-devblog-introducing-time-dilation.txt`): "A large majority of the load in large engagements is tied to the clock - modules, physics, travel, warpouts ... So, the idea here is to slow down the game clock enough to maintain a very small queue of waiting tasklets"; the envisioned fight dilates "down to 5% of real time" during warp-in, then about 30%; the physics simulation "Destiny" updates once per second and "only accounts for 5-10% of the load". The follow-up (`eve2012-devblog-time-dilation-hows-that-going.txt`) records ">1,300 pilots on a reinforced node (4 solar systems, supernode hardware)" and ">1,350 pilots on a normal node (83 solar systems)". The lesson: when the authoritative loop cannot keep up, slow the *game's* time uniformly rather than dropping work or players; game time becomes a state variable with a published rate.

**Second Life** (`highscalability2007-second-life-architecture-grid.txt`, `secondlife-wiki-server-architecture.txt`): "Each geographic area (256x256 meter region) in Second Life runs on a single instantiation of server software, called a simulator or 'sim.' And each sim runs on a separate core"; a space server routes by grid coordinates and tells each sim its neighbours; a dataserver fronts MySQL; assets (textures, meshes) are immutable objects served through caches; the viewer is handed off between sims at region edges. John Nagle on its limits: region-oriented seamless worlds "have trouble at the seams and can't handle crowds in one place" (HN 28421157).

**SpatialOS** (Improbable): an entity-component-worker model (`gamedeveloper-entity-component-worker-spatialos.txt`) in which entity components are owned by workers by spatial authority and replicated to interested workers through a central runtime; the experience reports are bad ("My opinion on it is extremely, extremely negative", HN 28419836; costs and the 2019 Unity licence dispute that took SpatialOS games offline, HN 18874400). Improbable has since pivoted to metaverse events (WP "Improbable (company)"). **Project Darkstar** (Sun; `waldo2008-queue-scaling-games-virtual-worlds-darkstar.txt`): every client event starts a task; "Under the covers, the task is wrapped in a transaction"; all world data goes through a Berkeley-DB-backed data service so tasks can move between machines; the motivation included that "a server crash can cause the loss of any change in the game or world since the last time the system was checkpointed. This can sometimes be hours of play". Sun Labs stopped work on it in February 2010 (WP "Project Darkstar"). It is the cautionary tale for this document: it put the per-event game loop inside a transactional store, paying a transaction per task in exchange for portability, and it is the one design surveyed that no shipped game of scale adopted.

**Minecraft-likes.** PaperMC's Folia (`papermc-docs-folia-regionised-multithreading.txt`) "splits the chunks within all loaded worlds into independently ticking regions so that the regions are ticked independently and in parallel", maintaining that "a ticking region has no directly adjacent neighbor regions which are ticking", merging and splitting regions as players move. The OpenCraft group's Dyconits (`donkervliet2021-dyconits-scaling-minecraft-like-services.pdf`) bound inconsistency per (region, subscriber) dynamically, and Servo (`donkervliet2023-servo-scalability-modifiable-virtual-environments.pdf`) moves terrain generation, player-built constructs and storage to serverless functions with speculative execution.

**Interest management**, the mechanism every scaled design shares: area-of-interest filtering of which entities' updates reach which client or server (`boulanger2006-interest-management-thesis-mmog.pdf` compares the algorithms; Colyseus, `bharambe2006-colyseus-distributed-architecture-multiplayer-games.pdf`, keeps a primary copy of each object on one node and read-only replicas wherever a node's interest range covers it, found through Mercury's range-queriable publish/subscribe, `bharambe2004-mercury-multi-attribute-range-queries.pdf`; Donnybrook, `bharambe2008-donnybrook-large-scale-p2p-games.pdf`, observes that "action games limit the number of players who can interact simultaneously to 16-32", estimates what each player is attending to, sends low-rate "doppelganger" predictions for the rest, and reaches 900 players; VON, `hu2004-scalable-p2p-networked-virtual-environment.pdf`, builds the overlay from Voronoi neighbours). Interest management is per-tick filtering of a fan-out: it is the fast plane's version of INBOX's selection-vs-fan-out decision.

| MMO | |
|---|---|
| Durable | characters (inventory, skills, currency), guild rosters, auction and trade records, world persistent objects, account and billing |
| Live | chat channels, presence, party and guild invites, zone population for matchmaking/instancing |
| Fast | per-zone/region/instance tick (EVE 1 Hz physics; action MMOs 10-30 Hz), interest-filtered updates |
| Authority | the zone/instance process for its area; a database for characters; trades as database transactions |
| Fold vs ephemeral | characters are folds over transactions (loot, trade, spend); mob positions, cooldowns and combat are ephemeral, checkpointed periodically or never |
| Got wrong | copies of the world as invisible walls (layering), seams and crowds at region borders, everything-through-a-transaction (Darkstar), lost hours on crash between checkpoints, middleware cost and lock-in (SpatialOS) |

### 1.4 Persistent and federated worlds

**Second Life's grid** is the region-server model (1.3) with a federation in OpenSimulator's hypergrid. **Decentraland** (`decentraland2017-whitepaper.pdf`): "Landowners control what content is published to their portion of land, which is identified by a set of cartesian coordinates (x,y)"; parcel ownership on a ledger; a content distribution layer serving each parcel's content by hash; peer-to-peer real-time interaction among nearby users. The parcel is the unit of authority, publication and distribution at once: exactly Wild Earth's 10 km tile. **Wild Earth** (the brief) inverts the MMO: the expensive, durable, shared artefact is the *world content* (gigabyte tile packages built from public geodata by residents and agents, plus a growing species and asset library), while the live game is small (animals, a few verbs, perception). Its tile is closer to a map in the 3D Tiles sense (`ogc-3d-tiles-spec-1.1.txt`: a spatial hierarchy of tilesets with bounding volumes and content URIs) or a PMTiles archive (`protomaps-pmtiles-spec-v3.md`: one file, a header, a directory, range-addressable tiles, so a client or peer reads only what it needs), with source provenance in STAC items (`stac-spec-overview.md`). Exchange between nodes is the BitTorrent v2 problem (`bittorrent-bep52-v2-merkle.txt`: per-file Merkle roots over 16 KiB blocks, so a peer verifies every block it receives against a root it trusts, and two torrents sharing a file share its root).

### 1.5 Recording and replay as durable logs

Two kinds exist and must not be conflated. **Input logs** (AoK, StarCraft, Quantum, rollback fighting games, Guild Wars' server-side recordings) are small and exact but only meaningful with the exact binary, data and seed: a replay is invalidated by any engine change (HN 47823580, "if the engine deviates in any manner, the replay becomes invalidated"), so a durable input log must name the simulation version, and replays of old versions need the old binary (a content-named artefact). **Snapshot logs** (Source demos, killcams) are large, robust to code changes, and need no determinism. Guild Wars shows the input log's operational value at MMO scale: load tests, bug reproduction in minutes, hardware qualification and spectator replays from one recorder. For fn2 the consequence is concrete: a match or instance recording is a stream whose records are inputs plus periodic state digests, whose header names the simulation's content identity, and whose checkpoints are content-named state snapshots; replay, audit and anti-cheat re-simulation are consumers of that stream.

### 1.6 Authority and anti-cheat

Four authority models appear: **agreement** (lockstep: every peer checks every other by digest; cheating is a desync, Bettner), **referee** (an authoritative server, FPS and MMO; clients are untrusted input devices), **commitment** (Baughman's commit-reveal lockstep, for peer games without a referee), and **audit** (record everything, re-simulate later, HN 4107813; Guild Wars' recordings). Information-hiding anti-cheat (Valorant's fog of war) is interest management applied to the adversary. fn2's natural role is the last two: it is a durable, signed, ordered log with Merkle checkpoint claims (STORAGE decision 4), so commitments, recordings and verdicts stored there are evidence that outlives the match. It is never the referee of a tick.

### 1.7 Event sourcing, CQRS and projections, in games and in general

Fowler's event sourcing (`fowler2005-docs-event-sourcing.txt`, already here) and Kleppmann's "turning the database inside out" (`kleppmann2014-turning-the-database-inside-out.txt`: the log as the source of truth, every index and cache a materialized view derived from it by a stream processor) are the general statements of what lockstep discovered. The stream-processing literature supplies what fn2's fold declarations still lack: **when is a projection's answer complete?** Kafka Streams (`confluent2021-rethinking-distributed-stream-processing-kafka.txt`, the SIGMOD 2021 paper's companion; the paper itself is behind the ACM wall) separates *consistency* (exactly-once via transactions over the log and state-store changelogs) from *completeness* (revision-based handling of out-of-order data, emitting revisions rather than waiting). Naiad's timely dataflow (`murray2013-naiad-timely-dataflow.pdf`) and differential dataflow (`mcsherry2013-differential-dataflow-cidr.pdf`) answer with **frontiers**: every record carries a logical timestamp; each operator learns when no more records at or before a time can arrive, and outputs at that time are then final. Materialize (`materialize-docs-consistency-guarantees.txt`) exposes this as strict serializability over timestamps: a read at time *t* waits until every input's frontier passes *t*. DBSP (`budiu2023-dbsp-automatic-incremental-view-maintenance.pdf`) gives the algebra: any query over Z-sets (multisets with signed weights) has a mechanically derived incremental form, proved correct. Flink's asynchronous barrier snapshots (`carbone2015-lightweight-asynchronous-snapshots-flink.pdf`) give a consistent checkpoint of a running dataflow without stopping it by flowing barriers with the data. Datomic (`datomic2026-docs-filters-as-of-history.txt`, already here) gives `as-of` and `history` views of one immutable log. INBOX §4.6 already has the frontier idea under another name (`cov(c)`, the position through which a fold is complete, with the read rule that falls back to the source above it); §2.2 below generalizes it.

### 1.8 Live planes: delivered now or never

The industrial pattern is a durable log and a non-durable bus side by side, sharing subjects, with the consumer choosing. **NATS**: "core NATS is at-most-once. A message reaches every interested subscriber that's connected at the moment of publish, at most once. If a subscriber is offline ... it never sees that message" (`nats-docs-core-nats.txt`); "JetStream adds a persistence layer on top, giving you at-least-once delivery - messages survive restarts and can be replayed" (`nats-docs-jetstream.txt`). **Redis**: "Redis' Pub/Sub exhibits at-most-once message delivery semantics ... the message is forever lost", against Streams, which "are persisted, and support both at-most-once as well as at-least-once" (`redis-docs-pubsub.txt`, `redis-docs-streams.txt`). **MQTT** (`oasis2019-mqtt-v5-spec.txt`): QoS 0/1/2 per message plus a *retained* message per topic (latest value, delivered to new subscribers), which is the presence primitive. **Matrix** (`matrix2026-spec-client-server-full.txt`): typing notifications and read receipts are *ephemeral events* returned in a room's separate `ephemeral` section of `/sync`, and presence in its own top-level section; neither is ever in the room timeline or its history. **Discord voice** (`discord2018-blog-2.5m-concurrent-voice-webrtc.txt`): the durable-ish control state (the "voice state object" per user, held by the Guilds service) is pushed to whichever voice server is selected; the media plane (a C++ SFU over UDP) holds nothing it cannot rebuild: "If the SFU crashes, it is restarted right away ... The state on the SFU is reconstructed by the signaling component without any client interaction", and the same procedure handles DDoS, region change and zero-downtime upgrade. That is the clearest statement in the corpus of the rule this document proposes: a faster plane holds no state that the plane below cannot reconstruct it from.

### 1.9 Fast planes: tick loops and unreliable transport

Transport: UDP with an application protocol (Quake 3, Source); **ENet** (`enet-docs-features.txt`: reliable and unreliable sequenced packets on channels over UDP, fragmentation, connection management); **netcode.io** (`netcodeio-standard.md`: connect tokens issued by a web backend authorize a client to a dedicated server, then encrypted, authenticated UDP packets; the backend that issues tokens is the only durable party); **QUIC datagrams** (`rfc9221-quic-unreliable-datagram-extension.txt`: unreliable, unretransmitted application datagrams inside an encrypted, congestion-controlled QUIC connection; `rfc9000-quic-transport.txt`). The fast path inside an otherwise durable system is **Cloudflare Durable Objects** (`cloudflare2021-durable-objects-easy-fast-correct.txt`, `cloudflare-docs-rules-of-durable-objects.txt`): one single-threaded object per key, an in-memory cache in front of replicated storage, *input gates* ("While a storage operation is executing, no events shall be delivered to the object except for storage completion events") and *output gates* ("When a storage write operation is in progress, any new outgoing network messages will be held back until the write has completed ... If the write ultimately fails, the outgoing network messages will be discarded"). Output gating is fn2's publish-after-durable (EXEC rule 8) applied at message granularity: a fast plane may compute ahead of durability, but it may not *tell anyone* a durable fact until the slow plane has made it durable.

### 1.10 Across the classes

| Class | Durable | Live | Fast (tick, budget) | Authority | Fold of a log | Principal wound |
|---|---|---|---|---|---|---|
| RTS lockstep | input log if recorded; result | lobby, chat | turns 200 ms (AoE) to 16 ms (rollback); 250-500 ms command latency tolerated | all peers by digest | everything | non-determinism, desync |
| FPS | result, ranks, demo | lobby, voice signalling | 64-128 Hz; 100 ms interp; 1 s rewind | dedicated server | nothing kept | trusted clients, leaked information |
| MMO | characters, trades, world objects | chat, presence, invites | 1-30 Hz per zone | zone process + database | characters (by transactions) | copies as walls, seams, lost hours, all-transactional loop |
| Federated world (SL, Decentraland, Wild Earth) | the content (regions, parcels, tiles, assets) and its provenance | presence, nearby chat | per region | region owner/server | catalogs and libraries | seams; content lock-in |
| helm (contrast, CLIENTS §1.2) | rows, dispatch obligations, premises, signed turns | wake, presence | none | the node, per room single writer | everything | rows lost in RAM; wake as delivery |

The pattern under all of them: **the durable part is small, slow, valuable and shared; the fast part is large, local, cheap and disposable; the bridge is a checkpoint and a log of consequential events.** Nobody successful made the fast part durable per tick (Darkstar tried). Nobody successful kept the consequential events (trades, results, ownership) anywhere but a transactional store.

## 2. The planes as an architecture for fn2

### 2.0 The four planes in one table

A *plane* is a class of state distinguished by its promise: what survives a crash, what order it has, how late it may be. fn2 today is one plane. The surveyed systems use four, and the boundaries between them are where every post-mortem in §1 lives.

| Plane | Promise | Latency class | Unit of state | Who runs it |
|---|---|---|---|---|
| **Slow** (fn2 as designed) | durable, totally ordered per commit domain, exact identity, recoverable under the declared fault profile, signed checkpoints | one commit batch (group commit; unmeasured, ENVELOPE §2.8) | events in the journal; content-named payloads; folds; obligations; pins | the fn2 executor |
| **Projection** | derived, declared, rebuildable; complete through a published frontier, never beyond it | the slow plane's latency plus a declared lag | fold entries keyed in the ordered-run engine; external views | the fn2 executor's maintenance class, or an external consumer |
| **Live** | ordered within an epoch, delivered at most once, lost at restart, loss always reported as a gap | one scheduler visit (no barrier) | items in bounded in-memory rings; latest-value keys with leases | the fn2 executor (same scheduler, no commit stream) |
| **Fast** | per-tick, lossy transport, authoritative only for the current tick and only until the next checkpoint | a tick (8-50 ms in §1) | a game's world state in its own memory | a separate executor, a separate process, often a separate node |

Six laws bind them; each is the inverse of a wound in §1.

- **L1 Authority flows down.** The only durable facts are those the slow plane committed. Everything above it is a cache, a speculation or a delivery. (Darkstar inverted this and paid a transaction per task; layering inverted it for *presence* and players vanished.)
- **L2 Every upper state is reconstructible from the plane below plus a declared loss.** A projection from the log and its declaration; a live stream from nothing (its loss is declared); a fast plane from its last checkpoint and whatever input log it chose to make durable (Discord's SFU "reconstructed by the signaling component"; Guild Wars' recordings).
- **L3 Output gating.** No plane tells an outside party a durable fact before the slow plane's outcome (Durable Objects' output gate; EXEC rule 8's publish-after-durable). A fast plane may simulate past an uncommitted trade; it may not show "trade complete".
- **L4 Loss is typed.** A plane that may lose items reports a gap with a cause (`live-overrun`, `epoch-reset`, `unavailable`), never a silent hole (INBOX headsmack 9, Matrix's `limited`).
- **L5 Positions never mix.** A commit position, a live sequence and a game tick are three types. Mappings between them are themselves events (a checkpoint records the tick it covers and the commit position of every input it consumed).
- **L6 Time is declared.** Every deadline names its time domain (the node's monotonic clock, or a game's tick domain whose rate is a published, changeable value, EVE's dilation); wall time never selects work in the slow, projection or live planes (EXEC rule 4).

### 2.1 The slow plane (fn2 as designed)

**Provides**: the ordered semantic event journal per commit domain; payloads as content-named blocks; one pageable ordered-run engine for every keyed structure; folds with interpretation, initialization and coverage; pinned versions and object leases; obligations released only by evidence; the Merkle event log and the typed signed checkpoint claim; replication by NNTP feeds and BP; the consumer protocol (selection over per-stream indexes, one commit-position cursor, durable versioned registrations, wake through subscription edges, INBOX §5.1). Every rule of EXEC holds unrelaxed.

**Must never**: run a game tick or any loop whose step is selected by wall time; hold state whose loss the game would tolerate (that is the live or fast plane's, and storing it here charges every principal's commit latency and journal bytes for it); interpret game verbs; promise a latency below one commit batch; accept per-tick writes (a 64 Hz server committing per tick is 64 commits/s per zone; one journal unit per isolated durable ack, STORAGE correction 9, would be about 21 GiB of journal per zone per day, *derived*: 64 × 86,400 × 4 KiB = 22.6 GB).

**Its interface upward** is what INBOX already designs, plus four things this document adds (§4): a durability class on every stream, a projection declaration that generalizes the fold declaration, a checkpoint event for external executors, and declared time domains.

### 2.2 The projection plane: folds generalized, with frontiers

A projection is a declared function from a set of slow-plane streams to a keyed structure, maintained incrementally, complete through a published position. Everything fn2 already derives is one: overview by (group, number), the `addr` index, the `inbox` fold, the per-(consumer, stream) read state, cursors and accounts (STORAGE §1; INBOX §4.2-4.6). Games add: a region/species catalog (Wild Earth), a character sheet (an MMO's inventory and skills as a fold of trade, loot and spend transactions), a zone index (which instances exist, at what population, for GW2-style placement), a leaderboard, a match index (RTS replays by player, map, version), a tile manifest index (which blocks of which package a node holds).

**The declaration** (§4.2 gives the fields): sources (stream kinds and an envelope-field predicate, never sealed content, STORAGE decision 5), key schema in the ordered-run engine, an interpretation written in the machine DSL with a per-event work bound, initialization, coverage (from history start, or from a stated position with the earlier range declared unavailable), retention (latest-only or versioned, STORAGE decision 1: "Internal folds are latest-only; a historical fold question is answered from a retained snapshot plus replay"), and a **maintenance mode**:

- **In-transaction** (overview, `addr`, a character sheet): written in the event's own commit, so it is complete at every installed position by construction; allowed only when its per-event fan-out is bounded by a declared constant (`max-addressees` is the precedent, INBOX §4.2) and charged to the writer.
- **After-commit** (the `inbox` fold, catalogs, leaderboards, spatial indexes): written by a budgeted maintenance-class machine in later ordinary batches, publishing its frontier `cov` (INBOX §4.6). The commit path never waits for it.
- **External**: a consumer process (a differential-dataflow job, a search engine, a game's own read model) reading through the consumer protocol and, if others rely on it, publishing its frontier back as a signed statement event `(projection-id, version, cov, digest)`.

**The read rule, generalized** (INBOX §4.6 is the special case): a read names a position *p* (explicitly, or "the current installed position"). If the projection's `cov ≥ p`, it answers from the projection. Otherwise the reader's declared fallback applies: *select* (recompute from the source streams, INBOX's rule), *wait* (park on the projection's frontier as a subscription edge until `cov ≥ p`, Materialize's strict-serializable read, `materialize-docs-consistency-guarantees.txt`), or *stale-ok* (answer at `cov` and say so). Naiad's frontiers and Kafka Streams' completeness (§1.7) are this rule in other systems; fn2's one commit order per domain makes it simpler than theirs (no event-time disorder: the frontier is a single position, not an antichain).

**Must never**: be the authority for anything (rebuildable from log plus declaration, L2); delay a commit; answer beyond `cov` as if complete; re-perform an external effect when rebuilt (STORAGE decision 1: "External effects are recorded as obligations or outbox entries released by evidence, never re-performed by replay"); hold payloads (references only, INBOX §4.6).

**Interface to the slow plane**: reads by `Seek(stream, after = p)` in position order (INBOX §4.1); writes through ordinary commit batches; its frontier is a resident value while any wait watches it, paged otherwise (EXEC rule 9). **Placement**: the fn2 executor's maintenance service class for in-transaction and after-commit projections; a separate process for external ones. **Rules relaxed**: none for internal projections. The equivalence obligation (INBOX §4.6: observations equal the select-only reference for every policy and materializer schedule) generalizes to every after-commit projection: *for every maintenance schedule, a read at p answered from the projection equals the declared interpretation folded over the source events at or below p.* DBSP (`budiu2023-dbsp-automatic-incremental-view-maintenance.pdf`) is the route to deriving the incremental interpretation from a non-incremental one with a proof, if projection queries outgrow hand-written folds.

### 2.3 The live plane: streams with no durability promise

ember's word was "live"; the systems in §1.8 show what it must be: the same subjects and subscription machinery as the durable plane, with the durability promise removed and the removal made explicit. Two kinds:

- **Live streams** (lobby events, typing, in-game chat channels a game declares non-durable, telemetry for spectators, "a seat started a tool call"): each item gets `(stream, epoch, seq)`; items sit in a bounded per-stream ring in the byte pool; subscribers hold the same subscription edges as durable streams; delivery is at most once per (edge, item). The **epoch** is the node incarnation, so a restart is visible as `gap(epoch-reset)`, never as a sequence that silently restarts at zero.
- **Ephemeral keys** (presence, a seat's current activity, a zone's population for placement, a player's position on a shared overview map): latest value per key with a lease; a new subscriber receives the current values (MQTT's retained message, `oasis2019-mqtt-v5-spec.txt`); expiry produces a removal item; nothing survives restart.

**What the subscription edges and the wait machine become.** An edge row gains a class (`durable | live | ephemeral`) and, for live classes, a resident delivered-through `(epoch, seq)` and a credit count. Wake is unchanged: a live append sets the stream's `SubscriptionDirty` bit and the notification service walks its edges (INBOX §4.4; EXEC rule 7: a state bit, never a message queue). The final frontier check reads the per-class frontier: the installed commit position for durable edges, the ring head for live edges. A reply may carry durable items (with commit positions, advancing the durable cursor) and live items (with `(epoch, seq)`, advancing only the resident edge state); the durable cursor is never moved by a live item (L5). To let a client order a live item against durable ones ("this typing indicator is about the post at p"), each live item is stamped with the installed commit position at its publication: a *happened-after* hint, not an order.

**Back-pressure**: a producer's live publish is admitted against its own principal's live-byte and item-rate budget (EXEC rule 5) and never waits for consumers; each edge has a credit window; when a slow edge falls more than the ring behind, it receives `gap(live-overrun, from, to)` and resumes at the oldest retained item (drop-oldest per edge, never per producer). Fan-out cost per append is the stream's parked-edge walk, bounded and resumable as for durable streams (≤ 32 edges per run, INBOX §4.4). **Presence fan-out** is the known hot spot (Discord's guild presence, Matrix's presence load): ephemeral keys are subscribed by *scope* (a room, a zone, a guild), never per pair of users, so an update costs one walk over the scope's edges.

**Promotion and demotion**: a live stream may declare a *summary policy* that writes durable events (a lobby's "match created" as an ordinary transaction; a presence session's "began/ended" for audit); a durable stream already produces live wakes. Neither direction changes the other plane's semantics.

**Must never**: write the journal for a live item; acknowledge durably; block a producer on a consumer; let a live item move a durable cursor; promise delivery across a restart.

**Placement**: inside the fn2 executor, as machines on the same scheduler, because the subscription edges, the wait machine and the notification service class are shared, and wake latency is "the scheduler's starvation bound plus one selection" (INBOX §4.4). **Rules relaxed**: rule 8 (durability) only, by definition: a live publish is not a transaction, has no `uncertain` state, and its outcome is `published(epoch, seq)` or a named refusal. Every other rule holds: rings and key tables are resident active state with structural capacities (rule 9 says resident capacity limits active execution state, which live state is), the simulator drives them (rule 10), and the CONSUMER checker gains a live-class oracle (items delivered in order within an epoch; every missing range reported as a gap). **The cost**: everything in the live plane is lost on crash, by contract; and live traffic competes for the executor's turn budget, so a live stream that needs more than the subscription-notification class's share belongs in the fast plane.

### 2.4 The fast plane: a tick executor beside fn2, never inside it

**Provides**: a tick loop (20-128 Hz in §1), UDP or QUIC-datagram transport (`rfc9221-quic-unreliable-datagram-extension.txt`, `netcodeio-standard.md`, `enet-docs-features.txt`), interest management (§1.3), prediction and reconciliation, lag compensation, physics, the game's verbs, per-species perception (Wild Earth), fog of war. Its authoritative state at tick *t* is

`World_t = Step*(Restore(Checkpoint_k), Inputs_{k+1..t}) ⊕ Scratch_t`

where `Checkpoint_k` is in fn2, `Inputs` are whatever the game chooses to make durable (all of them for lockstep and audited games, none for a casual FPS), and `Scratch` is state the game declares disposable (particles, AI working memory, interpolation buffers).

**Its interface to fn2**, in four verbs, all over the existing consumer protocol and transaction path (the fast executor is an ordinary authenticated principal; no new trust class):

1. **Open**: read the zone or instance definition at a pinned version (a projection read, STORAGE decision 2), the content it needs (tile packages, asset blobs by content identity, with object leases), the characters entering (fold reads), and the latest checkpoint; and **take the zone lease**: an obligation with an expiry and a fencing incarnation, so two executors never both own a zone (the same fencing STORAGE uses for writer epochs; a later incarnation's commits refuse the earlier one's by name).
2. **Commit consequences, output-gated** (L3): every fact a player may rely on after the session (a trade, loot entering an inventory, a purchase, a death penalty, a match result, a tile edit in a world builder) is an ordinary fn2 transaction carrying an operation identity and the expected prior version of the folds it touches (STORAGE decision 1's binding), so a retry after a fast-plane crash returns the original outcome. The executor withholds the player-visible confirmation until the outcome arrives. A trade between two players is one transaction in one commit domain, with an escrow obligation when it spans sessions (CLIENTS §4: "Obligations with evidence-gated release").
3. **Checkpoint, on its own cadence** (seconds to minutes; the game chooses its maximum loss): append a checkpoint event `(executor, zone, incarnation, tick, state digest, snapshot payload by content identity, input-log range, predecessor checkpoint, time-domain mapping)` (§4.5). fn2 verifies the signature, the predecessor chain and the lease; it asserts nothing about the state's correctness (the negative clauses of STORAGE decision 4 apply verbatim).
4. **Log inputs, in batches** (optional): append input batches to a durable match stream at a cadence (one event per second of ticks, not per tick), so replay, audit re-simulation (HN 4107813) and crash recovery by re-execution (Guild Wars) are consumers of fn2.

**Placement**: a separate process, normally on a separate node near its players, never in the fn2 executor. Putting it inside would break EXEC rule 4 (wall time would select work), rule 5 (one zone's tick would consume other principals' scheduling share at 64 Hz), and the latency promise of every fn2 principal; Darkstar is the measured precedent for the cost of running the game loop through a transactional store. **Rules it keeps**: bounded work per tick (a tick budget is EXEC rule 3 with time as the budget), deterministic simulation as a test method (its own simulator; for lockstep and rollback games, cross-machine determinism as a product requirement), reserved capacity per player. **Rules it relaxes, and the cost**: wall time drives it (cost: no schedule equivalence with fn2's reference semantics; the bridge is only the four verbs above); transport is lossy (cost: L4 gaps on the client side, handled by snapshots or redundancy, §1.2); durability is per checkpoint (cost: a crash loses at most one checkpoint interval of non-consequential state, exactly Darkstar's "hours of play" complaint but bounded by a cadence the game chooses, and zero consequential state because of output gating).

**The lockstep special case**: an RTS needs no authoritative fast executor; its fast plane is a turn relay (Quantum's "game-agnostic authoritative server component ... to synchronize clocks and manage input latency") whose only fn2 interface is verb 4 (the match stream), plus verb 2 for the result. A peer-to-peer lockstep game can append its match stream itself from the host peer, or from every peer with fn2 deduplicating by turn (operation identity per `(match, turn, player)`).

### 2.5 Placement, rules and costs at a glance

| | Slow | Projection | Live | Fast |
|---|---|---|---|---|
| Executor | fn2 | fn2 maintenance class, or external consumer | fn2 (notification class) | separate process/node |
| Reads below via | (storage) | `Seek` in position order | (none) | consumer protocol, pinned versions, leases |
| Writes below via | (storage) | ordinary commit batches | summary policy → transactions | transactions (consequences), checkpoint events, input batches |
| EXEC rules relaxed | none | none | 8 (durability) | 3 as a time budget, 4 (wall time drives), 8 (per checkpoint), 10 (own simulator) |
| Lost on crash | nothing promised | nothing (rebuilt) | everything, as `epoch-reset` | ticks since the last checkpoint; never a consequence |
| Never | tick, per-tick writes, game verbs | authority, blocking commit, answering past `cov` | journal writes, durable acks, blocking producers | telling a player a durable fact before fn2's outcome |

### 3.2 Wild Earth in detail: the client that bends fn2 most

Wild Earth is the only one of the five whose *durable* data is large, and it is the one that makes fn2's storage and peering design pay. Three of its needs are new.

**Gigabyte payloads exchanged between nodes.** A 2 GiB tile package at 64 KiB blocks is 32,768 blocks (*derived*). Ember asked whether hashing and naming every 64 KiB block is too slow. Hashing is not the cost: single-threaded BLAKE3 runs at about half a cycle per byte for inputs of 64 KiB and up on one AVX-512 core (`oconnor2021-blake3-spec.pdf`, Figure 3, read from the plot; the figure annotates 0.49), so 2 GiB takes about 1.1 × 10^9 cycles, roughly 0.35 s on one 3 GHz core, and scales across cores by the BLAKE3 tree (Figure 4) (*derived*). The real cost is *naming*: if every block is a separately named object with a row in the ordered-run engine, a node holding 1,000 tiles carries 33 million metadata rows (*derived*). The design STORAGE already chose avoids that if it is read as intended: **one content identity per object** (the BLAKE3 root of the whole package), one metadata row per object plus an extent map, and the per-block verification material kept as an *outboard tree* (BLAKE3/Bao-style range-proof material, STORAGE §1) stored as a payload beside the object, not as rows. A peer then verifies any received range against the object's root (BitTorrent v2's per-file Merkle roots over 16 KiB blocks, `bittorrent-bep52-v2-merkle.txt`, are the deployed precedent), resumes a partial transfer by comparing which ranges it holds (a projection: the manifest index), and two packages sharing an identical file share its identity. A PMTiles-like internal layout (`protomaps-pmtiles-spec-v3.md`: header, directory, range-addressable tiles) lets a client fetch one level of detail by range read under an object lease, without the package ever passing through the byte pool whole (EXEC rule 6: only a bounded window occupies the pool). Scale, for orientation: Earth's land is about 149 million km², 1.5 million tiles of 100 km² (*derived*); at 2 GiB each a full mirror is about 3 PB, so no node holds the world, and every node needs to know which nodes hold what (a projection over peers' advertisements, exchanged as records).

**Provenance and agent work.** Each package is built from public datasets by people and agents; its record names its sources (STAC item identities and licences, `stac-spec-overview.md`), the builder principal, the agent runs and their inputs, and the package identity. This is STORAGE's signed-record and statement machinery used as intended ("what does this node have, why does it keep it, what has it undertaken to do", CLIENTS §0). Agent work queues need **competing consumers with claims**, which CLIENTS §4 lists as absent ("Competing consumers / claim | helm (`work claim`, review queues) | none"): a claim is an obligation with an expiry, released by the result's commit or returned to the queue at expiry, charged to the claimant (§4.7).

**Peer exchange including field builders.** Residents building a region in the field (no connectivity for days) exchange packages by BP, where custody is an obligation (E5). A 2 GiB bundle needs fragmentation and resumable custody transfer; the content identity makes every fragment verifiable on arrival. The tile is also the unit of authority (Decentraland's parcel, `decentraland2017-whitepaper.pdf`): the region's builders sign its packages, and a node's acceptance policy says whose signatures it accepts for which tiles.

The live game itself is small and stays outside fn2: per-tile fast executors (a 10 km tile is 1,525 Second Life regions of 256 m, *derived*: (10,000/256)², so a tile executor partitions internally, Folia-style, `papermc-docs-folia-regionised-multithreading.txt`), per-species perception as interest management, player animals as folds committed on consequential events (a kill, a territory claim, a death), wildlife NPCs spawned from catalog projections built from GBIF occurrence data.

## 4. Mechanisms now, policies later (layers C, D, E)

INBOX §4 set the pattern: put the mechanism in the format and the reference model now, so that a later policy is a row change, not a migration. The same test applies here: **which fields, record kinds and primitives must exist in 5.1.1 so that the projection, live and fast planes can be added without changing a format, a wire frame or the host ABI?** Eight mechanisms answer it; each names its layer and what 5.1.1 serves versus only declares.

### 4.1 Streams carry a durability class; the consumer protocol carries it (C, D9, E3)

- **C**: the stream-id's kind tag (INBOX §4.1: "typed by kind (group, address, fold) so later kinds ... add a kind, not a format") gains a **class**: `durable | live | ephemeral`. Every 5.1.1 stream is `durable`; the class is in the format so a live kind is a new kind value, not a new id space.
- **D9 (the wait machine)**: the `Esub` edge row gains `class`, a resident `delivered-through (epoch, seq)` for live classes, and a `credit` count; the final frontier check dispatches on class (installed commit position vs ring head). A **live ring** machine kind (bounded per-stream ring in the byte pool, `(epoch, seq)` assignment, drop-oldest per edge with a gap) and an **ephemeral key table** (latest value with a lease, removal on expiry) are declared in the machine DSL with their capacities in the profile.
- **E3 (the consumer wire)**: each item carries its class; durable items keep the commit position (INBOX §4.8); live items carry `(epoch, seq)` and a *happened-after* commit position; the gap item's cause set gains `live-overrun` and `epoch-reset` beside `unavailable` and `bootstrap`; ack applies to durable items only; a credit frame returns live-edge window. Unknown classes and causes are ignorable by contract, so a 5.1.1 client survives a later node that serves live streams.
- **Served in 5.1.1**: the fields, the reference model and two simulator scenarios (a live edge overrun reports exactly the dropped range; a restart reports `epoch-reset` and never re-delivers a sequence number from the old epoch). **Served later**: the first live stream kind, when its first client asks (helm's presence and "seat working" are the likely first; decision 2 in §5).

### 4.2 The projection declaration is the fold declaration, generalized (C4, D maintenance, E6)

C's contract item 1 already requires "each fold declared with interpretation, initialization and coverage". Generalize that declaration to **`defprojection`** with: `id` and `version` (a changed interpretation is a new version with its own coverage, never an in-place change; STORAGE decision 1's migration rule); `sources` (stream kinds plus a predicate over public envelope fields); `key-schema` (an ordered-run schema); `interpretation` (a machine-DSL function with a per-event work bound and a declared output fan-out bound); `initialization`; `coverage`; `retention` (latest-only or versioned); `mode` (`in-transaction` with a fan-out bound and a charging rule, `after-commit`, or `external`); `read-fallback` (`select`, `wait`, `stale-ok`); and `frontier` publication (resident while watched). Overview, `addr`, `inbox`, read-state, cursors, accounts and pins are re-declared through it (the derived path is the only path; the C4 folds are its first instances). **D** owns one generic after-commit maintenance machine (INBOX §4.6's materializer, parameterized by the declaration) and the frontier as a wait target. **E6** exposes per-projection frontier, lag and resident bytes as operator status (never on the client wire, INBOX §4.8). The equivalence obligation becomes one CONSUMER-checker property over every after-commit projection (§2.2). **Served in 5.1.1**: the declaration form and the C4 folds through it; the generic materializer exists in the reference model as INBOX already plans for `inbox`.

### 4.3 A transport seam that admits datagrams beside streams (A3/A4, sim, E later)

The 21 host primitives (ENVELOPE §2.3) are stream-shaped: `recv` returns `Done(0)=eof`; `send` may be `Short(n)`. A datagram endpoint differs in three ways the ABI must not assume away: message boundaries, a peer address per message, and no end-of-stream. Add three primitives to the set, specified and simulated now, implemented by the native host when first used:

| # | primitive | signature | Linux |
|---|---|---|---|
| 22 | `datagram_bind` | `(addr: Inet) -> Endpoint` (startup) | `socket(SOCK_DGRAM)`, `bind` |
| 23 | `datagram_send` | `(endpoint, peer: Addr, from: Handle) -> op ⇒ Done(n)` (all or nothing) | `SENDMSG` (GSO batching optional) |
| 24 | `datagram_recv` | `(endpoint, into: Handle) -> op ⇒ Done(n, peer: Addr, truncated: bool)` | `RECVMSG` (multishot where available) |

QUIC (`rfc9000-quic-transport.txt`, `rfc9221-quic-unreliable-datagram-extension.txt`) is an **adapter over these**, exactly as TLS is an adapter over `send`/`recv` (`tls_handshake`, ENVELOPE row 11): a QUIC library (quiche, ngtcp2 or msquic, behind the host) presents streams and datagrams to the core as connection capabilities of two kinds. The simulator models datagram loss, duplication, reordering and truncation. Why fn2 itself needs this, not only games: LTP over UDP for BP (CLIENTS §1.5 records an ION-DTN LTP/UDP feasibility run), and a QUIC-carried consumer protocol for agents behind NAT (akapug's 10-08 need, CLIENTS §1.2) both use it. **Served in 5.1.1**: the three signatures in A4's ABI document, the connection-kind enum in the vocabulary (A2), the simulator's datagram model; no served datagram traffic.

### 4.4 The wake is a hint over any plane (D9, already nearly true)

One mechanism, three sources: a commit `install` sets `SubscriptionDirty` on touched streams (INBOX §4.4); a live publish sets it on its ring's stream; a projection's frontier advance sets it on the projection's frontier stream (so `read-fallback = wait` is an ordinary parked edge). The final frontier check makes every wake a hint (a lost wake costs latency up to the wait's timeout, never an item). Nothing new in the wire; one new edge target (a projection frontier) in D9.

### 4.5 A checkpoint record for external executors, and fencing (C schema, D5, E3)

A record kind **`external-checkpoint`**: `(executor principal, scope id (zone, match, tile), incarnation, tick (in a declared time domain, §4.6), state digest, snapshot payload by content identity, input-log range (stream, from position, to position), predecessor checkpoint identity, signer)`. D5's transaction machine admits it only if the predecessor is the scope's latest checkpoint at commit time and the incarnation holds the scope's lease (§4.7), else a named refusal (`checkpoint-conflict`, `fenced`). Consequential transactions from an executor carry `(scope, incarnation)` and are refused `fenced` once a later incarnation holds the lease (the zombie zone server cannot commit a trade after its replacement started). fn2 asserts the chain and the fence, never the state's correctness (STORAGE decision 4's negative clauses). A **scope-latest-checkpoint** fold (a projection, §4.2) answers "where does zone Z resume". **Served in 5.1.1**: the record kind in C's schema list and the two refusal words in D5's vocabulary (cheap now, a format change later); no executor exists.

### 4.6 Time domains as core state (C fold, D timers, E6)

EXEC fixes that the node reads `clock_monotonic` once per iteration and that wall time never selects a machine; deadlines are computed from it (ENVELOPE rows 17-18). Games need deadlines in *their* time (an auction ending at game-day 40; an escrow expiring after 10 minutes of match time; EVE's dilated clock). Add a **time-domain fold**: `domain-id → (kind: node | external, owner principal, mapping history)`, where the mapping history is a list of events `(commit position, domain value, node-monotonic anchor, rate)`; an external domain's owner (a fast executor) appends rate changes as events (time dilation is a rate event). Every obligation deadline is `(domain, value)`; the timer service converts it to the node clock through the domain's current mapping and re-arms when a rate event commits. The node's own domain is the identity mapping, so 5.1.1's deadlines are unchanged in behaviour. This keeps rule 4 (only the node's clock drives timers), makes "game time" auditable (every rate change is in the log), and gives the simulator nothing new to model beyond its existing virtual clock. **Served in 5.1.1**: deadlines typed as `(domain, value)` in the obligation schema with only the node domain populated.

### 4.7 Claims and leases: competing consumers and fencing (C, D5, E3)

CLIENTS §4 lists competing consumers as absent; Wild Earth's agent queues, helm's `work claim`, MMO zone leases and tile ownership all need the same thing. A **claim** is a transaction on a queue stream's entry creating an obligation `(holder, incarnation, expiry (domain, value))`; it is released by evidence (the result's commit, which names the claim) or at expiry (the entry becomes claimable again, an attempt counter increments, a declared limit moves it to a dead-letter stream). The incarnation is a fencing token: a result or checkpoint carrying a superseded incarnation is refused `fenced`. A **lease** is a claim on a scope (zone, tile, match) renewed by the holder's checkpoints. Claims are charged to the claimant (EXEC rule 5) and bounded per principal. This is one schema and two transactions in the existing obligation machinery, not a new subsystem.

### 4.8 Large objects: one identity, an outboard tree, range leases (B/C, E5)

Record in STORAGE's format notes (owed with STORAGE §4 decision 4's "portable source verification ... is a separate contract") that a payload's **content identity is one root per object**, its per-block verification material is an **outboard tree stored as a payload** (not as engine rows), and the engine holds one row plus an extent map per object. A range read acquires an object lease on the object (STORAGE decision 2) and streams a bounded window. A **have-ranges** projection per object records which ranges this node holds (for resumable peer exchange); BP custody of a large object is per fragment, with fragments verified against the outboard tree on arrival (E5). Measurement M3 in §5.3 tests it.

### 4.9 What must not go into fn2

The tick loop and anything scheduled by wall time; prediction, rollback, reconciliation, lag compensation, interpolation; physics and pathing; interest management and fog of war (per-tick filtering belongs to whoever ticks; fn2's selection-versus-fan-out is the durable analogue, not the same mechanism); rendering, assets' decoding, perception; game verbs and rules; matchmaking *algorithms* (lobbies may be live streams; the matcher is a client); voice and media (Discord's SFU pattern: control state may live in fn2, media never); anti-cheat heuristics (evidence and verdicts may be records; detection is a consumer); per-tick or per-frame writes of any kind; and any promise of latency below one scheduler visit for live items or one commit batch for durable ones. Each of these, placed inside fn2, would either relax an EXEC rule for every principal or turn fn2 into Darkstar.

## 5. Closing

### 5.1 The recommended plane architecture, in one page

fn2 stays what EXEC and STORAGE decided: one deterministic executor over bounded machines, one ordered semantic event journal per commit domain, content-named payloads, folds, obligations and signed checkpoints. That is the **slow plane**, and it is the only place a durable fact exists (L1). Every game in §1 that succeeded kept exactly this kind of state (results, characters, trades, ownership, content) in a transactional store and nothing else there; the one design that put the per-event game loop into the store (Darkstar) did not survive.

Above it, fn2 grows three things, each as a generalization of something it already has. The **projection plane** is the fold declaration generalized to `defprojection` (sources, interpretation, initialization, coverage, mode, read fallback) with a published frontier: in-transaction projections are complete by construction; after-commit and external ones answer only through their frontier, and a reader may select, wait for the frontier, or accept staleness by name. INBOX's `inbox` fold and its `cov` are the first instance; Naiad's frontiers and Materialize's timestamped reads are the precedent. The **live plane** is the subscription machinery with the durability promise removed and the removal typed: streams carry a class (`durable | live | ephemeral`), live items carry `(epoch, seq)` and a happened-after commit position, ephemeral keys carry leases, overrun and restart are gaps with causes, and the same edges, wake and final frontier check serve all classes inside the same executor (rule 8 relaxed, nothing else). The **fast plane** is not fn2 at all: a separate tick executor (per zone, match, instance or tile) that opens from fn2 at a pinned version under a fenced lease, commits consequences as ordinary transactions with operation identity and withholds their confirmation until fn2's outcome (L3, Durable Objects' output gate), checkpoints on its own cadence as `external-checkpoint` records, and optionally logs its inputs in batches so replay, audit and recovery are fn2 consumers (Guild Wars, Age of Kings).

Six laws keep the planes honest: authority flows down; every upper state is reconstructible from below plus a declared loss; output gating; loss is typed; positions never mix; time is declared. The fast plane may relax wall-time scheduling, durability per tick and transport reliability; the live plane may relax durability; the projection and slow planes relax nothing.

For the five clients: **helm** sees no change except, later, a served live class for presence; an **RTS** puts its match stream, result and ladder in fn2 and its turns in a relay; an **FPS** puts results, demos and evidence in fn2 and everything else in its server; an **MMO** puts characters, trades (with escrow obligations), zone checkpoints and directories in fn2 and its zones in fenced fast executors; **Wild Earth** is the client that exercises fn2 hardest, through gigabyte content-named packages with outboard verification trees, provenance records, agent work claims, BP custody for field builders, and catalog projections, with its tile simulations as fast executors outside.

The cost of all of this in 5.1.1 is fields and record kinds, not subsystems: a class on the stream kind, a generalized fold declaration, three datagram primitives specified and simulated, a checkpoint record kind with two refusal words, claims and leases on the existing obligation machinery, `(domain, value)` deadlines with only the node domain populated, and the large-object reading of STORAGE's payload design. Each later plane is then a new machine kind and a served row, with no format change, no wire change visible to an existing client, and no change of authority.

### 5.3 The three measurements that would validate it

Performance is published, never a gate; each measurement below has a correctness criterion and a set of published numbers.

**P1: a lockstep RTS replay driven through fn2's journal.** Take an open-source lockstep RTS whose replays are command logs (0 A.D., whose replays are command files, or a Spring-engine game such as BAR; both are deterministic lockstep engines with documented desync histories, HN 29154151, HN 50049476). Ingest an 8-player, one-hour match as a match stream: a header record naming the simulation's content identity, map and seed; one input-batch record per second of turns (5 turns per record at 200 ms, *derived*: 3,600 records per match-hour); a state-digest record every 60 seconds; the result as a transaction. Kill the node at every write, fence and install boundary during ingest (STORAGE §7's death cuts). A consumer streams the match back into the engine's replay mode. **Correct when**: every acknowledged record survives every death cut; the replayed game's state digests equal the recorded ones at every checkpoint; a deliberately perturbed record is detected by the first digest after it. **Published**: journal bytes per match-hour, commit batches, isolated vs batched ack cost (STORAGE M5), time to stream a full match to a consumer, and the same numbers at 1,000 concurrent matches (5,000 turns/s, 1,000 records/s, *derived*).

**P2: a live stream at 10,000 items/s with wake latency.** In the simulator first (deterministic, exact counts), then on the native host: 100 live streams at 100 items/s each (10,000 items/s total), 30 consumers with 10 live edges each plus one presence-like scope with 1,000 subscribers, one consumer stalled, and a concurrent durable workload (akapug's 7,000-row day replayed, INBOX §5.3). **Correct when**: within an epoch every edge receives every item in order or a gap covering exactly the missing range; the stalled edge receives `live-overrun` gaps and never blocks the producer; a restart yields `epoch-reset` and no old-epoch sequence; the durable workload's commit and wake latencies are statistically unchanged with the live load on (isolation, EXEC rule 5). **Published**: wake-to-reply p50/p95/p99 for live and durable edges, executor turn share of the notification class, pool bytes in rings, items and bytes per wake.

**P3: a 2 GiB tile package exchanged between two fn2 nodes.** Node A ingests a 2 GiB package (a real PMTiles or 3D Tiles archive of one 10 km tile, or a synthetic one of that size); node B fetches it by peering, then again by BP with fragmentation. Kill B at 50% and resume; flip bits in one range on the wire; serve a concurrent range read (one level of detail) to a client from A during the transfer. **Correct when**: B's object has A's identity; the corrupted range is detected and refetched alone; the resumed transfer re-sends only missing ranges; the engine holds one row plus an extent map per object on both nodes (not 32,768); the pool occupancy never exceeds the declared window. **Published**: ingest throughput and hashing CPU per GiB (against the ~0.35 s/GiB-per-core arithmetic of §3.2, which this measures), outboard tree size, metadata bytes per object, bytes re-sent after resume, transfer time over peering and over BP.

### 5.4 The five decisions for ember (each with a recommendation)

1. **Adopt the four planes and the six laws, with the fast plane always outside fn2** (a separate tick executor that opens under a fenced lease, commits consequences output-gated, and checkpoints as records): *recommended yes*. The alternative, a tick inside fn2, is Darkstar's design and relaxes EXEC rules 4, 5 and 8 for every principal.
2. **The live plane lives inside fn2's executor as a durability class on streams; 5.1.1 carries the fields, the reference model and two simulator scenarios, and the first served live kind (helm presence and seat activity) follows 5.1.1**: *recommended yes*, with the alternative (serve presence in 5.1.1) costing one machine kind and the P2 measurement before the release.
3. **One `defprojection` form replaces the per-fold declarations in C4, with a published frontier and the read fallbacks `select | wait | stale-ok`**: *recommended yes*; it is the inbox fold's `cov` made general, and it is what Wild Earth's catalogs, an MMO's character sheets and an RTS's ladders need without new mechanisms.
4. **Large payloads have one content identity per object, verification material in an outboard tree stored as a payload, and one engine row plus an extent map per object** (never a named row per 64 KiB block): *recommended yes*; it answers the hashing question (hashing is about a third of a second per GiB per core; naming per block is the cost) and is what gigabyte tile exchange and BP custody of large bundles require.
5. **Put the game-facing mechanisms in the format now, served later**: the `external-checkpoint` record with `fenced` and `checkpoint-conflict`, claims and leases with fencing incarnations on the obligation machinery (also closing CLIENTS §4's competing-consumers gap for helm and Wild Earth's agents), deadlines typed `(domain, value)` with a time-domain fold, and datagram primitives 22-24 specified and simulated: *recommended yes*; each is a few fields or words now and a format migration later.
