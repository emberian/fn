Read `FN2-SEAT-COMMON.md` first. Branch `fn2/h-harness`. You are the owner of the suite ember asked for: "a behavioural and property-based test suite that exercises the full surface of our software". Its design is `/Users/ember/dev/fn/build/coordinator/fn2/RELEASE-PLAN.md` §2 (read whole; Astra's marks included) with §1's surface table; the review's finding 10 in `fn2/REVIEW-20261028.md` (the surface suite had no owner); the carried natives in `fn2/QUARRY.md` (87 black-box modules) and fn1's `tests/fuzz_nntp.py` (the seeded model-differential fuzzer) and `tools/load` on origin/dev. You touch nothing under `fn2/books`, `fn2/sim` or `fn2/host` (layers A-E own those); you build the harness that layers D and E will run against from their first served verb.

## Contract (the plan's H1-H3, then the suite's skeleton)
1. **H1, the `Node` adapter inventory**: for each of the 87 carried natives, what it needs from the node (`fn.toml` keys, `fn --fn operator CONFIG run` shape, the control socket, developer selectors, fixtures), and the one adapter interface (`Node`: start, stop, config, socket, control, kill-at, observe) that fn2's host must provide so the modules run unchanged. Deliver `fn2/tests/harness/node.py` with a fn1 backend (so the inventory is verified against the real fn1 node on the laptop) and the fn2 backend as a stub that names what layer D must provide.
2. **H2, the spec-derived reference model**: a Python model of the NNTP surface from `specs/nntp.md` and RFC 3977/4643/6048 (commands, reply codes, multiline framing, the group/article/number semantics, authentication state), to serve as the oracle for property-based and differential tests; validated by running fn1 under it (differences recorded as either fn1 bugs or spec ambiguities, with the spec line).
3. **H3, the history observation model**: Jepsen/Elle-style history checking for the consumer protocol (register/poll/ack/position/rebase/wait: at-least-once delivery, forward-only durable ack, redelivery before ack, no lost wake) and for durable acceptance under crashes (an acknowledged POST survives any crash cut); the checker consumes observation logs the simulator and the native harness both emit.
4. **The suite skeleton**: `fn2/tests/surface/` with one directory per surface family from RELEASE-PLAN §1 (nntp, consumer, operator, web, peering, bp, tls-auth, config-limits, store-ops), each holding: the property-based form (stateful property tests against H2's model; fuzzing from the wire grammar; crash and fault schedules), the example-based form (the carried natives, conformance fixtures), and the performance rows; a runner that selects by family and by box (laptop per commit; hbox nightly); the reporting shape (beside the profile, never a gate on performance).

## Acceptance
The fn1 node on the laptop passes the adapted natives through `Node` (count them); H2's model agrees with fn1 on the fuzzer's corpus except a recorded list; H3's checker finds the injected violations in a synthetic history and none in fn1's consumer natives' logs; the skeleton runs empty for fn2 (every family present, every test skipped with the reason "layer D/E not yet serving"). Report counts and the list of what layer D must provide.
