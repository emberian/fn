# fn2 orientation (present state, 2026-10-28; rewritten whole, never appended)

fn2 is the bottom-up, semantics-first rebuild of fn, built in place in this repo and swapped to the root when it serves. The old tree is frozen (origin/dev = 6521f18c4, the breaking cut plus the gate work; it still builds and gates green, and it is the quarry). - "semantics-first and not worry as much about the proofs until we've actually gotten the implementation into a state where we WANT assurance from it"; "we only need to demonstrate that our TOPLEVEL THEOREMS aren't vacuous".
- "extremely methodical ... from the bottom up ..... so that it's actually comprehensive and not piecemeal".
- Nothing lifts whole up front: "You think you can take those books whole? are they actually worth taking? what happened to our bottom-up philosophy :) hopefully as we take them we can polish them up."
- "'TLS with our own crypto' there was never any reason to be doing our own crypto in ACL2. that requirement isn't a real requirement, we should just lose it." (OpenSSL, libsodium and vendored ML-DSA via FFI stand.)
- Performance: "is **this** [pure step/state/event/effects] why we're fundamentally bottlenecked ...? are you familiar with 'tigerstyle'"; "we've become WAY too empirical/measurement-driven, over measurements that don't actually make much sense with regards to the ultimate composed system overhead & performance".
- Purpose: "a high performance database node for the robigalia operating system someday ... the generalized redis/postgres for the datamodels we're reaching for"; earlier: "this is the persistent event log between systems"; "foundational orthogonal persistence".
- The twenty sentences a designer must not violate: fn2/EMBER-ARCHITECTURE-WORDS.md, closing section.
- Process: "we have too many parallel lanes ... iterating one statement at a time instead of iterating across the whole system and using mental simulations"; few seats; design whole before building; batch verification; "be reasonably light on the subagents"; kimi for bounded analysis and merges, Sonnet for staged build work, Opus for orientation and judgment, Fable to coordinate.

## The bottom-up order (each layer: one typed boundary of about a dozen operations, settled and simulated before the next starts)
0. Execution model (in consultation now). Decides: batch-as-step or event-as-step; the core/host boundary; where per-connection state lives.
1. Bytes: one byte pool with ownership states (workspace / leased / handed), handles, no allocation after init; the octet list only in the logic.
2. The host primitive set (≈21) and the simulator that implements the same set; the fault model from the papers table; deterministic simulation as the primary test from day one.
3. Durability: the log of wire-form records on the byte pool; group commit; checkpoint by dirty page or root; recovery over the tougher crash model. (Start from the existing crash/log models; extend.)
4. Index and catalog as fixed-width columns over the pool; the Message-ID table rebuilt at open, never persisted.
5. The core machines over the three DSLs (records/columns, machines, command grammars): NNTP command surface, POST/acceptance/identity, consumer cursors and wait, operator control; the web reader inside the node.
6. Peering and BP/TCPCL above the core.
7. Then assurance, in the order the automation routes suggest, for the top-level theorems only.
Serve from the first week (greeting, GROUP, ARTICLE, POST over the new store) and pass natives incrementally; a tree that does not serve is a design doc.
