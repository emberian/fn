## Chapter 1. Unit of state: one semantic event history, keyed objects as folds in the same stream

### 1.1 The decision as a claim

**Claim.** fn2 has one durable unit of state per commit domain: a totally ordered sequence of typed semantic events `H = e_1 … e_n` (article acceptances, withdrawals, cursor acknowledgements, obligation creation and release, evidence, configuration), stored as a retained prefix summary plus a suffix, `State = Fold(Summary_k, Events_{k+1..n})`. Every mutable keyed object (a consumer cursor, an account balance, a pin, a signer head, a live limit) is a *fold* over that sequence: its current value is a function of the events, and its updates are events of the same stream carrying `(principal, operation identity, expected prior version, mutation, stable outcome)`. A repeated operation (same principal, same operation identity) returns its recorded outcome within a declared retry contract rather than executing again. Coalescing updates is allowed only where every promised result survives. Replacing `Events_{1..k}` by `Summary_k` is not a storage checkpoint but a semantic act that needs an identified *sufficient-summary rule*: every observation the retained contract permits must give the same answer over `Fold(Summary_k, suffix)` as over `Fold(Events_{1..n})` (the Review §1; D13). Initially the rule retains exact identity and obligation evidence.

**What it buys.** One durability protocol, one recovery, one accounting (the Study §E, §K): acks, charges and articles share a flush, a chain, a root. Visibility pins are numbers (chapter 2). The checkpoint is a fold, so the storage keystone fn1 already proved (`fn-owner-recover-from-checkpoint-equals-full-recover`, `books/owner-checkpoint-open.lisp`) is the shape of the whole system's recovery theorem. Peers and consumers pull by position. "The log overrides" (issue #17) holds by construction. "Last value per key" is a sufficient summary for a fold's current value only when commit order is semantic order (Kafka's KIP-280 is the counterexample, §1.2), and one commit stream per domain gives exactly that.

**What it gives up.** (a) Keyed state cannot be read at old versions without versioning the fold (chapter 2 keeps folds latest-only; a historical fold question is answered from a retained snapshot plus replay, never by versioned entries). (b) A total order is a serialization point per domain. It does not by itself forbid parallel *preparation* or independent-key work, which is executor policy [Astra]; at fn's rates, 10^2–10^3 commits/s, nothing is lost [D, Envelope §1.5]. (c) Every mutation pays an event's fixed cost: an isolated durable ack is one journal isolation unit `S` (4 KiB proposed), not 40 B (the Review §9), so the fold saves bytes only under overlap. (d) History grows without bound unless summarized, and summarization is a semantic obligation, not a storage one. (e) Each fold's interpretation, initialization and coverage become part of the state's identity (`fold-id`): changing them is a migration with its own rule (§1.4, tradeoff 1).

### 1.2 State of the art

Systems that made the same choice, and what happened to them:

- **Raft and its state machines (etcd, ZooKeeper's ZAB).** The replicated log is the authority; the application state is a fold; snapshots replace a prefix. Raft's linearizable client semantics keep, per client session, the serial number and response of the latest request (the extended paper's §8), generalized in Ongaro's thesis §6.3 to concurrent requests by retaining response pairs until the client acknowledges a sequence-number frontier; sessions expire. The dedup table is state and is in the snapshot: a retry after a snapshot still gets the recorded response. Two cautions [Astra]: Raft's session protocol is *not* an eternal outcome oracle (bounding outstanding requests changes which retries remain supported; expiry retires the rest), and the direct precedent for fn2's problem is **RIFL** (Lee et al., SOSP 2015, `lee2015-rifl-implementing-linearizability-at-scale.pdf`), which treats durable RPC results, their association with the objects they mutated, migration of that association, and its garbage collection as one protocol. RIFL's lease-based client identity and its "completion record stored with the object" are the two mechanisms decision 1 needs to name.
- **FoundationDB.** The log servers hold the versioned, durable commit stream; storage servers are derived folds applied in version order; the log is popped once storage has durably materialized past a version (`zhou2021-foundationdb-unbundled-transactional-kv-store.txt` §2.4.3–2.4.4). That is a journal/materialization split of decision 1's kind, and an analogy only [Astra]: FDB's log is partitioned by tags, each storage server advances its own durable frontier, and storage servers fetch mutations speculatively before log durability and discard them at recovery, so there is no single checkpointed semantic prefix. What deployment taught about retries: a commit whose reply was lost returned `commit_unknown_result`, every application built idempotency by hand for years, and the later "automatic idempotency" (an idempotency id stored with the commit) is documented as experimental and does not resolve `transaction_timed_out` or `cluster_version_changed` [Astra]. fn2's decision puts recorded outcomes in the state from the first format, which is the right order: it is a property of the history, not of a client library.
- **Kafka.** A partition log is the authority; compacted topics keep "at least the last update for each primary key" (`kafka2026-docs-design.md`, "Log Compaction"); consumer offsets are themselves a compacted keyed topic, so cursors-as-folds has a decade of production behind it. The deployment lessons are all about *tombstones*: (i) a tombstone is removed after `delete.retention.ms` (default 24 h), so "it is possible for a consumer to miss delete markers if it lags" (the same doc); Kafka's contract tolerates a stale downstream materialization and never promises permanent refusal of a key, so this is a different contract rather than an unsound one [Astra], but it is a contract fn cannot have for identities that may be re-offered indefinitely; (ii) KAFKA-8522 (2019, fixed 3.1.0): under low throughput repeated cleaning "continuously update[d] the timestamp of the oldest segment resetting the countdown", tombstones "build up … forever", and the root cause was that the horizon was *estimated from segment mtime*, a proxy that could retain tombstones too long or too briefly; the fix (KIP-534) records an explicit `deleteHorizonMs` in the batch (`kafka2026-jira-kafka-8522-tombstones-survive-forever.txt`, `kafka2026-docs-kip-534-retain-tombstones.txt`); (iii) KIP-280: "keep the last value per key" kept the *wrong* state when producers raced, because offset order was not semantic order (`kafka2026-docs-kip-280-enhanced-log-compaction.txt`). Three lessons: state the summary rule over observations (can anything re-offer this key?), never over time or segments; compute a release or summary rule from recorded facts, never from a proxy; and say that commit order is semantic order.
- **Datomic.** Immutable facts `(entity, attribute, value, tx, added?)`; the transaction log is the truth, every index is derived, and there is a single writer (the transactor). The only destructive operation is *excision*: "the complete removal of a set of datoms matching a predicate", meant for privacy and domain retention and "unsuitable" for correcting errors; the request is transactional but its effect is not (it runs at the next indexing job and also edits the transaction log); excision attributes cannot themselves be excised, so "every excision creates a permanent record … forgetting and remembering that you forgot"; and its cost is proportional to the whole database (`datomic2026-docs-excision.txt`). Read precisely, Datomic is a *counterexample* to preserving historical observations [Astra]: the permanent record is the predicate that might have matched, not an inventory of the erased identities, and the removal runs outside the history's timeline. It supports "remember that forgetting occurred" and nothing stronger; fn2's exact-identity contract has to be carried by the retained identity set, not by an excision record. Datomic's `since` filter is decision 2 in miniature: identity is usually asserted in an entity's first transaction, so a `since` view "may not be able to see the information needed for lookup", and the idiom resolves identity against the unfiltered database and values against the filtered one (`datomic2026-docs-filters-as-of-history.txt`).
- **Event-sourcing practice.** Fowler: application state "is purely derivable from the event log, you can cache it anywhere you like", and replay is deterministic only if every external query's response is remembered and replayed ("the response to every external query needs to be remembered"), while external *updates* must be disabled during replay (`fowler2005-docs-event-sourcing.txt`, "External Queries", "External Updates"). Young: a rolling snapshot is "a denormalization of the current state of an aggregate at a given point in time", "just a heuristic", "conceptually the event stream is still viewed in its entirety", and "there is no delete" (`young2010-cqrs-documents.txt`, pp. 31–35, 44). Two things follow: snapshotting never licensed discarding history in this tradition, so fn2's sufficient-summary rule has to be justified on its own (the Review does); and the deployment pains are two, not one [Astra]: schema evolution of events and folds (§1.4, tradeoff 1) and replaying interactions with external systems (the addition at the end of §1.4). (Young's later *Versioning in an Event Sourced System* could not be fetched.)
- **Redis.** The append-only file is replayed at open; a rewrite synthesizes a minimal command sequence that reconstructs the dataset, and the modern multipart AOF is explicitly a base snapshot plus incremental files, which is the `Summary_k ⊕ suffix` representation in production [Astra]. Its limitation is exact and worth stating exactly: the rewrite preserves the stored dataset (including any dedup records or obligations the application keeps *as keys*, and expiry metadata) and does not preserve discarded command history. It is a sufficient summary for Redis's contract and would be one for fn2's only if every retained observation were a key, which is close to what "retain exact identity and obligation evidence" means.
- **Git.** Content-addressed objects, reachability GC, and shallow clones: a shallow boundary retains the boundary commits' parent references while dropping the ancestors' content, the "identity survives, content does not" shape at the level of whole histories, though not an inventory of every omitted ancestor [Astra].

Systems that made the opposite choice (mutable state is the authority; a log, if any, is physical redo):

- **Postgres.** The heap is the authority; the WAL is physical redo; logical decoding *derives* an event stream from it. Its tuple-version metadata needs maintenance with a famous failure mode: transaction-id wraparound, the finite 32-bit xid plus visibility rules forcing a freeze discipline even on unchanged tables, which took down Sentry (2015, HN 9936711, `sentry2015-docs-transaction-id-wraparound.txt`), Mandrill (2019, `mailchimp2019-docs-mandrill-outage-postmortem.txt`) and Joyent's Manta (2015, `joyent2015-docs-manta-postmortem.txt`); the Postgres 14 failsafe is a mitigation (HN 26756568). The inference to draw is narrower than "mutable authority accumulates debt" [Astra]: wraparound follows from the finite identifier representation (the Study §L point 3), its debt is observable through documented age counters, and fn2's latest-only folds have maintenance of their own (run compaction, checkpoint advance, safe allocation reuse). What the three post-mortems do establish is that maintenance debt stops a node when it reaches a hard limit and that in every case the operators could not see how much remained or how fast it was being paid (chapter 3, tradeoff 4).
- **LMDB.** The B+tree is the state and there is no history at all (`chu2012-lmdb-memory-mapped-database-openldap.txt`); peers, consumers and auditors get nothing to pull. fn1's own page store is this.
- **CRDT replicated sets.** Shapiro et al. split garbage collection into *stability* problems (an update's metadata can go once every concurrent update has been delivered, detectable by vector-clock minima "provided the set of replicas be known and that they not crash permanently") and *commitment* problems (removing 2P-set tombstones or resetting counters needs "atomic, unanimous agreement … 2PC or Paxos Commit") (`shapiro2011-comprehensive-study-crdts.txt` §4.1–4.2). Bieniusa et al.'s optimized OR-set removes explicit tombstones *without* waiting for global stability, by a causal context that still distinguishes observed from unseen additions, bounded `O(|elements|·n + n)`, and notes that when a map key is removed "value can be discarded, but the corresponding (e, n) pair(s) must remain" (`bieniusa2012-optimized-conflict-free-replicated-set.txt` §4.2, fn. 1) [Astra, correcting the draft]; delta-state designs do the same with a causal context (`almeida2016-delta-state-replicated-data-types.txt`); and Bauwens notes "if one node doesn't issue any operation, no causal stability can be determined at any node" (`bauwens2019-memory-efficient-crdts-dynamic-environments.txt` §3). The precise reason none of this transfers [Astra]: an OR-set *permits* a fresh add after a remove, and fn's permanent refusal of a re-offered identity is a different specification; the obstacle is unrestricted re-offering of externally chosen identities (Message-IDs) with no causal namespace to summarize, not merely that peers are not replicas. The CRDT trick is still the right shape: payload goes, the identity pair stays, and a summary is a compact object answering one observation exactly. fn2's rule should say which tier each discard is in: *stable* discards (a fold's obsolete versions; an expired op-identity window) need only local observation; *reset* discards (an identity, an obligation) need evidence no holder can re-offer, which on a single node never arrives.

### 1.3 Theoretical optimal

**The sufficient summary has a canonical target, not a storage optimum.** Fix the contract's observations: future *requests* and environment observations, not only already-selected events [Astra], since the summary must preserve which requests succeed and which events can arise (duplicate check on a Message-ID; the status of an obligation; the recorded outcome of `(principal, op-id)` within its retry contract; a consumer's position and delivery contract; each fold's current value; the historical selections chapter 2 supports). Two histories are *O-equivalent* if every observation answers the same on both, now and after any future continuation. The minimal sufficient summary of `Events_{1..k}` is the Myhill–Nerode class of the prefix in the automaton whose inputs are future continuations and whose outputs are `O`. This gives the decision a precise *correctness characterization*: a summary rule is sound iff its summary determines that class. It is not an executable audit [Astra]: the quotient can be infinite and its equivalence undecidable, and uniqueness is of abstract states, not byte-minimal representations. What it does supply is the proof shape (§1.5: an observation-preserving simulation) and three consequences.

1. *Exact identity cannot be summarized below the identity set, but the set is compressible.* The observation "is Message-ID `m` present, as exact octets" over `n` identities from a universe of size `u`, with zero false positives *and zero false negatives* [Astra], needs at least `log2 C(u, n)` bits (the information-theoretic membership bound; for an approximate structure with false-positive rate `ε` the bound is `≈ n·log2(1/ε)`, Bloom filters sit within `log2 e ≈ 1.44` of it, Pagh, Pagh and Rao reach `(1+o(1))·n·log2(1/ε)`: `broder2004-network-applications-bloom-filters-survey.txt` "A Lower Bound", `pagh2005-optimal-bloom-filter-replacement.txt`; a cuckoo filter beats a Bloom filter below `ε ≈ 3%` and supports deletes, `fan2014-cuckoo-filter.txt`). So the Review's "a hash may reject, never decide" is exactly right, and the draft's inference that this costs the strings themselves was not [Astra]: mean textual length is not entropy, Message-IDs share domains, prefixes and structure, and the requirement is *losslessly recoverable* exact octets, which the engine may store compressed. A *commitment* to the set (issue #17's single `identity-commitment` digest) proves nothing about one identity; to make duplicate refusal *checkable by a peer* after bodies are gone the claim needs an authenticated structure with membership and non-membership proofs. State the proof interface first [Astra]; an ordered Merkle tree over the exact identities (`O(log n)` proofs) is one construction, a sparse Merkle tree (depth tied to key width) another. Chapter 4 takes this up.
2. *Operation identity is unbounded unless the retry contract is.* To answer "repeated operation returns its recorded outcome" for retries that may arrive at any later time, the state must carry information growing with the number of independent outcomes, though not necessarily one literal entry each (structured identifiers and reconstructible outcomes compress) [Astra]. The levers are RIFL's and Raft's: bound outstanding operations per principal (then the table is `O(principals × window)`) or bound the retry lifetime (a sliding window). A finite contract has a second obligation the draft missed [Astra]: *retired* identities must be fenced so that a stale request cannot become a fresh execution. fn2's "declared retry lifetime" per schema (the Review §C) is therefore a retention class with a per-principal bound, a named exhaustion, and a fence on retirement.
3. *The RUM conjecture frames why a summary rule must exist at all.* Athanassoulis et al. conjecture that an access method bounding two of read, update and memory overhead lower-bounds the third; their Proposition 2 is the pure-append case: update overhead 1.0 implies read and memory overhead unbounded (`athanassoulis2016-rum-conjecture.txt`, p. 463; a conjecture, not a theorem). An unsummarized history is that case. Dayan and Idreos add the corollary for the engine under the folds: point lookups, long range lookups and worst-case space amplification are dominated by the *largest* level, so the merge effort that matters is at the oldest runs, which is where the summary cut falls (`dayan2018-dostoevsky-better-space-time-tradeoffs-lsm.txt` §1; `dayan2017-monkey-optimal-navigable-kv-store.txt` for filter allocation that makes absent probes `O(e^{-M/N})`).

**The fold equation is exactly as cheap as the fold is pure.** `State = Fold(Summary_k, Events_{k+1..n})` holds only if the fold is a deterministic function of the events; every source of nondeterminism (clock readings, random nonces, configuration, the responses of external systems) must itself be an event, as Fowler's gateway rule says and as ember ruled on 2026-09-27 ("the log can contain configuration events that set seeds and nonces"). That is not a cost; it is what makes the summary equation provable at all.

**Per-event cost: four quantities, one floor each** [Astra, correcting the draft's single "device floor"]. (i) The journal isolation unit `S` (4 KiB proposed) is a *format* parameter chosen for the damage radius, not a hardware constant. (ii) The 4.0 ms is a *measured* append-plus-`fdatasync` median on one stack [M, Envelope §1.1], not a bound. (iii) Batching is a *policy*: overlap (group commit; at 2.4 acks/s mean, `b ≈ 1` [D]) or a deliberate linger (Kafka's `linger.ms`). (iv) Hardware changes the fence, not the padding: a power-loss-protected NVMe makes a flush ≈ 0.02–0.1 ms [A] and may thereby *reduce* incidental batching and *raise* padding per operation; persistent memory's 8-byte store atomicity is a different thing from cache-line writeback and persistence ordering (`raad2020-persistency-semantics-intel-x86.txt`). So a lower-latency tier exists and is hardware plus a smaller `S`; a *weaker* tier (acknowledge before the fence, Redis's `appendfsync everysec`) exists on the same hardware and must change the promise explicitly. The information-theoretic minimum per ack, `log2(positions) + log2(consumers)` bits, is a few bytes; everything else is the cost of durability and identity.

**Distance from optimal.** Decision 1 sits at the canonical target for the authority (one history, folds derived) and at the format-and-policy floor for per-event cost. It is below the target in one place: the summary rule is stated as a goal ("retain exact identity and obligation evidence") and not against an enumerated observation set with a simulation obligation, so no one can yet argue that a given cut is sufficient.

### 1.4 Tradeoffs not yet on the table

1. **Fold migration needs an explicit initialization function and coverage boundary.** A summary is sufficient *for the folds and observations that exist when the cut is taken*. A fold installed later may be initializable exactly from the summary (`F_new(H) = g(Summary(H))`), or bootstrappable from a retained snapshot plus suffix, or may genuinely need history that is gone [Astra, replacing the draft's dichotomy]. The rule: every fold names its interpretation, its initialization (from which summary or snapshot, by which function) and its coverage (the oldest event it answers for); a new or changed fold may use an existing summary only through a valid bootstrap or migration rule, and unavailable history is never implied. A large migration is a resumable maintenance operation under the execution model's budgets. Cost model: re-fold `O(retained events)`; migration `O(fold size)`; both named in the fold's declaration.
2. **Consumers across a cut need two contracts, not one default.** A consumer cursor is a position in the event sequence; Clients §2.1 already specifies non-pinning consumers, explicit `unavailable` gaps, rebase and evidence-gated obligations [Astra]. What is unspecified is the history-cut contract: replacing missing events by a state does not preserve an event-delivery promise merely because the gap is named. Offer two subscription contracts explicitly: *retained delivery* (the consumer's unacknowledged range is an obligation the cut must honour, charged to the consumer's principal, with an inactivity bound after which it lapses with a named outcome, chapter 2 tradeoff 4) and *state bootstrap with gaps* (the consumer may be rebased onto the summary and told so). Retaining the metadata a consumer needs does not require retaining every payload or unrelated event in the prefix.
3. **Fold maintenance is shared cost with three separate questions.** Rule 5 already requires an allocation rule for shared costs and the Review's schema already gives outcomes a retry lifetime [Astra]. The three remaining questions are different: *admission* (a reservation per principal for unexpired operation identities, refused by name at exhaustion), *expiration work* (who runs the window's retirement and under which calendar share) and *charging* (retained bytes and maintenance charged to principals within the one shared ordered-run engine; separate per-principal indexes are not needed). Charging alone bounds neither work nor storage; reservations do.
4. **No `as-of` on folds, said aloud.** A Merkle event log and a signed checkpoint claim make time-travel look free; versioned fold entries would be MVCC with its retention debt (chapter 2). Latest-only is already the Review's schema; the sentence to add is that a historical question about a fold is answered from a retained snapshot plus replay of the suffix, charged as maintenance, never from versioned fold entries, and that such replay coverage is optional and separate from the pinned article metadata decision 2 supports [Astra].
5. **Coalescing the value does not retire the evidence.** Two advances of one cursor in a batch coalesce to one delta in the fold; each operation's promised outcome is still evidence that must survive (the Review's ruling). The journal cost of a hot key is therefore bounded below by its operation-result evidence, which may share encodings but cannot vanish, and the fold write saved is real but smaller than the delta count suggests. The M5 instruction [Astra's wording]: "coalescing the materialized value does not, by itself, eliminate promised operation-result evidence"; count the two separately.
6. **Commit domains.** "One ordered commit stream per storage domain" leaves open what a mutation touching two domains is. The first format should have one domain per node, with the rule stated as *each atomic mutation belongs to one commit domain* [Astra, replacing "folds never span domains"]: a derived read-only aggregate may span domains under an explicitly weaker consistency contract, and offering cross-domain atomicity later requires a protocol (a shared coordinator or atomic-commit substrate on one node; two-phase commit only across independent domains).
7. **Erasure against retained exact identities: a changed contract, not a placement option.** The draft proposed that, after reclamation, an operator-chosen class could retain only a collision-resistant digest of the Message-ID (pseudonymous, 32 B) and answer duplicate checks under A-CRYPTO. Astra's objection is decisive under the present contract [Astra]: after `m`'s octets are gone, a retry of `m` and a different `m'` with the same digest are indistinguishable, so the collision cannot be *detected and quarantined* (fn's D25/OBJ-001 contract), only assumed away; quarantining every digest match would quarantine genuine retries; and an unkeyed digest does not assure erasure, since guessable Message-IDs remain testable. The option is coherent only as a deliberately revised identity contract (probabilistic identity under a named assumption, with changed duplicate/conflict outcomes and a keyed digest if testing must be resisted), and it is removed from decision 1's amended wording. It remains in the closing section as a contract question for ember, because "can this node forget an identity" has no other answer.
8. **Operation identity needs request binding** [Astra, addition]. Specify the outcome when a principal reuses an op-id with a different mutation or expected version: a retry returns the recorded outcome; a contradictory reuse is a named refusal with the original binding as evidence. Summarizing only `(id → result)` erases the evidence that distinguishes the two; the summary must keep the request digest beside the outcome.
9. **External effects need durable intent and independent acknowledgement** [Astra, addition]. Replaying a fold must not resend an effect (a BP bundle, a wake, a peer offer) as if new. The history can atomically record an obligation or outbox entry; it cannot atomically commit a recipient's action. This is Fowler's "external updates" problem and fn's retention ledger is its answer: effects are obligations released by evidence (chapter 3), never side effects of a fold.

### 1.5 Principles from logics and deployments: proving it later

- **DaisyNFS supports the decomposition and prices it honestly.** The commit-batch machine (rule 8) is the transaction layer proven once against the tough model; every fold is sequential code over it, with the per-fold obligation one equation, `materialized_f = Fold_f(prefix)`, re-established at `install` and at checkpoint (`chajed2022-daisynfs-verifying-nfs-server.txt`; `chajed2021-gojournal-verified-concurrent-journaling.txt`). The honest price [Astra]: DaisyNFS reports roughly 20× proof-to-code for the transaction system against 2× for the sequential filesystem above it, and its sequential reasoning depends on GoTxn's verified interface and restrictions on shared-state access. fn2 must build the analogous abstraction across preparation, dependency writes, installation, recovery and reclamation, where the abstract history and the concrete durable representation are very different objects. *That composition is the expensive foundation*; the folds above it are the cheap part. Decision 1 is still the cheapest of the five to prove, because it makes the abstract state and the authority the same object; it is not cheap.
- **Perennial's crash invariant, stated with the right inequality** [Astra, correcting the draft]. At every crash point, the recovered history must *contain every acknowledged operation* and may contain additional complete but unacknowledged ones; a batch can be durable before its reply is sent, and recovery keeps it (rule 8: "a complete, valid final batch may be adopted even if its original reply was never sent"). Materialized pages may lag acknowledgements while the journal supplies the suffix, and partially installed pages need not describe one prefix. GoJournal models durability as a *lower bound* (`chajed2021-gojournal-verified-concurrent-journaling.txt`, Fig. 7); under fn's broader damage model insufficient evidence yields `unknown`, never a shorter history (`chajed2019-perennial-crash-safety-concurrency.txt` §2 for recovery helping). Versioned memory is unnecessary while folds are latest-only.
- **Durable linearizability, precisely** (Izraelevitz, Mendes, Scott 2016, `izraelevitz2016-durable-linearizability.txt` if fetched by scout B; definitions 3 and 5, §4). It says completed operations persist across a crash and the history remains linearizable, and permits some pending operations to survive. It does *not* supply duplicate suppression [Astra]: retries must be identified as one logical operation by the API and the recorded-outcome protocol, which is what RIFL adds. The relevant order is persistence, then installation and visibility, then (possibly much later) reply delivery; "ack point equals linearization point" was the draft's error, and strict linearizability concerns operations interrupted by crashes, not acknowledgement.
- **The ACL2 route** (`goel2013-acl2-abstract-stobjs-isa-modeling.txt`; `kaufmann2025-acl2-mutable-objects-several-implementations.txt`; acl2aiguide `03-modelling-data.md` §3.9–3.10). fn1's catalog states its logical value as "the committed history as a true list of held records" and proves every index equal to a fold of it once, through `defabsstobj`'s correspondence. Decision 1 generalizes that: one abstract stobj whose logical value is `(summary, suffix)` and whose exports are the folds' observations; the executable is the columns, runs and pool. `attach-stobj` gives a reference implementation and the fast one under one set of theorems. The guide's warnings apply verbatim: generate the obligations, one foundation replaced never nested, "decide up front which representation owns the held row".
- **What makes the proof dearer, and how to avoid the worst form.** *Coalescing* needs ordered-sequence equivalence, not commutation [Astra]: `set(1); set(2)` collapses to `set(2)` although the operations do not commute, so the lemma per coalescing rule is "the coalesced sequence and the original produce the same fold value and the same promised outcomes". *The summary rule* need not be a giant `defun-sk` over all continuations [Astra]: an observation-preserving inductive simulation (the summary state simulates the full-history state step by step with respect to `O`) establishes continuation equivalence, which is how fn1's checkpoint keystone is already proved in shape (`04-modelling-systems.md` §4.5). Order the work: ship with storage checkpoints (equality) and identity/obligation retention; prove the simulation when a fold is actually discarded.
- **Failed persistence before wraparound** [Astra, addition]. Rebello et al. found data-loss and corruption across PostgreSQL, LMDB, LevelDB, SQLite and Redis when `fsync` fails, because dirty pages are marked clean and a retry fences nothing (`rebello2020-can-applications-recover-fsync-failures.txt`). This motivates fn's `uncertain` state and recovery contract independently of whether the authority is a log or a heap, and it is the deployment example decision 1's proof must carry: the fold equation is conditional on A-PERSISTENCE-FENCE, and the theorem's hypothesis must say so.
- **seL4's ratio** (`klein2014-sel4-comprehensive-formal-verification-tocs.txt`) is the budget warning: person-years per thousand lines of a small fixed state machine. Every fold kind is more logic; every coalescing rule and migration function more lemmas. Keep the fold vocabulary small in the first format.

### 1.6 Verdict

**Keep, amended.** The decision is right, and the systems that made it (Raft and RIFL, FoundationDB's log/storage split, Kafka's compacted offsets, Redis's base-plus-increments AOF, Datomic's single writer) establish precedents with their own contracts rather than a theorem selecting this architecture [Astra: withdraw "convergence" and "optimality"]. Its weak points are that the summary rule is a goal rather than a characterized target with a proof shape, and that five consequences (fold initialization and coverage, consumer cut contracts, op-identity admission and retirement, request binding, external effects) are unstated. Amended wording for `STORAGE-DESIGN.md` §4.1, merging the draft's and Astra's texts:

> **Unit of state**: one ordered semantic event history per commit domain, a retained prefix summary plus suffix, `State = Fold(Summary_k, Events_{k+1..n})`; keyed mutations use the same commit protocol and record principal, operation identity, the request's binding (mutation and expected prior version), and stable outcome. Within the declared retry contract a retry returns the original outcome without re-execution and a contradictory reuse of an operation identity is refused by name; retiring outcome evidence requires an explicit rule that fences retired identities against fresh execution; unexpired operation identities are a per-principal reservation with a named exhaustion. Coalescing preserves every promised result, including every recorded outcome. Internal folds are latest-only; a historical fold question is answered from a retained snapshot plus replay, charged as maintenance. Each fold names its interpretation, initialization and coverage; a new or changed fold may use an existing summary only through a valid bootstrap or migration rule, and unavailable history is never implied. External effects are recorded as obligations or outbox entries released by evidence, never re-performed by replay. Discarding semantic history requires an identified summary rule, proved as an observation-preserving simulation against the retained contract's observations and future requests (identity decisions, acceptance and conflict bindings, obligations, retry outcomes within their contracts, consumer delivery contracts, supported historical selections); initially the summary retains losslessly recoverable exact Message-ID octets with their binding evidence, and obligation evidence. A consumer cut satisfies the consumer's declared contract: retained delivery under a charged, inactivity-bounded obligation, or state bootstrap with an explicit gap. A storage checkpoint, a signed checkpoint claim and permission to discard history remain three distinct acts. One atomic mutation belongs to one commit domain.

**The measurement that settles the remaining doubt.** A *summary-cut scenario*, in two sizes [Astra's correction adopted]: a tiny profile with exhaustive continuations and crash cuts targeting expired retries, contradictory op-id reuse, conflicting identities, outstanding obligations, a fold migration and a consumer gap, checking observation-equivalence of `Fold(Summary_k, suffix)` against the full fold; and the concrete profile with 10^6 events, where the summary's size is reported by component (identities after lossless compression, obligations, op-identity windows, folds) and its maintenance cost separately, against the 30-consumer workload (extends M5). This falsifies a summary rule; it does not prove one. If the identity component dominates, the identity-contract question in the closing section is worth ember's time; if the op-identity component dominates, the per-principal reservation is the first thing to tune.

## Chapter 2. Pinned versions: stable selection and identity; bytes only under a lease

### 2.1 The decision as a claim

**Claim.** A supported pin identifies a published logical version `v`, the history and incarnation it belongs to, its selection semantics (query definition, view, authorization generation) and a supported query scope. While valid it preserves *selection* (which articles exist and are visible, their numbers, the withdrawals that had happened) and *identity* (what `(group, number)` and a Message-ID denote) through any physical reorganization. It does **not** promise that an article's bytes remain available: a payload whose release was committed at some `w > v` and then reclaimed is answered `unavailable` to a reader at `v` that had not yet leased it. Before promising to stream an object a reply acquires a *logical object lease*, atomically against release; physical reads and sends hold generation-checked *borrows* of ranges until the adapter releases them; only a bounded window occupies the byte pool. The engine retains enough evidence to answer a supported pin's questions, which requires neither every intervening change nor any old physical root. A long cursor keeps its logical scan progress and re-seeks after a suspension; cached physical traversal state is optional and bounded. Three mechanisms stay distinct: durable obligations (`:archive`, `:forward`, `:checkpoint`), the logical version a selection reads at, and the physical leases and borrows of an active operation (the Review §7). A consumer's `query-version` and `view-version` are *selection-semantics* versions and its position is a durable scan position; none of them is a storage snapshot pin and none creates an implicit retention hold (`specs/consumer-progress.md`; the retaining consumer mode is a separately charged durable hold) [Astra].

**What it buys.** A stalled reader (a 16 MiB BODY at the 4,096 B/s stall floor streams for 68 minutes [D, the Study §0.1]) holds the object it leased and nothing older: never the whole write stream since its pin, which is what a root pin (LMDB) or a table-snapshot pin (a uniform LSM) would hold (the Study §C, read as a comparison of contracts, not of engines [Astra]). Compaction is never gated on the slowest reader. Visibility decisions are comparisons on version-stamped entries (fn1's `fn-cat-visible-at`), so taking a pin is cheap and holding one adds no *historical* storage beyond what the supported observations already require.

**What it gives up.** (a) A reply is no longer a function of the connection's octets and its pinned version alone: it also depends on availability, rebase and fault outcomes that the environment determines. The Review adopts this change to the connection-isolation claim (Clients §3.4) explicitly; §2.5 says what the theorem becomes. (b) Metadata that visibility reads is not latest-only: an article withdrawn at `w` must remain answerable to supported pins below `w`, so the engine carries *some* multiversioning, bounded by the supported observations and the pin-expiration rules (§2.3, §2.4). (c) Re-seeking needs a publication invariant and a stable logical key order, not merely birth stamps (§2.3). (d) The split (selection stands, bytes may vanish) is a different contract from FoundationDB's (selection expires, bytes never vanish inside it), not a kinder one: a client that needs *complete* payloads may prefer an atomic failure to a stable list with holes [Astra]. The decision chooses the first for NNTP's and consumers' sake and must say so.

### 2.2 State of the art

The same choice, split the same way:

- **Kafka.** A consumer's position is an offset into an append-only partition. A read below the retained range gets `OffsetOutOfRange` and the consumer resets by policy (`auto.offset.reset`); on a *compacted* topic a removed offset is simply a hole and a seek returns the next surviving record, with no retained identity for what was removed (`kafka2026-docs-design.md`, "Log Compaction", "Consumer Position") [Astra, correcting the draft: Kafka preserves positions, not fn's historical selection-and-identity answers]. What transfers is the shape of the failure: a named outcome and a rebuild, not a stall. Kafka's *durable* position had the bug fn2 must not repeat: committed offsets once expired after `offsets.retention.minutes` "regardless of the group state", so an active, rarely committing consumer lost its position (KAFKA-4682); KIP-211 made expiry run from the moment the group becomes empty, and the default rose from one day to seven (`kafka2026-docs-kip-211-offset-expiration-semantics.txt`, `kafka2026-src-group-coordinator-config-java.txt`). And `delete.retention.ms` is documented as a reader-age bound: it "gives a bound on the time in which a consumer must complete a read if they begin from offset 0 … otherwise delete tombstones may be collected" (`kafka2026-src-topic-config-java.txt`).
- **Certificate Transparency and transparent logs.** A client that remembers a signed `(log id, size, root)` has a pin on an append-only log; a consistency proof to any later size is `O(log n)`, and since the log already retains everything the proofs need, the client's remembered checkpoint adds *zero marginal retention* to the log (`rfc6962-certificate-transparency.txt` §§3.5, 4.4; `cox2019-transparent-logs-skeptical-clients.txt`). That is the exact statement [Astra, replacing "free forever"]: a pin costs nothing when the baseline already retains every answer the pin can ask for; it never establishes ongoing availability by itself.
- **Postgres, and the thing it built and tore out.** A snapshot's `xmin` horizon blocks vacuum from removing any tuple dead after it, in every table, so one forgotten `idle in transaction` bloats the cluster. Postgres 9.6 (2016, commit 848ef42b) added `old_snapshot_threshold`, in minutes, "similar to the Oracle feature, and we use the same SQLSTATE and error message": a snapshot older than the threshold gets `ERROR: snapshot too old` if it reads a page modified since it was taken, maintained through a timestamp-to-XID mapping checked against page LSNs (`grittner2016-postgres-commit-add-snapshot-too-old.txt`; `postgresql2026-docs-runtime-config-resource-v16.txt` §20.4.6). It was removed for Postgres 17 (commit f691f5b8, 2023-09-05) for "a number of known problems in terms of correctness and performance" and a prolonged absence of a repair plan; the diff touched about forty files across the heap-prune code and every index access method's scan path (`munro2023-postgres-commit-remove-snapshot-too-old.patch.txt`) [Astra: the removal is real, the draft's causal story was embellished]. Two lessons survive: bounded pin age is a production idea, and a numeric cutoff still needs correct synchronization among admission, publication and reclamation; fn2's single comparison at the lease or seek boundary is the cheap form only if that synchronization is designed.
- **Oracle, CockroachDB, Spanner: three different answers to "which promise loses under pressure".** Oracle's `ORA-01555: snapshot too old` is raised when "rollback records needed by a reader for consistent read are overwritten by other writers"; `undo_retention` is a target, not a guarantee, since space pressure may overwrite unexpired undo unless `RETENTION GUARANTEE` is set, in which case *writes* fail instead (`oracle2026-docs-ora-01555.txt`; Oracle's undo-management documentation [A]). CockroachDB keeps MVCC versions for `gc.ttlseconds` (documented default four hours) and refuses reads below the GC threshold, and it already has the scoped alternative §2.4 proposes: *protected timestamps*, scoped protections that backups and changefeeds place on exactly the ranges they need, so that GC of everything else proceeds [Astra]. Spanner defaults to a one-hour version window, configurable to seven days, and can fail an already-running read whose timestamp becomes too old [A]. The production consensus is narrower than "a window with a named refusal": it is that the window is explicit, that scoped protections exist for the holders that matter, and that a system chooses which side (reads or writes or space) gives way.
- **FoundationDB.** Five seconds from a transaction's first read, server reads usually fail with `transaction_too_old` while cached reads need not, and a commit with writes fails; the documented workaround for long snapshots is to "perform versioning in a layer" (`foundationdb2026-docs-known-limitations.txt`); the paper's reason is memory on resolvers and storage servers, and that exceeding the window "often exposes inefficiency in the application" (`zhou2021-foundationdb-unbundled-transactional-kv-store.txt` §6.4). Deployment opinion is blunt ("routinely wrecks your application logic", HN 43928135; also 36330508). FDB bounds the selection; fn2's window bounds the selection too (an expired pin is rebased) and additionally lets bytes vanish under a valid pin; the two contracts are incomparable [Astra], and "versioning in a layer" is what decision 2's re-seeking cursor is.
- **LMDB, TigerBeetle, SQLite, compared under one contract.** The draft charged these engines for root or table pins they do not have to take; the fair comparison is under the same logical-pin/object-lease contract (the Review's correction 8) [Astra]. What remains true: LMDB's documented hazard is reader-driven growth, "Avoid long-lived transactions. Read transactions prevent reuse of pages freed by newer write transactions, thus the database can grow quickly", with growth following unreusable page churn and free space, `mdb_reader_check` clearing *stale* (dead-process) readers rather than live slow ones, and `MDB_MAP_FULL` / `MDB_READERS_FULL` as the end states (`lmdb2026-docs-lmdb-h.txt`); TigerBeetle documents table-version retention under snapshots and leaves persistent snapshots unimplemented, which is its design choice, not a bound on LSMs (`tigerbeetle2026-internals-lsm.md`); SQLite's checkpoint advances up to a reader's end mark and only completion and reset are blocked, with the WAL index bounding lookup cost (`sqlite2026-docs-wal.txt`). The lesson all three carry is the one the decision takes: whatever pins must never pin a physical structure.
- **In-memory MVCC generally** (`wu2017-empirical-evaluation-in-memory-mvcc.txt`): "performance drops in the presence of long-running transactions … all the versions generated during the lifetime of such a transaction cannot be removed until it completes" (§5); with GC disabled, throughput falls as version chains lengthen; cooperative GC beats a background vacuum by 45% throughput with 30–60% less memory per transaction on read-intensive YCSB (§7.4). These are the academic numbers for retained versions, under the contract "any read may ask anything".
- **Datomic.** Its `since` filter cannot resolve identity because identity was asserted earlier; the idiom resolves identity against the unfiltered database and values against the filtered one (`datomic2026-docs-filters-as-of-history.txt`). That is decision 2's split, identity resolved at one version and payload answered at another, in a shipping product.
- **Tahoe-LAFS.** A retention lease is renewable and time-expiring, and a share whose leases have all lapsed is deleted *when garbage collection is enabled*, which is not the default (`tahoelafs2026-docs-architecture.rst`, "Leases, Refreshing, Garbage Collection") [Astra]. Tahoe's lease is a retention hold, not an operation borrow; decision 2 keeps the borrow as the thing that holds bytes during an operation and the obligation as the thing that holds them across time, and rejects a timer for either.

### 2.3 Theoretical optimal

**A pin costs zero additional historical storage exactly when the baseline already retains every answer it may ask.** That is the CT case, and it is the fn2 case for immutable article metadata with birth and withdrawal stamps: the permanent metadata already answers "was `n` visible at `v`" for every `v`. Registration, indexing, traversal and accounting still cost, and the physical bytes a lease holds include rounding, stranded extents, relocation copies and recovery dependencies, which an object lease alone does not bound; the logical bound `≤ C × A` holds only under the profile's concurrency assumptions [Astra, reinstating correction 7's scope].

**The information a pin forces the engine to keep is bounded by the supported observations, not by churn** [Astra, replacing the draft's `Ω(changes since the pin)`]. One key may change a million times after a pin; answering the pin needs the value at `v` and the current value, two versions, not a million. In general the retained evidence is the information needed to distinguish the supported observations at every valid pin from each other and from the present: for latest-only folds that is at most one retained version per (fold entry, live pin version) actually distinguishable, and for article metadata it is often nothing beyond the permanent stamps. Scoping a pin to a declared selection can only shrink this set, but `Ω(changes in scope)` is not a theorem either; the honest statement is that retention is derived from the supported observations and the protected holds, and that the engine's compaction must preserve exactly the entries those observations distinguish.

**Re-seek is sound only under a publication invariant** [Astra, replacing the draft's "iff" on birth stamps]. An article born before `v` can acquire a membership after `v`; a filter on article birth alone admits that phantom. The conditions are: every selection-relevant fact (membership, withdrawal, visibility, authorization, view definition) is materialized through the published frontier with its own version semantics; there are no retroactive changes to that history; logical keys are stable and totally ordered; and compaction preserves the *entire query result* at every supported pin, not merely entries with early birth. Under those, a cursor at `(v, progress)` resumes correctly, where progress must record the last *examined* key, not the last emitted one, or a filtered suffix is rescanned after each budget exhaustion. The cost per resume is a descent into the current index, which in an ordered-run engine may touch several runs and directories; "one descent, `O(log n)` page reads" is a hope for M2 to measure, not a bound.

**The isolation claim, stated relationally.** Before: a connection's replies are a function `F(octets, v)`. After: for two runs with the same history identity and incarnation, the same connection state, the same octets and the same pin, and *aligned* environment observations at the connection's requests (availability answers, rebase and view-change outcomes, fault classifications), the reply streams are equal. The observations must be defined independently of the output they justify [Astra]; "availability" alone no longer captures the amendment once rebase and view-change outcomes also shape replies. The strict version (replies independent of all of these) is recoverable only by epochs at the space cost the Study measured, or by refusing the read (FoundationDB's choice).

**What durable linearizability does and does not give** [Astra, correcting the draft]. It preserves the effects of completed operations across crashes and keeps the operation history linearizable (`izraelevitz2016-durable-linearizability.txt`, Definition 3). It does *not* say a later read requesting version `v` may linearize before its invocation, so it does not by itself make a pinned read repeatable after restart, resurrect volatile leases, or forbid later legal reclamation. A pinned read needs its own specification: a *historical-read operation* on a snapshot object whose sequential semantics permits the answer "the selection at `v`", with fence-before-publication (rule 8) as the evidence that `v` is durable.

**Distance from optimal.** At the floor for historical storage when the supported observations are already permanent; above it by whatever multiversioning the folds' supported pins require; the relational isolation claim is the honest minimum once bytes may vanish under a pin.

### 2.4 Tradeoffs not yet on the table

1. **Pin expiration as a contract, and the real compaction floor.** The Study §C already proposed bounded-age rebasing for metadata [Astra]; the missing work is the contract. Compaction's floor is not "the oldest unprotected pin": a protected hold at version 80 still matters when the window starts at 100 and the oldest ordinary pin is at 120, and an expired ordinary pin must not hold the floor. Derive what compaction must preserve from the supported observations and the protected holds together; make expiration effective *before* discarding its evidence (the Postgres synchronization lesson); and never switch an already-started response to another version (a BODY or XOVER promised at `v` finishes at `v` or fails by name). The window's unit (versions or time) and size are a profile choice for the workload, not a theorem; a parked consumer in retaining mode is a protected hold charged to its principal (chapter 1, tradeoff 2), not a pin.
2. **Scoped pins, closed over their dependencies.** Declaring a pin's selection scope (the group after `GROUP`; a range for XOVER; streams for a consumer query) is a useful optimization, not a missing requirement [Astra]: "historical metadata needed by supported pins" never prescribed global retention. CockroachDB's protected timestamps are the production form. A scope must be closed over what the selection depends on (memberships, shared withdrawal facts, view definitions, authorization, schemas), since a cold group can depend on changing shared metadata; and whether NNTP clients tolerate a cross-scope rebase response is a measurement, not an assumption. Put scope granularity and its bookkeeping in the M4 comparison.
3. **Lease the logical object, borrow the physical range; relocation under a lease.** Adopted by Astra with corrections [Astra]: the cleaner may *copy* a leased object while old readers borrow the source; *retiring and reusing* the source waits for every borrow and for recovery safety; placement resolution and borrow acquisition must be atomic against retirement and checked against the allocation generation; a borrow bounds bytes, not elapsed time (an external send may stall indefinitely), and a disk borrow may end as soon as the block is copied into owned pool memory even if the network send continues; relocation needs spare space and a bounded copy policy, so stranded space does not vanish instantly. The benefit stands: leases never strand extents permanently and the cleaner's wait is bounded by borrows, not by BODY streams.
4. **Durable consumer state is a scan position, not a snapshot; the retaining mode is the replication slot.** The draft's "month-old query-version holding versioned metadata" was wrong [Astra]: `query-version` changes with selection semantics and `view-version` with visibility and authorization; a poll pins a frontier only for its own duration. What *is* the Postgres replication slot (a durable hold nobody releases) is the optional retaining-consumer mode, which Clients already specifies as a charged durable hold; give it the inactivity bound and the `health` row (oldest hold, bytes held, owning principal), and the analogy is exact.
5. **A signed root does not prove a query answer.** An inclusion proof against the event-log root proves that an event is in the log; it does not prove an XOVER result complete, currently authorized at `v`, or unaffected by a withdrawal before `v` [Astra]. Provable reads need authenticated state or range proofs (chapter 4's identity and summary commitments as a log-backed map) or evidence connecting the fold to the log; a later signed root can authenticate an earlier prefix with suitable evidence. Snapping a pin to a checkpoint version is an optional staleness policy for clients that want their reads covered by a *cadence* checkpoint, not a prerequisite.
6. **Traversal caches are charged and disposable, not pinned.** The draft's "hold a page pin across execution yields, drop it across external waits" was unjustified [Astra]: a page retained across scheduler yields consumes shared cache capacity and can obstruct maintenance, and the rule bounds neither memory nor reclamation progress. Allow a bounded, charged, disposable traversal cache per cursor if M2 shows re-seek cost matters (Facebook's RocksDB traces say hot ranges will exist: under 3% of keys touched in 24 hours, clustered, `cao2020-characterizing-rocksdb-workloads-facebook.txt`); correctness must survive eviction and re-seek.
7. **What `unavailable` discloses, stated precisely.** A single `unavailable` does not reveal that reclamation happened after the pin, nor expiry versus withdrawal; the payload may have been absent all along [Astra]. State the permitted disclosure for each distinguishable outcome (unavailable, rebased, refused by authorization change, fault) rather than inferring a hidden cause from the result; SFSCQ's noninterference framing (`ileri2018-sfscq-proving-confidentiality-file-system.pdf`) is the tool when D04 (private groups) arrives.
8. **Pin lifecycle and authorization changes are transitions** [Astra, addition]. Admission, renewal, expiration and scope extension of a pin are core transitions with races against compaction and profile changes; authorization revocation during an old pin, and during an already-leased response, needs its own outcomes (the leased BODY completes or terminates by name; the next selection is re-authorized).
9. **Four retentions, kept apart in accounting and diagnostics** [Astra, addition]: historical-read retention (what supported pins keep), replay-history retention (what recovery keeps), payload retention (obligations and policy), and crash-recovery dependencies (what the checkpoint protocol keeps). One `health` row each.

### 2.5 Principles from logics and deployments: proving it later

- **Borrows are fractional permissions; the cleaner is more than that.** A reader's borrow of an immutable range is a fraction of its ownership and copying needs no more than that; *mutation and reuse* need the full permission (`jung2018-iris-from-the-ground-up.txt`). A zero borrow count is sufficient only with complete token accounting, generations, completion matching, prevention of new borrows, and durable placement and recovery invariants; the logical retention lease needs its own obligation model on top [Astra]. Epoch reclamation would not escape this: it also needs ownership and external-I/O rules, so it is not "one inequality and no ownership story". In ACL2 these are counting and generation invariants carried with the state (`04-modelling-systems.md` §4.4), in the shape of fn1's `pgs-fork-isolation`.
- **Perennial's contribution here is recovery refinement, not versioned memory.** Perennial's version numbers identify *crash generations* and invalidate old capabilities; its recovery leases mediate exclusive modification of durable resources and recovery reconstructs fresh capabilities after a crash (`chajed2019-perennial-crash-safety-concurrency.txt` §§5.1–5.3). They are not `(key, version)` entries and not read leases surviving a restart [Astra]. What applies is the discipline: every lease and borrow is a resource that a crash invalidates, recovery re-establishes exactly the durable ones (obligations), and the refinement is proved through crash invariants that mention generations.
- **The isolation theorem's new form.** `fn-ideal-connection-isolation` (Clients §3.4, milestone M7) becomes a relational property over aligned request observations with the same history identity and connection state (§2.3); it remains a trace property (execution model §4). Separately prove legal lease acquisition and release, failure classification, and exact payload delivery, and make sure "committed release and no lease" can never disguise corruption or unknown persistence as ordinary unavailability [Astra]. Teeth need reachable positive schedules *and* hypothesis-removal witnesses: release racing acquisition, relocation racing a borrow, expiration during a cursor, post-pin membership, an invisible scan suffix, a protected old pin, a stale placement generation, a crash during relocation, expiration after a response status [Astra's list].
- **The historical read is its own operation.** Durable linearizability covers completed appends and witness persistence (chapter 4); a pinned read is a historical-read operation on a snapshot object with its own sequential specification (§2.3). The DaisyNFS division still applies: leases, borrows, retirement and the snapshot object live in the transaction layer, proven once; selection code above it is sequential and never touches a physical address.
- **Which option is cheaper to prove.** Neither is one inequality. Leases add the fractional-ownership and generation lemmas; epochs add the same plus the space cost operators pay forever (the Postgres horizon, LMDB readers, SQLite end marks). The decision is right to take the ownership proof, which is of a kind fn1 already carried.

### 2.6 Verdict

**Keep, amended.** The separation of logical selection, retention obligations and physical borrowing is right and is where the production systems that let readers be slow have converged, under different contracts [Astra: keep the separation, reject the draft's amendment]. What was missing is the contract for pin expiration, the publication invariant behind re-seeking, the atomicity of lease acquisition against release, and the distinction between durable consumer positions and storage pins. Amended wording for `STORAGE-DESIGN.md` §4.2, Astra's text adopted with the scholar's additions:

> **Pinned versions**: a supported pin identifies a published logical version, history and incarnation, selection semantics and supported query scope. While valid it preserves selection and identity through physical reorganization; the engine retains sufficient evidence for those answers, which requires neither every intervening change nor any old physical root. Consumer query and view versions and durable scan positions are distinct from storage snapshot pins and create no implicit retention hold; a retaining consumer is a charged, inactivity-bounded durable hold. Profiles define pin expiration and rebase rules; expiration, protected holds and any promised historical-read window jointly determine which observations compaction must preserve, derived from the supported observations and closed over their dependencies; expiration takes effect before its evidence is discarded and never changes an already-started response. A cursor preserves logical scan progress through the last examined key and re-seeks safely after suspension; cached physical traversal state is optional, charged and bounded. Before promising payload success a reply acquires a logical object lease atomically against release; physical reads and sends hold generation-checked borrows until the adapter releases them; relocation preserves the leased content identity and publishes durable replacement placement before retiring old storage, and reuse additionally waits for all old borrows and recovery dependencies. Replies refine the reference semantics for explicit availability, rebase, authorization-change and fault outcomes, each with a stated disclosure; a valid lease prevents reclamation-induced loss of a promised payload under the declared platform assumptions.

**The measurement that settles the remaining doubt.** M4 repaired [Astra's controls]: a *real* historical pin (not an old `query-version`) held for `h` hours while 1,000 POSTs/s and 10 withdrawals/s commit and expiry runs; identical logical-pin/object-lease contracts across the shared-run engine and the COW comparison; reported separately: historical-read evidence retained as a function of `h` with and without scoped protections, temporary relocation space and stranded extents with and without logical-object relocation, actual read amplification of a 10^6-row XOVER's resumes (runs and directories touched per resume) against a bounded traversal cache, and reclamation progress under a stalled external borrow. If scoped protections leave retention flat, they are worth their bookkeeping; if stranded extents dominate, logical leases with relocation are the first thing to build.

## Chapter 3. Retention: classes as placement hints; one release predicate

### 3.1 The decision as a claim

**Claim.** Retention policy (per-group expiry, settable live; the obligation kinds `:archive`, `:forward`, `:checkpoint`; application-declared obligations later) never decides when storage is freed. It decides only *where bytes are placed*: payloads with similar expected lifetimes share an extent chain (one default class; operator-defined classes as a profile option; a crosspost takes the longest applicable lifetime; no resident tail buffer per class, since tails are paged under rule 9). Two acts are distinct [Astra]: *logical discard* of an object's last required copy, which is authorized only when every applicable retention requirement is discharged, every independent durable obligation is released and no promised read still requires it; and *physical retirement and reuse* of an allocation, which additionally waits for everything the format's allocator protocol (the Review §H) protects: the installed root, every checkpoint recovery may select, prepared successors, reservations, outstanding borrows, outstanding I/O, and unresolved recovery candidates. A committed relocation may retire an old copy while every requirement is preserved at its replacement. Class membership is never release evidence. A live policy change can leave survivors in an extent whose class has died; the cleaner moves them through the commit protocol. Event and control metadata is retainable independently of payloads: a small source inlined in a journal frame is copied out before the frame is reused.

**What it buys.** In the common deployment (one policy) expiry is a whole-extent drop with *zero survivor copying*, which is Kafka's and Postgres-partitioning's result (the Study §D point 1: "place together what dies together"); zero copying is not zero work or zero interference [Astra]. A policy change is a placement change, not a format change. There is one place to audit why a byte is still here, which is the operator's question in `docs/architecture.md` ("what does this node have, why does it keep it, what has it undertaken to do, and what evidence permits it to release that obligation"). Obligations survive policy: a pinned article outlives its group's expiry by construction.

**What it gives up.** (a) Placement is a prediction of death time; a wrong prediction costs survivor copying at `u/(1-u)` bytes copied per byte of net space recovered (`rosenblum1992-design-implementation-log-structured-file-system.txt` §3.4; Sprite's modeled read-plus-write cost is `2/(1-u)` when whole victims are read, with cost 1 for wholly dead segments [Astra, correcting the denominators]). (b) Each concurrently written class is one more open tail; with independently sealed `S`-sized units a batch's padding is `Σ_i (⌈x_i/S⌉·S − x_i)`, less than `g·S` and sometimes zero, a measurement for the chosen layout rather than a bound [Astra]. (c) Release has the checkpoint's latency: an allocation is reusable only after a checkpoint no longer needs it, so space recovery needs reserved space of its own (the Review §F).

### 3.2 State of the art

The same choice:

- **Kafka.** Retention is per topic (`retention.ms`, `retention.bytes`), deletion is by whole segment oldest-first, and tiered storage (KIP-405) has distinct local and overall retention controls under one predicate over the union (`local.retention.ms ≤ retention.ms`; a follower behind the local start gets `OFFSET_MOVED_TO_TIERED_STORAGE`; compacted topics unsupported) with the dependency that matters: *successful remote copying gates local deletion* (`kafka2026-docs-kip-405-tiered-storage.txt`) [Astra]. That is a relocation-before-retirement protocol, the same shape as decision 3's cleaner, and it is the precedent for "a committed relocation may retire the old copy". Kafka gets zero-copy expiry because a partition is a lifetime class by construction; fn's groups are interleaved in one journal, which is why fn2 needs classes to recover the property.
- **Sprite LFS.** The cleaner's cost-benefit policy `(1-u)·age/(1+u)` and the observation that hot and cold data separate when survivors are sorted by age are the origin of "place by expected lifetime" (`rosenblum1992-…` §3.6). Its accounting is conditional on victim choice, allocation granularity and spare capacity; it is not an online lower bound [Astra].
- **F2FS (Lee et al., FAST 2015).** Six active logs (hot/warm/cold × node/data) chosen by the *kind* of block, with ordinary user data in **warm** and selected data, including "data blocks moved by cleaning (… remained valid for an extended period)", in cold (`lee2015-f2fs-flash-friendly-file-system.txt` §2.4). The survivor rule is a heuristic about future updates, not a theorem about remaining retention [Astra]; §3.4 tradeoff 8 treats it as one. F2FS also has the closest precedent for the fourth conjunct: *pre-free* sections, reusable only after a checkpoint (§2.5) [Astra].
- **Multi-streamed SSDs (Kang et al., HotStorage 2014) and NVMe Flexible Data Placement (2023).** The host tags writes with a stream or placement handle that is a lifetime hint; the device places same-stream data in the same erase blocks. Kang measured on Cassandra: throughput held at ~90% of peak where the untagged drive fell 53%, p99.9 latency 54% lower, p99.99 61% lower, projected lifetime +23%, and a mapping that separated only 1% of traffic gained nothing (`kang2014-multi-streamed-ssd.txt`); the gains are workload-specific [Astra]. FDP (TP4146) is backward compatible, a non-FDP host uses the default reclaim-unit handle, and write amplification falls when the host deallocates or rewrites a whole reclaim unit; its handles identify *configured reclaim-unit resources*, a budgeted set, not arbitrary ordered classes; and the SNIA paper notes that host-side copying can reduce device WAF while increasing host writes (`snia2026-introduction-flexible-data-placement-whitepaper.txt`; `sabol2023-nvme-fdp-state-of-the-union-fms.txt`: streams "WAF=1 achievable without feedback", FDP "with feedback, backwards compatible", ZNS "WAF=1 guaranteed, not backwards compatible"). Linux exposes the hint as `F_SET_RW_HINT` with `RWH_WRITE_LIFE_{NONE,SHORT,MEDIUM,LONG,EXTREME}`, *inode-scoped*, and with the man page's stance: "There are no functional semantics implied by these flags" (`linux2026-docs-fcntl-f-set-rw-hint.txt`) [Astra]. "Retention classes as placement hints" is this abstraction one level up, with the same contract; passing it down is a backend-specific mapping (§3.4, tradeoff 1), not a free chain.
- **RocksDB.** Two distinct eviction contracts, not one [Astra]: FIFO compaction drops the oldest SST when the level exceeds a size, "can drop data without informing users", and with its TTL option may still evict unexpired files under the size limit; `DBWithTTL` separately keeps entries "at least ttl" and removes them "in compaction only", so a `Get` may return an expired entry (`rocksdb2026-docs-fifo-compaction-style.md`, `rocksdb2026-docs-time-to-live.md`). Both are explicit contracts about what a timer promises (a lower bound on retention, an upper bound on nothing), and FIFO is the design decision 3 rejects: a size trigger acting as the release authority.
- **Postgres.** Per-row `DELETE` plus vacuum is `O(rows)`; the documented practice for time-bounded data is to partition by time and `DROP` the partition, which avoids per-row deletion at the price of a parent-table lock, and still leaves survivors and permanent identities to be handled separately (`postgresql2026-docs-routine-vacuuming.txt`; Postgres partitioning docs [A]) [Astra]. Its replication slot is the hold nobody releases (chapter 2). The three wraparound post-mortems carry one lesson for *maintenance debt* generally: at Mandrill a hot shard's autovacuum fell behind until the XID limit forced a safety shutdown, detection was slow, and full-vacuum estimates ran to "days or even weeks" (`mailchimp2019-docs-mandrill-outage-postmortem.txt`); at Sentry "Is a VACUUM resumable? How long until completed?" were unanswerable and one autovacuum had silently failed (`sentry2015-docs-transaction-id-wraparound.txt`); at Joyent a multi-hour anti-wraparound vacuum, a queued `DROP TRIGGER` and every data-path query formed a lock queue, which is a *lock-dependency* failure as much as a debt-visibility one (`joyent2015-docs-manta-postmortem.txt`) [Astra]. Operators could not see how much debt remained; maintenance must not take locks the data path waits on.
- **ZFS and S3.** `zfs hold` puts a named user-level hold on a snapshot so `zfs destroy` fails until every hold is released; S3 object lock has a time-based *retention period* and an evidence-based *legal hold* on particular object versions. Both are independent-hold precedents for obligations beside policy; neither certifies that custody or delivery completed, which is what fn's grounded release requires [Astra].
- **Git.** Reachability is the release predicate (`git gc` frees what no ref, reflog or index reaches), and `gc.pruneExpire` keeps unreachable objects for a two-week grace that *mitigates rather than eliminates* corruption by concurrent writers (Git has no reservation registry). fn2 needs no grace only after complete reservation and borrow registration and writer fencing exist [Astra]; the Review §H provides them.

The opposite choice:

- **Tahoe-LAFS.** A share is deleted after lease cancellation or expiry *when garbage collection is enabled*, which is not the default; leases are renewable retention holds (`tahoelafs2026-docs-architecture.rst`). Tahoe promises something deliberately different from fn: a holder that fails to renew loses its hold. fn's custody obligations (a phone behind NAT on a DTN link for a week, Clients §1.3) must survive silence, so the renewable timer is rejected for *those*; time-limited contracts fn already has (group membership retention) are untouched (§3.3).
- **Cassandra tombstones.** `gc_grace_seconds` (ten days by default [A]) is coupled to repair and compaction coverage rather than being a timer-only deletion; a replica down longer than the grace can resurrect a deleted row [Astra]. A timer bounding repair, with resurrection as the failure, is the contract fn declines for identities.
- **SILK (Balmau et al., ATC 2019).** The deployment lesson about *maintenance*: compaction I/O produces client latency spikes of seconds, and rate-limiting internal work "does not suffice" (flushes starve behind compactions, the memtable fills, writes block; limiting compactions instead fills L0 and stalls flushes). SILK gives internal work the bandwidth of low-load periods, prioritizes flushes and low-level compactions, and preempts less urgent work, for up to two orders of magnitude lower p99 (`balmau2019-silk-preventing-latency-spikes-lsm.txt`). RocksDB's rate limiter is one token bucket over flush and compaction with priorities USER > HIGH > MID > LOW (`rocksdb2026-docs-rate-limiter.md`); per-tenant fairness is another layer (Pisces's weighted max-min at under 3% overhead, `shue2012-pisces-performance-isolation-fairness-multi-tenant-storage.txt`; Alibaba's FlexEngine with two-level I/O admission and bounded-memory compaction deferral, `wang2026-flexengine-lsm-multi-tenant-serverless.txt`). One cleaner bandwidth share is insufficient [Astra]; the execution model's maintenance calendar share gives CPU, and the Review notes that a calendar share is not proof the bandwidth sustains admission.

### 3.3 Theoretical optimal

**Each protection in the release rule is independently necessary; none of them is "the minimal formula".** Drop "retention discharged" and expiry frees what a group's policy still requires; drop "obligations released" and custody is lost; drop "no promised read" and a reader is torn mid-stream; drop recovery dependencies and a recovered older root references a reused block; drop reservations, prepared successors, outstanding I/O or unresolved recovery candidates and a prepared payload that is reachable from nothing installed is overwritten while its write is still in flight (the Review §H) [Astra, fatal on the draft's four-set root set]. The right form is typed ownership and dependency *edges*, where an identity reference is not a payload-retention edge and a relocation changes placement edges while preserving promise edges; safety is "freed *only if* no edge protects it", and collection *progress* is a separate liveness property under available workspace, functioning storage and fair scheduling. "Freed iff unreachable" confused the two.

**Survivor copying has a cost identity, not an online floor.** Copying `uE` survivors from a victim of capacity `E` yields `(1-u)E` net space: copy writes per net byte are `u/(1-u)`. Perfect placement makes `u = 0` for the victim that dies as a whole; but victims also acquire survivors from leases, checkpoint delays, withdrawals, obligations attached after placement and age variation within a class, and waiting, spare capacity, victim choice and allocation granularity change the problem [Astra]. One policy makes zero-copy expiry *possible*, not universally timely. `health` should report measured backlog (bytes copied, bytes recovered) and predicted future cleaning as separate quantities (§3.4, tradeoff 4).

**A release rule needs authoritative evidence or a proved conservative summary, with explicit clock assumptions** [Astra, replacing "recorded facts, never a proxy"]. A maintained reference count, a conservative bitmap or a retention frontier safely summarizes facts when its invariant proves the needed implication; recording a timestamp does not make the clock trustworthy. KAFKA-8522 condemns the *wrong timestamp semantics* (a segment mtime standing in for the deletion horizon), and its fix still uses time, recorded with the right meaning (`kafka2026-jira-kafka-8522-tombstones-survive-forever.txt`). fn2's rule: every input to release is either committed evidence or a summary whose invariant is carried by the state, and time enters only through specified inputs (arrival time versus authored time, clock jumps and restarts, retention-policy versioning) that the core decides expiry from.

**The clock theorem, narrowed to what is true** [Astra]: *no finite timeout alone implements an indefinite evidence-gated custody obligation or permanent duplicate rejection against arbitrarily delayed re-offers.* fn's peers are not replicas and its clients may be silent for arbitrary periods, so causal stability (the CRDT result, chapter 1) cannot be observed and a timer is unsound for those two contracts for some reachable schedule. Explicitly time-limited contracts (membership retention, a time-boxed operation-identity window, a sealed stream's retention default) are not prohibited; a permanent summary or an epoch-admission rule can prevent resurrection without every holder observing the release. Tahoe's renewable lease promises something else and is right for its contract.

**Distance from optimal.** On the floor for survivor copying under one policy and good prediction; on the floor for the protection set once it is stated as typed edges; above the floor on open tails by the layout's padding; above the floor on release latency by the checkpoint interval, which is the price of recovery never seeing a reused block.

### 3.4 Tradeoffs not yet on the table

1. **Pass the class down as the device's placement hint, through a backend mapping.** `F_SET_RW_HINT` is inode-scoped, so distinct chain hints need distinct files or a backend that maps chains to hints; FDP handles are a budgeted resource that must be assigned per chain with a safe fallback where unsupported; a wrong hint costs write amplification and never correctness, so no platform is refused. Measure host writes and device writes separately, since host-side copying can lower device WAF while raising host writes (SNIA) [Astra].
2. **Cleaning is multi-tenant work with joint causes.** There is no unique "causing principal": admissions, placement choices, victim timing, leases, retention changes and obligations all contribute [Astra]. Under rule 5: charge conservative *reservations* for predicted cleaning at admission and reconcile against measured work; keep a *global* capacity guard so that ordinary writes cannot exhaust relocation workspace even when no obligation kind is being refused; give the cleaner SILK-shaped priorities (urgent relocation and checkpoint work protected, less urgent work preemptible) rather than one bandwidth share; and under pressure preserve a *bounded* read service share, not unlimited read admission. D03's "refuse new obligations at capacity" is the admission side of this.
3. **Erasure is a separate decision, not a retention class** [Astra, fatal on the draft's "erasable class"]. Per-object keys make prompt erasure *possible* (key destruction is the EDPB- and CNIL-endorsed mechanism, `edpb2026-guidelines-022025-blockchain-v2.txt` ¶51–52, `finck2019-blockchain-gdpr-european-parliament.txt` §7.3.2), but deleting a key from current metadata leaves it in journal history, old checkpoints, snapshots, backups and memory; the key needs a separately specified, nonrecoverable lifecycle, key destruction must respect or explicitly supersede outstanding service obligations, and the costs are authenticated framing, nonces, range reads and key management, not one cipher pass. Sealed streams (chapter 5) do not give this under node control either: their keys belong to clients. Keep erasure as its own decision with an explicit adversary and scope; the Merkle leaf's per-record salt (chapter 4, tradeoff 6) is one component of it, not the whole.
4. **A live policy change is priced as a bounded estimate with assumptions.** Lengthening a group's retention turns its bytes in short-class extents into survivors whose copy volume is the surviving bytes themselves (not multiplied again by `u/(1-u)` [Astra]); shortening strands bytes in long-class extents until those die or are cleaned. Class occupancy cannot determine future `u`, pinning, checkpoint delay or a maximum stranding duration, so `policy set` reports a snapshot estimate or bound with its assumptions, says what happens to bodies already reclaimed (nothing: an extension does not resurrect), and `health` carries measured cleaning backlog beside predicted cleaning. STO-038 makes retention settable live; this makes it priced live.
5. **Obligations have sponsors; shared objects have shared accounting.** Protected admission and named refusal are already execution rules [Astra]; the additions are sponsorship for objects with no unique owner (a crosspost; a multiply pinned article), a global physical reserve with a defined sharing of its accounting among principals (including transfer when one obligation ends), and the rule that deleting a principal's account does not delete its obligations. An operator waiver is the escape from an otherwise permanently unsatisfiable obligation (a peer that will never return); normal grounded completion remains the ordinary release. The ClockDAG small-disk case (Clients §1.3) is this at its sharpest.
6. **Capacity pressure must not deadlock maintenance.** The Review §F reserves the checkpoint's allocations and §G backpressures on arena exhaustion; the missing proof is that admission preserves enough disk, journal capacity and working memory to finish relocation, checkpoint construction, anchor promotion and release recording [Astra]. Blocking all commits would block those maintenance commits and the acknowledgements that discharge obligations; so a pressure state *pauses consuming admissions while admitting reserved progress-enabling transitions*, and distinguishes three reasons by name: checkpoint-blocked capacity (a checkpoint will free it), genuinely all-live capacity (nothing will), and uncertainty quarantine (recovery must resolve it).
7. **The inline threshold is tunable, and its intuition is not obvious.** Short-lived inline content may expire before its journal frame is reclaimed and need *no* copy; permanent content inlined in a frame will eventually be copied when that frame is reused [Astra, reversing the draft]. The variables are payload lifetime relative to journal reuse, batching, shared metadata and block rounding; keep `T_inline` a profile value and measure (M1 with the copy-out counted), rather than a per-class default argued from theory.
8. **Survivor segregation is a heuristic worth evaluating, not a bound.** F2FS's cold classification of cleaned survivors predicts future *updates*, not remaining retention; a block can be copied indefinitely after reaching the longest class, and surviving to near a fixed expiry can mean *less* remaining life [Astra]. Use current retention and obligation information where available (the cleaner knows the survivor's requirements) and evaluate survivor segregation as a placement heuristic in the measurement; the draft's "bounded by the number of classes" is withdrawn.
9. **Time semantics are inputs** [Astra, addition]: arrival time versus authored time, clock jumps and restarts, retention-policy versioning, and whether an extension affects existing objects; the core decides expiry from specified inputs only.

### 3.5 Principles from logics and deployments: proving it later

- **The allocator proof's real precedents.** GoJournal supplies atomic journal operations, including allocator-bit updates, and leaves concurrency control to its client; FSCQ's contribution is the disjoint ownership of free and allocated objects; neither states a universal "free durable before reuse" protocol [Astra, correcting the draft]. The closer precedent for the checkpoint conjunct is F2FS's *pre-free* sections, reusable only after a checkpoint (`lee2015-f2fs-flash-friendly-file-system.txt` §2.5). fn2's invariant is the Review §H's: `RETIRE_PENDING → checkpoint no longer needs it → borrows and I/O ended → RELEASE_ALLOCATION → reuse under a new allocation identity`, with a proved conservative ownership/dependency representation that is never rescanned on the served path.
- **A MOVE is a stutter only under an abstraction that hides placement, and proving the stutter is real work**: byte and identity preservation, borrow safety, crash ordering and resource invariants [Astra]. Classes themselves never appear in the abstract state, which is why "hints, never evidence" keeps the proof small; but if classes control charging they affect observable admission and enter the accounting theorems.
- **Obligations are already a theorem shape in fn.** `fn-sys-release-is-grounded-end-to-end` (Clients §3.6) is the obligation conjunct; the keystone transfers to fn2 unchanged in statement.
- **Erasure is not an integrity property with a cipher assumption bolted on.** DiskSec/SFSCQ proves confidentiality across executions under its filesystem threat model, not forensic media erasure (`ileri2018-sfscq-proving-confidentiality-file-system.txt`) [Astra]; key secrecy and destruction need their own threat model, which is why tradeoff 3 is a separate decision.
- **DaisyNFS's division** still applies: allocator, borrows and retirement live in the transaction layer, proven once; the cleaner's *choice* of victim is performance, its *release* is safety.
- **Race witnesses the proof needs** [Astra's list]: an obligation attached between victim selection and release; a BODY lease acquired during relocation; a crash during anchor promotion; an old write completing after restart. Each names the transition that rejects unsafe reuse.

### 3.6 Verdict

**Keep, amended.** Both halves are the production consensus: placement by lifetime (Kafka, F2FS, multi-stream SSDs, Postgres partitions) and release by evidence (ZFS holds, S3 legal hold, fn's grounded release). The draft's reachability restatement was wrong in a way that would have permitted premature reuse, and its erasable class relocated the erasure problem; both are withdrawn. Amended wording for `STORAGE-DESIGN.md` §4.3, Astra's text adopted with the scholar's additions:

> **Retention placement**: group payloads by expected physical lifetime using placement hints; one default class, no resident state per class; class membership never authorizes release. Backend placement hints (mapped per backend to write-lifetime hints or placement handles, with a safe fallback), inline thresholds and survivor classification are optional, measured performance policies. Distinguish logical payload discard from physical placement retirement: discard the last required copy only when all applicable retention requirements and independent durable obligations permit it and no promised read still requires it; a committed relocation may retire an old copy while preserving those requirements at its replacement; reuse an allocation only through the allocator protocol, after protection by current state, recovery dependencies, prepared successors, reservations, borrows, outstanding I/O and unresolved recovery candidates has ended, using a proved conservative ownership and dependency representation never rescanned on the served path. Every release input is committed evidence or a proved conservative summary; time enters only through specified inputs (arrival versus authored time, clock jumps, policy versions). No finite timeout alone implements indefinite custody or permanent duplicate rejection; time-limited contracts are declared as such. Admission preserves globally sufficient maintenance resources and applies explicit principal and sponsor accounting (shared objects, a global physical reserve, obligations surviving account deletion, operator waiver only for unsatisfiable obligations); cleaning is reserved conservatively and reconciled against measured work, with SILK-shaped priorities and a bounded read service share under pressure. Capacity pressure has named reasons (checkpoint-blocked, all-live, uncertainty quarantine), pauses consuming admissions and admits reserved progress-enabling transitions. A live policy change reports a bounded estimate with its assumptions; cleaning and checkpoint progress, live bytes, reclaimable bytes, bytes blocked by recovery or borrows, relocation workspace and permanent identity metadata are separately observable. Erasure is a separate decision with its own adversary, scope and key lifecycle.

**The measurement that settles the remaining doubt.** A *pre-aged* cleaning scenario [Astra's correction]: prefill three classes (1-day, 30-day, permanent) to steady state at 1,000 POSTs/s with 1.5 memberships and 1% late-pinned articles, run through repeated cleaning at the longest class, then lengthen one group's retention and shorten another; compare fixed-budget placement policies (with and without survivor segregation); report copy bytes per net byte against `u/(1-u)`, padding per batch for the chosen layout, measured backlog versus the pre-change estimate, p99 read latency during cleaning with and without SILK-shaped priorities, and on a real SSD (M7 extended) host writes and device writes separately with and without per-chain hints.

## Chapter 4. Integrity: a Merkle event log, physical predecessor links, parent-held page hashes, and a typed signed checkpoint claim

### 4.1 The decision as a claim

**Claim.** From the first format fn2 carries three integrity structures with three subjects. (1) *Physical page integrity*: every reference carries the expected hash of the page it names, the page's header carries its own location and allocation identity, and a read must match both, so that a valid page from another location or generation is rejected (the Review §B). (2) *Physical commit order*: every sealed batch names its predecessor's commit number and seal hash, so recovery reconstructs the chain of batches, maintenance-only batches included (the Review §E; correction 3). (3) *Semantic inclusion and extension*: a Merkle tree over the canonical encodings of semantic events, with domain-separated leaves and interior nodes and an explicitly specified append-only shape, whose frontier and proof material are paged; at each checkpoint the node signs a *typed claim* naming at least the history identity and incarnation, the event cut and root, the fold/schema identity, the summary commitment, the exact-identity commitment, the checkpoint descriptor commitment and the signing key identity (the Review, decision 4). A peer or client that keeps a signed claim is an independent witness whose coverage makes rollback detectable to that extent (`A-INDEPENDENT-FRONTIER`); the claim is issue #17's checkpoint-substitution object. Recovery reconstructs candidate histories through the two anchor banks and the journal (the Review §F, §I) and only then compares them with independent frontier evidence (§I.8).

**What it buys.** Under the broad fault profile, tearing, rot, misdirection and stale (lost) writes are detected for every page reached through a verified reference, at one hash per page verified at cache fill, with cold pages checked on access or by scrub rather than at open (the Study §G; the Review's scope qualification). Recovery can tell "a predecessor is missing" from "the tail is torn" because the chain names what must exist. A holder of a signed claim can verify in `O(log n)` hashes that an event is in the history (inclusion) and that a later history extends an earlier one (consistency), so a receipt can cite something checkable and a fork becomes evidence when two signed views that cannot be reconciled meet. The signature turns a checksum into a claim an adversary who can write the disk cannot forge.

**What it gives up.** (a) About two hashes per appended event plus a root recomputation per batch, and proof material whose retention is an explicit obligation (§4.3). (b) Three structures to specify and keep consistent, where one would be simpler; the Review's argument that their subjects differ stands, and witnesses of the *event* root do not cover maintenance-only commits, which the physical chain and descriptor binding must carry [Astra]. (c) A typed claim is a format commitment: a verifier must be required to check its fields, and the transparency ecosystem's checkpoint body treats anything beyond `origin / size / root` as ignorable or unsigned (§4.2). (d) The signing key is part of the trust model: activation, overlap, revocation and distribution to witnesses need protocol; a compromised key can sign a fork that witnesses detect and cannot adjudicate, and witnesses cannot re-cosign a branch that conflicts with what they previously signed [Astra]. (e) The claim does not prevent equivocation; it makes certain conflicts (same size, different roots; conflicting authenticated openings at one position) concrete evidence, and makes the rest detectable only by clients that retain heads and check every accepted extension (Cox).

### 4.2 State of the art

- **Certificate Transparency (RFC 6962, RFC 9162).** The Merkle Tree Hash with domain separation, `MTH({d0}) = HASH(0x00 || d0)` and `MTH(D_n) = HASH(0x01 || MTH(D[0:k]) || MTH(D[k:n]))`, "required to give second preimage resistance"; a consistency proof from size `m` to `n` is the node list showing the first `m` inputs equal in both trees and "prove[s] the append-only property"; the v2 signed tree head is `{timestamp, tree_size, root_hash, sth_extensions}` under a log ID, with extensions authenticated but semantically ignorable [Astra]; each timestamp must exceed the last and freshness is required even during inactivity; a log "MUST NOT produce STHs more frequently than its parameters declare", because STHs can be used to mark clients (`rfc9162-certificate-transparency-v2.txt` §§2.1.1, 2.1.4, 4.1, 4.9–4.10). Split views are "detected by multiple clients comparing their instances of the STHs … gossip … not defined here" (§11.3); the gossip draft expired without standardization (`nordberg2018-draft-ietf-trans-gossip-05.txt`). Chrome's policy forbids "two or more conflicting views of the Merkle Tree at different times and/or to different parties", treats merge-delay breaches from load as typically not removal-worthy and inconsistent heads as typically removal-worthy, at its discretion (`chromect2026-docs-log-policy.md`; Aviator 2016, whose lesson is backlog control, `ctpolicy2016-google-aviator-incident.txt`). The incident that matters most for decision 4: in February 2017 Venafi's log signed two tree heads (sizes 90161 and 90167) with no consistency proof between them, because during an AWS outage an auto-scaling replacement restored "the last successful backup which did not reflect the current state of the database" and "signed the incorrect tree head"; Venafi reported no lost certificate data and restored the correct state, and the violation was nevertheless an inconsistent *published* view (`ctpolicy2017-venafi-inconsistent-sths.txt`). The lesson is "never sign after a restore before re-establishing the frontier", not "every restore is a new history" [Astra] (§4.4, tradeoff 4).
- **Trillian's verifiable data structures** (`eijdenberg2015-verifiable-data-structures.txt`). A verifiable log, a verifiable map (a sparse Merkle tree keyed by `SHA-256(key)`), and a *log-backed map* whose Signed Map Heads each commit to a log size and head and are themselves logged, in a *separate* log, so that a full audit can replay the map's evolution; the paper assigns *correct* evolution to that full audit, so logging a dishonest head makes it auditable, not correct [Astra]. fn2's summary and exact-identity commitments are map heads of this kind; their proofs are relative to the map root and never establish correct folding, authorization or freshness.
- **Go's transparent log and the C2SP checkpoint ecosystem.** Cox's client caches `(N, T)`, verifies a `TreeProof(cached.N, N)` before advancing and otherwise "fail[s] loudly"; "permanent" hashes (completed subtrees) never change, storage is `lg N` append-only hash files at just under two new hashes per write, and a server that tells clients apart "can still serve different logs to different clients" but "must keep up the lie, forever", which depends on clients retaining heads and checking every extension (`cox2019-transparent-logs-skeptical-clients.txt`). The C2SP checkpoint body is three lines, `<origin>` (a unique log identity that "forms part of the log claim"), `<decimal tree size>`, `<base64 root hash>`, optionally followed by opaque extension lines, then signed-note signatures whose 4-byte key id is a *lookup identifier* (`SHA-256(name || "\n" || algorithm byte || public key)[:4]`), explicitly not a cryptographic commitment; security comes from configured keys and algorithms (`transparencydev2026-docs-checkpoint-format.md`, `c2sp2026-docs-tlog-checkpoint.md`, `c2sp2026-docs-signed-note.md`) [Astra]. Extension lines are "NOT RECOMMENDED, as they are neither auditable by log monitors, nor signed in all signature algorithms" (ML-DSA-44 cosignatures cover only the first three lines), and "a log or cosigner MUST NOT sign any checkpoint which is inconsistent with any checkpoint it previously signed"; cosignatures carry their own signed timestamps (`c2sp2026-docs-tlog-cosignature.md`). Witnesses keep only the latest checkpoint per origin, answer a wrong `old <size>` with 409 and a same-size different root with 422 (and may keep it as evidence), and "MUST persist the new checkpoint before responding", with check and persist atomic, the spec spelling out the race in which two concurrent requests end with the witness "rolling back K leaves" (`c2sp2026-docs-tlog-witness.md`). None of this was prescribed by the Review (which never mentioned extension lines [Astra]); it is the environment any typed claim has to live in.
- **Sigsum** (`moller2023-sigsum-design-cats.txt`, 2023; `sigsum2026-docs-policy.md`). "No gossip protocols have been deployed for logs in practice" (as of 2023); a witness cosigns a head "only after verifying that the tree head is consistent with previous tree heads cosigned by the witness", a policy file names logs, witnesses, groups and a quorum rule, and "verification for users become[s] binary". The policy language permits `any` and even `none`, so a policy alone proves nothing about agreement [Astra]; §4.3 gives the condition.
- **Fork consistency** (`mazieres2002-secure-filesystems-byzantine-storage.txt`; `li2004-sundr-secure-untrusted-data-repository.txt`; `cachin2007-fork-linearizable-untrusted-memory.txt`). A system is fork consistent iff a forking tree exists over its completed *client operations* (Definition 6); "fork consistency is the strongest notion of integrity possible without on-line trusted parties"; silently discarding an offline user's changes "is the only type of undetectable attack", exposed by any later communication between the users; a small trusted consistency server "trivially guarantees fetch-modify consistency". Cachin's Theorem 1: in his Byzantine-register emulation model, any fork-linearizable protocol has a run with a correct server in which a client cannot finish until another takes steps (not even obstruction-free); Theorem 4: no sequential consistency for more than one single-writer register in that model. These results are about client operations and their legal views, within their models; fn2 still needs its response-to-history binding before they apply [Astra].
- **Rollback protection in hardware** (`parno2011-memoir-state-continuity.txt`; `matetic2017-rote-rollback-protection.txt`). Memoir's contribution is *avoiding* monotonic counters, using deterministic replay and only two NVRAM writes per boot, because a counter alone "is not crash resilient" and TPM NVRAM takes 34–82 ms per write and wears out at about 100,000 cycles [Astra, correcting the draft]; its state-continuity proof in TLA+ is 243 definitions, 74 theorems and 5,816 steps. ROTE spreads a counter across `f+1` enclaves at 1–2 ms under its enclave adversary model, which permits resetting the whole protection group. Neither prices a generic durable witness service; both say a local continuity argument must be designed with crash recovery.
- **Parent-held hashes and protocol-aware recovery.** TigerBeetle's grid and ZFS's block pointers (the Study §G); CTRL distinguishes a crash-torn tail from mid-log corruption and repairs from peers instead of truncating (`alagappan2018-protocol-aware-recovery-consensus-storage.txt`). The io_uring reports scout A collected principally demonstrate *application completion-accounting errors* [Astra]: byte counts overwritten and stale CQEs misattributed (`mooncake2026-issue-3066-io-uring-silent-corruption-5-15.txt`), short `ENOSPC` completions ignored (`nixl2026-issue-1696-io-uring-enospc-short-writes.txt`), link chains not working across submission boundaries (`liburing2022-issue-510-io-link-out-of-order.txt`), plus a kernel-version hang (`mariadb2021-jira-mdev-26674-io-uring-hangs.txt`) and Docker's seccomp blocking io_uring (`moby2024-issue-47532-io-uring-blocked-seccomp.txt`). The rule they support: check request identity, exact completed length and outstanding borrows before fencing or reusing memory; a short completion is not success (it may sometimes be continued); the epoll/worker backend is required by the seccomp reality (Envelope §1.7), not by these bugs.
- **Erasure against an immutable log** (`edpb2026-guidelines-022025-blockchain-v2.txt` ¶¶51–54, 63, 103–104; `finck2019-blockchain-gdpr-european-parliament.txt` §7.3.2). Encrypted personal data "is still personal data", encryption "will be overtaken by time", unkeyed hashes are "in general, not … sufficient", a salted or keyed hash is unlinkable only if the salt or key *and the original data* remain confidential and are then deleted, a hiding commitment becomes "useless" once data and witness are deleted, effective deletion or anonymization is required and personal data should not be put on-chain at all; "technical impossibility cannot be invoked". Finck presents key destruction as the CNIL-endorsed conditional alternative and leaves questions open. §4.4, tradeoff 6.

### 4.3 Theoretical optimal

**Proof sizes.** In Tamassia's hash-DAG authenticated-dictionary model, with `k` signed digests over `n` items, update and query time, proof size and verification time are `Ω(log(n/k))` in the worst case (Theorems 3 and 6), the best tradeoff is `O(1)` signatures with `Θ(log n)` hashing, and trees are optimal among DAGs (`tamassia2005-computational-bounds-hierarchical-data-processing.txt`) [Astra, correcting the formula]. It is a bound for that model, not for every commitment scheme. RFC 6962-shaped inclusion and consistency proofs are `O(log n)`: ~20 hashes, 640 B at 10^6 events for binary inclusion [D]; representations that keep only permanent nodes (Cox's tiles) can give larger proofs. A Merkle mountain range stores `n − popcount(n)` interior nodes for its completed forest, appends in postorder despite the note's "breadth first" wording, and is compatible with a C2SP root only if its peak aggregation equals the RFC 6962 tree hash (`opentimestamps2026-docs-merkle-mountain-range.md`) [Astra].

**Rollback detection: the ceiling, and the condition that makes a quorum safe.** Without an online trusted party the best any protocol can promise over an untrusted store is fork consistency (SUNDR), and signed claims make certain conflicts into evidence: same-size different roots, or conflicting authenticated openings at the same position; two signed roots of *different* sizes are not by themselves proof, since failing to obtain a consistency proof is not proof that none exists [Astra]. A witness set is an online trusted party only under an *agreement* condition: every pair of accepted quorums must share an honest witness, across policy changes; for a uniform `q`-of-`N` policy with at most `f` Byzantine witnesses, `2q > N + f` suffices; and each witness's persistence must itself resist the rollback in the threat model (the C2SP check-then-persist race) [Astra]. Two disjoint sets of honest witnesses can otherwise cosign incompatible branches, and sigsum's `any`/`none` policies show the policy language does not supply this. Local commits remain independent of cosigning, so their acknowledgements lack quorum protection until a covering checkpoint is cosigned; that is a stated coverage delay, not a CAP theorem (Gilbert–Lynch concerns an available atomic read/write object, `gilbert2002-brewers-conjecture-cap.txt`; the corresponding fn2 operation would be a *witnessed* read, which fn2 does not offer) [Astra].

**What a signed root proves, narrowly.** A signature authenticates a commitment; inclusion and consistency require proofs; a map proof authenticates an answer relative to the map root and establishes neither correct folding nor authorization, freshness or correspondence to the event history, which full audit establishes (Trillian) [Astra]. So decision 4 does not imply membership and non-membership interfaces for every summary; interfaces follow from promised queries, and for exact identity a hash-keyed sparse map still needs exact-key collision handling, since hashing cannot replace fn2's identity comparison (chapter 1 §1.3).

**Retention of proof material is an obligation, not a bound.** Dropping a subtree's leaves while retaining its root preserves proofs for leaves outside it and sacrifices openings inside it [Astra]. The format must state which events and historical cuts remain provable, who retains openings, and which subtree hashes support them; "retain every leaf forever" is one policy (32 B per event), not a necessity, and Cox's "permanent hashes" is about structural immutability, not retention. The physical chain's seals are retained while recovery may select a checkpoint that needs them.

**Cost of signing.** Ed25519 at ~30 µs to sign and ~78 µs to verify per KiB (Clients §1.2) is nothing per checkpoint; the hybrid ML-DSA-65 profile (D09) adds a 3,309 B signature per claim, also nothing per checkpoint and the reason the claim is signed per checkpoint, never per event. C2SP's cosignature algorithms (ML-DSA-44, fixed-width fields) are not D09's profile; an interoperability profile must bridge them (§4.4, tradeoff 9).

**Distance from optimal.** At the model's bound for proofs; at the fork-consistency ceiling without a quorum and at agreement with one; above the minimum in the claim's construction (§4.4, tradeoff 1) until the cycle is removed, and in the erasure story (tradeoff 6), which is a restricted proof contract rather than erasure.

### 4.4 Tradeoffs not yet on the table

1. **The typed claim as a logged statement about the *previous* cut.** Putting the typed fields in extension lines would be the thing the ecosystem warns against, and the draft's "claim as an event preceding the root" was circular: it logged a claim containing the root before computing that root, and its descriptor commitment can cycle through the batch seal, which the Review §E explicitly avoids [Astra, fatal]. The sound form: log a *statement about an already determined predecessor cut* `(k, root_k, fold-id, summary_k, identity_k, descriptor_k, key id, …)`, appended at `k+1` as an ordinary event with a defined effect on folds and numbering, and authenticate it by an inclusion proof under the enclosing standard three-line checkpoint (`origin` naming the history; size; root), with no recursive reference to the enclosing root or seal. Standard witnesses and cosignatures then apply unchanged; the typed claim is authenticated through inclusion rather than through its own signed body; and checkpoint inclusion is understood to establish neither correct folding nor query completeness, availability or freshness.
2. **Witness cosigning with honest-quorum intersection as the mechanism behind `A-INDEPENDENT-FRONTIER`.** Witnesses (peers that replicate a stream, receipt-keeping clients such as Mini, and the node for the peers it pulls) cosign a head only after verifying consistency with every head they previously cosigned and after persisting it, atomically (durable linearizability of check/persist/reply, §4.5). The acceptance policy states its fault assumptions, the honest-intersection requirement between every pair of accepted quorums (including across policy changes) and its transition rules [Astra]. Three kinds of durability are then distinct and named: *local durability* (fenced), *signed coverage* (a cadence checkpoint covers the event) and *policy-accepted witnessed coverage* (a quorum cosigned it); an acknowledgement is locally durable at once and witnessed only after a coverage delay. Witness coverage is an explicit lower bound in recovery.
3. **Keys: an executable rotation protocol, not a logged epoch.** Standard witnesses check configured log keys and Merkle consistency and do not interpret fn2's logged key statements, so "new key authorized" in the tree updates nothing a witness trusts [Astra]. Specify activation, overlapping validity, revocation and policy distribution to witnesses (sigsum's policy file is the distribution channel); carry the authorized key set in the typed statement for auditors. After compromise, recovery authority and append-only evidence are different things: witnesses cannot re-cosign the operator's preferred branch if it conflicts with their prior signatures, and the operator's remedy is a declared discontinuity (tradeoff 4), never a request that witnesses break their consistency obligation.
4. **Lineage, written against Venafi, without laundering.** A restore that *replays to the established frontier* preserves lineage and needs no new incarnation; the Venafi rule is simply never to sign before the frontier is re-established [Astra, fatal on the draft's "every restore is a new incarnation"]. An incarnation-change leaf cannot make an incompatible tree consistent, and standard witnesses must refuse such a continuation under the same origin regardless of explanation. Irrecoverable loss therefore requires a *declared discontinuity*: a new origin, an explicit lineage policy relating it to the old history, and preservation of old receipts, identities and obligations (chapter 1's identity set and chapter 3's obligations survive the discontinuity), never a higher counter that cancels prior promises. "Not changed merely by restarting" (the Review §A) keeps its Memoir-shaped continuity argument.
5. **Cadence and receipts are two contracts.** An event committed after the latest cadence checkpoint has no inclusion proof under it; a receipt is therefore either a wait for a covering checkpoint, a local durable acknowledgement with proof pending, or another named receipt contract [Astra]. Cadence needs a publication rule (RFC 9162's freshness, including during inactivity) and a coverage-delay contract; per-client STHs are never minted (client marking); a single timestamp chosen for a shared checkpoint does not prevent cosignature merging, and C2SP cosignatures carry their own timestamps, so timestamps may live in the statement or beside it; published checkpoints and signatures are reused rather than re-issued.
6. **A confidential-opening scheme is a restricted proof contract, not erasure.** A per-record salt stored with the record and destroyed with it makes the leaf unlinkable only if the salt and the original data were never disclosed: an ordinary public opening of `H(salt || record)` reveals the salt, deleting fn2's copy cannot erase recipients' openings, backups or cached proofs, and a leaf that also commits to the public Message-ID and signer keeps those associations after any content key is destroyed (EDPB ¶52) [Astra, fatal on the draft's erasure claim]. The honest option is a *confidential opening store*: proofs about a record are served only to parties entitled to its opening, the scheme states its disclosure and erasure limits, and permanent exact identities remain part of the privacy analysis (chapter 1, tradeoff 7; chapter 3, tradeoff 3). This belongs to the separate erasure decision.
7. **Equivocation evidence, stated exactly; mutual witnessing as optional infrastructure.** Same-size different cosigned roots, or conflicting authenticated openings at one position, are evidence; different sizes without a consistency proof are not. Clients that want Cox's guarantee retain heads and check every accepted extension. The node *may* witness the peers it pulls (it already keeps their roots for consistency proofs, the Study §I); doing so attests consistency only, never that it stores their articles or accepts custody, which need separate statements [Astra].
8. **Proof-service obligations, declared.** Which events and cuts remain provable after reclamation, who retains openings, and which subtree hashes are kept: a retention class for proof material per stream, stated in chapter 3's edge terms so the cleaner never drops a hash a declared obligation needs. The default for the first format may be "all leaves retained", as a policy.
9. **An interoperability profile** [Astra, addition]: the Merkle algorithm, the signature acceptance rule, encoding versions, and the bridge between C2SP's fixed-width cosignature fields and witness proof limits and fn2's extensible counters; C2SP's ML-DSA-44 is not D09's ML-DSA-65 hybrid, so either fn2 signs checkpoints under a C2SP-compatible key beside its own profile or it runs its own witness software.
10. **Witness recovery protocol** [Astra, addition]: bootstrap trust, retrieval freshness and policy updates; C2SP's monitoring endpoint can lag, so "the last cosigned head" is not automatically an authoritative latest-frontier read, and recovery compares independent evidence with the *reconstructed compatible frontier* (the Review §I.8): an older anchor plus a valid journal suffix may recover beyond a witness's head, contradictory evidence prevents normal rollback, and the absence of a witness ahead never establishes `intact` [Astra, correcting §4.1 and the draft's experiment].
11. **Portable source integrity stays a separate proof** [Astra, addition]: the Review's correction 10 (BLAKE3 range verification with length, chunk position, final-block and root-output handling) is distinct from event inclusion and physical page verification; the chapter's three subjects are four once content identity is counted.

### 4.5 Principles from logics and deployments: proving it later

- **Grove supplies the vocabulary, not the theorem.** Grove's append-only ghost resource `a ↦ ℓ` (updated only to `ℓ ++ ℓ'`) and its duplicable lower bound `a ⊒ ℓ`, with monotonic epoch lower bounds (`sharma2023-grove-separation-logic-distributed-systems.txt`, "Logs"), is the shape in which a witness's retained head is written. But the lower bound denotes an actual abstract prefix: a signed `(size, root)` becomes evidence for it only after proving the cryptographic interpretation, the witness transition and the durable-state invariant, and assigning incompatible witness observations one global resource would assume the agreement being proved [Astra]. Incarnation changes are not automatically epoch transitions.
- **Durable linearizability is the witness's obligation.** The witness's check/persist/reply is a durably linearizable append-only register (`izraelevitz2016-durable-linearizability.txt`, Definition 3), or the C2SP race rolls back `K` leaves. fn2's own checkpoint is not "buffered durable" [Astra]: acknowledged commits are durable through checkpoint *plus journal*, and checkpoint lag never licenses losing a completed operation.
- **Fork consistency, with the binding it needs.** The top-level statement without a quorum is Mazières–Shasha's Definition 6 over *client operations*, which requires fn2's response-to-history binding (a reply cites the cut that covers it) before SUNDR's client protocol applies; with an honest-intersecting quorum it strengthens to "no two accepted-quorum-cosigned heads are inconsistent". Cachin's impossibilities hold in their emulation models and are the reason not to promise fork-linearizable *reads* [Astra].
- **The physical chain is the cheap part; the typed statement's semantic fields are the dear part.** fn1's chained trailers are a keystoned shape; the batch seal with its predecessor hash is a local induction over the journal. The statement's summary and identity commitments are only as good as the fold equation (chapter 1) and the authenticated map's correctness, which are the expensive proofs; the Merkle tree over canonical fixed-width encodings is route 2 material (FGL for the structural lemmas, `swords2020-acl2-fgl-new-rewriter-features.pdf`), while collision resistance stays `A-CRYPTO`.
- **Cost warnings.** Memoir's 74 theorems are the size of a *replay-based* continuity argument; seL4's data says a change cutting across invariants costs a third of the original effort (`klein2014-sel4-comprehensive-formal-verification-tocs.txt`), which argues for fixing the statement's *content* and the interoperability profile before any proof starts. Verdi's transformer route (`wilcox2015-verdi-distributed-systems.txt`) is the order for the witness protocol: simple network first, drops and crashes by transformer.

### 4.6 Verdict

**Keep, amended.** The three-subject design is right and each subject has a settled precedent (ZFS and TigerBeetle for pages; chained seals for physical order; CT, Trillian and the C2SP ecosystem for semantic inclusion and extension). The draft's amendments were right in direction and wrong in three places (a circular claim, a quorum without an intersection condition, an incarnation that could launder inconsistency) and overclaimed erasure; Astra's wording is adopted with the scholar's additions. Amended wording for `STORAGE-DESIGN.md` §4.4:

> **Integrity**: parent-held physical hashes binding allocation context; explicit predecessor commit and seal links in every sealed batch, maintenance batches included; and a domain-separated append-only Merkle event log with a pageable frontier and proof material. A versioned typed checkpoint statement binds history and incarnation, an explicit event cut and root, fold/schema identity, summary and exact-identity commitments, an acyclic checkpoint descriptor and the authorized signing keys; for transparency interoperability it is logged as a statement about an already determined predecessor cut and authenticated by inclusion under the enclosing standard three-line checkpoint (origin naming the history; size; root), under a declared interoperability profile (tree hash, signature acceptance rule, encodings, counter bridge); neither the statement nor its descriptor references the enclosing root or seal. Checkpoint inclusion establishes neither correct folding nor query completeness, availability or freshness; portable source verification (BLAKE3 range proofs) is a separate contract. Local durability, signed coverage and policy-accepted witnessed coverage are distinct; shared checkpoints are published at a declared cadence with freshness, only covering checkpoints support inclusion receipts, and no checkpoint is minted per client. Witnesses atomically verify extension and persist their frontier before replying; the acceptance policy states its fault assumptions, the honest-quorum-intersection requirement between every pair of accepted quorums, key activation, overlap, revocation and distribution, and its transition rules. Recovery reconstructs candidates through anchors and journal before comparing independent frontier evidence; contradictory evidence prevents normal rollback; witness coverage is an explicit lower bound. Compatible restoration preserves lineage and never signs before the frontier is re-established; an irrecoverable discontinuity requires separately authorized lineage establishment under a new origin and never cancels prior promises, identities or obligations. Integrity material is retained according to declared recovery and proof-service obligations; any confidential-opening scheme states its disclosure and erasure limits, and deleting a salt or key does not erase previously disclosed associations or independently retained identity metadata.

**The measurement that settles the remaining doubt.** A VOPR scenario family with the oracle checking promises and evidence rather than relative counters [Astra's additions adopted]: disjoint quorums under a policy that lacks intersection (the oracle must flag the policy, not the run); witness rollback and persist-before-lost-response; stale monitoring replies; an older anchor with a sufficient journal suffix recovering beyond a witness head (must be `intact`, not `damaged`); a witnessed semantic head with lost maintenance state (must be `damaged`); restore-and-replay to the frontier (lineage preserved) against irrecoverable loss (discontinuity required); crashes at every anchor and witness boundary. Beside it, cost: Merkle hashes per batch, proof material retained per 10^6 events under the chosen proof-service obligation after 50% payload reclamation, and the coverage delay from commit to witnessed coverage at the chosen cadence with two simulated witnesses.

## Chapter 5. Sealed streams: client-encrypted opaque content with an explicit public envelope

### 5.1 The decision as a claim

**Claim.** A stream may be declared *sealed*. Its articles' authored sources are encrypted by clients before signing; the node stores, authenticates, indexes and serves ciphertext under the ordinary signed-record contract, holds no application decryption key and indexes only deliberately public fields. Each sealed article has an explicit public *envelope*: Message-ID, signer, stream, size, and whatever public fields the application deliberately supplies. The node checks the outer signature at admission as for any native article (which establishes who endorsed these bytes, not that encryption was done correctly [Astra]), builds overview and serves search over public fields only, and carries withdrawals and acknowledgements in the clear by Message-ID. The design creates no key-management protocol in the node: key establishment, rotation, membership, padding and encrypted client indexes belong to the application's protocol; the storage order can support an MLS delivery service under an explicit client integration protocol. Tahoe's verify/read distinction applies (verification operates on ciphertext commitments without decryption); Tahoe's time-expiring leases do not (the Review, decision 5).

**What it buys.** Content confidentiality from the node, its operator and relays as an *architectural boundary*, with no decryption-specific machinery in the node: fn already keeps "no secrets (encrypt before signing)" (Clients §1.1) and D09's signatures already bind the authored bytes. Repair and custody (BP carriers, ClockDAG devices) use ciphertext commitments unchanged. The node's total order per domain is what RFC 9750's ordering delivery service provides for MLS, given the client rule "apply the first valid Commit for an epoch, your own only after ordered delivery" and the bootstrap traffic (KeyPackages, Welcome) that is not an ordinary sealed event [Astra].

**What it gives up.** (a) Every node-side function that reads content: overview beyond public fields, threading by content, XPAT over bodies, the "what did we decide about X" search over sealed plaintext (issue #1), content moderation; withdrawal, admission, quotas and metadata policy remain. (b) The envelope *is* disclosure: signer, size, commit order and arrival time, stream, relations and any public field are seen by the node and, for the canonical object, by every relay; observers differ in what else they see (§5.4, tradeoff 8). (c) Client-side search over sealed content leaks through access patterns unless the client fully synchronizes and searches locally (§5.3). (d) The node cannot distinguish a validly signed undecryptable object from a good one; recipient acceptance and node acceptance are different events with different charges (§5.4). (e) Encryption promises neither erasure nor permanent secrecy (EDPB ¶51; group and session keys, backups and recipients' plaintext copies survive a content key), so sealed streams need declared confidentiality horizons and crypto-agility, not a slogan.

### 5.2 State of the art

- **MLS (RFC 9420, RFC 9750).** The wire object is `PrivateMessage {group_id, epoch, content_type, authenticated_data, encrypted_sender_data, ciphertext}`; sender data (`leaf_index, generation, reuse_guard`) and the signature (`FramedContentAuthData`) are inside the ciphertext (`rfc9420-mls-protocol.txt` §6.3); the delivery service sees "an opaque group_id, … the epoch of the group (the number of changes …), and whether the message is an application message, a proposal, or a commit", custom public metadata belongs in the authenticated `authenticated_data` field, and the architecture document itself notes that the service may still identify senders through authenticated transport, addresses and fan-out (`rfc9750-mls-architecture.txt` §§8.1, 8.1.1, 8.4) [Astra]. The delivery service is "trusted to break ties" between concurrent commits (§5.2). So MLS hides the *content signer* from the service at the protocol layer and fn2 publishes it; the difference is deliberate and narrower than "anonymous versus accountable" (§5.4, tradeoff 1).
- **Matrix.** Ten years of "public envelope with application fields" in production. On an `m.room.encrypted` event the cleartext wrapper is `type, event_id, sender, origin_server_ts, room_id, unsigned` (where `unsigned` is not authenticated) and the content's `algorithm, ciphertext, session_id` (plus deprecated `sender_key, device_id`); `m.relates_to` "MUST be included in the cleartext portion of the event … the server cannot decrypt the event", because the server aggregates relations, and clients are told to prefer the cleartext copy (`matrix2026-docs-m-room-encrypted-schema.yaml`, `matrix2026-docs-room-event-schema.yaml`, `matrix2026-docs-client-server-api.md`). The difference from fn2 is *compulsory* versus *application-selected* public fields [Astra], and Matrix's encrypted edits and reactions are the clean example of relation structure leaking through an envelope.
- **Signal.** Sealed sender moves the sender inside the encrypted envelope as a short-lived sender certificate because the service needs "where a message should be delivered" but not the sender; the article acknowledges timing and IP correlation; its 96-bit delivery token authorizes delivery *to a recipient*, not accountable per-sender quotas (`signal2018-blog-sealed-sender.txt`) [Astra]. The private group system stores encrypted membership entries and has members prove membership in zero knowledge with keyed-verification anonymous credentials, hiding identities while exposing encrypted entries and their access and update patterns (`chase2020-signal-private-group-system.txt`). Both are precedents for a hidden-signer profile, which changes authorization, signer chains and public evidence, not merely an envelope field.
- **Tahoe-LAFS.** A verify-cap "allow[s] a file checker/repairer to confirm that the contents exist, but does not let it decrypt the contents"; Tahoe offers random-key encryption beside convergence, and its convergence derivation includes a secret against guessing attacks; a verify-cap authenticates the object or version its commitment covers and mutable verification alone does not establish freshness; repair needs surviving shares and authority to store replacements (`tahoelafs2026-docs-uri.rst`, `tahoelafs2026-docs-file-encoding.rst`, `tahoelafs2026-docs-architecture.rst`) [Astra]. The useful conclusion is *no decryption-specific verification machinery*, not "free" verification. Leases are time-based with GC off by default; decision 5's rejection of the timer stands (chapter 3).
- **Searchable encryption and its leakage.** Curtmola et al. define security against a *trace*, "exactly the information we are willing to leak", with the access pattern and the search pattern as canonical leakage, and the adversary's view must be *simulatable from* it (`curtmola2006-searchable-symmetric-encryption.txt` §3). Cash et al.'s levels L1–L4 describe particular occurrence-pattern disclosures of pseudorandom tags (sorted tags L2, unsorted L3, at upload time); the count attack recovers queries from result counts; in their experiments padding against it needed at least a 1.6× larger index and one known email to 500 Enron employees revealed about 35% of the keywords in the others (`cash2015-leakage-abuse-searchable-encryption.txt` §§2, 4–5); Islam et al. recover about 80% of queries from the access pattern given a keyword co-occurrence model (`islam2012-access-pattern-disclosure-searchable-encryption.txt` §6). These are experimental results for specified attacks and datasets [Astra]; the transferable lesson is that literal public words are *direct disclosure*, stronger than any SSE leakage level, and that selective fetches from an encrypted index disclose access patterns.
- **Capabilities, and what a kernel can and cannot do.** Miller's sealer/unsealer pairs give "security properties similar to public key encryption" *within an enforced object-capability environment*, not against that environment's operator; caretakers explain revocable mediated access (`miller2006-robust-composition-thesis.txt` §24.1; `miller2003-capability-myths-demolished.txt`) [Astra]. seL4: a capability is "an unforgeable token that references a specific kernel object" carrying rights, mintable with a subset of rights and revocable through the derivation tree; badges label *invoked capabilities* (28 usable bits on 32-bit platforms, 64 on 64-bit) and delegated copies retain them; there is no sealed-data object type; kernel rights concern kernel objects, so stream-level read and append attenuation still needs a service protocol and its enforcement (`sel4-2026-reference-manual.txt` §§3.1.2, 4.2.1) [Astra]. Confinement of the node is a configured-system argument (no key via IPC, shared memory, initialization or collusion), not a consequence of lacking one capability.
- **Erasure and crypto-agility** (`edpb2026-guidelines-022025-blockchain-v2.txt` ¶¶51, 63, 103–104; `finck2019-blockchain-gdpr-european-parliament.txt` §7.3.2). Key destruction is a conditional alternative, not blanket erasure; encrypted data remains personal data; effective deletion or anonymization is required; personal data should not be on-chain at all; Finck leaves questions open [Astra].

### 5.3 Theoretical optimal

**The envelope is a leakage specification, and the claim is simulatability.** Write the allowed disclosure of a sealed stream as `L(trace)` in Curtmola's sense and state, per observer (node, relay, their collusion), what the observer learns: envelope fields, lengths, commit order and arrival times, observable traffic, withdrawals and acknowledgements. The security claim is that each observer's real view is *simulatable from* `L`, under stated cryptographic assumptions, honest-client conditions, auxiliary information and adaptive interaction [Astra, replacing the draft's "the envelope is the leakage function"]. There is no demonstrated Pareto frontier: fn2's point ("what the node orders, attributes and indexes is public; the rest is sealed") is a *chosen* disclosure, with known alternatives at each term: the content signer can be hidden at the protocol layer (MLS, Signal) with a separate authorization and evidence contract; lengths can be bucketed (revealing the bucket, costing up to the bucket's rounding, defeated by any true-length public field); the store necessarily observes its own commit order and timing but need not learn authored times or distinguish cover traffic from messages (fixed-rate transmission, dummy messages and cross-message padding are the application's options, RFC 9420 §15.1; out of scope by choice, not impossibility); query-dependent fetches leak access patterns, and the ORAM lower bound applies only in its model (Goldreich–Ostrovsky's balls-and-bins; later online-model bounds), while full local replication, scans, PIR and server computation trade different resources [Astra].

**Context binding is required in both signing orders, and the node can only check half of it** (Davis, *Defective Sign & Encrypt*, 2001). Re-signing a ciphertext is an authorship attack only if recipients read the outer signature as authorship of the plaintext, so the signature's meaning must be defined. For encrypt-then-sign (fn's order), bind the immutable context into the AEAD's associated data and sign context plus ciphertext. For sign-then-encrypt (MLS's order), AAD alone does not stop a recipient re-encrypting the signed plaintext under fresh AAD; the *inner* signature must bind the context too, as MLS's does by signing `authenticated_data` [Astra]. The context is canonical, immutable and pre-encryption (stream, signer, Message-ID, public fields), excludes later-assigned commit metadata and ciphertext-derived identifiers, and recipients verify agreement; the node verifies the outer signature and *cannot* verify that encryption used the prescribed AAD.

**Verification without decryption.** The BLAKE3 range verification of the Review §D works over ciphertext as over plaintext, so a scrubber, peer or carrier verifies and repairs sealed bodies with the same code and no key; the Merkle leaf commits to the ciphertext commitment plus the public envelope, and chapter 4's erasure caveat applies to the envelope part.

**Four memberships, not two** [Astra]: append authorization at the node; ciphertext-fetch authorization at the node; current cryptographic membership (who holds the current key); and possession of historical keys or plaintexts (which no removal revokes). The node can coordinate admission changes with public epoch commitments without holding keys; it cannot revoke what a former member already learned.

**Distance from optimal.** At the floor for node complexity (no decryption-specific machinery; opaque bytes need not change the node's equality refinement or identity simulator [Astra]); above the floor for disclosure by choice; below optimal in the unstated binding (now stated) and the unstated per-observer leakage (now required).

### 5.4 Tradeoffs not yet on the table

1. **Public signer by contract, not by necessity.** Keep public signers because fn's portable attribution contract (native author signatures verified by every relay; helm's "an unauthenticated From is a prompt-injection channel", Clients §1.2) needs them, not because accounting inherently does: transport principal, quota principal and content signer are distinct, and per-stream signing keys can reduce linkage without anonymous credentials [Astra]. A hidden-signer profile is possible and premature to commit to; it changes authorization, signer chains and public evidence and needs its own contract.
2. **Context binding, both halves.** Adopt §5.3's binding as the *supported client profile*: canonical immutable pre-encryption context as AEAD associated data, the outer signature over context plus ciphertext, recipients verifying agreement; the node's check establishes endorsement of bytes only.
3. **Key management is the application's, with an explicit integration protocol.** MLS over fn2 needs KeyPackage and Welcome delivery and authenticated bootstrap beside ordinary sealed events, and the client rule "apply the first valid Commit for an epoch, including your own only after ordered delivery"; acknowledged storage is not an accepted MLS transition [Astra]. Whether the application exposes epoch metadata in public fields is its choice, with the leakage stated.
4. **No server search over sealed plaintext; public-field search stays.** Server search over deliberately public fields is part of the contract and must not be contradicted [Astra]; literal public keywords are direct disclosure and are called that. A client-side encrypted index stored as sealed content does *not* reduce disclosure to sizes and timing (selective index-block and result fetches expose access patterns); full synchronization followed by local search does, at a replication cost measured in history size, object sizes, client count and catch-up bandwidth, which helm's 3–7k rows a day does not by itself make small.
5. **Size buckets reveal buckets.** Power-of-two rounding costs less than twice the encoded length plus framing, reveals the bucket, is defeated by any true-length public field, and nearly doubling small rows is a real cost; offer it as an application padding option with that statement, and state cover-traffic exclusions as scope [Astra].
6. **Robigalia: the envelope is unchanged and no platform guarantee is manufactured.** Kernel capabilities can gate who may invoke the node's stream operations and label invocations; stream-level read and append attenuation is a service protocol the node enforces; the node's lack of a key-store capability does not prove it never receives a key by IPC, shared memory, initialization or collusion, so "Robigalia proves it, Linux only promises it" is withdrawn [Astra]. The storage layer stores the delegation statements that justify minting capabilities; it stores no capabilities.
7. **Retention, cipher and agility are declared, not entailed.** A separate retention setting for sealed streams is reasonable; "shorter than plaintext" is not entailed; re-encryption cannot rescue ciphertext an adversary already copied; ML-KEM establishes keys and is not a content cipher, so the client profile specifies symmetric AEAD, key establishment and signatures separately with confidentiality horizons; neither encryption nor a kernel proves the operator "cannot be made to" decrypt [Astra]. Erasure is the separate decision of chapter 3; "per-object erasure is inherent" is withdrawn.
8. **Observer-specific leakage.** A relay carrying the canonical object sees its envelope, not necessarily originating-client identity, every fetch, local acknowledgements or every node's timing; the union is a *colluding-observer* model to be declared, not an automatic property of a peer group [Astra].
9. **Streaming encryption, invalid content, client recovery, permanent metadata** [Astra, additions]: the client profile specifies authenticated chunks, nonce derivation, chunk position and order, truncation detection and range-read behaviour (one giant AEAD record defeats bounded authenticated streaming); node acceptance and recipient acceptance are distinct, with validly signed undecryptable objects, Message-ID conflicts and their charges resolved; client crash recovery (nonce or ratchet rollback, pending commits, replay, device restore, catch-up after retention removed required protocol messages) is tested; and retained Message-ID, signer and identity evidence is reconciled with the stated privacy contract, since body expiry does not erase the relationship graph.

### 5.5 Principles from logics and deployments: proving it later

- **Absence of a key is an architectural boundary, not the confidentiality proof** [Astra, fatal on the draft]. A keyless node can receive deterministic encryption, nonce-reused ciphertext, plaintext disguised as ciphertext or auxiliary information that reveals the message. Confidentiality is a claim about the *composed* client–node functionality under cryptographic assumptions, honest-client conditions and a specified adversary, stated as simulatability from `L(trace)` (Curtmola §3), and that is where fn's refinement first becomes indistinguishability rather than equality (Clients §3.3). The node implementation's own refinement stays equality over opaque bytes; application cryptography lies outside the node's TCB and is indispensable to the end-to-end theorem.
- **Crash noninterference is relational, not integrity renamed** [Astra]. Returning exactly the wrong principal's authentic object preserves byte integrity and violates confidentiality; SFSCQ reasons across executions over authorization, metadata responses, caches, recovery and observable failure behaviour (`ileri2018-sfscq-proving-confidentiality-file-system.txt` §§3–4). fn2's sealed-stream theorem on the node side is of that relational kind over the envelope and authorization, with ciphertext opaque.
- **Folds stay unchanged under a condition.** Overview, cursors, withdrawals and obligations over a sealed stream are the same folds *if* they consume only canonical public metadata and treat ciphertext opaquely; extraction, indexing, control-message authorization and any new epoch or retention semantics add preservation obligations that reuse does not discharge [Astra].
- **What is dearer:** every node-side cryptographic function beyond signature verification (hidden signers, anonymous credentials, membership proofs) is a new assumption and a new verified component; its size depends on the construction, not automatically on EverCrypt's (`protzenko2020-evercrypt-verified-crypto-provider.txt`), and the application's key protocol's proofs (MLS's are extensive) stay outside.

### 5.6 Verdict

**Keep, amended.** The decision is Matrix's envelope with MLS's binding discipline and a declared leakage specification; its first-format choice of public signers is a contract choice to be argued, and it is argued. Astra's wording is adopted with the scholar's additions. Amended wording for `STORAGE-DESIGN.md` §4.5:

> **Sealed streams**: client-encrypted opaque content with an explicit public envelope (Message-ID, signer, stream, size, and application-selected public fields). The node authenticates the immutable envelope and ciphertext under the ordinary signed-record contract, holds no application decryption keys and indexes only deliberately public fields; its signature check establishes endorsement of bytes, not correct encryption. The supported client profile binds the canonical immutable pre-encryption context to the ciphertext (as associated data and under the outer signature, with the inner signature binding context where the application signs inside) and requires recipients to verify that binding; it specifies authenticated streaming chunks, nonce derivation, truncation detection and range reads, symmetric AEAD, key establishment and signatures separately, with confidentiality horizons and agility. Leakage is declared separately for nodes, relays and their collusion (envelope fields, lengths, commit order and arrival times, observable traffic, withdrawals and acknowledgements) as a simulatability claim under stated assumptions. Append and fetch authorization, current cryptographic membership and historical key possession are distinguished. Public signers are the initial profile; hidden-signer designs require a separate authorization and evidence contract. Key establishment, membership, rotation, padding and encrypted client indexes belong to the application protocol; storage order supports an MLS delivery service only with an explicit client integration protocol. Node acceptance and recipient acceptance are distinct, with undecryptable signed objects, conflicts and charges resolved by name. Server search over sealed plaintext does not exist; search over public fields does. Retention follows declared requirements and confidentiality horizons; encryption alone promises neither erasure nor permanent secrecy. Verification operates on ciphertext commitments without decryption; Tahoe's time-expiring leases do not replace evidence-gated release.

**The prototype that settles the remaining doubt.** MLS over fn2 as its delivery service in the simulator, with the client integration protocol: KeyPackage and Welcome delivery, application messages and commits as sealed articles under the context binding, the first-valid-Commit rule, a client that crashes and restores (nonce and ratchet state, pending commits, catch-up after retention removed protocol messages), a stripped-and-re-signed ciphertext refused by recipients, a validly signed undecryptable article charged and withdrawn by name, overview and cursors over public fields only, custody by ciphertext commitment. Measure the composed service [Astra]: bytes per useful message, catch-up bandwidth, index-fetch access-pattern disclosure for a client index stored as sealed content versus full synchronization, client storage, and concurrent-Commit recovery; record per-observer leakage from a simulated peer. Ciphertext is bytes; the protocol determines how many and when.

### The three tradeoffs that most change the design

1. **Witnessed integrity with the claim inside the tree (chapter 4, tradeoffs 1, 2, 4, 10).** The typed checkpoint claim becomes a logged *statement about the previous cut*, authenticated by inclusion under a standard `origin / size / root` checkpoint, so the existing transparency ecosystem's witnesses and cosignatures apply unchanged; `A-INDEPENDENT-FRONTIER` stops being an assumption and becomes a witness protocol with an honest-quorum-intersection condition (`2q > N + f` for uniform policies) and three named durabilities (local, signed-covered, witnessed-covered); recovery compares the frontier it reconstructs from anchors and journal with witness evidence rather than deferring to either; and a restore either replays to the frontier (lineage kept, nothing signed before) or declares a discontinuity under a new origin that cancels no promise. This changes the format (a statement event kind and its effect on numbering), the peer protocol (cosigning), the recovery algorithm (§I.8's comparison made concrete) and the operator's restore procedure.
2. **Typed ownership and dependency edges as the one release authority, with logical leases over physical borrows (chapter 3 tradeoffs and 3.3; chapter 2, tradeoff 3).** Release is "freed only if no edge protects it", where the edges are the installed root, every selectable checkpoint, prepared successors, reservations, obligations, promised reads, outstanding borrows and I/O, and unresolved recovery candidates; *logical discard* of a last required copy and *physical retirement* of an obsolete placement are different acts; a reader leases the logical object and borrows physical ranges per send, so the cleaner may relocate under a lease and retire the old copy once borrows end. This changes the allocator protocol's representation (edges carried, never rescanned), the cleaner (relocation of leased objects), the reply machine (borrow per block, lease atomic against release) and the accounting (cleaning reserved conservatively and reconciled; a global capacity guard; pressure states that keep maintenance moving).
3. **The summary rule as a proved simulation over declared folds (chapter 1, tradeoffs 1, 2, 3, 8; §1.3).** Each fold declares its interpretation, initialization and coverage; a new or changed fold uses an existing summary only through a declared bootstrap or migration; the sufficient-summary rule is stated against an enumerated observation set including future requests and proved as an observation-preserving simulation, not a `defun-sk`; operation identities carry request binding, a per-principal reservation and a fence on retirement; consumers choose retained delivery (a charged, inactivity-bounded hold) or state bootstrap with an explicit gap. This changes the fold DSL (three declarations per fold), the operation-identity schema and the consumer contract.

**One question only ember can decide**, surfaced by chapters 1 and 3 and left open on purpose: *what is an identity after erasure?* Exact Message-ID octets retained forever answer the duplicate check and preserve collision quarantine (D25, OBJ-001) and are personal data that no erasure can touch; a digest-only identity after reclamation is pseudonymous and erasure-friendlier but is a *revised* identity contract (probabilistic identity under a named assumption, changed duplicate/conflict outcomes, a keyed digest if testing must be resisted) with no collision quarantine. Astra defends the present contract; the scholar agrees it cannot be smuggled in as a placement class, and records that "can this node forget an identity" has no answer inside the five decisions as they stand.

### What to run first

In this order, because each gates the next design freeze: (1) the chapter-4 VOPR family (recovery semantics with witnesses: it decides the anchor comparison rule and the statement event kind before the format freezes); (2) the chapter-1 tiny-profile summary-cut exhaustion (it decides whether the fold declarations and op-identity schema are sufficient); (3) M4 repaired (chapter 2: real historical pin, identical contracts, four retentions apart; it decides scoped protections and logical leases); (4) the pre-aged cleaning scenario (chapter 3: it decides survivor segregation, priorities and the inline threshold); (5) MLS over fn2 (chapter 5: the client integration protocol); then the Review's M1–M7 as amended. Performance is reported beside each, never a gate.
