## 1. The code on `fn2/main` and `fn2/a-pool-host-sim`

### 1.1 The columns DSL (`fn2/books/columns.lisp`)

What it is: one macro, `defcolumns` (`fn2/books/columns.lisp:464-479`), that takes `((col KIND) ...)` with kinds `:u8 :u16 :u32 :u60 :bool` and `(:enum NAME (kws))`, and generates a `defstobj` with one resizable typed array per column plus a scalar `rows` field (`:372-387`), typed readers and setters whose guards carry the bounds (`:300-364`), a well-formedness predicate `NAME-wfp` (every column's length equals `rows`; `:391-394`), an `init` that resizes every column once (`:403-407`), the shape lemmas callers need for guard verification (`:117-234`, `:270-298`), and two non-executable views `NAME-row-view` / `NAME-view` (`defun-nx`, `:421-428`). The declaration is recorded in the world table `fn2-columns` (`:431-433`). The pool is its first user (`pool.lisp:8-25`), the outstanding table its second (`vocab.lisp:8-72`), then the scheduler, machine rows, trace ring, control row, the simulator's network/storage/flight tables and the OWN monitor: nine tables from one declaration form. That is the right shape and it is real: nothing in the served books builds a list (checked: no `coerce`, no `'list`, no `cons`/`append` outside `defun-nx`, snapshot and test functions; `grep` over `fn2/books` and `fn2/sim`).

Against the decisions:
- **Bounds-checked updaters**: the check is a guard, discharged by guard verification (every served export is asserted `:common-lisp-compliant`, e.g. `pool.lisp:477-500`), so a guard-verified caller runs the raw array access without a runtime check. That is the correct ACL2 realization of "bounds-checked", and the handle-taking exports do a runtime check on top (`fn2-pool-handle-code`, `pool.lisp:46-50`). Good.
- **The unexecuted logical view** exists (`defun-nx`, `columns.lisp:421-428`; `pool.lisp:426-435`) and nothing executes it. Good.
- **The hook for later obligation emission**: only the world-table row (`columns.lisp:431-433`). EXECUTION-MODEL §5 asks the same declaration to generate (a) the stobj, (b) a flat ATC-compatible representation and dispatcher, (c) the correspondence obligations. (b) and (c) do not exist and nothing in the generated events is shaped toward them (no flat layout descriptor, no per-column correspondence lemma family). The B2 draft (`lanes/b-quests/B2.draft`) creates a **second** DSL seed, `defrecord` in `fn2/books/records.lisp`, with its own "flat layout descriptor"; the machine DSL (the second of the three in EXECUTION-MODEL §5) does not exist at all (see 1.5). **AMBER**: three DSLs were decided; one seed exists, a second is being born in another lane with a different author and no shared layout vocabulary, and the third is absent while the machine rows are already hand-written. The ossification risk the brief names is already visible.
- Enum columns are u8 codes with keyword converters (`columns.lisp:58-75`); the pool's state enum is declared this way (`pool.lisp:10`). But the machine phases are **not** (see 1.5).
- Widths: `:u60` replaces ROUND2 §B.1's `u64` for every resident generation and counter, recorded as decision A-WIDTHS (`fn2/docs/a-pool-host-sim.md:33-43`) with an explicit retirement-at-limit rule instead of wraparound. Accepted and recorded: not a departure.

### 1.2 The pool (`fn2/books/pool.lisp`)

Rule-6 content, checked item by item:
- One region carved at init from profile size classes, no allocation afterwards (`pool.lisp:162-172`, `:98-160`); per-class intrusive free lists (`:194-209`, `:223-235`). Yes.
- Ownership states `free / workspace(owner) / leased-in(op) / leased-out(count) / handed(from,to) / retired` (`:10`), handles `(slot, gen, off, len)` passed as scalars, generation compared on every export (`:46-50`, `:62-67`, `:251-258`, `:286-293`). Yes.
- The octet list only in the logic: `fn2-pool-byte-slice` / `fn2-pool-bytes-view` are `defun-nx` (`:426-435`); the only executable list builders (`fn2-pool-logical-octets`, `:640-645`; the free-chain and invariant scans `:560-637`) are `:verify-guards nil` test/checker code and no served function calls them (checked). Yes.
- Readable prefix `[0, fill)`, loans appended after it, `complete-in` exposes exactly the reported count (`:237-249`, `:275-284`): the byte-fill boundary of EXECUTION-MODEL §4 has its subject.

Departures and defects:
- **`leased-out` records a count, not the holders** (`:13`, `:295-304`); `release-out` takes no owner or op (`:309-319`, comment `:306-308` defers identity to the outstanding table). The brief's contract wrote `leased-out(ops, count)`. Any caller holding a valid `(slot, gen)` can decrement a borrow it does not hold; the pool cannot refuse it. The outstanding table does carry the op→range binding (`vocab.lisp:20-23`) and `fn2-harvest-one` only releases on a matching terminal (`core.lisp:331-336`), so the composed path is sound today; but the owed keystone `fn2-pool-no-reuse` (`pool.lisp:719-723`) is stated over the pool alone and therefore cannot say "the borrower released it". **AMBER**: the ownership proof will have to be stated over pool+ops together; the pool's own statement is weaker than rule 6's "reuse waits for every external borrow to end".
- **One state per slot.** A slot that is `leased-in` cannot be read by its owner (`fn2-pool-readable-code`, `:286-293`, admits only `workspace` and `leased-out`), and cannot be leased out. A connection machine therefore cannot parse its already-received prefix while a receive is outstanding on the same slot, and cannot send from a slot with a receive in flight. The echo machine lives with this by strict alternation on one RX slot (`machines-a-run.lisp:165-188`); a pipelining NNTP connection (ROUND2 §B.2 lists separate RX/TX ranges) will need either two slots per connection or a richer state. **NOTE** for layer D: the profile already sizes 512 slots "separate RX and TX for every one of 256 connections" (`profile.lisp:119-121`), so the intent is two slots; the machine DSL must make that the only way.
- **Per-byte exports are the only byte path.** `fn2-pool-read`/`fn2-pool-write` move one byte per call behind a full handle/state/owner check (`:344-366`); `fn2-core-read`/`fn2-core-write` wrap each in a `stobj-let` (`core.lisp:159-167`). The scribe fills a 4 KiB sector by 4,096 such calls in 16-byte runs (`machines-a-scribe.lisp:44-55`, `:142-156`) and verifies it the same way (`:59-70`), and the simulated adapter moves every byte of every receive/send/read/write through `fn2-pool-read`/`fn2-pool-adapter-write` (`sim/sim-transfer.lisp:53-107`). There is no range copy, range compare, range checksum or range scan export. "Bounded copies within the representation" (rule 6) will be made of these unless D adds range primitives first; `fn2-turn`'s 0-bytes figure says nothing about this cost. **AMBER** (performance; see §5).
- `fn2-pool-reserve` picks the class by index (`:189`) and the listener hard-codes class 0 for a connection's RX slot (`machines-a-run.lisp:92`); `fn2-pool-class-for` (`:185-187`) exists and is used only by scribe. NOTE.
- Generation exhaustion: a slot at the limit is retired, never wrapped (`:216-222`); scenario-19 teeth exist (`tests/sim-layer-a.lisp:409-426`, the near-limit profile `profile.lisp:142-143`). Good.

### 1.3 The vocabulary (`fn2/books/vocab.lisp`)

The §D tables, checked:
- Events: the twelve operation results of §D.2 are the `fn2-event` enum (`vocab.lisp:31`); `ClockObserved` is the one-cell mailbox (`:56-62`, `:783-818`); the sticky signal word (`:63`, `:820-833`). `ControlObserved`/`EvidenceObserved` (`Qc`) are absent: deferred to D/E and said so (`a-pool-host-sim.md:93`). The incarnation field §D.2 puts on every event is absent; within one process it is implied, and the table dies with the process. NOTE.
- Actions: all fourteen of §D.3 (`:10`). A `Send` carries one range, not four (`:17-20`); recorded as a departure (`a-pool-host-sim.md:222-226`).
- Reservation before submission: `fn2-op-reserve` takes the row, the outbox credit and, by construction of the row, both result cells together (`:231-258`, `Qr = 2O` is the two inline cells `c0-*`/`c1-*`, `:28-45`); `fn2-op-enqueue` cannot fail for capacity after a reservation (`:322-337`); a full outbox is `:exhausted` at reserve time (`:243-246`). The owed keystone `fn2-ops-result-reservation` (`:1296-1303`) says exactly this. Yes.
- Exhaustion as a continuation: every refusal is a keyword and the machine parks (`machines-a-run.lisp:71-80`, `machines-a-access.lisp:156-167`). Yes, with one exception below.
- Stray results: `fn2-post-result` validates identity, phase, cell and payload shape before any mutation and otherwise counts `stray` and changes nothing (`:583-632`); the closed failure-reason sets per event are a real table (`:450-510`). Good: this is fn1's T6 kept.
- Capacities are profile values (`profile.lisp:5-36`, `:122-140`), not constants. Yes.

Defects:
- **A non-exhaustion refusal stops a machine for good.** `fn2-machine-issue-result` (`machines-a-run.lisp:71-80`): `:exhausted` parks the machine on the credit wait list, every other code (`:bounds`, `:state`, `:stale`, `:owner`) sets `stopped 1` and `wait-reason 0`; `fn2-machine-run` then refuses to run it forever (`:213-222`). No close is issued, the connection row and its pool slot are never released, and nothing reports it beyond the trace. For layer A's echo the reachable refusals are none (the arguments are machine-constructed), so this is latent, but it is the shape every D machine will copy. **AMBER**: a refusal that is not exhaustion must be a named posture transition (close-and-release, or a stop with evidence), not a silent leak.
- The vocabulary book's cost: 305 s to certify on the loaded laptop today (my run), 187-214 s in the lane's; 38 columns × generated shape lemmas. Information, as the seat says; but every book above it (core, machines, executor, the whole simulator) recertifies when it changes, and A5 is changing it now (`a-pool-host-sim` diff: TLS `:refused`, Close/Entropy `:io`, Entropy `:short`). NOTE.

### 1.4 The core, scheduler and executor (`core.lisp`, `sched.lisp`, `exec-state.lisp`, `executor*.lisp`)

- `fn2-core` nests pool, ops, sched, machines, trace and control (`core.lisp:12-18`); access through `stobj-let`, children bound together per transition (e.g. `fn2-core-issue`, `:195-228`; `fn2-harvest-one`, `:313-342`). Matches §A.1.
- `fn2-core-issue` reserves the op first, then the pool lease, and `fn2-op-unreserve` rolls the reservation back on a lease refusal (`:209-217`); the nine issue refusals are owed as "whole core unchanged" with evaluated teeth (`:379-394`; `tests/core-unit.lisp`). Good.
- `fn2-harvest-one` is where bytes become readable (`complete-in` at `:325-331`) and where output borrows end (`release-out` at `:332-336`), with the release-first ordering handled (`vocab.lisp:641-651`, `core.lisp:323-336`). Good; this is the byte-fill boundary made concrete, and `fn2-core-harvest-byte-fill` (`:438-461`) states it with an explicit adapter-write trace premise rather than inferring from bytes in memory. That is the most honest keystone in the tree.
- The scheduler: intrusive per-principal FIFOs with idempotent tail insertion (`sched.lisp:137-162`), pop-head (`:164-189`), a literal calendar from §C.2 (`:37-46`, `:91-105`; 80 entries concrete, 8 tiny), four service flags, and `fn2-sched-visit` advancing one entry per visit (`:193-205`). Matches §C.2; the owed starvation statement is over the actual visit function (`:254-276`).
- The loop: `fn2-transition` (one harvest, one mailbox, or one calendar visit; `executor.lisp:90-102`), `fn2-reference-loop` stopping at the first exhausted `H`/`K`/`Aturn` or when nothing is eligible (`:118-134`), `fn2-reference-turn`, and `fn2-turn` **defined as `fn2-reference-turn`** (`:146-148`). The "wait only when nothing eligible" rule is `fn2-exec-eligible-p` = runnable-or-wake-needed (`:7-9`) and the status `:idle` only when neither observations nor eligibility remain (`:11-15`). Matches §A.1/§C.4 for an unfused loop.
- Observations are harvested before any scheduling in a turn, as many as `H` (`:90-96`): §C.3's "bounded validation, completion bookkeeping, ownership transfer, runnable marking" and nothing else (`fn2-exec-harvest`, `:17-28`; `fn2-machine-observe` is state bits, `machines-a-run.lisp:14-67`). Good.

Defects and departures:
- **The refinement keystone is a tautology today.** `fn2-representation-relation` is `equal` (`executor.lisp:171-172`) and `fn2-turn` is `fn2-reference-turn` by definition (`:146-148`), so `fn2-turn-refinement` (`:177-191`) reduces to "the same function called twice agrees, preserves `wfp`, and fits the modeled cost". The docs say so (`OWED.md`, A4 rows; `a-pool-host-sim.md:156-157`). The seat accepted it as the named placeholder EXECUTION-MODEL §4 asked for. But the reference semantics EXECUTION-MODEL §1 describes ("one transition at a time under a specified scheduler", a separate object the concrete loop refines) does not exist as a separate definition: there is one loop, and its own trace is what TRACE checks against (1.6). Until a reference transition system is written apart from the dispatcher (even a slow list-based one), neither the refinement statement nor the TRACE checker has an independent subject. **AMBER** now, RED at the first fusion.
- **`fn2-exec-clock` disarms the wake on every clock observation** (`executor-wake.lisp:44-58`: `armed-deadline := ∞`, `wake-generation += 1`), so while any deadline is pending the timer service re-issues an `ArmWake` descriptor on every turn that saw a clock observation (`fn2-exec-arm`, `:21-32`; `fn2-exec-service`, `executor.lisp:71-84`). The native loop posts a clock observation every cycle (`a-pool-host-sim/fn2/host/adapter.lisp:280-283`). One op row, one outbox credit, one take and one ack per cycle, for the host to replace a deadline it already holds. §D.3 says "one replaceable wake request; coalesce". NOTE now (no deadlines exist in layer A); a cost in D when every parked wait has one.
- **The modeled cost (`fn2-turn-cost`, `executor.lisp:173-176`) and the WORK certificate count self-declared units**: a harvest is "24 steps", a mailbox "8", an empty visit "1", a connection issue "8 steps, 0 bytes" even when it issues a 4 KiB send (`machines-a-run.lisp:71-75`, `:165-188`), a scribe fill "16 bytes, 24 steps". These are loop-bound tokens, not measured work, and only scribe charges bytes at all. §B.3 wanted "a cost certificate per run covering scalar work, queue updates, hashing, descriptor construction". The certificate exists in form and is empty in content for the only I/O machine. **AMBER** (it makes WORK a self-report; 1.6).
- Machine rows use `ready-prev`/`ready-next` (the §B.1 names for the runnable links) for a *second* intrusive list, the op-credit wait list (`machines-a-access.lisp:156-186`), while the runnable links live in `sched.lisp:11`. Harmless, misleading. NOTE.
- The signal word has one meaning: any bit stops the executor (`executor.lisp:31-49`); "reload" is not distinguished. NOTE for E.

### 1.5 The layer-A machines (`machines-a*.lisp`)

- One wide `defcolumns fn2-machines` row carries the §B.1 common fields plus the union of every kind's fields: capability, pool range, `off/length/pending/borrows`, and scribe's `sequence/cursor/checksum/completed/verified` (`machines-a.lisp:11-21`). Kinds are listener, echo, null, scribe (`:15`); phases are **bare integers** `0..6` and `16..31` (`:35-43`, `machines-a-scribe.lisp:72-84`, `:303-320`), not an enum column, while the same file's `kind` is an enum. The seat noted this and deferred it to A6 (`lanes/a-continuation.md:58-59`). Rule 1 says "nested tables per machine kind, each a struct of arrays"; §5 says machines come from a machine DSL "with state enums, fields, accounts, continuations and budgets". What exists is one hand-written union table with integer phases and hand-threaded `fn2-machine-core-put` writes. **AMBER**: this is the exact twin the laws forbid; it is tolerable for an echo probe only if D does not inherit it, and D starts on this branch.
- Listener: accept credits, admits a connection by reserving a row and an RX slot, closes the accepted capability when no row is free (`machines-a-run.lisp:83-128`). Matches §D.2 "no unreserved accepted connection enters the core". Good.
- Echo: receive into the RX slot, lease the received range out, reissue the remainder on a short send, reset only when the last borrow is released (`:131-210`); null discards (`:202-206`). Zero-copy echo is real (the OWN digest check proves the sent bytes are the received bytes while borrowed, 1.6).
- Scribe: reserve a 4 KiB window, fill, patch checksum, write, fence, read back, verify, next (`machines-a-scribe.lisp:303-320`); `completed` advances only on the fence result (`:259-262`); failures stop without retry (`:106-110`). Matches the brief.
- Per-run caps are checked by returning counts, never enforced inside a run: a run returns `(bytes steps actions runnable)` and the loop sums them (`executor.lisp:52-68`, `:105-112`). The caps `4096/32/4` are asserted equal in the profile (`machines-a.lisp:104-116`: "changing quanta requires a machine DSL lowering"). So the "simultaneous caps" are a convention each machine honours by construction, with no guard, no assertion, and no independent measurement. NOTE, and the reason WORK is a self-report.

### 1.6 The simulator and checkers (`fn2/sim/`, `fn2/tests/`)

Determinism and replay: one xoshiro128** stream seeded from the run seed (`sim/prng.lisp:55-105`), every choice drawn from it, profile/seed/revision/fault choices recorded (`sim-state-data.lisp:15-54`), a rolling digest and a 64-entry observation ring (`sim-state.lisp:142-176`), and a replay control that reruns seed 73 and compares digest, PRNG state, observation count and a storage fingerprint (`tests/sim-replay-controls.lisp:26-50`). Replayable by construction: yes. But the revision string baked into the test is **A3's commit** (`tests/sim-layer-a.lisp:10`: `HEAD=e0cd1f4dd...`), not updated at A4 although the comment says it is "updated before acceptance"; a failure report names the wrong revision. NOTE, cheap to fix, and the kind of thing a VOPR takes from `git` at run time.

The fault model against the papers' crash table (README §"Crash model", rows 1-22): 26 classes (`sim-state-data.lisp:9-14`). Rows 1 (bitrot, class 7), 2 (read `:io`, 6), 3 (miswrite, 9), 4 (misread, 8), 5 (lying flush, 10, only under `:broad`), 7 (sticky death, 13), 10 (tear per 512 B unit at a crash, `storage.lisp:182-227`, `sim.lisp:84-103`), 11 (in-flight writes land in any subset and order at a crash, `sim.lisp:18-50`), 13 (crash during recovery, `sim-recovery.lisp:59-103`), 19 (fail-slow as latency, 14), 22 (short writes, 24; no-space, 12) are present. Row 6 (collateral damage to clean units) is explicitly not modeled (`storage.lisp:218-220`); rows 8-9 (the two views after a failed fsync) are modeled by `fn2-storage-reopen` with `revert` (`:157-176`) but I found no caller that chooses `revert = t` outside the storage book's own controls; row 12 (concurrency) is n/a by design; row 14 (FUA) exists as a per-write bit that persists its own request only (`:77-95`). B1 is now building the predicate form of this model and a trace-by-trace differential (`b-durability/fn2/tests/crash-model-differential.lisp`), which is the right way to find what the simulator cannot produce; its gap list will be the authority.

Two weaknesses in how faults are *applied*:
- **Misdirection is one deterministic shape**: `fn2-sim-redirect` sends a misread/miswrite exactly one sector (+4096) forward, modulo the device (`sim-adapter-base.lisp:242-248`). Not "another address". NOTE.
- **The fault budget is 128 per `fn2-sim-init` and is never replenished** (`sim-state.lisp:406`; the only decrement `:132`; the echo death cut also spends it, `echo-scenario.lisp:281-282`). The pool scenarios re-init per run (96 rounds each), so their density is fine. The echo acceptance is **one** run of 17,532 turns and 1,000 connection lifecycles (`seat-a4-accept.log`: `turns=17532 deaths=11`), with the first 16 sends and 16 receives forced to short/fragmented (`echo-scenario.lisp:256-268`), so at most ~96 random adapter faults land in the whole run and the last two-thirds of it is fault-free. Two classes were never chosen in the accepted run (delay and fail-slow: `fault-choice-mask=67092475`, bits 2 and 14 clear). The commit message says "1,000 echo connections ... with broad faults and 11 deaths" (`bed9edc28`); the brief asked for "1,000 simulated connections with partial I/O and drops" under broad faults. **RED**: the acceptance claim overstates what was exercised; the fix is one line (re-arm the budget per connection or per N turns, and report hits per class), and the run should be repeated.

The checkers, against §F.1 "independent semantic checkers; merely running the implementation twice is insufficient":
- **OWN** (`sim/check-own.lisp`) is independent evidence: its own per-byte provenance arrays (`:107-115`), digests of borrowed ranges taken at issue and checked at the adapter's physical read and at every turn boundary (`:237-262`, `:266-284`, `:457-471`), range/owner/lease identity cross-checked between ops and pool (`:425-452`), and the stray contract checked against an exact snapshot of every non-stray word (`:380-394`). This is a real monitor and the strongest thing in the tree. One gap: its read-side check (`fn2-own-observe-read`, `sim/check.lisp:43-48`) is called only by the A3 stand-in workload (`tests/sim-layer-a.lisp:87`, `:109`) and never by the echo or scribe machines, whose reads happen inside the core (`machines-a-scribe.lisp:59-70`). So "no read of uninitialized/lent input" is checked for the test workload's reads, not for the real machines'. **AMBER**: wire the monitor to `fn2-core-read` (a checker hook on the core read path, or a test-only wrapper the scenario installs), or the claim is for the stand-in only.
- **TRACE** (`sim/check-trace.lisp`) rebuilds the calendar literally from §C.2 (`:39-50`) and replays FIFO selection as lists without including `sched.lisp` (`:90-137`), and checks the outbox's actual OpRef order (`:145`) and the harvest wake routing against the posted FIFO owners captured before the turn (`:152-163`; `echo-scenario.lisp:173-199`). Independent of the scheduler: yes. But the *additional wakes* (a run making another machine runnable: listener → connection) are taken from the executor's own trace record and only checked for well-formedness (`:122-123`, `fn2-trace-wake-valid`); and the selection it checks is the executor's own report of what it selected (`fn2-exec-record`). TRACE therefore verifies "the executor's account of its scheduling obeys the calendar and FIFO rules", not "the executor did what a reference semantics would do". The brief's question "the checkers independent of the implementation (not the implementation run twice)" gets: OWN yes; TRACE half (independent model of the rule, implementation-supplied events). **AMBER**, tied to the missing reference semantics (1.4).
- **WORK** (`sim/check-work.lisp:12-25`, `:60-76`) sums the implementation's self-declared per-run `bytes/steps/actions` and compares them with the loop's counters and the caps. Independent of nothing but the arithmetic (1.4, 1.5). The only independently measured number is the trace-record count per kind. **AMBER**: WORK passes by construction; it would pass a machine that lied about its work.
- **ACCOUNT is claimed and absent.** `fn2/docs/a-pool-host-sim.md:19` and `:167` say "Checkers implemented in A: TRACE, WORK, OWN, ACCOUNT"; `sim/check.lisp:1` says "A4 implements TRACE/WORK/OWN" and `fn2-check` returns `:not-yet` for `:account` (`:66-69`). The layer brief required ACCOUNT in A (`FN2-LAYER-A-POOL-HOST-SIM.md:154`). **RED** (a decision document states a false fact about the gates); the honest line is "3 of 11".
- The scribe scenario's oracle (`tests/scribe-scenario.lisp:127-138`) checks consistency (`verified ≤ ack ≤ fences`; bad or misplaced sectors ⇒ not `:intact`; `valid < ack` ⇒ damaged/unknown; the named fault was hit) and, for the fault-free cuts, the exact frontier arithmetic. It does not assert the §E.4 classification each injected fault must produce (a misdirected write at cut 20 may legitimately come back `:torn-tail` or `:unknown`; nothing says which). That is adequate for a probe format B replaces; it is not "the recovery stub classifying every post-death image" against the table.
- The recovery stub takes the acknowledged frontier as an **external input** (`sim/recover-stub.lisp:181-182`, `:131-135`) supplied by the scenario from the dying core's `completed` counter (`scribe-scenario.lisp:109`, `:125`). Real recovery has no such input; B5 must find the frontier on the medium or in a witness. Known and stated (`a-pool-host-sim.md:179-180`). NOTE.
- `fn2-storage-init` allocates one full-image snapshot per **operation row** (`storage.lisp:41-52`: `nfences = O`, used at `sim-state.lisp:384`), i.e. `4096 × sectors × O` bytes; the B seat already flagged it (`lanes/b-continuation.md:105-108`). A concrete-profile device of a few hundred sectors would need gigabytes. **AMBER** for B3 (one fence in flight per domain, §D.3).

## 2. The testing story, as it stands and as planned

### 2.1 What fn1 has (origin/dev, the quarry)

- **Natives**: 259 `tests/test_native_*.py` files (QUARRY counts 247 modules, 57K lines; `QUARRY.md:293-375`): about 87 drive a node only through `Node`/`Client` (a socket, `fn.toml`, the control socket) and carry; 33 carry their socket half; 93 raw/source-text modules die with the old host. They are example-based conformance and behaviour tests of the public surface: NNTP commands, SASL/auth/STARTTLS/implicit TLS, consumer control, peering, store operations, resource rows.
- **A seeded generative fuzzer with a model oracle**: `tests/fuzz_nntp.py` (`origin/dev`) drives the live image with random and adversarial sessions from a seed, and in `diff` mode compares the served bytes with the ACL2 model's served path for the same transcript under every cut (whole, per item, bytewise, random, every single cut), with ddmin minimization and committed reproducers (`tests/fixtures/fuzz-nntp/`). In `node`/`bounds`/`store` modes it checks liveness, bounded work and store-input robustness. This is real model-based testing of the wire surface, and nothing in fn2 has an equivalent yet.
- **The load gauntlet** `tools/load` (11K lines; `QUARRY.md:336`): cells F1-F6 with named externally visible properties (P1-DURABLE, P2-IDENTITY, P4-RECLAIM, P5-RECOVERY, P8-CLIENTS), per-operation outcome records (`completed / attempted-uncertain / not-attempted`), a history shrinker (prefix/suffix/chunk deletion, ddmin), crash hooks at named boundaries (`tools/load/FAULTS.md`), and the W/T throughput and RSS rows with bars. Jepsen-shaped in its history and outcome discipline; example-shaped in its cell definitions.
- **Crash campaigns** `tests/campaign/` (`native_cuts.py`, `native_operator_campaign.py`, `native_production_kill.py`): every `fnn-at` cut of a native write path, kill at each through the public operator entry, reopen, check acknowledged content and the interrupted operation.
- **ACL2 assertion books** (1,015 files under `tests/acl2/`): executable examples and teeth per keystone.

None of it runs against fn2 today, and fn2 has no NNTP, control, CLI, web, peering, TLS or config surface for it to run against.

### 2.2 What fn2 has today (fn2/main at bed9edc28)

Property-based in the VOPR sense (seeded random schedules and faults with an independent checker):
- **Pool ownership under every fault class**: 10,000 seeded runs of the tiny profile and 1,000 near-limit runs, each 96 rounds of a stand-in machine issuing receive/send/read/write/fence/cancel/accept/close with random adapter takes, completions and a crash chooser, with OWN evaluated after every step (`tests/sim-layer-a.lisp:130-232`, `:321-364`; the seat's re-run `seat-a3-accept.log`: 10,000/10,000 and 1,000/1,000, 154.6 s and 13.6 s). OWN is independent (1.6). This is a genuine property test of rule 6.
- **The echo scenario**: 1,000 connection lifecycles over 256 concurrent slots, an independent client oracle (its own message, fragmentation and drop schedule, byte-for-byte check of the echo; `sim/echo-scenario.lisp:13-96`), death cuts at descriptor handoffs with restart, TRACE/WORK/OWN per turn (`:201-234`, `:293-352`). Property-shaped; its fault density is the RED of 1.9 and its checkers are half self-report (1.6).
- **Matched-operation fault controls**: each of the 26 classes forced once against a matching operation with the physical effect asserted (`tests/sim-fault-controls.lisp:142-193`, 26 cases), plus outbox saturation, op and pool retirement, stale-result and recovery-cut controls and a replay control. Example-based, deliberately, so the swarm figures are non-vacuous. Good practice.
- **The scribe probe**: 19 cases (10 death cuts in the fault-free run, 9 forced storage faults), each followed by the recovery stub with a consistency oracle (`tests/scribe-scenario.lisp:159-183`).

Example-based unit asserts: pool (`tests/pool-unit.lisp`, 938 lines, 49 asserts in A1's count), vocab (1,338 lines), core, executor, sched, wake, machines, recover, check-own, network backpressure; every owed keystone has evaluated positive and negative teeth (`fn2/docs/OWED.md`).

Not present: anything over a public surface (there is no public surface); any reference model distinct from the implementation (the "reference turn" is the implementation, 1.4); ACCOUNT, FAIR, HISTORY, IDENTITY, WIRE, CONSUMER, RECOVERY, RECLAIM (8 of 11 checkers); 17 of 20 §F.2 scenarios; liveness checks under a declared bounded-completion environment (§F.2 last paragraph); any stateful property test with a shrinker (every failure prints the 64-entry ring and the seed, `tests/sim-layer-a.lisp:305-319`, which is replay, not shrinking).

### 2.3 Against the practice in the papers

- **TigerBeetle's VOPR** (`~/paperbin/tigerbeetle2026-internals-vopr.md`): seed + commit replays any failure; faults tuned per seed; "several hundred batches" committed per run and checked; assertions dense and on in production; storage checkers compare data files byte-for-byte across replicas; liveness in a separate mode. fn2 has the seed and revision (stale constant aside), swarm-drawn probabilities per class (`sim-state.lisp:304-317`), and three checkers; it lacks assertion density in the served code (the books refuse by keyword and never assert; the one `assert`-like discipline is `assert-event` at certify time), the per-run fault budget makes long runs go quiet, and there is no liveness mode.
- **FoundationDB-style simulation**: the whole process (core + executor loop) under the simulated host with workloads as machines. fn2's design says this (ENVELOPE §2.6: "a simulator is a second host"), and A5 is wiring the same core to a real host; but the sim adapter and the native adapter differ in when storage effects happen (sim: at completion, randomly ordered; native: inline at take), so the two hosts do not share one adapter protocol implementation, only one core. Acceptable now; a divergence risk later (§4).
- **Jepsen/Elle history checking**: fn1's load harness already records per-operation outcomes with uncertainty and shrinks histories. fn2's HISTORY/IDENTITY/CONSUMER checkers (§F.1) are the place this discipline returns; none exists yet, and B3 is the first to need one.
- **QuickCheck/stateful property testing and model-based testing**: the papers README (§3-4) and the automation routes (§"three routes") point at an abstract model as the oracle. fn2 has an executable abstract model for exactly one thing, the pool (`fn2-pool-semanticp` and the owed statements' nx dispatchers over the real exports, `pool.lisp:502-764`), used as a checker's invariant, not as a generator or an oracle of outputs. There is no shrinking anywhere in fn2.

### 2.4 The answer to ember's question

**No.** There is no behavioural or property-based suite over the full public surface, because there is no public surface yet: fn2 serves nothing (no NNTP command, no consumer frame, no CLI verb, no web page, no peer, no TLS, no config). What exists is a deterministic simulator over the bottom layer with one genuinely independent property checker (OWN) and a well-made client oracle for a zero-copy echo, exercised by 11,000 short seeded pool runs and one long echo run whose adapter faults stop after 128 events; three of eleven checkers, three fragments of twenty scenarios, no reference model apart from the implementation, no shrinker. The classical gate that would cover the surface is fn1's: 87 black-box natives, a seeded differential fuzzer against the ACL2 model, a load gauntlet with history checking, and crash campaigns at every cut. None of it has an adapter to fn2 and none will have anything to adapt to before layer D serves the greeting. The prerequisite ember named is therefore not met and cannot be met by layers A-C; it is met only if D and E are built with the `Node` adapter (QUARRY `native_harness.py:1413`) and the fuzzer's `diff` mode as their acceptance from the first served verb, and if the simulator grows a reference model to be the oracle the fuzzer compares against, instead of fn1's old served path.

### 2.5 Findings, ranked

1. **RED** The claim "1,000 connections under broad faults" rests on ≤128 fault events in 17,532 turns (1.9 #1); the only long property run is mostly fault-free.
2. **AMBER** No reference model apart from the implementation: the VOPR-style runs check invariants (OWN) and self-consistency (TRACE/WORK), never outputs against an oracle; fn1's fuzzer had one (`fuzz_nntp.py diff`).
3. **AMBER** Eight of eleven checkers and seventeen of twenty scenarios do not exist; the layer briefs assign them, but no brief assigns the liveness mode or the shrinker, and the D/E briefs do not exist yet (§4).
4. **AMBER** fn1's 87 black-box natives, the fuzzer, the gauntlet and the campaigns have no `Node` adapter and no target; the carry plan is a sentence in QUARRY, not a quest in any brief.

## 3. The method: the monitor-plus-Codex loop

### 3.1 What the loop is

`briefs/FN2-SEAT-COMMON.md:120-124`: one Codex session per quest, detached with a PID file; the prompt names the decisions, the contract, the exact files, the acceptance and the rules, and pastes the ground truth in; when the session ends the seat "read[s] its report and the diff whole", loads every new book, runs the acceptance itself, reviews against the decisions, commits named files, pushes, and rewrites the continuation whole. The prompts are good: A1-A5 are 9.6-13.5 KB each (`lanes/a-quests/A*.prompt`), they quote the decision paragraphs and the real signatures (A4's "Ground truth" and "Notes from the seat on A3" sections; A5's "Ground truth from A4"), they say what the acceptance prints, and they carry the box-safety block verbatim. Codex's last messages are five lines (`A1.last.md`..`A4.last.md`); the substance goes to `build/REPORT.md` in the worktree, which is git-ignored and **overwritten by every quest** (A4.prompt: "build/REPORT.md (overwrite; start with 'Quest A4')"), so A1-A4's reports no longer exist except as fragments in the 0.5-5 MB session logs. The retained review record is the commit message, the continuation table and `fn2/docs/a-pool-host-sim.md`.

### 3.2 Is the review real?

The re-runs are real. `build/seat-a3-accept.log` (10:07:33) and `build/seat-a4-accept.log` (11:19:06) in the lane worktree are the seat's own executions of the acceptance drivers, with the same seeds and the same printed results as Codex's (`a3-acceptance-final.log`, `a4-accept.log`), and the commit messages quote them (`bed9edc28`, `e0cd1f4dd`). ### 4.3 The risks the brief named, as I see them in the tree

## 5. Performance

### 5.1 What has been measured

All on the laptop (an M-series Mac at load 12-40 from other sessions today), nothing on hbox or dregg-build:
- `fn2-turn`: 1,000-connection echo run, concrete profile with TRACE on, broad faults: 17,532 turns, mean **14.4-16.7 µs**, max 91-118 µs, **0 bytes consed** per turn after a 64-turn warm-up (Codex `a4-accept.log` and the seat's `seat-a4-accept.log`; the meter is a raw-Lisp wrapper around the real function, `tests/turn-meter.lsp`, with a 10,000-call control that conses 0). Steady-state echo with faults off: 14,209 turns, mean 19.2 µs, max 96 µs, 0 bytes (`a4-executor-allocation.log`).
- Pool: 0 bytes over 100,000 reserve/write/reset/release cycles; **620 bits of bookkeeping per slot** (A1); outstanding table: 0 bytes over 100,000 lifecycles; **843 bits per op row** (A2); the nine core helpers 0 bytes over 100,000 cycles (A3). These are allocation measurements, not time.
- Simulator: 10,000 tiny pool runs in 153-155 s (23.6 GB consed by the test-side lists, i.e. the checkers, not the core); 1,000 near-limit runs in 13.6 s.
- Certification: vocab 187-305 s, sim 205-413 s, sim-adapter-base 93-325 s, sim-state-data 154-286 s (lane logs and my run); growing with every column added.

What the per-turn number means: with every connection on the anonymous principal 0 (`a-pool-host-sim.md:99-110`), a concrete turn visits up to `K = 64` calendar entries of which at most four are principal 0 and sixteen are services; the other ~44 are empty principal entries that cost a visit and a trace record each (`sched.lisp:193-205`, `executor.lisp:52-59`). So 14-19 µs is the cost of ≤4 bounded machine runs plus ~60 bookkeeping visits with tracing on: roughly 0.25 µs per empty visit and a few µs per real run. It is a loop-overhead figure, not a per-request or per-byte cost, and it cannot be compared with any ENVELOPE floor.

### 5.2 Against ENVELOPE §1's floors

ENVELOPE §1.3 puts the CPU floor of a 2 KiB POST at ~10-15 µs [D] with 2 copies, 4 syscalls + 2/b, 1/b flushes, 0 allocation; §1.5 puts the ceiling at ~67k POSTs/s per core; §2.8 lists five FLOOR measurements owed before any bound is frozen (O_DIRECT append + fdatasync on ext4; the same on a PLP NVMe; io_uring vs epoll for the 2 KiB loops; OpenSSL per-connection memory; Message-ID rebuild at 1M). None of the five has been run; the storage design (STORAGE-DESIGN §6, M1-M7) adds seven more, none run. Nothing in fn2 moves an article yet, so no floor applies to it; but the cost structure that will apply is already fixed by A: every byte that enters or leaves the core goes through a per-byte checked export (§1.2), the scribe pays ~4,096 `fn2-core-write` calls plus 4,096 `fn2-core-read` calls per sector, and the simulator pays a byte-at-a-time `fn2-pool-read`/`adapter-write` per transferred byte (`sim-transfer.lisp:53-107`). The "2 copies" of §1.3 are, in this representation, 2 × N checked function calls.

### 5.3 The first real measurement, and when

Now, with A5's native echo on the laptop (it is the first time real bytes cross the core): report, per connection and per byte, the CPU of `fn2-turn` **divided by bytes echoed**, the whole-cycle CPU (`FN2 CYCLE` in `adapter.lisp:369-372` already prints it), and the syscalls per echoed KiB; and beside it, the cost of a 4 KiB range through `fn2-core-write`/`fn2-core-read` in a tight loop, so the per-byte export's price is a number before D's parser is designed over it. Then the first ENVELOPE floor (row 1: O_DIRECT 4 KiB append + fdatasync, which A5's storage path can already issue) on dregg-build, since B3 freezes the commit batch's geometry against it. Everything else waits for a served POST: measuring an echo against a POST floor would be exactly the measurement-driven mistake ember named (`FN2-ORIENTATION.md`, "WAY too empirical ... over measurements that don't actually make much sense").

1. **AMBER** The only time measurement is loop overhead with tracing on and 44 empty visits per turn, reported as "per-turn CPU" without that qualification (`bed9edc28` message; `a-continuation.md:21`).
2. **AMBER** The per-byte checked export is the only byte path and its cost has never been measured (§1.2); D's parser and B's codec will be built on it.

### The honest answer to ember's test-suite question

No: there is no behavioural or property-based suite over fn2's full public surface, because fn2 has no public surface yet, and what exists below it is narrower than its acceptance lines say. What is real: a deterministic, seed-replayable simulator over the byte pool, the outstanding table, an echo connection and a storage probe, with one genuinely independent checker (OWN, with its own byte-provenance evidence), a well-made independent client oracle for the echo, 26 matched-operation fault controls, and 11,000 short seeded pool runs that are a proper property test of the ownership rules. What is weaker than claimed: the one long echo run had at most 128 adapter faults in 17,532 turns; TRACE and WORK check the executor's own account of itself; three of eleven checkers and fragments of three of twenty scenarios exist; ACCOUNT is claimed and absent; there is no reference model apart from the implementation and no shrinker. What is example-based: the unit asserts and the owed-keystone teeth, which are good. What is missing entirely: anything over NNTP commands, the consumer grammar, the operator CLI, the web reader, peering and BP, TLS/auth, config and limits, because none of them exists in fn2 and the layers that will create them (D, E) have no brief; fn1's 87 black-box natives, its seeded model-differential fuzzer, its load gauntlet with history checking and its crash campaigns are the suite ember is asking about, and none of them has an adapter or a target in fn2. The prerequisite for assurance that ember named is therefore not met, is unreachable before D serves the greeting, and will only be met if D and E are built with the carried natives and the fuzzer as their acceptance from the first verb, with the simulator's reference model as the oracle.
