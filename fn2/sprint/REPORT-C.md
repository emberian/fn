# C sprint report

Implemented `c/runs.lisp`, `c/seal.lisp`, `c/page-lookup.lisp`, and `tests/c-examples.lisp` with executable `tests/c-examples-driver.lsp`.

The resident table is generated by A's `defcolumns` and sorted by `(group,number)`, with a sealed prefix and an append-only active tail. Capacity is resident execution capacity; `:exhausted` preserves the proposed record for a caller to spill/retry. Bytes stay in A's pool and exact Message-ID comparisons never use the scalar fixture `content-tag` as identity. GROUP and number lookup carry row continuations; metadata cursors binary-seek stored sparse keys and share their 32-step structural budget with output. The output model is `number TAB Message-ID CRLF` with a conservative 22-byte framing/number allowance, at most 32 entries and 4096 bytes. `fn2-sc-cursor-step` carries unfinished seek `(lo,hi,phase)`; the convenience wrapper gives a named `:cursor-continuation-needed` if the seek uses its whole quantum. It cannot silently loop on an unchanged stable key. The cursor example ranges over a fixed run; a pinned logical version across concurrent appends is not implemented by this API.

The seal writer zero-fills one 64KiB page in 4KiB quanta, encodes B's real `*fn2-format-page-header*`, a schema header, ordered entries with inline exact Message-ID bytes, and a per-entry offset directory through B's single layout interpreter. It hashes the full padded page using B's incremental BLAKE3 after the literal physical-page domain. The completed page takes an actual A pool lease-out; covered-byte mutation is refused until that lease is released. A parent-held digest is checked by B's real `fn2-format-check-page`. Sealing is explicitly `:sealed-volatile`: B3 does not exist. This is a dependency-page builder for B3, not a commit engine or durability claim.

`c/page-lookup.lisp` then searches the actual verified sealed representation, decoding the page's offset directory and inline entries through B's codec, comparing exact inline pool ranges against the query pool range. It handles at most four entries per call, conservatively below 4096 pool byte reads, and returns a stable row continuation. This proves the example is more than a hash of an unrelated serialization of the resident table. The page must remain pinned after its hash/identity check; no cold disk loader or page cache has been built.

Current intentional cuts: one page, one metadata schema, no schema-specific multi-page parent builder, no compaction/reservations, no committed-overlay installation, no physical object leases or retirement, no Ribbon or InfiniFilter, and no perfect hash. Identity lookup is a bounded exact linear scan of the metadata run, rather than a separate lexically sorted identity run. Ribbon belongs at the sealed-run negative-probe seam before this scan; InfiniFilter belongs before overlay exact lookup; neither may replace the final comparison. D retains the common pool fixture owner `(250,0,1)` so stored identity/body ranges and query ranges are explicitly readable by the same authority. The scalar `content-tag` is a toy collision metadata field, not an actual BLAKE3 digest or persistent source descriptor. Duplicate Message-ID reservation/content-conflict admission is not implemented by `sc-add`; the encoded conflict flag is zero in this scout, and D owns the POST stand-in decision.

`fn2-sc-summary-equation` and `fn2-sc-identity-exactness` are `defthm-owed` registrations, not admitted theorems. The first states that a supplied summary equal to the prefix fold plus the suffix equals the full scalar fold; the exactness statement concludes equality of logic-only Message-ID byte views when the real lookup returns `:found`. Five cuts of four records execute, and a summary+1 mutant fails equality. Source functions beyond cheap getters/initialization are logic-mode ideal functions with guard verification deferred for the sprint; no end-to-end guard-safety claim.
