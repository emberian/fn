# 9P2000 view: Linux kernel-client mount, 2026-09-19

What this note records, and what it does not. Two halves of the evidence were
taken separately because the store-backed half needs a certified book tree on
the Linux box and that certification was still running:

- **The projection half** (ACL2-backed, macOS, `tests/test_fn9p.py`): the
  bytes of `/groups/<g>/<n>` equal the NNTP reader's `ARTICLE` block over the
  same committed store, the group directory equals `LISTGROUP`, and a commit
  after the snapshot is invisible to it. Driven by the test's own 9P client,
  not by a kernel.
- **The kernel-client half** (this note, Linux): the in-kernel v9fs client
  mounts `tools/fn9p.py`'s protocol layer, walks it, lists it, reads a file
  byte for byte, and gets the intended refusals. The tree served here was
  built in Python from fixed octets rather than replayed from a store, so this
  half demonstrates protocol interoperability, not the projection.

A single run that is both — kernel mount of a store-backed snapshot with a
`diff` against the reader's reply — is chained on hbox behind the full
`make certify` in `/tank/fn/ninep` and lands in
`/tank/fn/ninep/mount-transcript.log`. It was not complete when this note was
written.

## Environment

- Host `hbox`, Linux 6.11.0-29-generic, in-kernel 9P client (`fs/9p`,
  `net/9p` with `9pnet_fd` for TCP).
- Server: `python3 tools/fn9p.py`'s `Node`/`serve_connection` over a synthetic
  tree on `127.0.0.1:5641`.
- `mount -t 9p -o trans=tcp,port=5641,version=9p2000,uname=fn,access=any,msize=8192 127.0.0.1 /mnt/fn9psmoke`

## What the refusals mean

Base 9P2000 carries a reason string and the Linux client maps it through its
own table. A string the table does not know becomes `ESERVERFAULT`, which the
shell prints as `Unknown error 526`. That is what the projection's own refusal
reads as: the server answers `stored article framing unavailable`, the same
reason NNTP reports as `503`, and keeping that reason is worth an unmapped
errno. Conditions a file system already has a name for use that name, so a
missing article is `ENOENT` and the read-only refusals come straight from the
`0444`/`0555` modes without a round trip.

The first mount of this tree returned `Unknown error 526` for the missing
article too; `tools/fn9p.py` now answers that case with the string v9fs maps
to `ENOENT`.

## Limitations

- Loopback only, no authentication, single store snapshot, read-only.
- Synthetic tree: this transcript exercises the 9P adapter, not the ACL2
  projection. The projection's own evidence is `tests/test_fn9p.py`.
- One kernel version, one client, one set of mount options. No claim about
  other 9P clients or about `9P2000.u`/`9P2000.L` behaviour beyond the
  documented fallback.
