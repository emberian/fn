The first run of `tests/ltp/run_fn_ltp_lab.py` since `4ec3541` in which the
lab could start at all, and the first one ever in which the receiver was
handed a primary block. `tests/evidence/2026-09-21-ltp-lab.json` is the
machine record the lab wrote; this file says what it means and what it does
not.

## What was broken

`4ec3541` (2026-09-19, "Key inbound staging by ACL2 bundle identity") made
`bundle` a required keyword-only argument of
`tools/run_bp_receive.receive_bpa_request`, because fn stages an inbound
bundle under the identity ACL2 derives from the bundle's own primary block.
Every caller in `tools/` was updated. `tests/bp-dtn7/run_four_node_lab.py`
was not, and was repaired on 2026-09-21 by `w11/workflow-replay`.
`tests/ltp/run_fn_ltp_lab.py:96` was not, and is repaired here. Between the
two, both integration labs were dead for a day and every `make check` was
green, because nothing in the tree ran a lab.

## The repair, and exactly what it costs

`IonStagingInbox` now serves fn's `bundle` callback as well as
`inventory`/`download`/`delete`. It cannot serve it by handing over the
bundle: ION's `bp_receive()` deletes the delivery-queue element, zeroes the
payload content and destroys the bundle inside one SDR transaction it commits
*before it returns*, and no ION API gives an application the octets
afterwards. That is the same seam that forces the staging copy, written up in
`tests/ltp/README.md`.

What `BpDelivery` does report is the source EID and the creation timestamp —
which is exactly `fn-bpp-primary-identity-value` (`books/bp-primary.lisp`):
source, creation time, sequence, for a bundle that is not a fragment. So the
block is re-encoded from those three observed fields through ACL2's own
`fn-bpi-host-bundle-prefix`, by way of the new
`tools/bundle_bridge.encode_primary` (which gained the `ipn` endpoint form
this laboratory registers). Every field the reconstruction supplies rather
than observes — destination, report-to, flags, CRC type — is one the identity
projection provably ignores, and `books/bp-primary.lisp` carries those
theorems (`fn-bpp-with-destination`, `fn-bpp-with-report-to`). The lifetime is
the one this run asked ION for, so the receiver's expiry verdict is about the
bundle's real deadline.

**The cost, stated plainly: the identity fn staged this bundle under came
from ION's report of the bundle's fields, re-encoded canonically, and not
from the bundle's own octets as they crossed the link. A transport that
misreported those three fields would be believed here.** The dtn7-rs lab does
not have this gap, because its agent hands over the bundle. Closing it for
ION needs the primary block captured inside `fn_ltp_stage.c` before
`bp_receive()` returns, through the C API and not through any shipped utility.

Two smaller limits of the same kind. `fn_ltp_stage.c` substitutes `_` for `/`
in the staged name, which is not invertible, so a `dtn`-scheme source cannot
be recovered from it; `observed_fields` refuses rather than guessing, and the
laboratory is pinned to the `ipn` scheme, whose text form contains no `/`.
And `--lifetime` is ION's `bpsendfile` TTL in seconds while RFC 9171 section
4.2.8's field is milliseconds; `tests/ltp/ion_bpa.py` writes that
correspondence down in one named constant, and it is a conversion between two
programs' argument units, not a quantity ACL2 also computes.

## What this is not

Everything `tests/ltp/README.md`'s "What this is not" says, unchanged: one
implementation, one host, one profile, IPv4 loopback UDP with zero light time,
no contact plan, no BPSec, no authenticated peer, no author signature, no
power-loss qualification, and no receipt returned over BP — ION's
`bpsendfile` prints no bundle identifier and `bp_send()` returns only an
in-process SDR address, so there is no transport handle for fn's durable
attempt record to bind, and the return leg stays out of scope. LTP
reliability is not fn application acceptance. This is feasibility evidence
for one adapter route.
