# fn after the proof-iteration repair

Status: architectural reassessment and proposed experiments, at fn
`df5097b6`, 2026-09-23. This document does not change a release requirement,
select a private-group cryptosystem, or authorize deployment. The selected
[trajectory](plan-2026-09-22-trajectory.md), [decisions](decisions.md),
[takeover](takeover-2026-09-23.md), and [BP review 3](review-2026-09-23-bp-node-machine-3.md)

## Recommendation

Finish the selected v0, and use it as the first complete instance of a broader
purpose: **durable, attributable communication between independently running
humans, agents, and administrative domains**. Then prioritize a small native
consumer contract and a real dregg integration experiment alongside the
selected post-v0 transport work. Do not turn fn into another turn executor,
consensus service, agent scheduler, or universal database.

That is an increase in ambition. It asks fn to make preserved communication
usable by a system whose participants act at different times, retain different
knowledge, and possess different authority. It is also a sharper boundary:
the article, its evidence, the node's undertaking, and an application's result
remain four different things. NNTP remains a first-class usable product, not
a compatibility demonstration to abandon after the agent API exists.

The new affordance is cheap repeated examination of executable designs. It
makes larger *complete* joins and comparative experiments realistic. It does
not make policy selection, cryptographic analysis, hardware qualification,
interoperability, or application correspondence disappear. Spend the gained
capacity on those joins and on discriminating examples before spending it on
more independent subsystem books.

## The useful architectural boundary

The smallest durable core worth building applications on is an immutable
source plus explicit evidence and local undertakings. It supports distinct
projections for ordinary news, an agent inbox, archival export and a dregg
consumer. Those projections may index or hide facts; they cannot retroactively
change the preserved source or claim that all sites share the same policy.

There are three particularly useful identities to keep outside any one
transport: immutable content, the author's event/incarnation namespace where
one is used, and the application's request/result correlation. Message-ID
remains the NNTP identity; a BP creation tuple remains a carrier identity;
an endpoint remains a locator. Retrying one application request can use another
carrier without becoming another application operation. Causal references
describe claimed dependencies, with missing and conflicting evidence exposed;
they do not manufacture a total order or force every reader to resolve an
unbounded graph before reading an article.

| Layer | fn should decide | Consumer/domain should decide |
| --- | --- | --- |
| Content and evidence | Exact bytes; profile and source bindings; bounded decoding; provenance; conflicts; historical verification context | Meaning of a report, patch, turn receipt or application payload |
| Local acceptance | Admission capacity, durable commit, allocation, explicit refusal/uncertainty | Whether an accepted report warrants action |
| Delivery | Authorized peer scope, durable attempts/outbox, bounded retries, application retention receipts | Desired recipients, application retry policy after its own outcome |
| Consumer progress | A precisely scoped resumable view and, if adopted, explicit durable acknowledgements | Transactional processing, side effects, idempotency and application result |
| Authority | Enforce the selected fn post/read/relay/release policy | dregg capability exercise, resource transfer, participant agreement and program predicates |

The end-to-end principle is directly relevant: crash recovery and duplicate
suppression at a communication layer cannot by themselves establish completion
of an application's operation. This is the placement problem described by
[Saltzer, Reed and Clark](https://web.mit.edu/saltzer/www/publications/endtoend/endtoend.pdf).
It argues for a precise consumer boundary, not an unreliable lower layer.

### A concrete asynchronous exchange

An agent in silo A publishes an exact-source signed request. A's node commits
it with its archive obligation. The BP path transports it when a contact is
available. B's node accepts it under B's own numbering and policy, and may
issue a receipt for the *retention undertaking named in that request*. That
receipt does not say that B's agent has read it or executed its request.

B's agent later records the input identity in its own durable inbox, validates
application authority and dependencies, performs an application transition,
and records a result plus a response in its own outbox. It can then acknowledge
its fn consumer position. Repeated delivery is harmless only to the extent
that this application transition or its external target honors the same
idempotency key. A payment, shell command or remote API outside that transaction
needs its own reconciliation; fn cannot promise exactly-once external effects.

The response travels as another attributable article. A dregg consumer can
verify a carried dregg receipt using dregg's verifier. A successful fn signature
means who authored the bytes under a profile; it does not mean the dregg
proof verified or the requested turn was authorized. A negative application
result is still valid preserved correspondence.

The following words should never share one undifferentiated `ack`:

| Evidence | What it can establish |
| --- | --- |
| TCPCL acknowledgement | A fact about the convergence-layer transfer |
| BP delivery/status report | A reported BP processing event |
| fn accepted completion | This node durably accepted this transaction under its stated assumptions |
| fn obligation receipt | The issuer undertook the specifically bound subject and terms under an authorized receipt profile |
| Consumer acknowledgement | This consumer committed progress under its own declared acknowledgement contract |
| Application result/receipt | The application's stated outcome and any independently checked proof |

BP itself separates local application delivery from its administrative status
reports; see [RFC 9171 §5.7](https://www.rfc-editor.org/rfc/rfc9171.html#section-5.7)
and [§6.1.1](https://www.rfc-editor.org/rfc/rfc9171.html#section-6.1.1).
fn's durable retention promise is an additional application contract.

## Opportunities that repay the new capacity

### 1. Make portability explicit before extending the statement vocabulary

Retain the selected exact-source Ed25519 **and** ML-DSA-65 profile. Its signed
subject includes domain, version/profile, principal, ordered algorithm-tagged
keyset and exact authored bytes. An old generic statement signed over a digest
is a different profile; there must be no silent conversion between the two.
Algorithm agility means an explicit additional profile with coexistence and
refusal rules, not a negotiation that drops the required second signature.

For v0, the narrow carrier is enough. Preserve bounded unknown profile bytes
as evidence where the enclosing article policy permits, while refusing all
authority effects from them. Unsupported and malformed are useful distinct
observations. Neither means that an intermediary should rewrite the source.

For the first post-v0 experiment, carry one versioned application payload in
an ordinary signed article. Start with an application/profile identifier,
subject references, optional causal references and opaque bounded bytes; do
not add arbitrary Lisp or a generic embedded query language. Keep the exact
grammar experimental until two independent consumers and an older relay have
exchanged it. A private registry or namespace can initially prevent collisions;
selecting a universal schema registry is unnecessary.

The existing four statement kinds are authority-sensitive. Adding a
`task`, `result` or `application` kind to that enum is not automatically a
better extension than an opaque payload with an explicitly registered decoder.
Require a reason for each new core semantic effect. Unknown payload types may
be preserved and forwarded within quota without acquiring an interpreter or
authorization. Portable content references do not inherit the authority of
whatever object they happen to name.

### 2. Give agents a durable consumer contract

The existing client is enough to correspond, but its watermark promises only
that output was printed before its local progress file advanced. A process can
die after printing and before a downstream consumer commits work. A new store
at the same endpoint can reuse small local numbers and an old watermark can
skip them. Copying one state file to another node also has no portable meaning.
These follow from the source boundary above; they are not observed failures
of the deployed node in this assessment.

Experiment with an opaque cursor scoped to `(store-incarnation, consumer,
query-definition/version, position)`. The exact encoding is open. A bare
hostname, TLS key, article timestamp, Message-ID or BP EID is not a substitute
for a store history identity. Restoring/cloning a history must follow D10,
and cannot silently mint the same cursor namespace with different contents.

Prefer at-least-once consumption with explicit acknowledgement. First make
polling correct and bounded; an eventual push notification can simply mean
“poll again.” If fn stores subscriber acknowledgements or promises an unread
backlog, account for their metadata, retention roots and release authority.
A subscription must not silently create an unlimited durable obligation.

The first filter should be a small ACL2-defined selection over existing
groups plus, if needed, principal/profile. Its response describes the scanned
committed prefix, limits and continuation. A changed authorization or filter
must invalidate/rebase the cursor explicitly. A filter that exposes newly
visible *old* articles cannot safely resume using only the newest article
number. Either its view is fixed or visibility changes themselves enter the
enumerated change stream; that is a semantic choice to test, not an index
optimization.

The acceptance stamp remains the right local NEWNEWS input, and T2 should
land. It is not a causal clock, portable event ID, exactly-once consumer
position, or ordering across silos. Do not put the consumer design on the
stamp migration's critical path.

### 3. Join to dregg through evidence, not shared execution semantics

The local breadstuffs checkout inspected for this assessment is
`c93404d81c013d4c5b304a852d26f190d0aab19f`. Its `README-LLMs.md` describes
cells, capability-gated turns and receipts; `coord/src/lib.rs` distinguishes
causal chaining, coordinated multi-party turns and bounded counters. This is
orientation from source, not independent verification of that system's claims.
fn already cites the related blocklace and capability-chain structures in
[identity](../specs/identity.md), [statement](../specs/statement.md),
[lace](../specs/lace.md) and [policy](../specs/policy.md).

The useful bridge is a byte-preserving carrier for an application request,
result, proof or dependency manifest, plus explicit provenance and delivery
state. Keep dregg's verifier/executor as the authority on dregg semantics.
The bridge must not reimplement that verifier in Python or turn fn's ACL2
kernel into a second dregg executor. If a trusted native FFI observation is
eventually needed, name its exact input, output and correspondence assumption.
Start with client-side verification so the server can remain an ordinary
news server serving opaque application payloads.

Use one immutable report or receipt exchange as the first experiment. Do not
start with an atomic cross-silo transfer: that adds failure modes from a
second protocol before the transport boundary is measured. If later work
needs consensus, escrow, revocation finality or a two-phase protocol, the
application owns those invariants and fn carries its messages. Set union of
facts does not prove exclusive task ownership, absence of double spending,
or instant global revocation. The relevant research criterion is whether the
application's invariants survive independent execution and merge, rather than
whether its transport uses a CRDT; see
[Bailis et al., Coordination Avoidance](https://arxiv.org/abs/1402.2237).

### 4. Make silo boundaries concrete

A group is a routing/visibility label, not an OS isolation boundary. A node
principal, a transport peer principal, an author and a receipt issuer can be
different actors. Review 3's identity partitioning before receive deduplication
is therefore already a necessary foundation. It prevents one admitted
principal's claim from being confused with another's; shared memory, CPU,
history slots and capacity still require their own isolation policy.

For a first cross-domain experiment, use distinct stores, explicit configured
peers and allowlisted groups/payload profiles. State whether the relay and
administrators are trusted. The current controlled-host BP profile may carry
unsigned receipts under its declared network trust; it does not authenticate
an end-to-end receipt issuer through an untrusted relay. Keep that v0 scope
honest. Before claiming safe release through untrusted silos, add the signed
receipt/issuer binding and test it, rather than letting native article
authorship stand in for receipt authentication.

Authorization should name an action and a resource: publish in this scope,
read this view, introduce this dependency, request this undertaking, or release
this pin. A signed message addressed to an administrator is still data. The
bridge to a dregg action requires a separate, explicit authority check, and
an article's natural-language instructions must never become ambient shell,
filesystem or operator authority.

Keep historical validation and present permission as separate queries. “This
key was enrolled when these bytes were accepted” is archival evidence, not a
perpetual license to execute their instruction. A delayed command must be
checked against the application's chosen execution-time/epoch policy, and a
disconnected site cannot enforce a revocation it has not learned. The policy
must say whether to hold, refuse, or permit that operation under its local
knowledge. This choice belongs to the authority domain, not the BP expiry clock.

Be especially careful with capabilities in preserved news. The OCapN locator
draft treats a sturdyref containing a peer and Swiss number as a capability;
serializing it can transfer authority. Its presence is not harmless just
because it resembles an address.
[OCapN locator specification](https://github.com/ocapn/ocapn/blob/main/draft-specifications/Locators.md).
Use non-secret references by default. Live bearer tokens and private signing
keys do not belong in an indefinitely replicated article archive. A bridge
that intentionally transfers a capability needs confidentiality, audience,
attenuation, lifetime and replay semantics of its own.

This does not select a private-group design. Shared community groups remain
the first release. Preserve opaque ciphertext carriage and metadata boundaries
for later work. MLS requires an application policy for group evolution and
delivery; ordinary commutative object merge does not supply it.
[RFC 9750 §5.2](https://www.rfc-editor.org/rfc/rfc9750.html#section-5.2).
The [private profile packet](private-profile-packet.md) remains the decision
agenda for confidentiality, archives and compromise recovery.

### 5. Treat preservation as preserving interpretation

No-autoexpiry retention is already selected. A useful archive must retain the
source, signature/profile, enrolled key snapshot, provenance, relevant policy
and dependency evidence needed to interpret an accepted claim. A current
keyring cannot recreate what was known at acceptance. A later revocation or
algorithm deprecation changes a present assessment; it must not rewrite the
historical accepted verdict.

Add export/import and restore exercises before calling this long-lived
preservation. An export manifest identifies exact bytes and profile versions;
it does not export local article numbers as global IDs. Restoration should
report missing evidence and unsupported algorithms explicitly. Retaining old
decoders or migration witnesses is part of a format evolution plan. A future
re-attestation under a new signature suite is a new statement about the old
source and evidence, not replacement of the original signature.

Preservation also gives disconnected exchange a concrete advantage: a useful
delivery can carry its bounded interpretation dependencies proactively rather
than require an interactive lookup after arrival. That extends REP-003/004's
batch principle to key/profile/policy evidence. A dependency manifest is a
claim to check, and acceptance of an opaque article is distinct from accepting
a dependency-complete authority-bearing operation. Missing dependencies stay
visible and bounded; they do not become an implicit network fetch or authority.

Compaction should follow demonstrated retention roots, including authority
dependencies and consumer progress if adopted. Capacity refusal is the safe
v0 behavior. Do not use age, BP carrier expiry or a newer assertion to erase
an old obligation. D13 still needs an explicit duplicate-history/resurrection
policy before finite metadata reclamation can be claimed.

## Three paths, with costs stated in terms of uncertainty

| Path | What it buys | What it risks | Assessment |
| --- | --- | --- | --- |
| Finish the old sequence verbatim | Fastest decision process; existing T0–T16 gate remains clear | Discovering consumer/authority mismatches only after transport and storage APIs have hardened | Safe baseline, but leaves the new affordance underused |
| Finish v0 and run bounded substrate experiments alongside/after it | A useful NNTP node plus evidence about the smallest agent/dregg contract; preserves the selected finish line | Requires disciplined separation of exploratory contracts from release requirements | Recommended |
| Replace v0 with a general cross-silo coordination platform | Maximum conceptual breadth | Unspecified authority, consumer semantics, execution and privacy become release blockers; no complete product boundary | Reject unless the user explicitly wants a different project |

The recommended path keeps T0–T16 and the takeover dependency order. It changes
what the next design capacity investigates. A v0 release can be complete while
an experimental consumer interface is not; the experiment must not quietly
become another mandatory release row. Conversely, a discovered defect in an
already claimed v0 acceptance, recovery or authority property is a v0 defect,
not research to defer.

### What belongs in the core now, and what can remain an extension

The cost is not simply the number of changed files. A low-level record or
identity change fans out through replay, checkpoints, proofs and every ingress
caller; a client payload experiment can often leave all those bytes alone.
Cheap certification reduces that fan-out's feedback delay, but not its semantic
risk. Use the distinction below to avoid both premature freezing and gratuitous
schema widening.

| Choice | Do now under the selected work | Keep above the core until demonstrated |
| --- | --- | --- |
| Article identity and authorship | Exact authored source, explicit profile/version, dual-signature subject binding, immutable historical key/verdict context; old bytes retain their meaning | Application task IDs, result types and proof payloads as signed content |
| Store schema | T2 acceptance stamp with schema-0 compatibility; T4 every finish arm; authoritative retention events | A new task-state machine, generic per-article application columns, or consumer acknowledgement bundled into every article record |
| BP identity/outcomes | Peer partition before dedup, versioned identity roles, correlated operation/epoch completion, durable outbox and named receipt terms | Application “started/completed/failed” state; those are distinct carried messages |
| Native interface | Existing submit/read/inspect outcomes and actual historical verdict; bounded opaque extension bytes with no implicit authority | A consumer protocol first prototyped against a selected cursor contract; no speculative universal RPC ABI |
| Namespace and restore | Preserve local numbering and explicit incarnation distinctions; do not advertise endpoint identity as store identity | A durable cursor record can be separate metadata once E2 defines its lifecycle; do not squeeze it into the acceptance stamp |
| Capability boundary | No authority from unknown content; explicit operator/peer admission; no live secrets in generic replicated state | dregg's attenuation, exercise and external-effect semantics remain in its consumer |

The early carrier lane can therefore ship a strict v1/suite1 codec and unknown
profile vectors now. It need not invent a general statement language. The BP
foundation can freeze the reviewed finite schema now. It need not add agent
execution receipts. The restore/upgrade lane should preserve store identity and
evidence rather than generate an endpoint-shaped identity; if no durable store
incarnation is exposed yet, record that missing consumer prerequisite instead
of claiming an existing public cursor ABI. Each is a concrete v0-compatible
boundary decision, not a reason to postpone the current join.

## Proposed progression and experiments

These are proposed milestones, not additions to the requirement/proof registry.
On adoption, write the relevant contract and scenario together, allocate stable
IDs, and attach the actual called subject and evidence. Do not pre-populate
`proofs.json` with proposed theorem events.

| Stage | Complete behavior and decisive experiment | Dependencies and stopping rule |
| --- | --- | --- |
| V0: qualified news and disconnected correspondence | Two native nodes post/read, protected-feed, sign/verify exact source, exchange a BP article and application receipt, recover the named cuts, preserve an unrelated pin, and reopen historical verdicts. Self-contained image and isolated upgrade preserve prior accepted state. | Existing T0–T16 plus BP review 3; finish this selected gate. No new consumer protocol required. |
| E1: portable application evidence | One dregg-produced report/receipt crosses native NNTP, one legacy relay, BP and carried-media import where supported. Its exact signed source and application bytes agree. A second consumer verifies it independently. Unknown payload/profile remains preserved within policy and gains no authority. | T10 and actual T12 join. If it cannot fit current article/ADU limits, measure whether bounded manifest dependencies or larger limits are needed; do not silently split the acceptance unit. |
| E2: durable consumption | A native consumer polls, commits an input/result/outbox record, acknowledges, crashes at each boundary, restarts and converges without a missing input. A second store at the same endpoint cannot accept the old cursor silently. Two consumers remain independent. | E1 supplies realistic payloads; cursor namespace and acknowledgement contract must be selected. The result is at-least-once transport plus a scoped application transaction, not arbitrary exactly-once effects. |
| E3: two authority domains | An untrusted relay substitutes source, keyset, issuer, subject and terms; no substituted receipt releases a pin. Two silos disagree about admission yet preserve attributable evidence. An unrelated capability/article cannot authorize administration. | Selected post-v0 signed-receipt and portable authority profile; isolated stores and explicit trust model. Until this passes, retain the v0 trusted-peer limitation. |
| E4: bounded retained service | Measure backlog, index lookup, recovery and refusal on a declared community workload with sleeping consumers, delayed receipts, repeated imports and capacity exhaustion. Compaction preserves the exact protected closure; restore preserves evidence and creates/validates the right incarnation. | Served indexes and existing v1 compaction/pruning plan; include subscriber metadata only if E2 made it authoritative. No claim of unbounded retention capacity. |

E1 can be designed while v0 joins run, and its byte vectors can exercise the
carrier without changing Store. E2's standalone consumer model can be explored
after a cursor contract is selected; it should not widen T2's record migration.
E3 depends on an actual trust choice. E4 needs measurements before data-layout
optimization. The experiments are complete when their application-facing
claim is demonstrated; merely admitting a new record type is not an exit.

Keep the selected LTP-after-DTN order. A useful proposed refinement to v1 is
to run LTP implementation in parallel with E1/E2 and served-index work once
their dependencies permit, rather than make every application experiment wait
for another convergence layer. That scheduling change is a recommendation,
not a silent override of trajectory §2.2. BPSec, portable policy/membership,
compaction and later interfaces remain distinct contracts; their priority
should follow the chosen threat model and workload.

For every experiment, use the same loop that became affordable: one or two
candidate ACL2 interfaces, reachable positive witnesses, hypothesis-removal
counterexamples that actually falsify the conclusion, bounded proof iteration,
source-matched incremental certification, and a native application exercise.
Measure edit-to-verdict, native resource cost and user-visible behavior
separately. A faster theorem cannot excuse a slow served guard or a callback
that bypasses its subject.

## Decisions worth the user's attention

Update after review, 2026-09-23: the user selected the recommended options for
questions 1–3 below: report/receipt and reply, consumer-owned durable inbox/outbox
with an explicit fn cursor/ack contract, and separate stores/administrators with
trusted transport peers first. See the [decision register](decisions.md).
Questions 4–5 remain recommendations; the experiment's contracts and evidence
remain to be developed.

These questions choose product boundaries. Routine implementation details can
continue while they are discussed.

1. **What first dregg exchange should fn make dependable?** Recommend an
   immutable report/receipt and reply between two sleeping agents. Alternatives
   are a task request/result protocol or an authority-bearing cross-silo
   operation. The latter makes application execution and revocation policy
   immediate dependencies; the first exposes the transport/evidence boundary
   with much less ambiguity.
2. **Who owns durable consumer progress?** Recommend a consumer-owned
   inbox/outbox with an explicit fn acknowledgement/cursor interface, leaving
   the existing reader watermark as convenience. A server-owned durable
   subscription is also possible, but creates new reservation, administration
   and retention obligations. Decide whether server-managed backlog is wanted
   before giving it an API.
3. **What does a silo distrust?** Recommend first separate administrators and
   stores with explicitly trusted transport peers, followed by an untrusted
   relay experiment. If the first deployment needs mutually distrustful peers
   or co-resident hostile processes, signed receipt authority and stronger
   resource/OS isolation move earlier. A group name alone cannot satisfy that.
4. **Who may recover or rotate an author's authority?** Recommend selecting
   a small explicit operator/enrollment workflow for v0 and designing portable
   succession separately, with a history-preserving recovery exercise. An
   individual root key, delegated devices and community recovery carry
   different trust assumptions. The mandatory hybrid suite does not choose
   among them.
5. **May v1 deliver application usefulness in parallel with LTP?** Recommend
   yes: keep LTP next in transport while a bounded E1/E2 lane establishes the
   consumer contract. If strict sequential completion is preferred, prepare
   vectors and interface design now but defer that implementation until LTP.

No question here asks whether to keep the selected exact-source hybrid suite,
no-autoexpiry retention, native semantic ownership, or v0 DTN. Those choices
are already made. No private-group cryptosystem or network exposure is chosen.

## Explicit non-goals and completion boundary

The proposed expansion does not add a universal task language, a central agent
scheduler, global total ordering, a replicated transaction executor, arbitrary
remote evaluation, a generic SQL/search engine, global erasure, automatic
expiry of obligations, or a promise that any received request is safe to
execute. It does not require the whole dregg implementation to become ACL2,
and does not require fn to depend on dregg to function as a news server.

The work authorized without another product decision remains substantial:
finish the native v0 joins, fix current defects, preserve format/profile
boundaries, measure current workloads, qualify the served crash model and
publish exact evidence. The recommended new commitment is to validate fn's
next application boundary through a real portable-evidence and durable-consumer
slice before expanding its protocol surface further.
