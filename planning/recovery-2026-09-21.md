## Memory incident

The Mac records a boot at **11:25 EDT**. Jetsam reports show severe memory
pressure at **08:24–08:41 EDT**, so boot time is not the time work became
unusable. The last main commit before recovery was at 07:42 EDT.

There is strong evidence of an escaped development-test loop. At 04:31 EDT an
intermediate `tools/feed_wire.py` edit started a parent-directory walk above
the intended stopping directory. At `/`, `dirname('/')` stayed `/` forever.
The creation-barrier test mocked `fsync_dir`, so every loop iteration retained
another mock-call record. Shell terminations reported exit 143 while at least
one Python child survived. The loop was corrected at 04:41 EDT and the corrected
three-test run completed; the already-running processes retained the old code.

PID 99056 is directly identified in a 06:45 EDT process snapshot as
`python3 -m unittest tests.test_feed.JournalTests.test_creation_barriers_precede_any_append -v`.
The later Jetsam and force-reset records identify it and Python PIDs 96056 and
99661 as the dominant consumers. Attribution of the other two to adjacent
reproducer/retry commands is inferred from launch order. The diagnostic memory
accounting is not a measurement of uncompressed physical RAM consumption.
Current main and the original lane contain the corrected traversal; the
current file's last commit is `1555d03f`.

Provenance remains in local Codex session
`rollout-2026-09-21T03-53-34-01a0c2f4-bf9f-76f3-9a92-2a53c4388d9b.jsonl`
(lines 826–827 introduction, 965 shell termination, 1028–1037 correction and

Before further heavy testing, commands need process-group containment with
bounded termination, escalation and reaping, including cancellation of the
parent shell. A timeout that leaves a child running is not a completed cleanup.
Add a child-survival regression and a finite directory-walk regression. This
incident implicates a development test, not the native Lisp server or a proved
ACL2 function. Merely reducing certification concurrency would not fix it.

2. **One native service composition:** integrate ready TLS/admin/fault packets,

3. **DTN and preservation closure:** integrate the pending BP proof/publication
   packets and expand the actual crash/contact tests and correspondence where
   those composed paths require them.
4. **Remaining v0 contracts:** complete identity/authority, live configuration,
   storage preservation and release evidence. Keep their scope explicit rather
   than shrinking v0 to the first successful two-node demonstration.

Use bounded Terra/Luna repair tasks, Sol for substantial integration/proofs,
and root Astra for periodic convergence. Reuse completed remote evidence;
avoid parallel duplicate closures and repeatedly rebuilding nearly identical
images. A component packet should land with one coherent review and concrete
failure repair, not a chain of ceremonial reviews.

project-completion metric. There is no measured basis to promise the full v0
or v1 within it. The next useful forecast point is a composed native two-peer
matrix: it will separate remaining product gaps from integration failures.
v1/M6 still includes additional profiles/interfaces, long asymmetric-contact
operation and separately qualified mission work. No existing result establishes
flight readiness.
