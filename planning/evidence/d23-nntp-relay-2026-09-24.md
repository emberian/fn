# D23 on the NNTP side: an allowlisted relay carries, it does not verify

Lane `lane/d23-nntp-relay`, 2026-09-24. Decision D23 (planning/decisions.md)
overrides the D02 entry's consequence for transit. A node that has not
enrolled an author, and whose delivering boundary allowlists the author's
principal, stores and relays that author's signed article. Its verdict record
says `carried` and never `verified`. A node that enrolled the author verifies
against its own enrollment, as before.

## What changed

- **One owner.** `fn-pa-current-plan (received snapshots carried)`
  (books/peer-authored-accept.lisp) gains the delivering boundary's
  carried-source list. The new arm is `(:carried source principal keys
  signatures)`. It is taken only when this node has no keyring snapshot of the
  principal (never enrolled and never revoked) and `fn-pa-carriesp` finds the
  principal's lowercase hex in the list. A revoked principal, or one enrolled
  under other keys, is refused whatever the list says. Served POST, bound
  submissions and BP transit pass `nil`.
- **The record.** The Store token vocabulary gains `:carried`
  (`*fn-stx-verdicts*`, books/stx-verify.lisp; code 4 in
  books/stx-evidence-records.lisp). `fn-pa-carried-event` builds a schema-1
  kind-4 composite with the same record, authored-source and carrier binding
  as the enrolled constructor. Its verdict has token `:carried`, the carrier's
  principal as detail, and keyring generation 0. No observation is taken or
  claimed. Replay records the composite without a snapshot lookup:
  `fn-hsig-article-event-carried-bindsp` (books/hybrid-store.lisp) and the
  new `fn-replay-identity-step` branch with `fn-replay-apply-carried-verdict`
  (books/replay.lisp). The Store's prepare admits a kind-4 event only when
  that step answers `:ok` (books/store-node.lisp `fn-sn-prepare-identity`).
- **The reader.** `fn-stx-verified-item` renders `carried <principal-hex>`.
  `HDR :fn-verified` therefore answers `0 carried HEX`.
- **The boundary list.** The list is extra rows in the peer's configuration
  group, one per principal: `(name "carries-principal" HEX 0)`. They are
  written by native `operator CFG peer add ... carries HEX [HEX ...]`
  (books/native-admin.lisp) and by `fn peer add ... --carries HEX`
  (host/store-node-host.lisp). `fn-owner-transit-decide` reads them for the
  delivering peer (host/owner-host.lisp, global `fn-owner-transit-carried`).
- **Host.** `fnn-owner-attempt-transit` (host/native/owner.lisp) takes
  `nntp-transit-p`. Only `fnn-owner-drain-one`'s NNTP transit call passes `t`.
  On `:carried` it advances the clock, builds the event with
  `fn-owner-peer-carried-relay-event` and publishes it through
  `fnn-owner-identity-commit`. The transit log line carries
  `detail=carried`, which is a log detail and not a decision input.
- **Verifier.** `tools/fn_verify.py` parses `carried HEX` and exits 3
  (undecided) with the reason "the node carried this article for a neighbour
  without verifying it". It still runs its own check and reports it. It never
  exits 0 or 1 for that token. Fake-node case:
  `tests/test_fn_verify.py::test_a_carried_article_is_undecided_3_never_0_or_1`.
  All 7 FakeNodeVerifyTests pass locally (uv, cryptography + dilithium-py).

## Theorems (statements; the host line calls the subject)

books/peer-authored-accept.lisp. Subject: `fn-pa-current-plan`, called by
host/owner-host.lisp `fn-owner-peer-carrier-plan`, which
host/native/owner.lisp `fnn-owner-attempt-transit` calls. Also
`fn-pa-carried-event`, called through `fn-owner-peer-carried-relay-event`.

- `fn-pa-current-plan-outcomes`: the plan is `:absent` or its car is one of
  `:ok`, `:carried`, `:refused`.
- `fn-pa-carried-arm-needs-the-list-and-no-local-snapshot`: `:carried`
  implies `fn-pa-carriesp principal carried`,
  `(fn-hl-current-for-principal principal snapshots) = nil`, and that the
  source and principal are the carrier form's.
- `fn-pa-current-plan-off-the-carried-arm-is-the-d02-plan`: if the plan is not
  `:carried`, it equals the plan with `carried = nil`. An enrolled receiver
  accepts as before, and an unlisted, unenrolled principal is refused
  `:local-enrollment`.
- `fn-pa-current-plan-without-carried-list-never-carries`: with `nil`, the
  car is never `:carried`. This covers served POST, bound submissions and BP
  transit.
- `fn-pa-carried-event-requires-the-carried-arm` and
  `fn-pa-carried-event-is-a-carried-record`: a non-nil carried event implies
  that the plan is `:carried`, that the event satisfies
  `fn-hsig-article-event-carried-bindsp`, that its keyring generation is 0,
  and that its decoded verdict token is `:carried`.

books/owner-signed-post.lisp:

- `fn-osp-carried-event-keeps-the-relayed-octets` and
  `fn-osp-carried-event-stores-the-relayed-octets`: the stored record's payload
  is exactly the received (relayed) octets, and the authored source is the
  carrier's. Together with `fn-peer-relayed-octets-change-only-path-and-xref`
  (existing), the carrier travels intact and only Path/Xref change. The

- `fn-osp-replay-records-a-carried-composite`: for an event that satisfies

  this step's `:ok`.
- `fn-osp-carried-record-reads-carried`: the reader item for a pinned
  `(:carried detail gen)` is `carried <hex detail>`. With
  `fn-own-read-hdr-fn-verified-is-the-pinned-verdict` (existing), the HDR
  reply begins `carried` and never `verified`.

books/stx-verify.lisp `fn-stx-verdict-is-never-carried`: the SUB-002
verdict function never yields `:carried`.

State unchanged on refusal: every refusal arm of `fnn-owner-attempt-transit`
returns before `fnn-owner-identity-commit`, which is a host fact. On the
ACL2 side, the constructor is nil off the carried arm
(`fn-pa-carried-event-requires-the-carried-arm`). The existing transit
refusal rows (439, no Store change) are unchanged. I added no new

## Teeth

The test books are tests/acl2/peer-authored-accept-tests.lisp,
owner-signed-post-tests.lisp and native-admin-tests.lisp.

- **Witnesses.** The carried plan and event on the fixture principal. On the
  owner, a Store with no enrollment takes the POST's staged octets, the
  carried event is prepared, published and completed, and a reader opened
  afterwards renders `carried 0707…07`. Replay's step on that context
  returns `:ok`.
- **must-fail per hypothesis.**
  - The list: nil, and a list naming another principal.
  - No local snapshot: enrolled; revoked with the list; re-keyed with the list.
  - Carried arm: an enrolled receiver builds no event, and no list means no event.
  - Sequence: the event one identity sequence late faults.
  - Binding: a forged composite that claims `:verified` at generation 0
    passes `fn-stxa-bindsp` but not carried-bindsp and not snapshot-bindsp.
- **Native admin.** `carries` rows land in the delta. Uppercase HEX or a bare
  `carries` is refused `:carries`.

## Findings

- **Consumer poll.** `fn-cpj-project` (books/consumer-poll-projection)
  refuses a carried composite as `:authored-binding`, because it requires
  `:verified`. An agent consumer is therefore never handed a carried article
  as authored. This is intended, but a consumer iterating a Store that holds
  carried articles will see those refusals.
- **Topic history.** A topic proposal that references a carried article is
  `:unbound-event` (`fn-th-select-accepted-event`), because it has no
  snapshot at generation 0.
- **The relay does not check signatures.** `carried` claims nothing. A relay
  will forward a carried article whose signatures are bad, and the enrolled
  receiver refuses it (`:signature`).
- **`fn peer list`** does not print `carries-principal` rows (tools/run_store.py).
- **The BP boundary's list** is the d23-bp-carrier lane's. The row shape and
  reader here are reusable.
