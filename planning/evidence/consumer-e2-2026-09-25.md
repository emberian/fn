## What now works

Two agents, each a separate `tools/fn_consumer.py` process with its own
SQLite database, exchange a signed report R and a signed reply Q through one
developer owner, across all six ownership-boundary cuts, and each uncertain
fact is settled by its owner (the consumer's database, fn's `position`, fn's
Store serving the exact source back). The same operation with a changed
source is kept as conflict evidence by both consumers with no second
transition and no reply.

## Step 2: the consumer transaction

`tools/fn_consumer.py` (an external application client; it decides only its
own application meaning). One `BEGIN IMMEDIATE` SQLite transaction holds:
the provenance inbox row keyed `(history, incarnation, fn source identity,
application-id, operation-id)`; the unique `operations(application-id,
operation-id)` decision, compared on the SHA-256 of the exact authored
source bytes; at most one row of `transitions` (UNIQUE on the operation) and
its `app_state` change; the immutable signed outbox reply (source and both
signatures fixed before commit, so every retry posts the same bytes); and
the fn cursor to declare. Only after COMMIT does it call `consumer ack`.
Its fn facts all come from the image: `consumer poll/ack/position`,
`consumer-project` (ACL2's projection of the polled event: scope, sequence,
source identity, Message-ID, exact authored source, verdict principal),
`consumer-inspect` (the scanned position) and `hybrid-sign`/`hybrid-author`.
An empty page is acknowledged (it progresses); a page shorter than the
16-event scan bound ends the wake.

Limits stated: the consumer checks the historical verdict principal and its
own envelope; it does not re-verify the hybrid signatures itself (no
independent dregg verifier in this experiment). Exactly-once is of the local
transition only, under SQLite's atomic commit and the unique operation index.

## Step 4: fn's side, proved (PRF-116)

Book `books/consumer-owner-local-progress.lisp`, teeth in
`tests/acl2/consumer-owner-local-progress-tests.lisp`. Host lines:
`host/owner-host.lisp` `fn-owner-consumer-local-poll` calls `fn-col-poll`,
`fn-owner-consumer-local-ack` calls `fn-col-ack`; both from
`host/native/owner.lisp` `fnn-owner-consumer-local-serialized`.

- `fn-col-poll-scan-page-contract` (keystone): for any window, a `:scan`
  answer's continuation p satisfies position ≤ p ≤ max(position, frontier)
  and p ≤ position + budget; an empty page's scanned prefix has no matching
  event and, with budget > 0 and position < frontier, p > position (empty
  pages progress); a nonempty page's event is the one at p − 1, it matches,
  and nothing before it in the window matches. So a continuation never
  passes a matching event it did not return.
- `fn-col-poll-is-the-index-window-scan-unfolds`: the host-called poll is
  that selector over the carried index window, continuation written into the
  owner-pinned scope cursor. (Composed with the existing
  `fn-col-poll-index-window-is-committed-prefix`, the window is the committed
  Store event list under the maintained index relation.)
- `fn-col-poll-is-a-page-or-a-refusal`: a page is a read; the host-called
  poll answers `:poll` or `:refused`, never a write proposal.
- `fn-col-scope-entry-position-is-natural`: discharges the contract's
  `natp` premise at the host-called poll.
- `fn-col-ack-is-the-kernel-ack-unfolds`: the host-called ack is `fn-cp-ack`
  under the pinned local principal, query version 1, view 0.
- `fn-cp-ack-writes-only-a-forward-declaration-in-scope` (keystone): a write
  is exactly `(:ack cursor)`, in the recorded scope, not below the recorded
  position and not equal to it (strictly forward for a natural recorded
  position), within the committed frontier; an in-scope equal position
  within the frontier is the no-op.
- `fn-cp-ack-after-its-commit-is-a-no-op` (keystone): once the ack event is
  applied, the same ack is a no-op (an uncertain ack retried is harmless).

Teeth: RESULT-TEETH. Certification: RESULT-FARM.

Not proved: "position advances only by an ack *of a served page*". The
kernel accepts any in-scope forward cursor within the frontier; the local
owner (same UID) can declare a position it never polled. That is the
selected contract (an ack is a declaration), stated here rather than
claimed. The unavailable gap is unreachable in this profile (no native
content reclamation); the byte and cursor bounds are codec ceilings.

## Step 5: the §5.2 join

Traced on dev: no native code calls `fn-rcl-reclaimable` or
`fn-rcl-verdict`; the only native reclaim is `checkpoint pack-reclaim`

that nothing constructs from an E2 position. So the profiles are distinct
and there is no runtime disagreement today; the prose disagreement is
repaired: specs/storage.md's lifetimes row is now "Consumer positions",
which pin nothing, and its `held-consumer-cursor` text names the holder as
a reserved per-group-number slot. No integer cast connects them.

### PKT-165: a retaining consumer mode (decision packet for ember)

- Trace: an E2 position 100 and an article numbered 2 at journal position
  101 are different coordinates; `held-consumer-cursor` compares a per-group
  number.
- Constraint: D03 retention is an explicit obligation; the E2 contract
  says the cursor creates no pin and specifies an unavailable gap.
- Default (in force): no implicit pin; content reclaimed before a poll is
  an explicit unavailable gap.
- Alternative: a retaining consumer registration that takes a separately
  charged durable hold (admission charged at register, released only by
  unregister or explicit waiver), with a proved projection from a position
  to the set of held objects (event prefix → article identities after it in
  the query). Cost: a new Store event kind and charge, a projection proof,
  a reclaim holder built from that projection, and capacity accounting.
- Affected: store-reclaim holders, consumer-store-events, capacity.
- What continues without it: everything in this lane.
