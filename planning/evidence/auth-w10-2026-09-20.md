`fn principal set-password`, posting permission follows the credential's
flag, and STARTTLS runs end to end. Every line below is what the SERVER
said; nothing in the harness recomputes a digest or decides a code.

The one skip is `nntplib`, removed from the standard library in Python
3.13. **The independent-client half of this evidence is therefore NOT
supplied**: everything below is fn's own client talking to fn. The test is
written and skips loudly rather than being deleted; running it needs a
Python with `nntplib`, `slrn`, or `tools/inn_lab.py`. That is a real gap
and it is the first thing the next lane should close.

## Limits of this evidence

- These are runs, not proofs. That a WRONG password is refused is exhibited
  on one concrete pair of octets below; it is second-preimage resistance of
  the attached SHA-256 (A-CRYPTO, `specs/failures.md`) and is not a theorem.
- The TLS half is Python's `ssl` and is outside the model
  (`docs/trust-boundary.md`). What the transcript shows about TLS is that
  the handshake happened and the stream resumed, not that it is secure.
- The certificate is self-signed, generated into a temporary directory by
  the test, and is not committed. The client does not verify it.
- `books/served`, `books/owner` and `books/nntp-auth` are ADMITTED, not
  CERTIFIED, on this revision; see `planning/lanes/HANDOFF-w10-auth-served.md`.

## Cost of the ACL2 digest on the enrolment path

The brief asked for a measurement if the bridge were too slow for the
executable SHA-256. It is not. `fn principal set-password` starts one ACL2
session (`include-book "books/auth-secret"`, which pulls the attached
SHA-256 of `books/sha256.lisp`) and makes three calls in it: two
`fn-authsec-enrol` projections and one `fn-digest-tagged` for the local
principal id. Two full `set-password` runs, each its own session, complete
inside the 5.3 s of
`test_set_password_writes_a_verifier_and_no_secret`, and the session start
dominates: the digest itself is one SHA-256 over at most 272 octets, five
compression blocks. No Python `hashlib` is on this path and `bin/fn` no
longer imports the module.

## Reading the transcript

| line | what it establishes |
| --- | --- |
| `482` to `AUTHINFO PASS` before `USER` | RFC 4643 §2.3.2's out-of-sequence code, and the session is unchanged |
| `480` to `POST` and `GROUP` | RFC 4643 §2.2's gate; `fn-auth-restricted-keywordp` names the commands |
| `481` to the wrong secret, then `480` again | the failed PASS left the connection unauthenticated AND uncached: the next command is still gated |
| `281` then `211` | the credential the operator set opens the gate |
| `502` to a second `AUTHINFO USER` | RFC 4643 §2.3.1 note [2]; never 480, which §2.3.2 forbids here |
| `340` for alice, `440` for reader | posting follows the credential's flag, not the pinned configuration: both principals are on the same server, in the same configuration, and only one may post |
| reader's `CAPABILITIES` has no `POST` | the label is the conjunction of the configuration and the allowance, so it cannot promise what the 440 refuses |
| `580` with no certificate, and no `STARTTLS` label | RFC 4642 §2.2.2 |
| `483` before TLS under `protected_only` | RFC 4643 §2.3.2 |
| `382`, handshake, `101` again | the host upgraded on the `(:starttls)` effect and re-entered with `(:tls-established)`; the protocol state was reset (the cached name and the subject are dropped) |
| `AUTHINFO USER` label gone after the handshake is used | RFC 4643 §2.1: the arguments are what the server will accept NOW |
| no `STARTTLS` label inside TLS, and `502` to a second one | RFC 4642 §2.1, §2.2.2 |

The owner's stderr is empty in both runs: no connection was dropped and no
bridge call failed.
