   per-link header is not in `fn-cverb-capture-within-pack-octets`.

   no-op.

### 1. `store probe N` was superlinear for two reasons

All measurements are on hbox, using `store STORE probe N` over a scale-profile store
(max-transactions 1048576, 2 KiB articles), run under `systemd-run MemoryMax=40G`.
The script is `bounds-p5-2026-09-25/probe-measure.sh`. The profiles come from
sb-sprof in the developer core (`prof-reopen.lisp`, `prof-commit.lisp`).

| Stage | N | commit s | reopen s | exponent (commit / reopen) |
| --- | --- | --- | --- | --- |
| before (b9949fb6 image, ZFS) | 100, 250, 500 | 23.98, 55.98, 124.41 (wall; fsync) | 0.70, 5.71, 49.76 | ~2 CPU / **3.1** |
| replay carried (tmpfs) | 250, 500, 1000 | 5.24, 19.23, 77.44 | 0.26, 0.54, 1.51 | **2.0** / 1.5 |
| finish carried | 500 to 4500 | 2.59, 9.12, 31.83, 154.01 | 0.56, 1.59, 4.58, 21.40 | 1.9 / 1.6 |
| prepare and finish carried | 1000, 2000, 4500 | 0.82, 1.82, 5.14 | 1.81, 4.52, 16.66 | **1.2** / 1.6 |

- **Reopen, cause 1: whole-state recognition per replayed record (fixed on dev).**
  Of the N=500 reopen samples, 81% were in `fn-node-statep` under `fn-cpr-loop`.
  The loop ran `fn-cnode-statep` three times per event, and that includes the
  pairwise `fn-articles-freshp`, so the cost was O(N^3)
  (`probe-reopen-profile-n500-before.txt`). Dev's b5f7340d (owner-checkpoint)
  carries the invariant through the fold. The carrying theorems are
  `fn-cpr-apply-event-preserves-cnode-statep` and
  `fn-cpr-loop-preserves-cnode-statep`, with `mbe` on the executable path. This
  lane takes that change through the dev merge. For the pre-merge image, the three
  files books/config-physical-replay.lisp, books/store-checkpoint-open.lisp and
  tests/acl2/config-physical-replay-tests.lisp were copied byte-identical from
  dev (see §3).
- **Commit, cause 2: the offline commit walked the history twice per record
  (fixed here).** host/store-node-host.lisp `fn-store-sn-finish` called
  `fn-sn-finish`. That finds the completion record by `fn-sn-find-record`, and
  `fn-sf-record-pair` runs `fn-record-p` over every record. This was 89.7% of
  samples at N=1000 (`probe-commit-profile-n1000-before.txt`). Once the finish was
  carried, `fn-store-sn-prepare` → `fn-spc-prepare` → `fn-sf-candidatep` →
  `fn-sf-next-lower` accounted for 93.7% at N=2000, because it folds
  `fn-store-event-txid` over the history
  (`probe-commit-profile-n2000-finish-carried.txt`). The served owner had already
  been moved off both walks by the commit-path lanes (books/owner-commit-carried.lisp,
  books/owner-prepare-carried.lisp). The offline store bridge that `store post`,
  `probe` and every developer fixture use had not.
  - **Change:** `fn-store-sn-finish` calls `fn-ccar-sn-finish` and
    `fn-store-sn-prepare` calls `fn-pcar-spc-prepare`. Their equalities to the
    references hold with no hypothesis: `fn-ccar-sn-finish-is-sn-finish` and
    `fn-pcar-spc-prepare-is-spc-prepare`. No book changed, so no new theorem and no
    new teeth are needed. The host lines are host/store-node-host.lisp
    `fn-store-sn-prepare` (the `next` binding) and `fn-store-sn-finish` (the `next`
    binding). The file now includes both carried books; both were already in the
    default and DTN images.
  - An earlier attempt added an indexed lookup to books/store-node.lisp with its own
    keystone, and it certified. It was withdrawn before commit because it duplicated
    `fn-ccar-seek` and would have invalidated every certificate downstream of
    store-node.
- **Still superlinear (finding, not fixed): reopen ~ N^1.6.** At N=4500, 65% of
  reopen samples are in whole-state recognizers that run once per open:
  `fn-sn-statep` (25%) and `fn-node-statep` (40%, which includes `fn-cpo-open-observed`).
  Their `fn-articles-freshp` / `fn-memberships-conflictsp` / `fn-pair-memberp`
  is pairwise over the articles (`probe-reopen-profile-n4500-after.txt`). This
  runs once per process open, not per record, but every CLI command is a process
  that opens the Store. At 20,000 records it is minutes per command.
  One shared follow-up covers both quadratic predicates of `fn-node-statep`:
  `fn-articles-freshp` and `fn-node-articles-have-archive-bindingsp`. The
  checkpoint-cost lane found the same pair (planning/evidence/checkpoint-cost-2026-09-25.md).
  That lane also made `fn-article-listp`, `fn-no-duplicatesp` and `fn-subsetp`
  linear with equality theorems; the follow-up should reuse those. It is
  lane-sized, because the node recognizer's checks at open feed the recovery
  keystones.
- `probe` is a developer fixture builder, but it runs the production commit path
  (prepare, publish, finish). The fixture could not be built another way without
  the same cost, so the fix is in the production path.
