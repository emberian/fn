## 4. The profile: the served-path guard is no longer quadratic

`profile` sends the same shape of transfer at 64 KiB and at 256 KiB and
reports the ratio, because a loaded box moves both measurements together:

- 65,536 octets: **0.106 s**
- 262,144 octets: **0.146 s**
- ratio **1.38** for a 4x transfer (bar: below 8x)

The guard `fn-tcl-drive` names is checked once per socket chunk by its ACL2
executable counterpart. While it was `fn-tcl-sessionp`, that check walked
every octet staged so far, so a 4x transfer meant 4x the chunks *and* 4x the
walk -- about 16x the guard work. 1.38x is that cost gone; the residue below
4x is the per-run process startup, which both measurements pay once. The
`crash` scenario's 120,000-octet transfer, which w8 had to keep small for this
reason, now takes 24 acknowledged segments without difficulty.

The covered scope: this is one box, one loopback, one segment MRU (4096) and
one pair of sizes. It is a refutation of a quadratic guard, not a throughput
number, and the send direction is still quadratic (`specs/tcpcl.md` §6).

## 5. A finding: the model differential is only sound for a receive-only session

The first run of the lab -- the first run there has ever been -- failed
`replay` at

```
'(:OUTBOUND-SENT 0 "passive")' != '(:SEND :MSG-REJECT 3)'
```

`tcpcl replay` folds `fn-tcl-drive` over the trace and calls nothing else, so
it models a node that consumes octets and never originates a transfer. A node
that also sends reaches `fn-tcl-send` and `fn-tcl-pump` from the *host*, not
from the wire; the replay's state has no outbound transfer when the peer's
XFER_ACK arrives, and the machine is right to answer MSG_REJECT Unexpected
where the loop said `:outbound-sent`. `exchange`'s listener carries a reply
bundle, so its trace was never a valid subject for this differential.

The trace was wrong, not the machine. `scenario_replay` now drives its own
receive-only listener and the differential holds exactly (9 loop events, 9
model events, equal). Extending it to a sending node means putting the host's
aux calls into the trace; that is not done and is recorded open.

## 6. dtn7-rs interop: one bundle each way

dtn7-rs **0.21.0** at revision `4daf02d7ea927e9293753b2a5c4497457f6e5a40` --
the revision `tests/bp-dtn7/pin.json` names -- cloned to `/tank/fn/dtn7/repo`
on hbox and built with `cargo build --release --locked` under `swarm-build`
(cargo 1.98.0-nightly). Its `tcp` convergence layer is RFC 9174:
`core/dtn7/src/cla/tcp/proto.rs` carries the Table 2 message types and the
CAN_TLS contact-header flag.

`python3 tests/bp-dtn7/run_fn_tcpcl_interop.py --image build/fn-host-dtn
--dtn7-repo /tank/fn/dtn7/repo`, `ok: True`.

**Leg 1, dtn7 to fn.** `dtnsend -r dtn://fn-b/incoming` gave
`Bundle-Id: dtn://dtn7x/-843243606819-0`, `Result: Sent 109 bytes`.
dtn7 dialled fn's listener; fn's own event digests, computed in ACL2 by
`fn-tcl-host-event-digests`:

```
passive event (:SEND :CONTACT 6)
passive event (:SEND :SESS-INIT 36)
passive event (:SESSION-UP 10 64000 64000 NIL)
passive event (:SEND :XFER-ACK 18)
passive event (:BUNDLE-RECEIVED 1 126)
passive event (:SEND :SESS-TERM 3)
passive event (:PEER-TERMINATING 1)
passive event (:CLOSE)
```

fn negotiated a 64,000-octet segment and transfer MTU with TLS false,
acknowledged the transfer, and staged **126 octets** as `passive-1.bundle`. Exit 0.

**Leg 2, fn to dtn7**, returning the same octets:

```
active aux (:SEND :CONTACT 6)
active event (:SEND :SESS-INIT 36)
active event (:SESSION-UP 10 64000 64000 NIL)
active aux (:SEND :XFER-SEGMENT 148)
active event (:OUTBOUND-SENT 0 "active")
active aux (:SEND :SESS-TERM 3)
active event (:PEER-TERMINATING 0)
active event (:CLOSE)
```

dtn7's side of leg 2, verbatim:

```
Bundle dtn://dtn7x/-843243606819-0 already in store, updating it!
Dispatching bundle: dtn://dtn7x/-843243606819-0
Bundle contains an hop count block: dtn://dtn7x/-843243606819-0 32 2
Previous Node Block was updated: dtn://dtn7x/ dtn://dtn7x/
Transmission time: 29.337us for 1 bundles in 126 bytes to 127.0.0.1:54298
Session terminated for dtn://fn-a/ (127.0.0.1:54298)
```

So dtn7 completed the contact exchange and SESS_INIT with fn, accepted fn's
XFER_SEGMENT, decoded the 126 octets as a BPv7 bundle, recognised it as its
own, and dispatched it. fn's `:INBOUND-REFUSED 1 6` on that last line is
correct and not a failure: dtn7's epidemic router immediately tried to forward
the bundle back, and fn had already sent SESS_TERM, so the machine refused
with Table 6 reason 6, Session Terminating.

**What this does and does not show.** It shows two independent RFC 9174
implementations holding a session and moving a bundle in each direction, with
fn's every protocol value computed in ACL2. It does **not** show fn
originating a bundle: nothing in this tree encodes BPv7
(`specs/bp-design.md` §1.4 is a design), so **dtn7 authored the bundle in both
directions** and fn carried it back as a convergence-layer peer. A bundle fn
composed would fail dtn7's parser today. That is the honest boundary of this
interop and the reason the harness is written the way it is.
