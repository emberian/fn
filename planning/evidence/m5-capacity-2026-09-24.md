# M5 capacity: the transaction budget is ACL2's (2026-09-24)

Lane `m5-capacity`, branch `lane/m5-capacity` from dev `87846f9e`. Source
commit `e45a5ab3`; the test and documentation follow-up is on the same branch.

## Where the 128 came from, and who decided

- **The number.** `operator init` writes the store's metadata file
  (`config.json`, an FNSM frame) from `fn-bs-config-for-profile :development`
  (`books/byte-store-frame.lisp`): `*fn-bs-meta-development-values*`, whose
  fifth field is 128. `*fn-bs-meta-scale-values*` holds 4096. The native
  operator could not ask for the second one (`host/native/io.lisp`
  `fnn-initialize` took a profile argument that no caller passed).
  `tools/run_store.py:34` `MAX_TRANSACTION_COUNT = 128` is the Python host's
  copy of the same value.
- **The decision (before).** `host/native/owner.lisp` `fnn-owner-attempt`
  compared the host counter `fnn-owner-service-records` with
  `fnn-config-max-transactions` (the host reading field 4 of the profile) and
  returned `:unaffordable`; then it asked ACL2's
  `fn-store-publication-admissibility`, feeding it the same host counter. The
  four non-article commit paths (retention, identity, consumer, topic) had the
  same host comparison. The ACL2 prepare the owner calls did not know the
  budget at all.

## Theorems (statements)

Over the function the host calls (`fn-sbud-prepare`, from `fn-owner-prepare`):

- `fn-sbud-prepare-refuses-at-budget`: if `budget <= (fn-sbud-used (fn-sbud-oc-store oc))`
  then `(fn-sbud-prepare oc record budget) = oc`. Nothing is staged and every
  component of the configured owner is unchanged.
- `fn-sbud-prepare-below-budget-is-the-owner-prepare`: if `budget` is a natural
  and the count is below it, `(fn-sbud-prepare oc record budget) = (fn-opc-prepare oc record)`,
  the prepare whose correspondence to the owner event is
  `fn-opc-prepare-equals-owner-event-under-relation`. Whether that prepare
  then accepts the POST is its own business (duplicates, groups, clock). The
  budget does not decide it.
- `fn-sbud-refusal-kind-at-budget-is-unaffordable`: under the same hypothesis
  as the first, the word is `:unaffordable`.

Over the budget and the count (`books/store-budget.lisp`):

- `fn-sbud-budget-is-the-profile-admissibility`: `(fn-sbud-admitp (fn-sbud-budget profile kind) used)`
  holds iff `(fn-bs-publication-admissiblep profile used (fn-store-publication-ceiling kind))`.
  The carried budget is exactly the admissibility check the host used to
  call. The difference is that the count is now ACL2's.
- `fn-sbud-used-names-the-transaction-namespace`: under `fn-sf-statep` of the
  Store's file kernel, the committed records' sequence numbers are exactly
  `0 .. used-1`. That is the `%020d.txn` namespace the host enumerates at
  open, so ACL2's count equals the store's file count.
- `fn-sbud-named-profile-article-budgets` (ground facts): 128 and 4096.

**The budget cannot change while the store exists, and why.** The profile
bounds the work of opening the store before any configuration record is
replayed. `fnn-transaction-files` enumerates the directory up to the budget,
and the replay input is bounded by `max_recovery_record_bytes`. A
configuration record is inside that bounded input, so it cannot raise the
bound that admits it. `fn-ocl-publish` therefore does not carry the budget.
The owner holds the profile in one state global, set only by
`fn-owner-install-profile` after recovery. This is a code fact, not a
theorem: no logic-mode transition takes or returns the profile.

## Teeth

- `tests/acl2/owner-store-budget-tests.lisp`: a host-shaped configured owner
  reached through the owner's own events (one committed record, a second
  reservation, so used = 1). Budget 2 (used = budget-1) stages the record and
  equals `fn-opc-prepare`, which is not the identity. Budgets 1 (= used) and 0
  (used = budget+1) return the owner unchanged with word `:unaffordable`.
  Budget 2 gives `:refused` from the refusal-kind function, which is how the
  word separates. One `must-fail` per hypothesis, each at these constants:
  budget 2 for the refusal, 3/2 for `natp`, 1 for "below", 2 for the word.
- `tests/acl2/store-budget-tests.lisp`: the development profile gives
  127 `:admissible`, 128 and 129 `:unaffordable`. The scale profile gives 128
  and 4095 `:admissible`, 4096 `:unaffordable`. A non-profile gives budget 0.
  Headroom of an initial store is `(0 128 0 10)`. A misnumbered kernel
  refutes the namespace theorem without `fn-sf-statep`, and a sequence-1
  record refutes the candidate lemma without `fn-sf-candidatep`.

## The pessimistic numbers, with their scope

**Bytes.** The per-record profile ceiling is 196,608 octets. An article
record is at most `*fn-record-max-octets*` = 65,538.

| profile | transactions | aggregate replay bound | article records at most |
| --- | --- | --- | --- |
| development | 128 | 128 × 196,608 = 25,165,824 octets (24 MiB) | 128 × 65,538 = 8,388,864 octets (8 MiB) |
| scale | 4096 | 4096 × 196,608 = 805,306,368 octets (768 MiB) | 4096 × 65,538 = 268,443,648 octets (256 MiB) |

**Work the budget adds per POST:** one `len` walk of the committed record
list, Θ(N) with N ≤ budget, so at most 128 or 4096 cons steps (exponent 1).
The kernel's own `fn-sf-candidatep` already does the same walk plus
`fn-sf-next-lower`, also Θ(N). A POST refused at the budget still costs one
allocation-frontier reservation, with its durable replace and fsync, and the
reservation's consumption. The host reserves before it prepares, and the
prepare now owns the refusal. At capacity, every refused POST is therefore
one durable frontier write. That is the price of having one owner, and it is
bounded by the uint32 frontier.

**Work the larger budget admits, measured elsewhere:**

- Reopen, on the Python bridge (`planning/scale-profile.md`): 2.7 s at N=128,
  12.7 s at N=256, and approaching Θ(N³). Extrapolating with exponent 3 to
  N=4096 gives about 12.7 × 16³ ≈ 52,000 s (14 h). That figure is an
  extrapolation on a bridge the native image does not use, not a
  measurement.
- Native (`planning/evidence/t17-msgid-index-2026-09-24.md`): a 5.0 ms median
  served command at N=120, still super-linear (×10.5 from N=16 to N=120).
  Owner RSS was 0.40, 1.02 and 1.95 GB at N=16, 50 and 120. Extrapolated
  linearly (about 15 MB per article), that is about 15 GB at N=1000 and about
  61 GB at N=4096. Also an extrapolation, from three points.
- So `--profile scale` makes the T17 N=1000 run **admissible**. Whether hbox
  completes it is the measurement still to make. The 4096 budget is a
  ceiling, not a supported capacity (as `scale-profile.md` already says).

## The deployed node

- `/tank/fn/node` was not touched, read or listed by this lane.
- By the brief and the node record, the store was made by `operator init`
  at `da5fd8cb` with an fn.toml that names no profile, and the operator had
  no `--profile` then. Its budget is therefore the **development profile:
  128 transactions**, 7 used today.
- **Coordinator check:** `sha256sum` of the node store's `config.json`
  should equal `dcbd90d3…` above. Note that `da5fd8cb`'s frame format
  (`fn-store-experiment-7`) must be the one this image writes.
- **Changing it** is not a configuration record (see above). Two routes:
  1. A new store from `init --profile scale` with the articles migrated.
     No migration exists, and re-posting would change local article numbers
     and injection.
  2. An offline in-place profile upgrade: owner stopped, `config.json`
     replaced atomically by the scale frame, then restart. Development to
     scale is monotone (same format, same per-record ceiling, larger count
     and aggregate), so every existing store stays admissible. But there is
     no verb for it and no theorem. It needs an ACL2 predicate `upgrade
     admissible (old new)` (same format and frontier format, no bound
     smaller), a host step through the same publish path `init` uses, and a
     crash cut at the replace. That is the next packet if the node is to
     pass 128.
- At the current rate the node has 121 transactions left. Each article,
  retention, keyring, consumer or topic event takes one.

## Findings and what is open

1. **Running owner's headroom.** `operator status` opens the store, so it
   refuses while the owner holds it. On the live node, the only headroom
   signal is still the `441 … no capacity` line itself. `fn-owner-headroom`
   exists with no caller, and adding it needs an ACL2 FNCT control request
   and reply. Open.
2. **Host sequence twin.** `host/native/owner.lisp` `fnn-publish` still names
   the transaction file from the host counter `fnn-owner-service-records`.
   ACL2 would refuse a mismatch (`fn-sf-candidatep` requires sequence =
   `fn-sbud-used`), so it is checked, but it is still a second count. Asking
   ACL2 for the next sequence would remove the counter. Not done here.
3. **The Python owner** (`tools/run_owner.py:1302`) keeps its own count
   comparison ahead of ACL2's. It now installs the profile, so both agree.
   Its removal belongs to the Python host's retirement.
4. **The `--affected-by` filter** (certification, above).
5. **`make check`** fails in this worktree only on the generated ledger
   being stale (`planning/ledger.*`, which lanes do not edit). Its warnings
   on the new books were fixed: the must-fails are at constants and the
   candidate lemma is `:rule-classes nil`.
