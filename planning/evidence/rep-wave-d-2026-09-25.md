### 1.2 What the numbers say

- **Live heap is the retained payload list, exactly as the census said.**
  270 MB is the image. At N = 1,000: +36 KB per 2 KiB article and +528 KB
  per 32 KiB article, against 16 × 2,048 + 3.7 KB = 36.5 KB and
  16 × 32,768 + 3.7 KB = 528 KB from the definitions (sixteen bytes per
  retained octet: one cons per octet, held once). The "well under a
  gigabyte at N = 10,000, 32 KiB" of the brief needs the retained copy
  to be one byte per octet: 320 MB of payload plus the image.
- **A 32 KiB POST allocates 20.8 MB** (635 bytes consed per payload
  octet) and **an ARTICLE 5.8 MB** (177 per octet). The POST's allocation
  is the wire machine consuming the body a byte at a time through list
  walks (59% of its CPU in the rep-wave-c 32 KiB profile:
  `fn-scar-feed-counted` → `fn-wire-feed-byte`, `fn-ag-cdr`,
  `fn-wire-ag-cdr`, a new wire state per byte), the record recognizer over
  the payload list (`fn-record-payloadp` 10%), then the record's own list
  (`fn-octets-list`, once). The ARTICLE's is the served response built as
  an octet list (dot-stuffing and the reply lines over the archive body).
  "A POST and an ARTICLE cost what the bytes cost" is therefore two
  boundaries away, §3.
- **On ZFS the POST is the durable publish**: 250 to 400 ms median with a
  tail to 1.3 s (2 KiB) and 3 s (32 KiB), against 1.5 to 19 ms on tmpfs in
  the rep-wave-c rounds. This is the live node's file system; the
  representation work moves the CPU term, not this one. Its own
  investigation (fsync placement, ZFS `sync`, the transaction directory)
  is not this lane's.
- **The checkpoint reopen is the worst path at 32 KiB**: 18.3 s against
  10.7 s for the journal replay, with 7.4 GB consed, 4.8 GB resident and
  6.9 GB peak, and a live heap after it of 1.39 GB against 0.80 GB after
  the load and 0.83 GB after the journal reopen: the checkpoint decode
  holds a second copy of the history's payloads at the moment it hands the
  owner its state (an octet-list decode of the checkpoint's payload
  bytes beside the record it builds). At N = 10,000 this is the path that
  decides whether the node reopens at all inside the 40G envelope; the
  N = 10,000 rows carry the answer.
- Greeting, STAT and OVER do not move with N or L at these sizes (0.09 to
  1.8 ms); the Message-ID index and the group index are not on this
  lane's list.

## 2. The representation chosen, against the ACL2 and SBCL constraints

**The candidates.** (a) An ACL2 string per payload: 4 bytes per character
on SBCL (`simple-character-string`; a base string cannot hold octets
above 127), a fourth of the list, and still a value of the logical record,
so every recognizer and codec changes with it. (b) A byte array per
payload as an ordinary value: ACL2 8.7 has no logical array type outside
a stobj. (c) The owner as one abstract stobj whose logical view is the
owner value: the design's boundary 10; every host entry becomes an export
whose `:exec` is a twin of the whole owner chain, or a run of the logical
chain on a handle-bearing owner, which needs a commutation theorem per
function of the chain. Neither is a lane, nor a wave. (d) **A payload
arena: one abstract stobj holding every retained payload back to back in
one `(unsigned-byte 8)` array with an offset and a size per handle, the
logical view being the list of payloads oldest first, and the record's
payload field becoming a handle, a natural, in the logical model.** One
byte per octet, sixteen per handle; the array is one SBCL object of the
generation the store lives in, so a full collection copies it once and
never walks it; a handle is a position, never reused. This is (d), the
design the census proposed, and it is a model change: the record's
`fn-record-payloadp` becomes `natp`, and every function that reads a
retained payload's bytes takes the arena as a formal.

**Why the model change cannot be avoided.** Any design in which the
runtime holds bytes where the model holds a cons list is, in ACL2 8.7, a
stobj with the list as its logical view. The list can then be read only
by functions that take the stobj as a formal, reached from the host entry
through every function on the way down; a value-based function that
receives the payload receives the list. So either the *whole* chain from
each host entry to each byte consumer takes the stobj (the owner as a
stobj, (c)), or the record holds a *handle* and only the byte consumers
take the arena (d). (d) touches fewer functions by two orders of
magnitude, §3 counts them.

**What the arena guarantees, proved here** (§4): a sealed handle denotes
the same octets after any later seal, a seal's handle is the old count
and is never reused, nothing removes a payload, and the relation with a
store history (the arena is the history's payloads oldest first) is the
same after a commit's seal and after an open's seals from the empty
arena. Reclamation (D13) therefore cannot dangle by construction: a
tombstone is a new seal, the reclaimed handle stays valid until the next
open rebuilds the arena from the retained records, and the space is
reclaimed at open, never in place. That is written into
`build/lanes/rep-wave-d/LANEDUMP.md` for lane reclaim-lifecycle as an
interface obligation; the theorem form is `fn-arena-seals-keep-sealed`.

**The pinned reader.** A reader's view (`fn-own-conn-archive`,
books/owner-served-carried.lisp) pins articles whose bodies are, today,
the shared list; with handles, a pinned view holds handles, and
`fn-arena-seals-keep-sealed` is the theorem that its handles read the
same octets after every later commit: there is no in-place write export,
and the only transitions of a live arena are seals.

never data (D27). A 1 GiB article costs 1 GiB in the arena and 1 GiB in
the store file, never sixteen.

identity, refused by §7's last property); a profile ceiling on N × L

## 4. What landed: the arena (`books/payload-arena.lisp`, PRF-118)

`fn-arena` is a `defabsstobj`: recognizer `fn-arn-payload-listp` (a true
list of octet lists), creator nil, executable a concrete stobj with a
resizable `(unsigned-byte 8)` array, a resizable offset array and a
resizable size array (`(integer 0 *)` cells), a count and a fill.
Exports: `fn-arena-count` (`len`), `fn-arena-payload-len h` (`len` of
`nth`), `fn-arena-get h i` (`nth` of `nth`), `fn-arena-payload h` (`nth`,
the list consed once: the escape hatch for a caller not yet moved),
`fn-arena-seal-list xs` (`append` of one payload), **`fn-arena-seal-buffer
fn-octets`** (`append` of the octet buffer's value: the export the served
POST will call at the finish, an abstract stobj export taking another
stobj, which ACL2 8.7 admits) and `fn-arena-clear`. The abstraction
relation `fn-arena$corr`: the concrete object is well formed, the fill and
the count are within their arrays, every handle's range lies below the
fill (`fn-arn-rangesp`), and the slices in handle order are the logical
list (`fn-arn-slices`).

Every executable function is guard-verified (asserted in the test book).
`nth` and `update-nth` stay closed from the relation on; the abstraction
`fn-arn-slices` and the ranges are lemmas about lists. Two lemma shapes
mattered: a fact about a state after a write must be stated with the
*outer* state's count and fill as free variables (`fn-arn-seal-entry-reads`),
because the write's field equalities rewrite the inner ones away before a
rule stated over them can match; and a sum must be stated in the order the
prover normalises it (`fn-arn-write-appends-2`), since matching is
syntactic.

**The hypotheses' teeth** (`tests/acl2/payload-arena-tests.lisp`): the
exec path on a live local arena and a live local buffer (three seals, the
reads, a clear; then 3,000 octets three times through the byte array's
doubling and the handle arrays' growth, the middle handle unchanged by the
seal after it); the obligations on a ground arena `((1 2 3 4 5 0 0 0)
(0 3) (3 2) 2 5)` against `((1 2 3) (4 5))` (get: without the
correspondence, without the octet bound, without the handle bound, without
`natp i`, each an asserted witness and a `must-fail`; get's `natp h` has no
falsifying witness, a handle that is not a natural reads as handle 0 on
both sides, so the weakened theorem is proved, `pat-w-get-needs-no-natp-h`;
seal-list: the append, and without octets the array cannot hold 300); the
keystones (`natp h`: on the empty arena a negative handle reads the new
payload, `nth` of a negative being `car`, so the hypothesis is not
redundant and the witness is `-1`; the bound: the handle at the count is
the new payload); the store relation on a three-record history (a commit
keeps it, an open from the empty arena establishes it, an arena with the
payloads in the wrong order does not satisfy it, an arena missing a payload
does not survive a commit).

**Not proved, and unchanged:** the host discipline that the buffer holds the
payload from the fill to the seal (A-HOST, as for boundary 6). **Not
landed:** the host join. `fn-arena-seal-buffer` has no caller yet: the
call belongs to the finish after the model change of §3 (i), where a
handle can be stored; sealing today would add one byte per octet beside
the sixteen and remove nothing, so no measured "after" is claimed for it
(§5).

## 5. Re-measurement

No behaviour changed in this lane's image, so the "after" table is the
"before" table; §1 is the baseline every later number is matched against,
and this record does not quote a representation improvement. The counts
the arena's asymptotics depend on, from its definitions: a seal from the
buffer copies L octets once (`fn-arn-write-buffer`, one array write per
octet) and writes two handle cells; a read by handle copies nothing; the
arrays double, so N seals resize O(log(N·L)) times.
