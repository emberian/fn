# Qualification of candidate dfa810fc, 2026-09-26

**Verdict: not deployable as cut, because of PKT-481.** A reader's `ARTICLE`
for a stored article of 2 MiB or more kills the owner. It exits 4 with
`owner core/store fault; process stopped: ACL2 error in fn-owner-chunk:
Control stack exhausted`. Every later read of that article does the same.
- public-exposure (34c2ba45) introduced it. b6759850 serves the same 2 MiB
  and 3 MiB articles byte-identically.
- The live node on bbf52159 predates the defect and is unaffected.
- The coordinator ruled that dfa810fc is not brought to ember. The fix is lane
  exposure-reply-size's, and the repaired cut 69046a76 is qualified next.
- The evidence below for bytes that the fix does not change carries over to
  it. The last section says which evidence carries.

#### The four rollback consequences

`rollback3.py` wrote `logs/rollback3.log` (`1e1242fe…`). Every case ran on
copies. The bbf52159 lines are the real image's.

**(i) Accounts and login bindings (PKT-440, PKT-391's class).**

The docs say: "Once an account code is redeemed on a release with accounts,
releases before it cannot open the store; roll back only from the
pre-upgrade snapshot (PKT-440: an older image refuses configuration delta
kinds 15 and 16 at decode…)". They also say: "The same rule covers the
login-binding rows (delta code 17 …): a store that ever published a binding
is refused by releases before it".
- **Invite only.** Issuing a code offline, with no redeem, already bars the
  store: bbf52159 `status` exits 4. Delta 15 alone is enough, and the docs
  sentence names only the redeem.
- **Redeem on the live copy.** On a copy of the live store:
  - cleartext `XREDEEM` gets 483;
  - over STARTTLS, `XREDEEM` gets 381 and `XREDEEM PASS` gets 281;
  - `friend1` logs in (281) and posts (240);
  - the same code for a second login is answered 381;
  - `account list` shows `redeemed friend1 ce64…` and no code.
- **bbf52159 on the redeemed store.** `status` and `recover` both exit 4 with
  `fault operator status ACL2 refused configuration namespace observation`.
  The refusal is generic and does not name accounts.
- **The snapshot restores.** bbf52159's `recover` and `status` return rc 0 on
  the pre-upgrade snapshot, and its owner serves.
- **A binding applied live.** `principal bind qual P` against the running
  dfa810fc owner answers `accepted operator principal bind applied`. bbf52159
  then exits 4 on `status` and on `recover`.
- **The control case.** The same copy with a dfa810fc owner run and no bind is
  opened by bbf52159 (rc 0). The live `auth.toml` holds no `signing` field,
  so a plain upgrade does not publish code 17.

**(ii) The pull journal (PKT-432).**

The docs say: "A release from before 2026-09-26 refuses a pull journal that
holds the `:pull-unavailable` record … so rolling a node back to such a
release means deleting its `pull/` journals first; the cursor then restarts
one day back".
- The store was made by the bbf52159 image, including its `peer add` and
  `peer pull S 2`.
- The dfa810fc owner pulled from a scripted peer that lists a ghost ID and
  answers it 430. Two rounds logged `cursor=held unavailable=1`, giving
  `pull/S.fnfd` of 369 octets.
- The offline `status` and `recover` of both bbf52159 and b6759850 return rc 0.
  Their **owners exit 4** with `owner core/store fault; process stopped:
  invalid complete FNPL evidence: …/pull/S.fnfd`.
- After `pull/` is deleted, bbf52159's owner starts and asks `NEWNEWS fn.*
  20260925 130141 GMT` at 20260926 130144, which is one day back.
- The refusal is a fault at owner start, not an offline refusal. An operator
  who checks with `status` after a rollback sees rc 0 and then a node that
  will not start.

**(iii) Pre-C1 (PKT-444).**

The docs say: "refused by name by every open (`recover`, `run`, `health`,
`inspect`, `checkpoint`): `pre-C1 control record (txid N, <message-id>): run
store repair-control`, exit 1. … `fn store ROOT repair-control` exists but
refuses (`repair semantics undecided (PKT-444)`)".
- On a copy of the committed witness `tests/fixtures/pre-c1-control-store`
  (control-across-peers-2's), each of `recover`, `inspect`, `checkpoint`,
  `operator health` and `operator run` exits 1 with `pre-C1 control record
  (txid 2, <prec1-cancel@example.invalid>): run store repair-control`.
- `repair-control` exits 1 with `store: repair semantics undecided
  (PKT-444)`.
- The `ordinary` twin recovers, and so does `tests.test_native_pre_c1_open`
  (3/3 on prod and dev).
- The deployed bbf52159 also refuses the witness, generically (`ACL2 replay
  rejected …`, exit 4).
- The live store is not affected: dfa810fc opens its copy with rc 0.

**(iv) The checkpoint file (not in the docs).**
- bbf52159 and b6759850 both refuse a checkpoint that dfa810fc wrote. Their
  `status` and `recover` say `open=full-replay reason=checkpoint-open-refused`
  and return rc 0 (`logs/checkpoint-rollback.log` `e568bd8a…`).
- dfa810fc likewise refuses the 20,000 fixture's checkpoint, written by
  8cc3cd4c, and replays in full: 524 s to `LISTENING`.
- Nothing is lost. The cost of a rollback is a full-replay open.
- docs/operator.md should say so beside the pull journals, for the fix lane or
  the docs.

## PKT-481: what this qualification found

**(c) The defect: the owner is killed by a large served reply.**
- **Trace.** On a profile with `max-article-octets 4194304`, POSTs of 262,144
  and 524,288 octets and of 1 MiB are served back identically. At 2 MiB and 3
  MiB, `POST` answers 240 and `ARTICLE` gets no reply. The owner stops with
  `ACL2 error in fn-owner-chunk: Control stack exhausted … fault operator run`
  and exits 4.
  - The harness is `bigart.py`, with `logs/bigart.log` `4e6fdce9…`.
  - b6759850 serves 2 MiB and 3 MiB identically.
- **Bisection:** `bigart.py` at 2 MiB over images already on hbox
  (`logs/bigart2.log` `2e36d6b6…` and `logs/bigart3.log` `a3594f46…`):
  - **OK:** rep-wave-d-3, key-replay-fixture r2, rollback-history green2,
    sanding r3 and pack-chain-join.
  - **FAULT:** public-exposure r4, and every first-parent throughput-gate
    image from f370581b through 0f2af947, a3d0d683, eea8c446, 75f04d80,
    deb68237, fac2c417, e3e081ae, 12f447e8 and 51b4ff48 to a80534ed and
    dfa810fc.
  - So it came in with **public-exposure (34c2ba45)**.
- **Suspected cause (not proven here).** The per-step observation
  `fn-owner-exposure-observe` (host/owner-host.lisp) builds the step's whole
  reply as one octet list with `fn-served-reply-octets`
  (books/served.lisp:1124). That is a non-tail `fn-ag-append` over octet
  lists, whose recursion depth grows with the reply size. It is also an
  octet-list materialization on the served path (D27).
- **Reach:**
  - **Any single served reply** over about 2 MiB, not only ARTICLE.
  - `OVER 1-20000` on the 20,000-record fixture (1,706,674 octets) survived,
    so an OVER over roughly 25,000 articles would cross it (`bigreply.py`,
    `logs/bigreply.log` `ca008886…`).
  - The same run measured OVER at about 10 ms per line: 197 s for 20,000
    lines. That is a cost finding for PKT-321's class.
  - The live node's scale profile caps articles at 32,768 octets, so ARTICLE
    cannot reach it there. OVER could, once a group passes about 25,000
    articles.
- **Fix:** lane exposure-reply-size, which reuses `bigart.py` and
  `bigreply.py`.
