# P8: an independent verifier for `HDR :fn-verified`

P8's last clause asks that the verdict be checkable without trusting fn.
`tools/fn_verify.py` fetches an article and the node's `HDR :fn-verified`
line and recomputes the signature half of the verdict. Its carrier decoder,
source projection and preimage are written from the specification. It uses
libraries the node does not use for these primitives, and it compares the
result with the node's line. It imports nothing from fn and runs no fn
binary. Under AGENTS.md this is the independent witness. It is not a twin:
the server's decision stays in ACL2, and this check runs on the client.

## What is verified, and by what

| component | node's implementation | verifier's implementation | independent of the node? |
| --- | --- | --- | --- |
| Ed25519 (RFC 8032, pure) | libsodium `crypto_sign_verify_detached` | pyca/cryptography 50.0.1 `Ed25519PublicKey.verify` (bundled OpenSSL 4.0.2) | yes: a different library |
| Ed25519, second opinion | | PyNaCl 1.6.2 (libsodium) | no: the same library as the node; it only has to agree |
| ML-DSA-65 (FIPS 204, pure, empty context) | OpenSSL 3.5.8 `EVP_PKEY_verify_message_init` with NULL parameters | dilithium-py 1.4.0 `ML_DSA_65.verify(pk, m, sig, ctx=b"")`, pure Python | yes: shares no code with OpenSSL |
| ML-DSA-65, second opinion | | pyca/cryptography 50.0.1 `MLDSA65PublicKey.verify` (OpenSSL 4.0.2) | only partly: it is OpenSSL, a later version |
| carrier: base64, nine canonical CBOR items, widths | ACL2 `fn-hc-field-decode` | `decode_carrier`, which refuses non-minimal heads and trailing octets | yes |
| authored source: drop the physical lines of Path, Xref, Injection-Date, Injection-Info and FN-Authorship, keep the rest in order, then CRLF and the body | ACL2 `fn-hc-authored-source` | `independent_check` | yes |
| preimage: CBOR bstr(`fn-authored-source-hybrid-v1`) ‖ 1 ‖ 1 ‖ principal ‖ 1 ‖ Ed key ‖ 2 ‖ ML key ‖ u16be(len source) ‖ source | ACL2 `fn-hsig-signed-preimage` | restated | yes |
| binding to the request: the signed source's Message-ID is the one asked for | the Store's index | checked | yes |
| binding to a principal: the carrier's keys are the keys pinned for its principal | the node's kind-3 enrollment | the verifier's own keyring file | yes. The pin comes from the author, not the node |

Both components must verify, and every implementation consulted must agree.
If they disagree, the result is exit 3 and never a verdict.

## What it cannot check

- **The node's keyring.** The node publishes none over NNTP.
  `hybrid-key-history` prints status and principal but no key payloads, and
  the HDR line names the principal and generation but no keys. The verifier
  therefore takes a keyring file (`fn-verify-keyring-v1`) whose keys come
  from the author. For an unpinned principal the result is exit 3. The
  verifier cannot confirm that the node's generation `1` held these keys. It
  confirms only that the carried keys are the pinned ones.
- **Enrollment and policy.** The verifier does not check whether the node
  *should* have accepted: enrollment was current, the principal was not
  revoked, or the group policy allowed it. Those checks are local node
  policy, and this check covers signatures only.
- **The primitives themselves.** dilithium-py and pyca/cryptography are
  trusted under A-CRYPTO in the same way the node's libraries are. The
  claim is independence of implementation, not proof. Nothing here proves
  that a real signature is unforgeable.

## Test results

`tests/test_fn_verify.py` has two layers:

- `FakeNodeVerifyTests` (6 cases) always runs when the libraries are
  installed. Its carriers are signed in the test over the verifier's own
  preimage, so it tests the comparison logic only. Results: valid → 0.
  Tampered body with the node saying `unverified signature` → 1. Unsigned
  with `absent` → 1. A forged `verified` over tampered bytes, a forged
  `absent`, a wrong principal, another article's signed source served under
  this Message-ID, and the right principal with keys that were not pinned
  → 2. An unpinned principal, 430, no HDR, a garbled HDR, and a refused
  connection → 3. A usage error → 64.

  launcher `e4eeefd2…`, core `793b937d6b0ac6b0…`, `image.sha256`

## Findings for the specification

1. **No keyring publication.** Nothing in specs/ says how or where a node
   publishes the keys behind a `verified` line, and the node publishes
   none. For independence this is the right default, because keys fetched
   from the node repeat the node's claim. The spec should say it: the pin
   comes from the author, and the HDR generation is the node's local
   coordinate, not something a reader can resolve.
2. **The preimage bytes are only in the books.** specs/identity.md calls
   the preimage a "length-delimited exact authored-source subject" but does
   not give its layout. The layout is `fn-hsig-subject-body` plus
   `fn-digest-tagged-preimage`, with a u16 big-endian source length. The
   projection is `fn-hc-authored-source`: whole physical lines, so folding
   is kept byte-exact. ML-DSA-65 is used in pure mode with an empty context
   string (NULL OpenSSL parameters). The verifier had to read the books to
   get all three, and a verifier written from the prose alone would
   diverge. The spec should state these bytes.
3. **`unverified` is not reachable for a served article.** A served POST
   (and transit) with an invalid carrier is refused with 441 or 439, not
   stored with an `unverified` verdict. On a real node, "both say not
   verified" therefore means an unsigned article (`absent no-field`), and
   a tampered POST leaves nothing to check (exit 3). The `unverified`
   example in specs/substrate-transport.md §5 is reachable only for
   records written by other paths.
4. **The HDR line binds a Message-ID, not bytes.** The line carries no
   content identity. A node could therefore serve another article under
   the Message-ID and the line would still read `verified`. The verifier
   closes this by requiring the signed source's Message-ID to equal the
   request. The fake-node case `<swapped@…>` shows the check has teeth.

## What this does not establish

- A frozen developer image in a scratch Store, not the deployed node.
- The primitives are trusted (A-CRYPTO). The independence is of
  implementation, and for Ed25519 it is between OpenSSL and libsodium.
