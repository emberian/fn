## The ACL2 differential

`tests/test_native_crash_model.py` ran against this developer image with the
bridge on `acl2-literal-4g` over the gate's certified books: **6 of 6 OK**
([`crash-model.log`](campaign-6c0626c5/crash-model.log)).
`test_all_native_post_process_death_cuts` takes all 18 `POST_CUTS` as
subtests. At each, it SIGKILLs a `store post` at the cut, imports the store
into ACL2, and checks the following: the observed scan equals the scan of
`fn-bs-crash` of the program state at that cut, the open states are equal,
the served image and all three directories agree, and the transaction names
are equal. It passes at every cut, the five new ones included. Each new cut
was also re-run alone and passed (3.0 s each).
`test_recovery_stage_unlink_process_death_scans_and_reopens` and
`test_injected_outcomes_stay_refused_or_uncertain_and_recover` pass.

**The P10 lane's warning at `record-created` is borne out, and it weakens the
check without failing it (finding H2).** The test builds the model's program
from octets it reads off the store at the cut. For a record cut, the
candidate frame is the new `.txn` if there is one, and otherwise the
`.stage-` file. For the frontier, it is the `.allocation-` stage. At
`record-created` and `frontier-created` that file is empty, so the program
compared is `fn-bs-record-program stage name '()` (resp.
`fn-bs-frontier-program stage '()`), a write of zero octets, and the
prepared record is `fn-bs-record-of-octets '()`. The comparison passes, but
it is a comparison against a program parameterized by the observation it
judges. At these two cuts the differential shows only that the namespace (a
created, empty stage) is a crash image of *some* write program. It does not
show that the image is a crash image of the write of *this* article. The
other 16 cuts read non-empty octets that the model's program then writes. A
stronger check would take the program's octets from the intended frame, not
the observed file. That change is the harness owner's; this lane did not
make it.

### H1: the probe's expectation table predates the new cuts (harness)

`expectation()` in `tests/campaign/native_nntp_post_probe.py:186` knows only
two pre-publication cuts (`PRE_PUBLICATION = {"frontier-staged-durable",
"record-staged-durable"}`, `:175`). It sends every other non-finish cut to
"uncertain, exit 3".

- **`frontier-created`, `-written`, `record-created`, `-written`, EIO.** The
  node answers the same bytes as at `*-staged-durable`, with exit 0 and the
  article absent, and a repost gets `240`. These cuts sit inside
  `fnn-write-staged-at` before the fsync. The docstring says an EIO there "is a
  pre-publication failure of the same arm as a failing write", and it reaches
  `fnn-refuse-io`. By the rule the probe applies to `*-staged-durable`, these
  four rows are right. The probe's table needs them in `PRE_PUBLICATION`.
- **`record-stage-unlinked`, EIO.** The cut sits inside `(ignore-errors
  (fnn-unlink stage) (fnn-at store :record-stage-unlinked) (fnn-fsync-dir
  (fnn-staging store)))` (`host/native/io.lisp:1617`). That is the best-effort
  cleanup after `record-durable`, which the comment there says P-RECORD
  swallows. The EIO aborts only the staging-directory barrier. `fnn-finish`
  runs, and the client gets `240` after the completion was consumed. The
  article is durable and rereads identical, and recovery finds no orphan. This
  is P2's `240` case, not an uncertain one; the probe allows `240` only at
  `finish-*`. Also: the swallowed EIO leaves no line in the owner log.

Neither is a node change; both need the probe's table to learn the new cuts.
The coordinator decides whether that is the probe owner's fix.

## What this shows for P2 and P10

- **P2, cut half, holds on this pair at all 25 cuts.** It holds through both
  entries and at the wire. After every kill, the acknowledged prior rereads
  byte-identical by both readers, and so does every candidate that survived.
  No `240` preceded any death.
- **P2, wire half, holds on this image at the 13 cuts W1 to W3 were found at.**
  Uncertain is sent as `441 posting failed; the outcome is uncertain, do not
  repost` with exit 3. A durable article is never reported refused. Each
  refusal names its kind. At the 5 new cuts, the node's EIO bytes are the
  storage-failed refusal (4 pre-publication cuts, article absent) and `240`
  (`record-stage-unlinked`, article durable). The probe's judge marks those
  rows failed only because its table lacks them (H1). The wording of the
  refusal lines is still pending ember's decision.
- **The operator CLI keeps the three outcomes distinct:** 0 accepted or
  duplicate, 1 refused, 3 uncertain, 5 usage/refused selector, −9 death.
- **P10:** the five model sites that lacked a host cut now have one, the
  campaign takes all 25 cuts, and all pass, **on the developer image**. The
  ACL2 differential accepts the observed store as a crash image of the program
  at each of the 18 post cuts. At `recovery-stage-unlinked` it checks only that
  the store scans and opens. At the two
  `-created` cuts it does so only against a program built from the empty
  observed file (H2). The production image refuses every selector (27 of 27)
  and was exercised only by the two boundary kills. The developer and
  production cores differ (`f9ba0c63…` vs `99cee8c0…`), so "passes on the
  production image" is still true only as "on the developer image built from
  the same source and books".
