# Evidence: fn as a BPv7 node against dtn7-rs, each side authoring (w11/bp-node)

Date 2026-09-21 (UTC). Branch `w11/bp-node`, worktree
`build/lanes/w11-bp-node`, from `dev` at `dbf1aa7` and merged forward to
`3a2640c`. Box **hbox** for everything below, every ACL2 and every build
under `swarm-build`; remote root `/tank/fn/lanes/w11-bp-node`, certificate
cache `/tank/fn/certcache`. ACL2 8.7, `/tank/fn/acl2-8.7/saved_acl2`,
sha256 `64030dda0b03bbb6cf50984889f5ce1e2ba867b6ce3c9a65403afc44f9b4fdb5`;
the SBCL that built the image is `SBCL 2.2.9.debian`.

**Headline, against `tcpcl-dtn-w9-2026-09-20.md`'s.** That record's caveat
was that fn exchanged a bundle with dtn7-rs over RFC 9174 and **dtn7
authored it in both directions, because nothing in the tree encoded BPv7**.
`books/bp-node` certified for the first time tonight, and the authorship is
now one each way: dtn7-rs authored 132 octets that fn decoded, and fn
authored 138 octets that dtn7-rs decoded and delivered. Both octet strings
are kept, in `tests/bp-dtn7/golden/`, and the dtn7-authored one is inlined
in a certified ACL2 book.

## 2. The image

`build/fn-host-dtn`, **272,527,376-octet core**, built by

```sh
FN_NATIVE_BUILD=host/native/build-dtn.lisp \
FN_NATIVE_IMAGE=build/fn-host-dtn \
FN_NATIVE_LOG=build/native-host-build-dtn.log \
FN_ACL2=/tank/fn/acl2-8.7/saved_acl2 \
swarm-build sh tools/build_native_host.sh
```

**This is the DTN-only image, not the deployment image**, and that bounds
every claim below: `host/native/build-dtn.lisp` omits `books/served`,
`books/nntp-effects`, `host/reader-host.lisp` and
`host/native/reader-model-host.lisp`, so the `reader` and `model` verbs are
absent and fault at `fnn-call`. Every book it does include is certified in
this tree, `books/bp-node` included; the build refuses an uncertified book
rather than loading it with a warning.

## 4. `tests/bp-dtn7/run_fn_bp_interop.py`, fn against dtn7-rs

dtn7-rs **0.21.0** at revision `4daf02d7ea927e9293753b2a5c4497457f6e5a40`,
`/tank/fn/dtn7/repo`, `dtnd -n dtn7x -e incoming`. `ok: true`. The harness's
DTN time for the run was `843272138572` ms.

**Which side authored which bundle, explicitly, because that is the whole
point of this record.**

### Leg 1 — **dtn7-rs authored, fn decoded**

`dtnsend -r dtn://fn-b/incoming` with a 32-octet payload. fn's `bp receive`
journalled the transfer's octets as they arrived, then decoded them with
`fn-bpn-receive`:

```
BP accepted xfer=1 adu=32 path=.../fn-journal/passive-1.adu
BP summary accepted=1 refused=0 uncertain=0
```

`adu_matches_payload: true` — the ADU fn recovered is byte-for-byte the file
`dtnsend` was given. Exit code 0, `not_accepted: []`.

The wire image: **132 octets**, sha256
`3ba1d435188867c7f5b184cbb90dacacb73ec40865b60ece080af524583616df`, saved as
`tests/bp-dtn7/golden/dtn7-rs-0.21.0-authored.bundle`. Head
`9f 88 07 1a 00 02 00 04 00 …` — the indefinite-length bundle array of
RFC 9171 §4.3.1, an eight-element primary block, version 7.

`dtnsend -v` printed its own hex of a **115**-octet bundle. The difference is
exactly the 17 octets of the previous-node block `dtnd` adds before
forwarding (`85 06 03 00 00 4b` plus the 11-octet CBOR of `dtn://dtn7x/`);
every other octet, creation timestamp `843272141627` included, is identical.
The 132-octet wire image is the vector, because the wire image is what an
implementation has to accept.

### Leg 2 — **fn authored, dtn7-rs decoded and delivered**

```
BP authored creation=843272138572 sequence=1 lifetime=3600000 payload=33 octets=138
BP summary accepted=0 refused=0 uncertain=0
```

fn's own node ID `dtn://fn-b/` as the source, its clock observation as the
creation timestamp, its configured lifetime, CRC32C on every block, a
hop-count block and a bundle-age block, the ADU as the payload block — all
of it computed by `fn-bpn-send` in ACL2, none of it by host Lisp. dtn7-rs
decoded it, delivered the ADU to its `incoming` endpoint, and
`dtnrecv -e incoming` returned 0 and printed
`fn -> dtn7, a bundle fn authored`; `dtn7_delivered_the_adu: true`.

The wire image: **138 octets**, sha256
`f6688bdea94aa138b4fd338ecb171b1486dbde0d439a2756cde9a067b29b11b7`, saved as
`tests/bp-dtn7/golden/fn-authored-accepted-by-dtn7-rs-0.21.0.bundle`.

### How the octets were captured

`host/native/bp.lisp` now journals the wire image on both paths — the
inbound transfer's octets under `.wire` **before** the node is asked what it
makes of them, and the authored bundle **before** it reaches a socket — and
the harness reports each with its length and SHA-256. Neither file is a
re-derivation after the fact, and the receive-side capture is kept for a
refusal as well as for an acceptance.

## 5. The vector inside a certified book

`tests/acl2/bp-bundle-tests.lisp` has claimed an external vector from
`tests/bp-dtn7/golden/` since the commit that created it, and that directory
had never existed on any ref (lane `w11/phantom-cites`, 2026-09-21). Every
vector in the book was built by fn's own constructors and round-tripped
through fn's own codec, which cannot disagree with another implementation.

The 132 dtn7-authored octets are now `*bpb-dtn7-0-21-0*` in that book, and it
asserts three separable things about them, each of which a different defect
would break:

1. `fn-bpb-decode` **accepts** them, so fn parses what dtn7-rs writes;
2. the fields recovered are the ones dtn7-rs sent — source `dtn://dtn7x/`,
   destination `dtn://fn-b/incoming`, CRC type 0, flags 131076
   (`no-fragment` + `report-delivery`), the previous-node and hop-count
   extension blocks in dtn7-rs's order, the payload text — so fn agrees
   about what the octets **mean** and not merely that they parse;
3. `fn-bpb-encode` **reproduces them byte for byte**, so the deterministic
   spelling fn's decoder insists on (RFC 9171 §4.1, RFC 8949 §4.2) is the
   spelling dtn7-rs actually emits. This is the strongest of the three and
   the one a canonicality defect would break.

It also asserts that the transfer bound refuses the same foreign bundle
below the limit, so the preflight is exercised on real octets and not only
on fabricated ones.

## 6. What is NOT claimed

- One bundle each way, one peer, one revision. Nothing about fragmentation
  (fn refuses a fragment with `:fragment-not-reassembled`), BPSec, status
  reports, custody, or any field neither side exercised.
- The **canonical-block CRC is still exercised only against fn's own
  encoder** in the outbound direction: the bundle dtn7-rs authored carries
  no CRC at all (CRC type 0), so §1.4.1 of `specs/bp-design.md` stays open
  on that point. A dtn7-rs capture with CRC32C would close it.
- The image is the DTN-only build list. No claim follows for `reader` or
  `model`.
- T1 to T6 of `specs/bp-design.md` §1.6 are stated against an `fn-bpn-step`
  that does not exist. `books/bp-node` is the two ends of §1.5 and not the
  machine, and nothing here claims otherwise.
- `bp send` still takes its creation-timestamp sequence number as an
  argument rather than from a durable frontier, and says so in its own
  header. A restarted operator must not reuse one.
