## What the peer path did before

`fn-scar-peer-step-pinned` (`books/served-carried.lisp`) tested the carried
session recognizer (a pointer comparison of the session's node with the
owner's) and then handed a named peer session to `fn-pix-peer-step-pinned`,
which tested `fn-peer-sessionp` again, and so `fn-node-statep` (O(N^2)), on
every event. The IHAVE/CHECK transfer arm then went to `fn-peer-step`, which
tested it a third time. A guard-verified copy could not skip the test: the
transit arms call `fn-peer-command` (guard `fn-peer-sessionp`) and
`fn-peer-decide-offer` (guard `fn-node-statep`).

## What the node guard was for

One call: `fn-retain-admissiblep`, whose guard is `fn-retain-statep` of the
node's retention. Every other function on the peer arms is guard t. Its
`:logic` body conjoins `fn-retain-statep`; its `:exec` body needs only two
numbers to add and compare.

## Design (`books/peer-guard-carried.lisp`, prefix `fn-pgc-`)

- `fn-pgc-retain-admissiblep`: the reference's executable body, guard t,
  with `natp` tests on the two numbers it adds.
- `fn-pgc-decide-offer`: `fn-pix-decide-offer` (trie history test) with
  that call; guard t.
- `fn-pgc-peer-sessionp`: `fn-peer-sessionp` without its node conjunct.
  It is a guard only, never evaluated at run time.
- `fn-pgc-peer-command`: every transit arm (IHAVE, CHECK, TAKETHIS, MODE
  STREAM, CAPABILITIES), guard `fn-pgc-peer-sessionp`.
- `fn-pgc-transfer-step`: `fn-peer-step`'s transfer branch without
  `fn-peer-step`'s session test.
- `fn-pgc-peer-arm`: `fn-peer-step-pinned` past its first two branches,
  guard `fn-pgc-peer-sessionp`.
- `fn-scar-peer-step-pinned` now calls `fn-pgc-peer-arm`. Its guard
  obligation is `fn-scar-peer-sessionp-gives-pgc-peer-sessionp`.

`books/peer-inbound.lisp` is unchanged, so its 166 dependents do not need
recertification.

The premise is not new. It is `fn-node-statep` of the store's node. The
host's own relation carries it (`fn-ocl-relation` / `fn-own-relation`,
through `fn-scar-ocl-relation-carries-node-statep` and
`fn-scar-relation-carries-node-statep`). The existing
`fn-ocl-*-preserves-historical-relation` theorems and
`fn-scar-ocfg-read-keeps-store` prove it at open and preserved by every
served, transit and commit step. The owner puts that node into every peer
session (`fn-own-conn-live-session`, `books/owner.lisp:1291`), so the
carried session test is a pointer comparison.

## Teeth (`tests/acl2/peer-guard-carried-tests.lisp`)

- **Structure.**
  - All six functions on the chain are `:common-lisp-compliant`.
  - A program-mode check walks their guards (`all-fnnames` of `guard`) and
    finds no `fn-node-statep`. The body of `fn-pgc-peer-sessionp` has none
    either.
- **Reachable witness.** `*pt-ps1*` over `*pt-node1*`, with `live` being
  that node. The carried step gives:
  - IHAVE held: 435. CHECK held: 438.
  - IHAVE absent: 335 plus begin-article. CHECK absent: 238.
  - MODE STREAM, CAPABILITIES and a delegated STAT.
  - Every answer equals `fn-peer-step-pinned`.
  - The transfer arm, after IHAVE absent: the article event gives the
    reference's submission, and a non-article event gives the reference's
    436 and close.
- **One failure per hypothesis.**
  - **`(fn-node-statep live)`, the brief's case.** The session holds
    `*pix-t-orphan*`, a node whose binding names an id no article has.
    `live` is that same node.
    - The pointer comparison admits it, and the carried step answers
      `335` to `IHAVE <orphan@…>`.
    - The reference refuses the session and answers nothing (`must-fail`
      on equality).
    - With a node-state `live`, the same session is tested by
      `fn-node-statep` and refused, as the reference refuses it.
  - **Keystone, `fn-peer-sessionp`.** The same orphan session at the arm
    (`must-fail`).
  - **Keystone, named peer.** On a real reader session the arm decides the
    offer, while the reference delegates to the reader step, which answers
    502 (`must-fail`).
  - **Keystone, trie correspondence.** With the empty trie, the arm answers
    335 for the held id where the reference answers 435 (`must-fail`).
  - **`fn-retain-statep`.** A ledger whose reserved count disagrees with its
    pins. The copy admits and the reference refuses (`must-fail`).
  - **`fn-node-statep` of the decision.** The same ledger in a node: the
    copy wants the offer, and the reference defers it on capacity
    (`must-fail`).

on one peer connection, 2 100 commands. Both images are built by

- **Base: 1.363 ms per command.** `FN-NODE-STATEP` is 77.0% of all samples

  `FN-PIX-PEER-STEP-PINNED` → `FN-PEER-SESSIONP` → `FN-NODE-STATEP`.

**Cost sentences, with their scope:**

- **The node conjunct on a peer event** is one `equal` of the session's
  node with the store's. That is O(1) when they are the same object, which
  `fn-own-conn-live-session` makes them.
  - A session holding any other node falls back to `fn-node-statep`,
    O(N^2) by definition. No owner transition installs one; this is not
    proved.
  - Measured: `fn-node-statep` has zero samples at N = 120.
- **The pessimistic per-offer bound is now linear.** It is
  O((P + R) · L), with P and R the retention ledger's pins and releases
  and L the Message-ID length.
  - It is paid only by an offer of an absent id that reaches the capacity
    test. It is `fn-pgc-retain-admissiblep`'s id scan, which is the scan
    the reference's `:exec` body already made.
  - A duplicate offer stops at the trie, O(L), by T17's bound.
  - Measured: CHECK absent is 0.123 ms at N = 120, below STAT on the same
    run.

## Findings

1. **The config recognizer is now the largest per-event peer cost.** At
   N = 120, `FN-SCAR-PEER-SESSIONP` → `FN-CFG-VALUEP`
   (`FN-CFG-ROW-LISTP`, `FN-CFG-LABELP`, `FN-RECORD-STRING-OCTETS`) is 50%
   of the after profile.
   - It is the session recognizer's `fn-cfgp` conjunct. It is evaluated
     at least twice per event: by `fn-scar-auth-sessionp` and again by
     `fn-scar-peer-step-pinned`.
   - Its cost is O(config size), not O(N). The same conjunct runs on the
     reader path.
   - Carrying it (a pointer comparison against the owner's configuration,
     as the node conjunct now does) is the next step of the same shape. It
     was not done.
2. **`fn-pix-peer-command` and `fn-pix-peer-step-pinned` are off the host
   path.** Nothing the host calls reaches them now, and the registry cites
   `fn-pgc-peer-arm-is-peer-step-pinned` in their place under PRF-067.
   - They remain in `books/peer-offer-indexed.lisp` with their teeth.
   - Removing them would touch that book, its tests and the prefix row.
     It is left to the coordinator.
3. **The keystone has no node premise of its own.**
   `fn-pgc-peer-arm-is-peer-step-pinned` is stated under `fn-peer-sessionp`,
   the reference's own first test. So no new owner relation or preservation
   theorem is needed. The owner's existing `fn-node-statep` premise reaches
   it through `fn-scar-peer-sessionp-is-peer-sessionp`.
