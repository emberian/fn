# XPAT with more than one pattern token: what INN 2.7.4 answers, and what fn answers

Question: RFC 2980 §2.9 says "If there are additional arguments the are joined
together separated by a single space to form one complete pattern."  What is
the one complete pattern's grammar, and what does a real server answer when it
cannot match?  `tests/acl2/nntp-legacy-tests.lisp` asserted 221 with an empty
list and fn answers 501; this is the measurement that settles which is fn's.

## The foreign client: INN 2.7.4 on hbox

INN is not shipped or torn down by this measurement; it is the lab install at
`/tank/fn/inn/2.7.4` (source at `/tank/fn/inn/src/inn-2.7.4`), the same build
`planning/evidence/inn-lab-f4e8272-2026-09-20.md` drove, pinned by
`tests/inn/pin.json`.  No daemon was started: `nnrpd/article.c`'s `CMDpat`
computes the pattern and the match with exactly two library calls, and both
were driven directly against INN's own compiled `libinn.a`.

`nnrpd/nnrpd.c:188` routes `XPAT` to `CMDpat` with `CMDany` maximum arity.
`nnrpd/article.c:1383`-`:1384`:

    if (ac > 3) /* Necessarily XPAT. */
        pattern = Glom(&av[3]);

`lib/argparse.c:118` `Glom` concatenates the remaining arguments with a single
SP between them (`strlcat(save, " ", i)`), which is §2.9's join.
`nnrpd/article.c:1418`, `:1455` and `:1538` then match with

    uwildmat_simple(text, pattern)

whose comment at `lib/uwildmat.c:440` reads "User-level routine for simple
expressions (neither , nor ! are special)".  `CMDpat` performs no syntax check
on the pattern at all: its only 501s are for the range, the Message-ID and the
header field name.  A pattern that does not match therefore yields the ordinary
221 with an empty list, never a 501.

Driven on hbox, 2026-09-20, `gcc -I/tank/fn/inn/2.7.4/include probe.c
/tank/fn/inn/2.7.4/lib/libinn.a`, calling INN's `Glom` and `uwildmat_simple`
with `CMDpat`'s arguments and the subject of fn's seed article:

    XPAT ... *T *t* (joined)     pattern=[*T *t*]  subject=[Test]  uwildmat_simple=false
    XPAT ... *T* (one token)     pattern=[*T*]     subject=[Test]  uwildmat_simple=true
    second token alone *t*       pattern=[*t*]     subject=[Test]  uwildmat_simple=true
    XPAT ... *T,*t* (comma)      pattern=[*T,*t*]  subject=[Test]  uwildmat_simple=false
    XPAT ... * * (joined)        pattern=[* *]     subject=[Test]  uwildmat_simple=false
    joined vs spaced subject     pattern=[*T *t*]  subject=[T st]  uwildmat_simple=true

So INN answers `XPAT subject 1-1 *T *t*` with **221 and an empty list**: SP is
an ordinary literal in the joined pattern, and the last line shows the joined
pattern matching precisely the subject that contains the SP.

## fn, measured

`tools/acl2 --timeout 240` over a driver rebuilding the test book's fixture
from `books/nntp-effects` (worktree `build/lanes/w10-nntp-tests`, dev 1019c97):

    (lg-reply *lg-env* "XPAT subject 1-1 *T *t*")   =>  501 syntax error
    (fn-wildmat-parse (fn-nntp-xpat-join '("*T" "*t*")))  =>  (:ERROR :SYNTAX)
    (fn-wildmat-itemp 32)                           =>  NIL
    (lg-reply *lg-env* "XPAT subject 1-1 *T*")      =>  221, line "1 Test"
    (lg-reply *lg-env* "XPAT subject 1-1 *Q*")      =>  221, empty
    (lg-reply *lg-env* "XPAT subject 1-1 *T,*t*")   =>  221, line "1 Test"

`fn-nntp-xpat-join` (`books/nntp-responses.lisp:1524`) joins exactly as `Glom`
does; the divergence is one line later.  `fn-nntp-xpat-response` (`:1620`) hands the
joined octets to `fn-wildmat-parse`, which enforces RFC 3977 §4.1's
`<wildmat-exact>` (`fn-wildmat-exactp`, `books/wildmat.lisp:182`: %x22-29,
%x2B, %x2D-3E, %x40-5A, %x5E-7E and non-ASCII).  SP is %x20 and is excluded, so
every pattern joined from two or more tokens fails the parse.

## Two divergences, both real

- **OB-XPAT-SPACE.** fn answers 501 where RFC 2980 §2.9's response list
  (221/430/502) and INN answer 221 with an empty list, for *every* XPAT whose
  pattern has more than one token.  A header value is prose and contains
  spaces, so this removes phrase search, XPAT's ordinary use.  RFC 3977 §4.1
  says of its exclusions "This should not be a problem, since these characters
  cannot occur in newsgroup names, which is the only current use of wildmats" —
  which is exactly the assumption XPAT breaks.  `fn-nntp-xpat-join`'s
  multi-token branch cannot today produce a successful match, so its §2.9
  conformance is arithmetic only.  The cure is a pattern grammar for header
  text that admits SP, in `books/wildmat.lisp`, without widening
  `<wildmat-exact>` where `newsgroup-name = 1*wildmat-exact` reads it.
- **Comma.** fn reads `,` in an XPAT pattern as wildmat alternation and matches
  `*T,*t*` against "Test"; INN's `uwildmat_simple` reads it as a literal and
  does not.  Here RFC 2980's "at least one pattern in wildmat" is on fn's side
  and INN is the deviation, so this is recorded and not changed.
