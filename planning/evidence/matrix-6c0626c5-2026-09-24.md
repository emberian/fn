# v0 matrix on the 6c0626c5 image, 2026-09-24

On the frozen `6c0626c5` production image, run `20260924T154510Z` of
`tools/v0_matrix.py --backend native-operator` reached 157 of 220 rows, and
**2 of them disagreed**. Both are INN lab rows, and both come from one fn
defect: **with a Path identity configured, every inbound transit transfer
(`IHAVE` and `TAKETHIS`) is stored durably, but the peer gets `436 transfer
failed; the outcome is uncertain` and the service stops with `uncertain
operator run`.** Node B hit it on the first transit offer of the run and
stayed down. That took out the 24 IHAVE/CHECK/TAKETHIS rows (which the tool
labels `not-built`, a harness misreading; see below), the live
reconfiguration pair, `V0-POST-CONCURRENT` and B's two capability pins.
The run is published as `planning/v0-matrix.json` (`rows_digest`
`65fca41a…`). The live node `/tank/fn/node` (`da5fd8cb`) was not touched.

The defect is reproduced by hand on a clean store below. It needs only
`peer add` and then `policy set path-identity`. Nothing new was found
wrong with the rows.

**Consequence for T0.** On this image, a node that has a Path identity
takes transit from a peer or from INN once. The article is durable, the
sender is told the outcome is uncertain, and the service stops until
someone runs `recover`. On the matrix's evidence, this image should not
replace the hbox node until the transit completion is fixed.

## Disagreed rows

- **`V0-INN-INTEROP`**: expected accepted, observed **refused**, meaning the
  lab's verdict was `violated` (25 held, 5 not exercised, 3 violated). The
  three violations:
  - `innfeed-feeds-fn`: innfeed's `CHECK` drew `238`, and its `TAKETHIS`
    drew `436 <inn-lab-fed-…@example.invalid>`. This is the transit defect:
    the lab's fn node has Path identity `fnA.hbox.test`.
  - `fn-duplicate-435[fn-article]`: the second IHAVE of fn's own article
    drew no reply. fn's service had already stopped on the TAKETHIS.
  - `fn-loop-refused`: IHAVE, transfer and ARTICLE all drew no reply, for
    the same reason.
- **`V0-INN-LOOP-FN`**: expected refused, observed **accepted**. The row
  reads `fn-loop-refused=violated (None / None / None)`. No loop article
  was accepted. The service was down, so every reply was absent. The row maps
  a violated lab finding to `accepted`, which reads as "fn took a looping
  article" and is wrong about the direction. This is a harness finding about
  the row's mapping, not an fn loop defect. The loop rows of the native
  transit phase (`V0-TRANSIT-LOOP-*`) were not reached either, so this image
  has no loop observation.

## Finding: transit into a node with a Path identity reports uncertain and stops the service

**Observed in the run.** The matrix sets `policy set path-identity
b.gate.example.invalid` on B and `peer add a …` (config records 5 and 6).
Step 134, `transit AB`, relays `<alpha@a.example.invalid>` from A to B, and
the relay gets `RuntimeError: server closed the connection`. B's main log
ends with:

```text
accepted peer connection=15 peer=a time=2026-09-24T15:46:19Z
uncertain operator run
```

Step 136, `transit BA`, gets `ConnectionRefusedError`. A copy of B's store
reports `transactions=5 articles=5` after `recover`. That fifth article is
alpha, so the transfer was durable.

**Reproduced by hand** ([transcript](matrix-6c0626c5/repro/transcript.txt),
logs beside it). All steps use the production image. On a fresh `store
init fn.letters` with `peer add a a.gate.example.invalid 127.0.0.1 11190
'fn.*' - 127.0.0.1 true`, `IHAVE` of a new article draws `335` and then
`235 article transferred OK`, and the service stays up. After `policy set
path-identity b.gate.example.invalid`, the next `IHAVE` of a new article
draws `335` and then `436 transfer failed; the outcome is uncertain`. The
connection closes, and the owner exits with `uncertain operator run`. No
diagnostic is written to stdout or stderr: the unclassified-OS-error branch
of `fnn-owner-attempt-handlers` would have logged, so it was not that
branch. After `recover` (2 transactions, 2 articles), `ARTICLE` serves the
article with `Path: b.gate.example.invalid!!a.gate.example.invalid!not-for-mail`.

**What this says.** Under P2, answering uncertain after a consumed
completion is allowed: it is not a false refusal. But there was no
persistence ambiguity here. Every transit transfer into a node with a Path
identity is misclassified as uncertain, and the uncertainty fences the store
and stops the service. It stops for every peer and every reader. The
1a9dd747 image took the same sequence on the same row (335/235, service up),
so the regression came in between. The candidates are the signed-ingress
transit path `fnn-owner-attempt-transit` (`host/native/owner.lisp:789` in
the gate tree) and the W1/W2 outcome plumbing. The Path-prepended payload
now differs from the offered octets, and something after the Store attempt
treats that difference as indeterminate. That is a hypothesis for the fix
lane, not a measurement. The native peering witness in this run passed
(335/235 both ways) because its nodes set no Path identity.

The live node's configuration was not read. Whether it sets a Path identity
decides whether the T0 upgrade would hit this on its first transit.

## Harness problems

1. **A dead peer reads as "not built"** on the 22 hand-relay transit rows.
   The run's own "What was NOT exercised" section says B died, but the
   transit rows name a lane that owns a missing feature. The rows should read
   not exercised against the death, the way the CFG and PIN rows do.
2. **`V0-INN-LOOP-FN` maps a violated finding to `accepted`.** "Violated"
   with all replies absent is not an acceptance of a looping article.
3. **`--publish-current` published a run that stopped early.** The first
   launch passed a short `--native-image-source` and was stopped by me
   during the ship step. The relaunch then failed at once with
   `gate error: deploy identity is already active: native-6c0626c5-c60bb37`,
   because the stale lock was left in `~/fn-deploy/.locks/`. That run
   (220 rows not exercised, exit 2) was still written to
   `planning/v0-matrix.json`. I restored the file from HEAD, removed the
   stale lock and deploy tree (both mine), and discarded that run
   directory. The transcript is kept as
   [`matrix-6c0626c5/driver-lockfail.log`](matrix-6c0626c5/driver-lockfail.log).
   A gate-error run should not be publishable, and an interrupted ship
   should release its lock.

None of these was fixed on this branch. The run's rows are the tool's, as
published.

## What this does not establish

This is one run on one box, over loopback. A row observes a reply, an exit
code or a file. It is not a theorem, and it says nothing about which ACL2
subject the host calls. The transit finding is one transfer in the run and
four by hand, all on the production image. Its cause is not located. The
uncertain-outcome rows use the developer image's fault selector. The
AUTHINFO session rows run on clear loopback under `[auth] required`, so
the 483 clause is not observed.
