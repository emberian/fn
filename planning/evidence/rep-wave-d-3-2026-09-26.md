**What a node can now do that it could not before:** open from the
checkpoint it published at N = 10,000 × 32 KiB. rep-wave-d-2 made `store
checkpoint` complete at that size and left a 670 MB file the owner could
not read: it died "Heap exhausted, game over" in
`FNN-STATE-CHECKPOINT-LOAD` after 56 s, holding the file as octet lists
twice beside the value it built, and the node was down until the operator
removed the file. The reader now reads the file from the octet buffer by
index, in the shape the writer produced it, with no list of the file or of
the joined program; the payload lists it builds are the records' own, once
each (§1, §5). A checkpoint file the reader will not read within the
profile's bounds is refused by name (`open=full-replay
reason=checkpoint-exceeds-bound`) and the journal replays; a corrupt one is
`reason=corrupt` as before; neither is a fatal error (§2).
**What this lane did not do:** the file's second copy of every payload
stays (§3, PKT-307); the writer's per-octet export cost is not changed
(§7); the records-shape freeze (PKT-293) is ember's and did not start.

## 1. The reader over the buffer (PRF-135)

The reader's input is the writer's plan shape (`fn-sccb-plan`, PRF-133):
one frame `(HEADER A B TRAILER)` per FNSC segment, the header and the
trailer as short octet lists (37 and 32 octets), the chunk as the buffer's
cells A..B, the chunks contiguous in file order. The host
(`host/native/io.lisp` `fnn-state-checkpoint-plan`) reads the file one
segment at a time, and before each read asks ACL2 whether the segment is
read (`fn-store-sco-segment-admit`, §2); it appends the chunk's bytes into
the live buffer (`fnn-octets-append-vector`, the same boundary as
`fnn-octets-fill`: the host asserts the cells it wrote hold these bytes,
A-HOST) and hands the plan to `fn-store-sco-decode`
(`host/store-node-host.lisp`), which calls `fn-sccr-decode-plan`.

`books/store-checkpoint-reader.lisp` (prefix `fn-sccr-`, `docs/prefixes.md`):

| Theorem | Statement | Host line |
| --- | --- | --- |
| `fn-sccr-run-is-run` | `(implies (and (fn-octets-p st) (natp i) (natp end) (<= i end) (<= end (len st))) (equal (fn-sccr-run i end stack st) (fn-scc-run (fn-oct-slice-list i end st) stack)))`: the stack machine by index over the cells [i, end) is the list machine over that slice | inside `fn-sccr-decode-plan` |

How it reads. `fn-sccr-planp` checks the shape. `fn-sccr-join` verifies the
chain frame by frame: the header parsed from its list, the index, count and
sequence, LENGTH = B − A, and the seal over the previous trailer, the
header and the chunk against the trailer. The seal is `fn-scc-seal` =
`fn-frame-trailer`, the constrained digest, closed; it has no buffer-range
twin in the logic (`sha256-buffer` digests the whole buffer behind a list
prefix, and `fn-frame-digest` is only attached to SHA-256 on the image), so
the chunk is read for its seal as a list of at most one segment
(`fn-sccb-slice-acc`, the writer's own reader; garbage before the next
segment), exactly as the writer seals it. Nothing joins the chunks: the
program is the buffer's cells from the first frame's A to the last frame's
B, and `fn-sccr-run`/`fn-sccr-step` run `fn-scc-run`/`fn-scc-step` by
index. A payload leaf is `fn-sccb-slice-acc` of its range: the record's own
octet list, built once (the retained representation until PKT-293); a
natural's digits and a string's characters are short slices; one cell is
read by `fn-sccr-cell`, a natural by type prescription (`nfix` under `mbe`,
so that the guard obligations over index sums close; the rewrite runs from
`nth` to the reader, never back). Every executable function is
guard-verified (asserted in the test book).

The assurance chain: `fnn-recover` → `fnn-recover-from-state-checkpoint` →
`fnn-state-checkpoint-load` → `fnn-state-checkpoint-plan` (I/O: the file's
bytes into the buffer, the plan) → `fn-store-sco-decode` → `fn-sccr-decode-plan`
(the executed subject over the representation) → the twin and the keystone
(the refinement to `fn-scc-decode-segments`) → `fn-sco-thaw`,
`fn-sco-extend`, `fn-sco-open` (unchanged; the maintained relation and the
behavioural theorem are rep-wave-d-2's and checkpoint-cost's:
`fn-sn-recover-from-checkpoint-equals-full-recover`) → the owner's
`open=checkpoint:S` line and the served state.

## 2. The refusal

`fn-sccr-admit-segment header total segment-bound file-bound` decides,
before the host reads a segment, from its 37-octet header and the octets
read so far: `(:ok EXTENT CHUNK-OCTETS)`, `(:refused :header)` (the codec
does not parse it) or `(:refused :exceeds-bound)`. The segment bound is
the profile's `fn-store-sco-segment-read-bound` (one segment written with
R = max-record-octets, as before); the file bound is new,
`fn-store-sco-file-read-bound` = `fn-sccr-file-read-bound H R` = 3 × the
profile's max-history-octets + one segment's framing: the checkpoint value
carries the history's records twice (§3) and its derived tables beside
them, and the reader then holds at most this many octets in the buffer
(one byte each) and the value decoded from them, which is the envelope the
journal replay of the same history already needs. It is a policy from the
operator's profile (D27: no constant bounds data; the profile is the
operator's), decided in ACL2, and never wrong: past it the checkpoint is
refused by name and the journal replays, slower. The host's own arm for an
over-long segment (`:segment-header`, a host comparison against an ACL2
number) is gone; ACL2 decides both bounds.

The verdict is carried as the status `:exceeds-bound` from
`fnn-state-checkpoint-load` into `fn-sco-select`'s new arm
(`books/store-checkpoint-open.lisp`): `(:full-replay :checkpoint-exceeds-bound)`,
before the generic `:corrupt`; `fn-sco-select-bounds-the-suffix` is
unchanged (the arm never serves). `status` renders it as
`open=full-replay reason=checkpoint-exceeds-bound` (`fn-nls-open-words`).
Native: `test_a_checkpoint_past_the_profile_bound_is_refused_by_name`
(§4): the first segment's LENGTH field set to 2^64 − 1, the open replays
the journal, the observation is the full replay's, the line names the
refusal; one bit of the same field flipped is `reason=corrupt`; the file
restored, `open=checkpoint:3 suffix=2`.

The residency bound the brief asks for is this file bound together with
the per-step transient: one segment's chunk as a list (sixteen bytes per
octet of at most R) for its seal, garbage before the next; and the value's
own lists, which are the records' (§3).

## 3. The file's second copy of every payload: why it stays

The record's finding (rep-wave-d-2 §5): 670 MB for 320 MB of payload. From
the code: `fn-sco-freeze` (`books/store-checkpoint-open.lisp`) replaces
the checkpoint value's record LIST with the count when the event index
reproduces it (`fn-sco-thaw` rebuilds the list from the index), so the
file carries the records once in the event index; but the value's `cpr`
slot is the configuration fold's paused state `(:paused cn ...)`, and `cn`
is the configured node whose store holds the same records
(`fn-sco-cpr-prefix` applies each event to it). The file therefore carries
every record's payload twice: in the fold's node and in the event index.
The reader builds both, as the list decoder did, because both are in the
tree the codec was given; the reopened owner then holds two lists per
payload where a replay's owner holds one (the baseline's "live after
checkpoint reopen" against "live after load": 1,393 against 798 MB at
N = 1,000 × 32 KiB, rep-wave-d §1.1).

Decoding "once into the arena/buffer-held record" needs the held record
(PKT-293) and, independently, a checkpoint VALUE that carries each record
once: freezing the fold's node's record list as the record list is frozen
(a count, with the thaw rebuilding it from the index) is a change to the
checkpoint value's shape (`fn-sco-freeze`/`fn-sco-thaw`,
`fn-sco-thaw-of-freeze`, `fn-sco-freeze-of-capture-carries-the-count`, the
node's own shape opened in the open book) and to what a schema-2 file
means, i.e. a format evolution the reader must either accept both of or
bump the schema for. That is PKT-307 (§7), to decide with PKT-293, since
the arena changes what the record holds anyway; it is not a lane's call
and not a "list copy for now": the copies here are the format's.

## 7. PKT-307, for ember: the checkpoint value carries each record once

Trace: §3 (the fold's node and the event index both hold the records;
`fn-sco-freeze` freezes only the record list), rep-wave-d-2 §5 (670 MB for
320 MB), the rows of §5 here (the reopened owner's two lists per payload).
Constraint: a checkpoint file's meaning is its schema; the fold's node is
opened inside the open book's theorems (`fn-sco-cpr-prefix`,
`fn-sco-cpr-resume`, `fn-sco-cpr-finish` and their append lemmas), so a
frozen node needs a thaw before the fold resumes and the keystone
`fn-sn-recover-from-checkpoint-equals-full-recover` restated through it.
Default (recommended): decide it with PKT-293. Under the held record the
file carries handles and bytes separately anyway (the arena's sealed
payloads once, the records' fields twice, which is small), and the freeze
of the fold's node comes with the codec over the arena, one schema bump
(3) that the reader accepts beside 2 for one release. Rejected: freezing
the node's list now under schema 2 (a second reader path for one file
schema, redone under the arena); a content-memo in the decoder sharing
equal payload lists (a hash or a byte compare per leaf on the open path,
logically invisible, and moot under the arena). Affected: the checkpoint
value's shape and the open book's fold theorems, the file schema, the
reader and the writer, `checkpoint_open_equals_full_replay`. What
continues without it: everything; the node reopens from its checkpoints
at sixteen bytes per octet twice, within the replay's residency (§5), and
the auto-publication at 2,048 records is far below the sizes measured
here.
