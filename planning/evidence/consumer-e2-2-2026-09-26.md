## What now works

A consumer that dies between fn's acceptance of its submission and its own
record of that acceptance no longer records the operation refused when a
later resend is refused: every attempt is durable before it crosses the
native boundary, a refusal settles only the attempt it answers, and the
operation stays uncertain until fn's D25 answer to the saved artifact or
fn's Store serving that artifact back settles it. Retries send the saved
artifact (source, both signatures, the author's key context) and nothing
is re-signed. The consumer checks every received report's Ed25519 and
ML-DSA-65 signatures itself, with a keyring it was given, and consumes only
what it verified and what the application's claim rule entitles the
signer to.

## Step 2: the repair (tools/fn_consumer.py, schema fn-consumer-2)

Three records, never one mutable outbox row:

- `submissions`: the immutable artifact (authored source, Ed25519 and
  ML-DSA-65 signatures, the principal, the Ed25519 key, the ML-DSA-65 PEM,
  the keyring generation, the original context). SQLite triggers refuse
  UPDATE and DELETE. `hybrid-author` is called with these bytes and this key
  context only; the configuration's current key paths and generation are
  used only when a new artifact is signed.
- `attempts`: inserted `in-flight` and COMMITted before `hybrid-author` is
  run; answered in a separate transaction. An `in-flight` row found when a
  process opens the database becomes `unanswered` (one consumer process per
  database is the stated assumption).
- `observations`: `post-answer` (exit 0: fn's ACCEPTED or DUPLICATE, the
  status word recorded) or `store-observation` (fn's poll served the same
  Message-ID with the same authored source and, by the consumer's own check
  of the served carrier, the same two signatures).

State is derived (`submission_state`): stored once any observation exists;
pending with no attempt; refused only if every attempt has a durable
refusal; otherwise uncertain. `reconcile_due`: an uncertain submission is
resent once per open attempt (unanswered, exit 3, or any non-definitive
exit) and not again after a later refusal; then only an observation settles
it. Terminology in code and docs: randomized ML-DSA signing changes the
signature and the carrier, not the authored source.

## Step 4: independent verification

`tools/fn_verify.py check-article ARTICLE MSGID --keyring K` is a new
offline form of the existing independent verifier (pyca Ed25519;
dilithium-py ML-DSA-65 on hbox; every installed implementation must
agree): it prints the independent check (principal, both component
verdicts, both carrier signatures, SHA-256 of the projected authored source)
and exits 0/1/3. The consumer runs it as a separate process on the received
article `consumer-project` returned (the projection's `received` field),
with the keyring in its own configuration (made from the authors' public
key files by `fn_verify.py keyring-entry`, never read from fn). It compares
the verified principal and authored source with fn's projection and
records `own_verdict` (verified, unverified, undecided, disagree) beside
fn's verdict principal and verdict. Nothing in tools/ imports fn_verify
(tests/test_anchor.py, 34 OK on the laptop with the journal test; the hbox
run of test_anchor failed for the environment: its store-command tests need
an ACL2 on PATH the runner did not set). `test_check_article_is_the_offline_independent_check`
(tests/test_fn_verify.py, hbox log `69120d6340c60de6…`) covers verified,
tampered, unsigned, unpinned and swapped-Message-ID articles.

## Step 5: who may claim an operation identity

The consumer's configuration carries the application's claims
`[application-id, operation-id prefix, principal]`; the longest matching
prefix names the one principal entitled to that identity. A verified report
by another principal is conflict evidence (`reason` unentitled) and does not
occupy the identity; a changed source from the entitled principal is
conflict (`changed-source`), as before. Native both orders above.

## PKT-322: a revoked author cannot reconcile by resend (decision packet)

- Trace: the red test. After revocation, `hybrid-author` of the byte-exact
  accepted artifact is refused by the enrolment check before
  `fn-owner-existing-action` is asked, so D25's "already stored here" is
  unavailable to that author; the consumer's only settlement is fn's Store
  serving the artifact back, which needs the consumer registered in the
  group (it is, in this profile). NNT-019's PKT-164 is the same shape on
  NNTP.
- Constraint: D25 answers by identity; permission is a separate current
  fact; a refusal must never be read as "not stored".
- Default (in force): refusal before identity; the client stays uncertain
  and settles by observation.
- Alternative: answer an exact held artifact `:duplicate` before the
  enrolment check (identity before permission for byte-identical resends
  only; a new or changed carrier still needs a current enrolment). Cost: a
  reordered decision in `fnn-hybrid-control-author` with a theorem that the
  early `:duplicate` commits nothing and leaks nothing a revoked author could
  not already read; the enrolment theorems' statements change.
- Affected: hybrid-control, PRF-117's route statement, NNT-019/PKT-164.
- What continues without it: everything in this lane.

## Interface for the next lane (the two-store exchange)

- The artifact: `submissions` row (fields above); the two-store lane
  carries it unchanged across the relay; a relay's stored projection may
  differ, the authored source and both signatures may not.
- The attempt journal: `attempts` and `observations` as above; a hop's
  forwarding attempt is a different record from an application
  submission attempt.
- The verifier boundary: `fn_verify.py check-article` on the received bytes
  with the receiving consumer's own keyring; `own_verdict` beside fn's.
