# A BP node's heap counts its BP terms (CONVERGE-2 batch mb3)

**An installed BP node cannot start: its launcher sizes the process for the store alone, and the node's own startup check then refuses the BP sessions.** `fnn-bp-session-install` (host/native/bp-session.lisp:19) asks `fn-bpsp-startup` (books/bp-session-profile.lisp:81) whether `(sb-ext:dynamic-space-size)` holds the store figure (`fn-heap-figure-octets` of the store, the core and the nursery) plus the BP held projection (`fn-bpsp-held-projection`: 32 octets a held octet, 512 a row, 64 an ADU, from the node profile) plus the session allowance (the session profile's, at least `table + n x each`). The launcher's heap probe (`fn heap -- bp-node serve ...`, host/native/heap.lisp `fnn-heap-command-profile-base`) recognises the command through `fn-bph-command-plan` but reserves only the store's `:run` figure (`fn-heap-reserve-operation-decide`) and its extensions, none of which names a BP term. Until MEM-002 (dev train 15) every start that bypassed the probe ran at the saved 32,000 MB and hid the gap. Since then `test_native_consumer_exchange_two_nodes` fails with `store: BP session funding refused (:REFUSED :BP-SESSION-CAPACITY-NOT-HELD)`, whether the image is started directly or through the installed launcher (hbox:/tank/fn/scratch/n-row17/r2.log). The same refusal awaits any installed `bp-node serve` and `bp-app receive`. The figures on hbox (store figure, held projection, allowance against the probe's heap) are owed until the box is back.

## The rule

- **Decision** (books/bp-heap-command.lisp, beside `fn-bph-command-plan`): `fn-bph-extend-reservation BASE BP-TERMS CORE MACHINE` adds the held projection and the session allowance to the probe's decision for a `:run` BP plan. It is refused by name when the machine cannot hold the sum, as the other extensions are. BP-TERMS are the same values `fnn-bp-session-install` reads: the session profile under the BP root and the node profile's held octets, rows and ADU octets.
- **Observation** (host/native/heap.lisp): for a BP plan, the probe reads those two profiles from the command's roots, with the same readers the node uses (`fnn-bp-session-profile`, the node-profile reader), and passes them in. It decides nothing itself.
- **Keystone** (statement first): for a BP `:run` plan whose terms are read from the same files, a reservation the extension accepts makes `fn-bpsp-startup`, at that dynamic space, answer `:hold`, never `:bp-session-capacity-not-held`. Teeth: the base reservation alone, under the same terms, answers `:bp-session-capacity-not-held` (a ground witness at the two-node test's profile).
