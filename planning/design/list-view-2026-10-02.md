# Decision: should LIST answer from the live view? (2026-10-02, open, ember's call)

## The rule today

NNT-042 (an explicit spec change from gpt-6's wave-5 review, section 1, 2026-09-26):
"A reader connection's view is a version (ViewId): a successful GROUP or LISTGROUP
acquires a fresh coherent view and performs its normal selection effects; **other reads
stay on that view until the next refresh boundary**; a failed selection leaves the
previous view and cursor unchanged; a cancel committed after an article leaves it
visible to a connection pinned before the cancel until it acquires a view past it."

LIST is one of the "other reads", so it answers from the connection's pinned view.

## Why it came up

served-incremental-1 (PRF-1229) moved LIST off an O(G·N) walk onto the carried group
summary: 377.6 MB / 187 ms per LIST at 100k articles became a flat 23-25 KB. Codex r51
F2 found the flat cost holds only for a connection at the TOP view (fn-scat-top-viewp).
A connection pinned at an older view (LIST does not advance it) runs fn-scv-summary per
group over the rows appended since its pin: G x D. Measured (served-incremental-5):
about 1.2 MB and 1.5 ms per LIST for a connection 1,000 rows behind, 10 groups. The
claim is now scoped to the top view in PRF-1229.

## The options

**(A) LIST answers from the live view without moving the connection's pin.**
- RFC 3977 basis (served-incremental-5's reading):
  - 7.6.3: LIST ACTIVE MUST list every group that is selectable with GROUP. GROUP
    re-pins to live, so the groups GROUP can select are live's groups. An old pinned
    view can MISS a newly created group, so today's LIST arguably violates 7.6.3.
  - The water marks are "as described in GROUP", i.e. "at the moment" (6.1.1.2: the
    set may change after selection; low-water monotonicity holds because live is newer).
  - 6.1 lets only GROUP / LISTGROUP / NEXT / LAST / ARTICLE n change the current
    article number, so LIST must NOT re-pin. It only reads live.
- Effect: LIST is flat in N at every view; no new machinery.
- Cost: amends NNT-042 ("other reads stay on that view" gains an exception for LIST)
  and restates the pinned-boundary theorem's LIST case (reference becomes
  fn-nntp-list-command at the live archive). A connection can see a group's high
  water in LIST that its pinned GROUP/OVER would not show until it re-selects.

**(B) Keep NNT-042 as is; carry per-view group summaries.**
- Each pinned view keeps (or can cheaply derive) its own group summary, maintained
  as a delta as rows append.
- Effect: LIST flat at every view with NNT-042 unchanged.
- Cost: per-pin carried state and its invariant/proofs; more machinery, for a
  behaviour the RFC does not require (and arguably contradicts for new groups).

**(C) Do nothing; keep the scoped claim.** LIST is O(G·D) for an old-view connection.
D is bounded by how long a connection stays pinned without re-selecting.

## Recommendation so far

The coordinator recommends (A): simplest, flat everywhere, and it closes a latent
RFC 7.6.3 gap (a newly created group missing from LIST on an old-view connection).
served-incremental-5 prepared option A's diff, amended NNT-042 text, and restated
LIST boundary case on a side branch; nothing has landed.

**RFC state and watermark rules need a more careful explanation than the decision gives.**

- Section 6.1 (`rfc3977.txt:1972–1975`) introduces selected-group/current-article state; it does not contain the decision's exclusive list of commands allowed to change it. The decisive rule is §7.6.1 (`:3759–3762`): “The LIST command MUST NOT change the visible state of the server in any way”; subsequent commands must not be affected by whether LIST was issued. Repinning on LIST would violate this even if the cursor fields stayed unchanged. A's read-only live response can satisfy it.
- GROUP reports bounds at selection (§6.1.1.2, `:2005–2009`). The RFC expressly permits removals, reinstatements, and additions after selection (`:2042–2056`). LISTGROUP selects identically and enumerates articles at selection (§6.1.2, `:2171–2181,2211–2217`). The RFC does not demand fn's stable cross-command article snapshot, nor equality between LIST and an earlier GROUP response.
- LIST imports GROUP's watermark definitions (`:3890–3892`). The low-mark rule has its stated empty/all-zero exception and monotonicity scope (`:2058–2068`); clients may discard bookkeeping below it. High marks may decrease after removal (`:2069–2080`). “Live is newer” is not, on its own, a proof of low-mark behavior through empty groups, withdrawal and reinstatement.
- Section 3.2.1 (`:538–607`) still controls generic refusals and authorization. It supplies no special “your pin is old; first issue GROUP” exception allowing a successful but incomplete LIST. These are ordinary authorized commands in the counterexample.

**Removal is not creation in reverse in this implementation.** The allocation domain and currently served table differ:

- `books/node-config.lisp:85–93` defines the served table using `(fn-cfg-group-names ... (fn-cfg-generation config))`, but `fn-cnode-domain-of` uses `(fn-cfg-group-all-names (fn-cfg-groups (fn-cfg-value config)))`; its comment says “every name the history ever created.”
- `books/config.lisp:2596–2597` maps `:remove-group` to `fn-cfg-groups-retire`. At `:2421–2433`, that function sets retirement generation while retaining the entry; its comment says “The entry, its creation stamp and its watermark stay.” The theorem at `books/config-invariants.lisp:45–47` states `(equal (fn-cfg-group-all-names (fn-cfg-groups-retire es gen name)) (fn-cfg-group-all-names es))`.
- The LIST and GROUP membership expressions quoted above use this allocation domain. Consequently, a name present before retirement remains listable and selectable even at the live archive, subject to read authorization. Merely choosing that live archive in A does not implement removal from the wire selection domain. B/C likewise retain it if their pin contained it. A served-table repair must align selection and discovery, not change LIST alone.
- Ordinary reconfiguration also protects selected groups: `books/owner-config.lisp:373–395`, `fn-ocfg-group-pinned-by-readerp`, examines `(fn-auth-reader-session (fn-own-conn-session (car conns)))`; the admissibility condition at `:414` is `(not (fn-ocfg-group-pinned-by-readerp deltas (fn-own-conns o)))`. A retirement of the group a reader is currently standing in is therefore not an ordinary reachable case of that path.

If future removal really makes a group unselectable, A should omit it from live discovery while any explicitly retained old article pin follows its own lifetime policy. B/C can retain a stale listing whose next GROUP gets 411. That is a discovery mismatch, but it is not the *omission of a selectable group* forbidden by the particular §7.6.3 MUST. Do not present that future scenario as today's retirement behavior.

The strongest argument for A is **fresh discovery without silently changing what an ongoing article reader sees**. The strongest objection is **splitting the meaning of availability on one connection**, especially the low-water mark. For example: pin a view with articles 1–10; cancel the low end in a later completed view; live LIST may report low 6 while pinned ARTICLE 1 and OVER 1–10 still expose the earlier articles. A preserves the server's old article pin, but a client can discard its own bookkeeping for 1–5. This is a material loss of the broad original guarantee, not a free optimization. If ember considers that whole-connection consistency the product promise, choose B and separately redesign group discovery; B alone is not RFC-complete here.

Fn already leaves the DATE-to-NEWNEWS no-miss property across pins/in-flight prepare as a separate A-CLOCK-dependent target (`specs/nntp.md:299–304`). |
| **HDR/OVER by Message-ID; STAT <msgid>** | Being independent of a selected group does not itself make them live. Current OVER lookup uses `(fn-scat-msgid-article (fn-nntp-token-string token) v fn-arena fn-cat)` (`books/served-catalog.lisp:2880–2884`); STAT-by-ID passes `session v` to `fn-nntp-msgid-retrieval-cat` (`books/served-catalog-dispatch.lisp:83–95`); HDR/XHDR pass `v` to `fn-nntp-hdr-command-cat` (`:135–138`). Preserve these pins for the narrow A decision. Changing them is another cancellation/visibility exception. RFC §6.2.1 (`rfc3977.txt:2583–2593`) also forbids a nonzero returned article number unless immediately following numeric ARTICLE retrieves the same article. STAT inherits ARTICLE; HDR/OVER reference that rule. A future live-by-ID/pinned-by-number design must use zero where that correspondence is unavailable. |
| **Live names, pinned marks** | It can repair the name omission while retaining old summaries for already known groups, but using the existing historical-summary calculation retains C's cost; achieving the intended flat-cost improvement needs B or equivalent summary support. Newly created groups have no corresponding old summary: inventing “empty” marks for a currently populated group is not justified by GROUP's definitions. Live marks for only those groups produce a mixed-time response. Removal, recreation, status and permissions need rules too. This also amends NNT-042's one-view-per-command guarantee; it is not a free compromise. |
| **Other LIST variants / authorization** | “LIST” is a family, not one renderer: current fast-form recognition is only bare LIST/ACTIVE (`books/served-catalog.lisp:3215–3221`: `(or (null args) ... (fn-nntp-keywordp (car args) "ACTIVE"))`). Descriptions, creation facts, subscriptions and other metadata need an explicit scope decision. RFC selectability is client-relative; fn documents restricted discovery and article projections at `specs/nntp.md:1732–1747`. Live must not mean bypassing those restrictions or mixing live names with an unrelated status/access configuration. |

A suitable decision wording is: **“LIST and LIST ACTIVE [wildmat], and LIST COUNTS [wildmat], observe one coherent latest completed discovery view, restricted to the client. They do not change the connection's article view, selection or cursor. Article reads retain NNT-042's pin until its existing refresh boundaries. Other discovery commands have explicitly named policies.”** This retains within-command coherence while acknowledging that discovery and ongoing retrieval can observe different completed versions.

Before claiming an implementation of that decision complete, its evidence should cover the concrete creation case above; old/current readers across low-end and high-end cancellation and empty groups; LIST followed by numeric and Message-ID retrieval with unchanged pin/cursor; fresh GROUP after LIST; authorization/status/COUNTS agreement; actual retirement behavior; and LIST during an in-flight durability batch. Cost evidence should vary group count, pin lag, withdrawals and output size, and report the durable-view fallback. These are proposed checks, not tests run in this consultation.

The remaining decisions are the exact discovery-command scope and whether ember accepts the low-water/client-bookkeeping tradeoff. Implementation, composed proofs/certification, those client scenarios, bounded-output work, and correcting the registry/decision-file coordinate mismatch remain open. Registries and current-view files were left untouched under the consultation's read-only instruction.

## DECISION (ember, 2026-10-02): A, as Astra scoped it

LIST / LIST ACTIVE / LIST COUNTS answer from one coherent, latest COMPLETED durable reader view
(restricted for the client), without advancing the connection's article pin or changing its
selected group / current article. Pinned article retrieval and cancellation visibility are
preserved. NNT-042 is amended deliberately (not "a faster implementation"). Follow-ups from
Astra: the live low-water vs pinned-retrieval conflict gets an explicit policy; NEWGROUPS,
NEWNEWS and LIST NEWSGROUPS each get a named view policy; "flat everywhere" holds only if the
completed durable view is answered from carried summaries (live durable is not catalog top).
