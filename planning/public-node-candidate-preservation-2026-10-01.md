Before a deployment candidate is selected:

1. Run actual init, start, accepted/refused/uncertain POST, read, restart, and reread on one immutable Linux package/source/capsule/profile coordinate using its real pool and operation sources. Distinguish persisted acceptance from socket success. Current unavailable outgoing/source paths must either be completed or remain explicit refusals; they cannot support a positive read acceptance claim.
2. Bind the package's launcher, runtime/core, actual libraries, profile and capsule to the exact trusted artifact pin. Match the launch geometry and supported profile to the target's service limits. The new request-budget authority supplies no physical-fit or RSS guarantee; retain that distinction in the candidate result.
3. Establish compatibility with a preserved copy of the current live Store before choosing an import path. Refusal or a required explicit conversion must remain visible. Do not initialize over `/var/lib/fn/store` or reinterpret old records under a new schema.
4. During an authorized quiescent cut, preserve the complete node directory, current package prefix/link, system unit and drop-in, and related certificate-sync configuration. Keep the node-secret key separately with the backup: the documented Store export excludes `keys/`. Verify the archive/export hashes and an off-host recoverable copy with private-file permissions. The read-only inventory is not a consistent backup.
5. Retain the current package and original node unchanged for rollback. Rehearse candidate import/start/read/restart in a separate directory first. A rollback must restore the original package link, node and unit/drop-in together; verify listener, authentication, original article identity and reread after restart.
6. Select one convergence qualification and present its actual acceptance and preservation results before the public package/service switch. DNS/firewall/certificate changes are not prerequisites for this existing endpoint and should only change when the concrete deployment requires them.

Use `docs/install.md` section 4 and the existing public-node runbook for the release layout. `tools/deploy_fresh.sh` documents retirement/import/rollback, but its defaults create a fresh Store and use a user service; the actual live node uses a system service and an older prefix layout. Do not run its defaults on this node. The hbox first-install runbook likewise is not a live-node upgrade command. No destructive teardown from the historical runbook is part of this preparation.
